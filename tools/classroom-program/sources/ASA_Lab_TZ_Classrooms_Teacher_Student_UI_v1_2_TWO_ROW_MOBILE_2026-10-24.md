**Документ:** `ASA-CLASSROOM-TEACHER-STUDENT-UX-20261023`  
**Редакция:** 1.2 — двухстрочная мобильная композиция вместо шести постоянных блоков, 24.10.2026  
**Репозиторий:** https://github.com/spikeal8-maker/asa-lab  
**Последний контрольный снимок GitHub, использованный при пересмотре:** `6bc68e5efe50952df5342350c32dc5500e1ca3db` (24.10.2026; **перед разработкой обязательно повторно fetch текущего `main`**). Исходный аудит v1.0: `633b6d59cc42c1eb952d31c1238a14faf0bfca19`.  
**Программа:** страницы «Мои классы» → открытый класс преподавателя → профиль ученика у преподавателя → журналы, рейтинги, настройки, уведомления.  
**Характер:** продуктовый UI/UX + необходимые API/SQL/безопасность, реализация отдельными проверяемыми срезами.  
**Статус:** ТЗ, **не свидетельство реализации**, не разрешение на необратимые изменения данных, деплой или merge.

> **Нормативный принцип v1.2:** на телефоне над основным содержимым профиля ученика допустимы **ровно две постоянные строки**: (1) контекст класса + переключение учеников + текущая личность и компактный статус; (2) выбор одного из девяти разделов + контекстное действие. **Никаких отдельных строк метрик, оценок, рейтинга, безопасности, игр и повторного названия активного раздела.** Детальная информация и редакторы открываются по требованию. Доступность (44×44 touch, legible text), все API-возможности и безопасность сохраняются. Тесты реального собранного React и UI-density являются блокирующей приёмкой.

## 0. Область, источники, приоритет решений

### 0.1. Что входит

1. Компактный кабинет преподавателя, список «Мои классы», открытая страница класса и её восемь разделов.
2. **Профиль ученика, открытый преподавателем из конкретного класса**: девять разделов после добавления «Настройки», навигация, шапка, метрики, оценки, проекты, доступы, аватары, игры, защита.
3. Ручной журнал оценок по датам и журнал назначенных заданий; шкалы, столбцы, компактные ячейки, исправления оценок и уведомления.
4. Классный рейтинг: измеримые факторы, управляемые веса, честное активное время, приватная аналитика «Требуют внимания».
5. Политики Safe Mode, индивидуальные и классовые ограничения, согласование публикаций и игровых разрешений.
6. Исключение выбывших учеников из всех **активных представлений конкретного класса** с сохранением необходимой истории и самостоятельных данных Account.
7. Общий визуальный язык и проверка отображения на ПК, разделённом экране, телефоне, при системном масштабе Windows и масштабировании браузера.
8. Приёмочные тесты, восстановимость, защита данных, разделение исполнителей и интеграция в `main`.

- Переписывание ядра «Курсы», Arduino/Electronics, Scratch, ИИ-чата, игр или Public Projects вне согласованных узких контрактов. Эти направления развивают отдельные боты.

### 0.4. Критический аудит редакций 1.0–1.1 и исправления [NORMATIVE]

**Ошибка v1.1:** попытка «уплотнить» шесть–семь самостоятельных горизонтальных блоков сохраняла вертикальную структуру: `класс → соседи → личность → показатели → оценки → разделы → работы`. При 44–64px на блок это расходовало около 280–340 CSS px до первой работы. Пользователь прямо отверг такой макет 24.10.2026. **Это не допустимая альтернатива:** новые исполнители не должны воспроизводить рисунок v1.1 с более мелким padding.

| Что в v1.1 раздувало экран | Обязательное решение v1.2 |
|---|---|
| Отдельные строки «К классу» и «Предыдущий/следующий» | Объединить контекст, навигацию и личность в **одну** локальную строку |
| Аватар/имя в отдельной высокой шапке | Небольшой аватар (если помещается) **внутри** общей строки текущего ученика |
| Ещё одна строка `Работы · Сдано · Ждут · Рейтинг` | Без отдельного ряда; только релевантный короткий сигнал внутри строки текущего ученика и числа внутри нужных разделов |
| Лента `[5][4][3][5]` выше всех девяти вкладок | **Полностью убрать из общей шапки**; все оценки доступны одним выбором «Оценки» и в журнале |
| Девять пунктов + фильтры | **Один** компактный selector раздела и **одно** действие текущего раздела во **второй** строке |
| `h2 Все работы`, дополнительные breadcrumbs, табы, карточки с подзаголовками | Не повторять выбранный раздел; начинать сразу с первого рабочего элемента |
| Всё время видимые формы игр/безопасности/рейтинга | Только в соответствующем редакторе «Настроек», который заменяет каталог |
| Множество крупных карточек проекта/ученика | Одна плотная, но доступная строка на объект; подробности и превью раскрываются по нажатию |
| Старый лимит: первая работа ≤310px после глобальной шапки | Новый **hard cap ≤128px на 390px** для populated default state; не «в пределах 310px» |

**Область действия:** новое правило двух строк — для **обычного представления мобильного профиля** при достаточной эффективной ширине 320–599 CSS px. На 280 CSS px и при 175–200% zoom допустим специальный режим доступности, если четыре touch-контрола физически не помещаются; это измеряемое исключение, не разрешение вернуть шесть строк. Содержимое раскрытых настроек/редактора оценок — отдельные режимы; к ним ограничение двух строк над контентом не применяется, но лишние постоянные панели по-прежнему запрещены.

При конфликте прямого позднего требования владельца с v1.0/v1.1 относительно **высоты композиции** применяется v1.2. Приоритет защиты прав/данных и доступности не изменяется.

### 3.1. Нормативный UX-инвариант

### 3.2. Адаптивная модель по рабочей ширине, не по размеру телефона

- Выбирать компоновку по **эффективной CSS-ширине контента** (container queries/ResizeObserver + рабочий fallback). Sidebar, split-screen и Windows 125% являются частью baseline. В Chromium, Safari/iOS и Firefox не должно быть page-level горизонтальной прокрутки.
- **320–599 CSS px:** две строки A и B. Для 320px задавать `minmax(0,1fr)` центральной области, ellipsis длинного имени, без переноса других контролов; поле текущего ученика сохраняет доступный раскрывающий selector. ### 3.5. Компактность не должна усложнить частые действия

1. Смена ученика — нажать одну из двух **соседних** стрелок в строке A; выбор по имени — нажать текущего ученика и найти нужного по авторизованному списку класса. Ни один сценарий не требует проходить меню из нескольких уровней.
2. Открытие ученической работы — один tap по строке, без промежуточной карточки. Быстрая оценка в журнале — один tap по клетке, следующий — выбор значения, без экрана «Подробнее» и обязательной причины.
3. «Оценки»: один выбор раздела в строке B; первая оценка появляется сразу после него. Метрики/детали — не более двух осмысленных действий. Настройки — раздел + одна категория, затем готовая форма. **Редкие функции можно спрятать, частые — нельзя.**
4. Текст главных кнопок и ошибки не заменять голой пиктограммой там, где смысл неочевиден. Полные имена соседей доступны через `aria-label`, фокус/детали picker, а не лишь mouse `title`. Значок безопасного режима — с текстовой альтернативой и раскрываемым объяснением эффективной политики.
5. Скролл назад после смены раздела или ученика не перескакивает к произвольному месту. Browser back закрывает sheet/picker, затем возвращает в тот же класс/журнал с месяцем, scroll и фильтром. При ошибке save форма остаётся, focus доступен, пользователь получает честный status. Только одно overlay одновременно.
6. На iOS/Android системное меню выбора раздела/поиска не должно перекрывать основные действия. Keyboard открывает минимум контента; при выборе пункта/закрытии focus возвращается к разделу.

### 3.6. Автоматическая блокирующая проверка UI-density

Встроить E2E measurement helper на built React (без synthetic DOM замены):

### 3.7. Запрещённые способы формально пройти бюджет

- `display:none` для нужной функции без альтернативного достижимого пути; fake numbers; пустые/несохранённые статусы, выдаваемые за настоящие; невидимые кнопки.

## 6. Журнал по датам и выставление оценок

### CL-JRN-01 — правильная модель журнала [P0]

Раздел открытого класса «Журнал» по умолчанию открывает **ручной журнал «По датам»**, не журнал назначенных курсов. Отдельный режим «Задания» сохраняется и не подменяет ручное выставление оценок.

## 7. Рейтинг класса: формула, веса, реальные действия и приватная аналитика

### CL-RAT-01 — существующий рейтинг [регрессия]

Текущая расчётная шкала — **от 0 до 100 баллов**. На `main` имеются пять факторов: новые проекты, дни со входом, активные дни с изменениями, подтверждённое активное время, оценки. Включённые факторы сейчас усредняются **с одинаковым весом**; период 7/30/90 дней. Сохранить совместимость текущих старых настроек.

### CL-RAT-02 — управляемые веса [P1]

- В обычных «Настройках класса» рейтинг — **одна строка**: `Рейтинг · 30 дней · 5 факторов · Изменить`. Все ползунки/описания **лениво появляются только в выбранном редакторе**. В редакторе — компактные строки (название, включить/выключить, вес 0–100%). На desktop — ползунок + число; на mobile — одно числовое поле веса рядом с короткой доступной шкалой/индикатором, ползунок раскрывается по запросу, чтобы пять крупных slider-track не образовали длинный экран. Длинное объяснение источников и формула — через `Как считается?`; краткий итоговый preview и эффект на игры доступны перед сохранением.
- Модель: `weight` целое 0–100 на фактор; выключенный фактор имеет effectiveWeight=0. Если суммарный вес >0, сервер нормализует выбранные веса на сумму, но интерфейс честно показывает **фактические доли**. Никаких скрытых весов.
- **Формула:** `rating = round(sum(effectiveWeight_i * normalizedScore_i) / sum(effectiveWeight_i), 2)`, результат ограничен **[0,100]**. Если нет выбранных доступных факторов — `rating = null` и выводить `—`, не число 0. Значение 0 допустимо только при достоверно измеренном нулевом результате.
- Разделять «достоверный ноль активности» и «телеметрия ещё не доступна»: последнему назначать статус `unavailable`, выводить `—/данных нет`, не выдумывать ноль или минуты. Правило обработки unavailable должно быть единым в UI и на сервере; нельзя менять знаменатель молча. Рекомендуемый вариант: из расчёта исключать объективно **недоступный для измерения** фактор с объяснением, но включённый и корректно измеренный ноль учитывать. Значение и версия алгоритма возвращаются из API.
- При сохранении — проверка версии, idempotency, атомарная запись; исключить исчезновение настроек при перезагрузке. После изменения весов экран явно подтверждает изменение места/балла и предупреждает о возможном влиянии на **порог доступа к играм**.
- База: существующие булевы `settings.factors` сохраняются миграцией совместимости; новая `weights` карта и версия алгоритма добавляются **additive**, а при отсутствии весов старые настройки воспроизводят прежнее равное усреднение.

### CL-RAT-03 — новые показатели [P1, строго после instrument/coverage]

Возможные дополнительные факторы, включать только при валидных серверных событиях и независимых тестах:

1. **Своевременная сдача назначенных заданий**: подтверждённые `submittedAt`, deadline и разрешённая Attempt; отсутствие назначений — `unavailable`, не штраф.
2. **Доля завершённых назначений**: завершённые из действительно назначенных и доступных конкретному ученику; не учитывать чужие/архивированные несостоявшиеся назначения.
3. **Регулярность реального редактирования**: число дней с документированным действием, без нескольких бонусов за один день.
4. **Динамика учебных результатов**: только сопоставимые канонические оценки с достаточной выборкой, без необоснованного штрафа за первые попытки.
5. **Подтверждённые учебные достижения**: только по утверждённым событиям/наградам; защитить от самоназначения и искусственного накручивания.

Новые показатели не внедрять скопом без валидации. Для каждого в карточке фактора указать источник, период, нормализацию 0–100, отсутствие данных, ограничения и negative tests.

### CL-RAT-04 — простой вход и активное время [P1]

- В текущем коде «дни со входом» дают вклад за факт успешного входа. В новой рекомендуемой формуле **простой вход без последующего доказанного действия не добавляет рейтинг**. Сохранить счётчик успешных входов как информационную метрику, но рейтинг начислять за подтверждённую полезную активность.
- Открытая вкладка, idle, переключение в фон, replay без изменений и многократные открытия одного проекта не дают активных минут. Принять существующие интервалы реальных изменений как baseline и проверить нагрузочные, offline/reconnect, overlapping-tab сценарии.
- Максимальные лимиты дней/секунд/работ должны быть документированы, не переопределяться только в React. Ни простой вход, ни попытка имитировать события не должны увеличивать балл.

### CL-RAT-05 — «антирейтинг» как безопасный отчёт преподавателю [P2]

- Не создавать публичный список «плохих учеников», не вычитать произвольные наказания из оценок. **НЕ создавать отдельный большой dashboard-блок**: после проверки источников добавить в существующий реестр учеников компактный фильтр/представление `Требуют внимания (N)` с объяснением по запросу. Никакой второй таблицы «антирейтинга» и негативных ярлыков.
- Точные категории: «Нет подтверждённой активности N дней», «Есть просроченные обязательства», «Сдано, но ожидает проверки» (это задача учителя, **не вина ученика**), «Доступ/сеть мешают работе» при наличии доказанного сигнала.
- N — настраиваемый порог, результаты объяснимы, ученик не видит чужой список; доступ только авторизованному преподавателю, не влияет на Gradebook. Не наказывать за отсутствие телеметрии, болезнь/отпуск или не назначенные задания. Возможны отдельные нейтральные поощрения.

## 8. Safe Mode, игры и публикации — три разных политики

### CL-SAFE-01 — эффективная защита [P0]

В действующей Seat-сессии итоговая защита вычисляется как `class.safeModeDefault OR seat.safeMode`. Следовательно:

- Если классная защита включена, индивидуальное значение `false` **не отключает** защиту.
- UI учителя должен явно отображать `Обязательная защита класса`, `Индивидуальная защита ученика`, **Итог: включена/выключена**. Если итог включён классом — индивидуальный выключатель не обещает невозможного; показать нейтральное объяснение.
- В шапке ученика показывать именно **итоговый** статус; настройку индивидуального значения оставить во вкладке «Настройки». При ошибке сервера показывать неизвестное/повтор, а не ложное «Выключена».
- Для всех API, использующих Safe Mode, определить реальное влияние: публичность/видимость учебных работ, открытые профили, публикация, любые разрешённые внешние каналы. Проверить не только кнопки, но и серверные read/list/detail/media/export/copy пути.
- Не перепутать Safe Mode и доступ к офлайн-играм: в нынешней политике это **независимые** разрешения. Ученик может иметь защиту и законный доступ к учебным шахматам/шашкам; включение игр не разблокирует публикации.

### CL-GAME-01 — сохранить игры, переместить управление [P0 UI]

Функциональная политика игр уже внедрена (#626/#621): класс `allow/deny/rating_threshold`, ученик `inherit/allow/deny`, проверка перед открытием/сохранением/чтением проекта и по revoked session. Исходное поведение индивидуального `allow` может иметь приоритет над классным режимом по текущему API, а `deny` запрещает независимо от класса — не менять существующую семантику незаметно.

- `ClassroomGamesSettings` класса — оставить во вкладке **«Настройки» класса**.
- `ClassroomGamesSettings` отдельного Seat — **убрать из DOM обычного просмотра профиля**, лениво подключать только по выбору `Настройки → Игры`. Одно компактное управление без второго `fieldset` с рамкой/второго заголовка. Не оставлять невидимый большой placeholder; не вызывать readPolicy до открытия категории.
- В UI использовать «Разрешить игры», «Запретить игры», «Как настроено для класса» / «Доступ к играм», «Открываются при рейтинге от X», «Сейчас запрещены: …». Кнопка «Сохранить» требует подтверждённого API, версия/conflict и восстановление после refresh.
- На ученическом экране показывать доступ к играм и причину блокировки, а не учительский переключатель. На сервере не допускать обхода direct URL, повторной игры и сохранения запрещённого Project; онлайн lobby/matchmaking остаётся отдельным неподдержанным режимом.

### CL-PUB-01 — ученическая публикация [P2, отдельный backend/security исполнитель]

Нынешний `migrations/0234_public_projects.sql` пропускает только допустимые **личные Account-проекты** и отклоняет StudentSeat/classroom-origin/immutable learning work. Это **нормативный текущий запрет**; его не обходить интерфейсной кнопкой или старым PR #575.

Будущий продуктовый сценарий:

1. Преподаватель в настройках **класса** задаёт политику «Ученические публикации: запрещены (по умолчанию) / разрешено отправлять на модерацию».
2. В «Настройках» ученика преподаватель задаёт индивидуальную настройку **«По классу / Запретить / Разрешить отправку»**. Индивидуальное разрешение действует **только при разрешающей политике класса**; классный запрет и эффективный Safe Mode не обходятся индивидуальным `allow`.
3. Разрешение относится **только к собственным свободным работам**, законно доступным этому Seat; учебные immutable originals, оценки, чужие проекты/копии защищённых работ не становятся публичными. Если тип допустимой работы не доказан — сервер отклоняет с понятной причиной.
4. Ученик видит действие **«Отправить на публикацию»**, а не прямую публикацию. Формируется заявка на модерацию преподавателем/уполномоченным модератором; после решения — публикация отдельной разрешённой immutable версии. Принцип минимизации публичных сведений: без Student Code, приватного ФИО и школ/классов без разрешённых product/privacy правил.
5. Серверная проверка **в момент подачи, одобрения, чтения, выдачи изображения, копирования и публичного открытия ссылки**. Включение защиты/отзыв разрешения после публикации немедленно прекращает публичную выдачу (deny-on-read/revoke policy), но сохраняет приватную учебную работу и аудит.
6. Права Account на его **независимые личные проекты** нельзя автоматически отключать лишь из-за связи Account с классом. Старую Gallery/новую Public Projects не смешивать без проверки canonical origin.
7. Функциональные тесты: default deny, класс allow + Seat inherit, Seat deny, класс deny + Seat allow, Safe Mode override, suspended/removed/archived, private/immutable origin, linked Account, denied/cross-class/cross-tenant, revocation after publication, list/detail/image/copy, audit и concurrent changes.

**Ответственность:** контракт согласовать с ботом Public Projects; UI-исполнитель класса не правит в одиночку публикационные SQL/functions и не «подкладывает» блокирующую Security-логику без review.

## 9. Удалённый ученик в журнале и остальных представлениях [P0]

### CL-REMOVE-01 — подтверждённая причина

В `migrations/0209_classroom_quick_journal.sql`, функция `classroom_journal_quick_read`, массив `students` строится по `classroom_id = p_class` **без `status <> 'removed'`**. В `apps/web/src/components/quick-journal-model.ts`, `journalRoster`, этот массив только сортируется. Соответственно удалённый Seat может продолжать появляться в активном ручном журнале. Это дефект серверной проекции, а не проблема CSS.

### CL-REMOVE-02 — целевое поведение

- После операции «Удалить из класса» преподаватель больше **не видит ученика в активном составе, обычном ручном/задательном журнале, селекторе ученика, новых назначениях, рейтинге, активном списке проектов класса, списке уведомляемых участников и фильтрах**. Поиск и refresh не возвращают запись. Не учитывать такого Seat в текущих количествах и знаменателях.
- Удаление — **отзыв участия (soft-remove)**, а не безусловный физический `DELETE` личного Account, проектов, исторических оценок, снимков/версий, аудита или чужих классов. Существующие данные обязательны к сохранению по требованиям проекта. Доступ Seat к классу и старые сессии/коды прекращаются. Связанный Account продолжает сохранять свои независимые личные данные и другие законные membership.
- **Исторические оценки и события** доступны только в отдельном защищённом архивном/аудиторском представлении авторизованному преподавателю, с пометкой «Участник выбыл». Не использовать эти архивные данные для нового выставления оценок или рейтинга действующих детей.
- Исключение должно быть **на сервере во всех необходимых SQL/read-проекциях**, а не только фронтенд `filter`. Авторизация исключённых Seat не ослабляется. Различать suspended (сохранён в классе, но доступ закрыт) и removed (выбыл из активного состава).
- После удаления очищать клиентские кеши/локальные выборки, устаревшие асинхронные ответы не восстанавливают ученика в активном списке. Повторный DELETE идемпотентен, возвращает корректный результат.

### CL-REMOVE-03 — обязательные тесты

`teacher class -> manual journal -> remove Seat -> reload journal/roster/profile/search/ratings/assigned views`, а также archived, suspended, Account-linked, 2 classes, 2 browser tabs, кэшированные ответы, исторический audit, 401/403 и сохранность файлов/проектов. Снимок БД до/после с проверкой инварианта сохранённой истории. Никаких миграций, уничтожающих данные, ради исчезновения строки.

## 10. Уведомления и результаты со стороны ученика [P1]

Использовать существующую `learning_notifications`, `LearningInbox`, `StudentJournalResults`, `SeatResults`, **не создавать второй локальный центр сообщений, баннер уведомлений под шапкой ученика или постоянный уведомительный блок в профиле**. ### CL-NOTIFY-02 — доставка и приватность

- Account и StudentSeat получают данные **только по канонической действующей связи learner identity** и своей сессии. Не «доставлять всем с похожим именем» и не отправлять уведомление в чужую школу/класс.
- Учитывать разрешения категории, общую настройку доставки, `read/unread`, rate limits, отсутствие внешнего канала; выключенная доставка не уничтожает оценку или событие. E-mail/MAX/Telegram использовать **только если они реально подключены и разрешены**; отсутствие MAX не препятствует выполнению школьного задания.
- `eventId` / receipt / authoritative revision предотвращают дубль при сетевых повторах; отказ записи уведомления для критичного оценочного события корректно откатывает транзакцию или явно сообщает о сбое по текущему каноническому контракту. Не посылать «Оценка поставлена» после DB rollback.
- UI ученика: «Моё обучение» → «Результаты» и «Уведомления» Account/Seat, контекст текущего/разрешённых классов. Никакой видимости чужих учеников или teacher-only управлений.

## 12. Порядок исполнения, независимые PR/коммиты и границы ботов

### 13.3. Проверка качества интерфейса

Помимо `assert visible`, тесты/артефакты должны контролировать:

- геометрию `boundingClientRect`: нет наложения шапки, selector, действий, ячеек и popover; локальное, а не page-level переполнение; **расстояние до первого полезного контента**, количество вертикальных рядов и открытых настроек — по §3.3/§3.6;
- реальные размеры цельных русских слов/ФИО: без разрыва по 1–4 символа, без сжатых непригодных controls;
- достаточный `focus-visible`, контраст, `aria-*`, клавиатурную последовательность, disabled/error states, `prefers-reduced-motion`;
- визуальное сравнение **до/после** и независимый просмотр скриншотов, включая разные наполнения и страницу после внесения **каждой новой функции**; обязательны JSON-замеры **2 rows и ≤128/144px**, 390px `first project visible`, 320px `no hidden CTA` и отсутствие скрытых базовых разделов;
- точный `BUILD_SHA` на каждой сборке, viewport, browser/version, synthetic test user; отсутствие настоящих секретов на снимках и в logs.

### 13.4. GitHub Actions и критерии CI

- На точном HEAD кандидата: format/lint/typecheck/build без использования результата чужого или устаревшего кэша как нового evidence; focused unit/component; Playwright built UI; реальный PostgreSQL/API/ACL; migrations/forward-upgrade; профильные security negative tests.
- Не ослаблять assertions, deadlines, timeout, branch protection или disable/skip jobs ради зелёного статуса. Обнаруженные сторонние baseline failures документировать отдельно с фактическим run URL и причиной; **не выдавать** локальный focused PASS за полный общий PASS.
- В отчёте на каждый срез: SHA, число пройденных/упавших тестов, ссылки на точные run/artifacts, обзор конфликтов по путям, независимое review, статус merge, deployed SHA и визуальная оценка.

## 14. Правила безопасности, данных и развёртывания

1. **Никаких операций на живой школьной БД** в процессе разработки ТЗ. Проверять migrations и rollback в отдельном изолированном контуре с синтетическими или должным образом обезличенными данными; реальный live backup/restore требует отдельного владельческого разрешения и подтверждённой контрольной копии.
2. Нельзя «для чистоты» удалять grade revisions, project drafts/snapshots, LearnerIdentity, Account, StudentSeat audit, игровые сохранения, notification receipts и связки других классов. Удаление из класса — точный отзыв участия; последующее использование частной истории контролируется ACL.
3. Любые секреты (Student Code, пароли, токены) скрыты до явного authorized reveal. Полный секрет никогда не попадает в logs, trace, screenshot, title/aria-label и ответы неавторизованного API.
4. Server authorization — **единственный источник прав**. Клиентский disabled, скрытый таб и спрятанная кнопка не заменяют backend 403/404; проверка tenant/school/class/Seat/Account и revocation обязательна.
5. Раннее снятие Safe Mode, изменение весов (если затрагивает admission), изменение доступа к играм и разрешение публикации могут иметь последствия для ребёнка. Требуется понятное предупреждение о результате **до сохранения**, явное подтверждение соответствующей операции, аудит и возможность безопасного отката политики.
6. Не применять `force push` к чужим активным веткам, не переписывать `main`, не объединять широкие старые PR #577/#575/#605 без диффа к **текущему** HEAD. Не менять сетевую инфраструктуру/DNS/FRP/1Panel при UI-работе.
7. Деплой — отдельный этап после exact CI + независимого review + разрешённой визуальной приёмки. Размещённый контейнер должен сообщать проверенный SHA; отдельно проверять готовность DB schema. На production rollout нужен backout/rollback план, проверка миграций и соответствующих данных.

## 15. Контракт работы контролёра, исполнителей и независимого ревью

### 15.1. Роли

- **Инженерный контролёр:** сверяет исходные документы/код/PR, распределяет безопасные непересекающиеся срезы, принимает финальные решения. Не выдаёт успешный статус по тексту исполнителя.
- **Продуктовый исполнитель:** единственный writer для согласованного набора путей, делает код, тесты, скриншоты реально собранной страницы, чистый diff и пояснение решения.
- **Независимый reviewer:** только чтение, exact-SHA source + SQL/API/security + browser/visual review; формулирует `APPROVE / FINDINGS / BLOCKED` с конкретными файлами и доказательствами; не меняет исходники исполнителя.
- **Смежные владельцы:** Public Projects — политика публикации и модерация; Learning/Courses — учебные результаты и уведомления; Games — admission/игровая защита; Electronics — контактные мишени; общая Portal UI — только после согласования владельца shared paths.

### 15.2. Правило единственного автора и окончания блока

- Один writer на пересекающийся путь, не создавать конкурентные варианты `ClassroomStudentPage.tsx` и `ClassroomPage.tsx` поверх свежего `main`. Если HEAD меняется или изменился владелец файла — выполнить повторный fetch/rebase-safe review и зафиксировать статус конфликта; **STOP только для реальной опасной коллизии**, а не после первого небольшого теста.
- Работать до **целого пользовательски видимого блока**: исходники → тесты → независимая оценка → корректировки → необходимые CI → безопасная интеграция в `main` → отчёт. Новые блоки не объявлять завершёнными по наличию PR.
- Никакого самообъявления `OWNER_ACCEPTED`: владелец должен видеть **настоящую** страницу собранного приложения и подтвердить визуальную пригодность либо замечания; synthetic-built browser evidence не равно live deployment.

## 16. Definition of Done: требование считается готовым, только если

Для каждого ID из §2 присутствуют **все применимые** пункты:

1. Есть однозначная ссылка на утверждённое ТЗ/задачу и связь с предыдущими КЛ-01–КЛ-17/Issue #589.
2. Реальный код в `main` реализует требуемое поведение; функции из уже объединённых PR не задублированы; отсутствуют произвольные пустые кнопки/обманчивые статусные блоки.
3. Реальные authorization/API/SQL корректны, если изменение требует серверной логики; миграции протестированы на upgrade и не уничтожают историю или проекты.
4. Unit/component/E2E/PG/security checks прошли на **точном принятом SHA**; общие CI нарушения названы честно и классифицированы.
5. Визуальная приёмка собранного приложения есть на desktop/mobile/split-screen/Windows 125%; все actions/данные доступны, девятый раздел достижим через **один** mobile selector. **UI-DENSITY_PASS обязателен:** §3.3/§3.6, baseline и численный after; мобильный профиль **строго из IdentityRail + SectionRail**, без самостоятельных KPI/оценок/игр/защиты над выбранным содержимым; настройки с единственным активным editor.
6. Независимый reviewer зафиксировал решение на точном SHA; разрешённый merge выполнен и перепроверен на текущем `main`.
7. Если заявляется установленная функция, подтверждены **DEPLOYED_SHA, схема БД, результат реального smoke**; иначе писать `DEPLOYED: NOT_RUN`.
8. Обновлены документация, отрицательные регрессии и traceability матрица. `owner_accepted` только после фактической оценки владельцем, `not_reviewed` — отдельный допустимый честный статус.

## 17. Итоговый критерий продукта — сквозной сценарий учителя

**Приёмочный путь 1 — работа на уроке:** преподаватель открывает «Мои классы» → находит класс → выбирает «Журнал» → видит список действующих учащихся и компактную сетку дат → кликает рядом с нужной клеткой → выбирает оценку без обязательной причины → видит подтверждение → следующая клетка → открывает ФИО ученика → видит компактный профиль и новую оценку → переходит в девятую «Настройки» и управляет правами/играми → возвращается в исходный месяц журнала без потери контекста.

**Приёмочный путь 2 — ученик:** StudentSeat/linked Account законно открывает «Моё обучение» → видит результат в «Результаты» → в своих уведомлениях видит подтверждённую текущую оценку/изменение → доступ к разрешённым учебным играм соответствует политике → не получает доступ к чужим оценкам, публикуемым работам или секретным настройкам преподавателя.

**Приёмочный путь 3 — управление и защита:** учитель видит действительный итог Safe Mode → исключает ученика из класса → обновляет журнал/реестр/рейтинг → ученик отсутствует во всех активных представлениях, не входит старой сессией → старые оценки/аудит и личные проекты Account не уничтожены → сценарий старой публичной ссылки не нарушает политику приватности.

**Приёмочный путь 4 — качество композиции:** на 1920×1080/Windows 125%, 320px/390px телефоне, split-screen и широкой 4K области все предыдущие шаги остаются пригодными. Глобальная шапка одной строкой; **на телефоне только две локальные строки над контентом** и девять логических разделов в одном selector; первая работа ≤128 CSS px от конца глобальной шапки при 390×844 и без предварительного скролла; **нет** постоянной полосы оценок/метрик/игр; оценочный popover не вылетает за экран. Отдельный `UI-DENSITY_PASS` обязателен.

**Вся программа принимается только после четырёх путей и выполнения актуальных регрессий КЛ-01–КЛ-17.** Это не препятствует включению отдельных целых прошедших приёмку блоков в `main` раньше.

## 19. Приложение — нормативные ультракомпактные эталоны [NORMATIVE]

Следующие схемы — **текстовые контракты структуры**, не изображения и не mock React. Их цель — контроль **числа строк**, а не визуальное декоративное наполнение.

### 19.1. Учительский профиль, 390 CSS px, «Все работы», populated

```text
┌──────────────────────────────────┐
│ ASA Lab (global 56px)           │
├──────────────────────────────────┤
│ ← Робо…  ‹  [● Сидоров А.]  ›  │  A ≤52px
│          2 ждут · 7/26 · 🔒     │  (ВНУТРИ A, не новый ряд)
│ [Все работы (18) ▾]  [Фильтр]  │  B =44px
├──────────────────────────────────┤
│ Светофор Arduino           →    │  ПЕРВЫЙ настоящий проект
│ Электроника · вчера             │
│ Рука робота                →    │  ВТОРОЙ настоящий проект
└──────────────────────────────────┘
```

Смысл схемы: **две** управляющие полосы, не 6. Верхняя вторая строка под имени — только второй текстовый baseline **внутри той же 52px кнопки**, не самостоятельный DOM-ряд со своим margin/padding. Действительный проект может иметь вторую текстовую строку **внутри своей компактной записи**, это уже содержимое. При ширине 320px уменьшать только необязательные подписи, сохраняя все контролы 44px и реальное имя доступным через picker. Нельзя рисовать `7/26`, `2 ждут`, аватар и защиту как четыре отдельные «карточки» или заставлять весь header расти.

### 19.2. При выборе «Оценки» — тот же верх, без вторичного hero

```text
A  ← Робо… ‹ [● Сидоров А.] ›
B  [Оценки ▾]         [Период]
   [5] 12.10 · Работа    [4] 10.10 · Задача
   [3] 08.10 · Работа    …
```

Реальные оценочные записи и два отдельных `nextOffset` обрабатываются в **содержимом**. Никакой дублирующей ленты над селектором. Из оценки открывается настоящий редактор/review. Вкладка «Настройки» — тот же A/B, сразу плоские строки `Данные и аватар`, `Вход и доступ`, `Безопасность`, `Игры`; одна открываемая форма заменяет список.

### 19.3. «Мои классы» и открытый класс — две строки перед списком

```text
Мои классы:    [Мои классы]  [+ / ⋯]
               [Поиск…]      [Фильтр]
               Робототехника 7А       26 ›

Открытый класс: [← Мои классы · 7А]   [⋯]
               [Ученики (26) ▾]       [Поиск]
               1. Сидоров Алексей      ›
```

Журнал: после двух строк класса — **одна** плотная локальная строка месяц/режим/поиск и затем таблица, без новых «информационных» вставок.

### 19.4. Немедленный `UI-DENSITY_FAIL`

Любой один случай — блокер: третья **постоянная** служебная строка в профиле 320–599; отдельная оценочная/KPI/игровая полоса до selector; второй заголовок `Все работы`; героическая карточка ученика под навигацией; фальшивый первый item вместо данных; первый проект ниже 128px от глобальной шапки на 390px; click/touch <44px; overlap/скролл всей страницы вбок; необъяснимое отличие 320/390 при одном и том же состоянии; «пройдено» без реального built-browser SHA и независимого визуального review.
