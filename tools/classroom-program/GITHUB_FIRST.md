Эта система выдаёт ботам только следующие разрешённые задачи. Источник состояния — GitHub, а не локальный ZIP и не память разговора.

## Распределение ответственности

- GitHub Issue #715 — цель программы и последовательность.
- Отдельный Issue с маркером ASA-CLASSROOM-TASK — **одно** поручение исполнителю.
- registry.json — 38 карточек, 34 исходных требования, зависимости, девять решений.
- receipts/ID.json — проверенные и включённые в main доказательства принятия.
- decisions/KEY.json — отдельно утверждённое решение владельца с источником.
- docs/execution/current.yaml — каноническое состояние активного среза ASA Lab. **Issue не заменяет текущий task selection в этом файле.**
- GitHub Actions — исполнимые проверки и выдача Issue, не исполнитель программного кода.

## Как дать задачу боту

Передайте ему ссылку на Issue #715 и следующую инструкцию:

> Ты — программный контролёр ASA Lab «Классы». Продолжай программу по GitHub Issue #715. Восстанови актуальный GitHub main, прочитай AGENTS.md, START_HERE_FOR_AI.md, docs/execution/current.yaml, реестр и принятую текущую задачу. Назначь исполнителю один ограниченный срез, проверь реальные CI/PG/browser и независимое ревью на точном SHA; затем интегрируй только разрешённый результат, запиши доказательства в GitHub и выбери следующую READY-задачу. Не меняй чужие подсистемы, школьную БД и Docker без отдельного разрешения. При blocker — STOP с точным отчётом, не подменяй доказательства текстом.

Исполнитель получает конкретный Issue, делает только его и останавливается. Контролёр может вести многосрезовую программу дальше, если владелец явно поручил довести её до конца.

## Как выдать следующую карточку из GitHub

После независимой проверки и принятого merge Draft PR #712 в default branch:

1. GitHub → Actions → Classroom Program — Next GitHub Issue → Run workflow.
2. Выберите main и действие **inspect**: увидеть уже открытый Issue или одну READY-карточку.
3. Выберите **create**, чтобы создать следующий Issue **только если** выполнены зависимости, а предыдущий принят в main.
4. Передайте выданный Issue исполнителю. После выполнения, independent review и принятия контролёр фиксирует receipt в GitHub и закрывает Issue. Повторите шаг 1.

Повторный create не создаёт дубль текущей открытой задачи. Закрытый Issue без принятого receipt, неожиданные дубликаты, устаревший checkout и неутверждённые решения блокируют следующую выдачу.

Workflow **не запускает бота сам**, не сливает PR и не делает deployment. Это безопасная GitHub-очередь для передачи задач. На данный момент она только предложена в PR #712; GitHub Actions workflow_dispatch начнёт действовать после принятия PR в main.
