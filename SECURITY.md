# Политика безопасности ASA Lab

## Поддерживаемые версии

До первого production-релиза поддерживается только текущая ветка `main`. После появления релизов матрица поддерживаемых версий будет зафиксирована отдельно.

## Сообщение об уязвимости

Не публикуйте сведения об уязвимости в обычной Issue, Pull Request, Discussion или публичном канале.

Используйте приватный канал GitHub `Report a vulnerability`, когда он доступен для репозитория. В ином случае свяжитесь с владельцем репозитория `spikeal8-maker` приватно через GitHub и передайте минимальное описание без детских или production-данных.

Сообщение должно содержать:

- затронутый компонент и версию;
- класс уязвимости;
- условия воспроизведения;
- ожидаемое и фактическое поведение;
- оценку влияния на tenant isolation, детские данные, авторизацию или compute sandbox;
- безопасный proof of concept без реальных персональных данных;
- предлагаемые меры, когда они известны.

## Приоритетные категории

Особенно критичны:

- cross-tenant чтение или изменение данных;
- обход прав педагога, администратора или StudentSeat;
- раскрытие StudentSeat code, token, password или signed URL;
- исполнение пользовательского кода вне sandbox;
- доступ worker к внешней сети или данным другого tenant;
- изменение immutable ProjectVersion или Submission;
- утечка скрытых тестов автопроверки;
- обход entitlement/quota с финансовым влиянием;
- supply-chain compromise модуля или worker image;
- потеря подтверждённой сервером версии проекта.

## Координация исправления

1. Подтверждается получение сообщения.
2. Назначается severity и владелец.
3. Воспроизведение проводится на синтетических данных.
4. Для активной угрозы вводятся feature flag, rate limit, module disable или иной containment.
5. Исправление получает regression test.
6. Для high/critical выполняется targeted security review.
7. После исправления обновляются advisory, runbook и архитектурные правила, если причина системная.

Точные сроки реакции будут утверждены перед production-запуском вместе с on-call и incident-management процессом.

## Запрещённые данные

В security report нельзя помещать реальные ФИО детей, открытые коды доступа, пароли, access/refresh tokens, полные project payload, содержимое детских комментариев, платёжные данные или production database dumps.
