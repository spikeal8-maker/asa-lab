5. Runtime README начинал конфигурацию с preview и содержал подробный artifact-рецепт; граница между компонентной сборкой, CI и обычным обновлением была недостаточно явной.
6. Readiness-план всё ещё возвращал coming_soon и ремонт уже исправленного #256; общие входы не обязывали прочитать единый deployment runbook.

Этого достаточно для воспроизводимого конфликта инструкций и неоднозначного выбора
объекта ботом. Конкретная команда упомянутого владельцем повторного развёртывания
не предоставлена: нельзя доказанно приписать тому боту внутреннюю причину или
утверждать, что любой отдельный порт означает ошибку. Старые диагностические
контейнеры — дополнительный фактический источник путаницы, а не доказательство
нового самостоятельного продукта.

## Исправленный маршрут

Единый runbook — `docs/deployment/SCRATCH_INSTALLATION.md`; входы AGENTS,
START_HERE, change workflow, Scratch router, Quick Start, recovery и runtime README
теперь направляют туда. Разделены первая установка, обновление существующей ASA,
неисправность порта и изолированная проверка. Не вводится новый deployment engine.

Неизменяемая цепочка: selected computer → PostgreSQL project/root/volume →
те же Compose files и согласованные ports/origins → guarded update общего состава →
одинаковые Web/API/Scratch revision → host-port + пользовательский путь.
Один build/bundle/service/origin не превращается во второй продукт.
Неизвестный или занятый endpoint означает диагностику/STOP, а не перебор портов.
Старые TEST/diagnostic требуют отдельного списка и разрешения на cleanup.

Предыдущие исключения владельца не отменены: Scratch доступен всем, готовый
редактор без нижней полосы, серверное хранение ещё не реализовано. План B/E и
последующих этапов не объявляется принятым этим документационным исправлением.

## Границы и проверка

Изменяются только Markdown-документы. `compose.yaml`, код updater/startup,
портовые настройки, runtime, dependencies, БД, секреты и `current.yaml` не меняются.
Новые runtime-контейнеры не создаются; старые не останавливаются и не удаляются.
Public domains/DNS/TLS/FRP не проверяются и не изменяются.

POST_STEP_REVIEW: документационная синхронизация среднего риска, без изменения
trust boundary или runtime. Это собственная проверка, не независимая приёмка B/E.
Результаты фактически выполненных gates и exact-docs-SHA CI фиксируются в delivery
receipt в issue #260; продуктовый CI baseline не выдаётся за CI новых документов.

Локально выполнены и прошли: `pnpm gate:blocks --docs`, `pnpm gate:governance`,
`pnpm control-plane:check`, `pnpm compose:check`, четыре существующих теста
`node --test tools/blocks/deployment.test.mjs`, Prettier и `git diff --check`.
