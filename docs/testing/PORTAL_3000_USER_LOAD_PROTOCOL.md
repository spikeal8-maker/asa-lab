# Протокол нагрузочной приёмки портала ASA Lab: 3000 пользователей

Этот документ детализирует §5 [ЭТЗ оболочки](../product/ASA_PORTAL_SHELL_AND_AVATAR_ETZ.md).
Он не является новым нормативным бюджетом, evidence выполненного запуска или
разрешением на нагрузку, deployment и работу с рабочей БД. Все профили ниже —
воспроизводимые входные условия будущего изолированного запуска с синтетическими
данными. UI/unit PASS, размер gzip и расчёт RPS не подтверждают мощность сервера.

## Манифест до запуска

Согласовать и сохранить один run manifest до измерений. Он должен содержать:

- точный Git SHA Web/API/Scratch, digests образов, версию миграций и инструмента
  нагрузки, команду запуска и hash сценария, seed и время начала/окончания UTC;
- CPU/vCPU, лимит RAM и фактический memory limit каждого сервиса, число реплик,
  версию PostgreSQL, диски/IOPS, сеть, proxy/compression/cache configuration;
- эффективные pool settings и таймауты, auth/rate-limit policy, CSRF/origin policy,
  конфигурацию тестовых capability/session credentials без публикации секретов;
- число уникальных людей, сессий, открытых и видимых вкладок отдельно;
  распределение Account/StudentSeat/teacher/author/admin и используемых маршрутов;
- заранее утверждённые SLO для каждого класса операции: успешный вход, чтение,
  inbox, запись, editor-open; p95/p99, error rate, completed/arrived throughput,
  максимальная очередь пула и предел CPU/RAM/IO, условия аварийной остановки;
- профиль источников (школьный NAT, распределённые IP либо оба), seed и процент
  видимых вкладок, частоту действий/сохранений и размеры payload;
- режим cold/warm browser/server cache, cookies/session lifetime, retention
  сырых метрик/логов и ответственного за отдельное разрешение запуска.

Незаполненные ресурсы или SLO означают `NOT_READY`, а не разрешение подобрать
порог после результата. Действующий [performance-budget.json](performance-budget.json)
сохраняется: entry JS ≤300 КиБ; фактический page weight ≤400 КиБ; usable sign-in
≤1200 мс при 10 Mbps и ≤4000 мс при 1.6 Mbps. Прежнее требование 300 входов
за 30 секунд и runtime floor не является измерением 3000 одновременно.
Новый профиль дополняет эти бюджеты; не заменяет их более удобными величинами.

## Изоляция и подготовка

Использовать специально разрешённое CI/нагрузочное окружение с отдельной
одноразовой БД, синтетическими аккаунтами, StudentSeat и проектами. Рабочая
установка, её volume, backup и реальные данные не являются источником fixture.
Назначение, адреса, ресурсы, срок жизни и удаление окружения согласуются отдельно.
Этот документ не запускает Docker, не создаёт второй постоянный Compose project
и не меняет канонические порты или browser origin проекта.

Один seeded набор содержит 3000 уникальных principals и явное распределение
scopes: Account с личными работами; Seat в назначенных классах с индивидуальными
credentials; преподаватели с правами только своих классов; независимые author
capabilities; ограниченные admin grants. Создать пустые и заполненные inbox,
несколько проектов и ревизий на человека, публичные опубликованные карточки и
частные работы классов. Сохранить размеры данных и число строк. Дополнительная
вкладка пользователя использует его сессию; не создаёт 3001-го человека.

Вход выполняется через штатный auth/Seat flow с cookies, CSRF и разрешённым
Origin. Используются реальные capability checks/RLS/session refresh и обычные
защиты. Не отключать rate limits, CSRF, origin, session или RLS ради зелёного
результата. Не подменять авторизацию mock API и не обходить её прямой записью
тестового токена в запросы. Предусмотреть обычные logout/expiry/refresh в смеси,
не скрывая время восстановления пользователя после истечения сессии.

Для школьного NAT повторить вход с большим числом пользователей за одним
источником; отдельно — распределённые источники с тем же arrival rate. Политические
отказы (например, rate limit/403), ошибочные credentials и инфраструктурные
5xx/timeout учитываются раздельно. Отказ штатной политики не является 5xx,
но его влияние на долю успешных школьных входов и время ожидания входит в
пригодность профиля. SLO нельзя объявить выполненным, исключив такие пользователи
из знаменателя. Секреты, cookies и персональные значения не входят в отчёт.

## Профили и последовательность

Сначала выполнить короткий smoke на 50 пользователях: вход, чтение, scoped
сохранение, выход и проверку чужого доступа fail-closed. Затем прогреть стек
без нагрузки сверх утверждённого уровня и выполнить одинаковую seeded смесь
на 300, 1000 и 3000 пользователях. Длительности, включая cooldown, фиксируются
в манифесте. Для каждого профиля выдержать не менее 30 минут steady state
после ramp; cold-cache start измерить отдельным запуском.

| Профиль | Приход входов | Вкладки и поведение |
| --- | --- | --- |
| Базовый школьный старт | 3000 за 15 минут: 3,33 входа/с в среднем | Одна видимая вкладка на человека; 3000 portal inbox pollers после входа |
| Плотный старт урока | 3000 за 5 минут: 10 входов/с в среднем | Та же смесь, отдельно NAT и распределённые источники; пики и completed rate измеряются |
| Фоновая работа | Такой же ramp | 50% вкладок реально скрыты, 50% видимы; управляемый возврат hidden→visible и focus/open inbox |
| Несколько вкладок | Такой же ramp | 10% людей с двумя видимыми portal вкладками: 3000 людей, 3300 вкладок; отдельных cross-tab дедупликаторов сейчас нет |
| Редакторы | Такой же ramp | 20% людей в редакторе, остальные в портале; portal inbox размонтирован в редакторе; отдельные editor sessions/heartbeat/save |

Пассивный inbox сейчас планирует следующий запрос после завершения предыдущего
с интервалом 15 с и jitter 0,8–1,2; скрытая вкладка не опрашивает, ошибки получают
bounded backoff до 120 с. Поэтому `3000 / 15 ≈ 200 RPS`, 50% видимых ≈100 RPS,
3300 видимых ≈220 RPS — только номинальные оценки без длительности ответа,
backoff, открытий и возвратов вкладок. Для редакторского профиля 2400 видимых
portal вкладок дают номинально ≈160 inbox RPS; editor traffic считается отдельно.
Single-flight действует на экземпляр inbox, не на пользователя во всех вкладках.

В steady state seeded генератор выполняет фиксированную смесь: каждые 60 с
20% активных portal пользователей переходят Home/My Projects/Gallery/Knowledge/
Learning/Help/Settings; каждые 120 с 10% открывают или фильтруют inbox; каждые
300 с 5% читают событие/сохраняют notification preferences. Эти действия не
заменяют периодические запросы. Для заполненных inbox фиксировать размер
списка, количество unread и snapshot/asOf semantics. Случайные времена действий
имеют сохранённый seed и jitter, чтобы не получить искусственную синхронизацию.

В editor профиле 600 пользователей распределены по заранее названным модулям;
указать частоту открытий, активных взаимодействий, editor telemetry и сохранений,
размеры документов/assets, revision conflicts/retries. Например, 10% редакторов
сохраняют раз в 30 с: номинально 2 save RPS, плюс autosave по фактическим
правилам модуля. Сохранять только в scoped fixture проект; затем перечитать
revision/document и сравнить ожидаемые hashes. Не заменять реальное сохранение
фиктивным успешным ответом и не объявлять autosave измеренным по кнопке UI.

HTTP генератор воспроизводит arrival rate/бизнес-операции, но не доказывает
browser visibility и usable UI. Отдельный браузерный cohort на фиксированных
устройствах/viewport1440/1024/390/320 проверяет реально скрытые вкладки,
одновременные visibility/focus/open, cold chunks, retry, переходы и сохранность
drafts. Фиксировать число браузерных экземпляров и не выдавать 30 браузеров
за 3000. Все внешние запросы и первоначальные deferred chunks учитываются.

## Метрики, остановка и вердикт

Собирать arrivals/completed/in-flight/throughput, latency p50/p95/p99 и
status/error distribution по операциям и actors, включая login/refresh,
inbox GET/read/preferences, project list/open/save. Измерить browser transfer
bytes и usable UI под реальной compression/network emulation отдельно от
raw/gzip filesystem расчёта. Warm cache не подтверждает cold start.

На стороне API фиксировать CPU/RAM/GC/event-loop lag, active requests, network
ingress/egress, timeout и rate-limit counters. У PostgreSQL — active/idle/waiting
pool connections, pool acquisition wait p95/p99, queue depth, query latency,
lock waits/slow queries, CPU/RAM/IO и число реплик API. Штатный `ASA_DB_POOL_MAX`
по умолчанию равен 10 на pool/API instance (`apps/api/src/app.factory.ts`);
это ограничение соединений, а не число поддерживаемых пользователей. Наблюдение
ожидающих запросов обязательное, pool size не повышается автоматически тестом.

Аварийно остановить поступление новых действий при утверждённых пределах
ошибок/очереди/CPU/RAM/IO, OOM, потере прогресса, нарушении scope/RLS или
повреждении данных. Сохранить trace и метрики до остановки; не стирать неудачный
run, не увеличивать timeout и не менять policy/ресурсы посреди измерения.
Проверить, что drain/cooldown возвращает очередь и resources к baseline.

Evidence содержит run manifest, hashes сценария/seed, sampled sanitized request
logs, timeline с ramp/steady/пиками/остановками, raw time series, percentile
расчёт с population/sample count, error taxonomy, SLO comparison и browser
journeys. Отчёт различает `PASS`, `FAIL`, `NOT_RUN` для каждого профиля, точного
SHA и ресурсов. Частично выполненный запуск не подтверждает всю программу.
Owner acceptance и deployment отмечаются отдельно.

Будущие ИИ-чаты/streams пока отсутствуют. Для них нужен отдельный профиль:
число активных streams, arrival/turn rate, input/output tokens, time-to-first-token,
stream duration, concurrency/queue/cancel/reconnect, provider quotas/errors,
память и network. Верхняя третья UI-кнопка в fixture не доказывает этот сервис;
его предполагаемую нагрузку нельзя включать в текущий 3000-user PASS.
