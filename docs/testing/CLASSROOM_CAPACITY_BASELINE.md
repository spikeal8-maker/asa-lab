# Пункт9: воспроизводимая проверка нагрузки

## Что можно проверить без отдельного сервера

Workflow **Classroom Capacity Baseline** создаёт временную PostgreSQL17.7 в
GitHub. Настоящий API обслуживает30 независимых сессий:15 Account и15 StudentSeat,
15 проектов Scratch и15 электроники. Входы и операции запускаются параллельно.
Две волны сохранения разделены реальной минутой. После каждого подтверждённого
сохранения документ читается через API и сравнивается по семантическому SHA256:
порядок ключей PostgreSQL JSONB не считается повреждением данных.

Проверяются также повтор того же mutationId после намеренного игнорирования
первого ответа, отклонение устаревшей версии и отказ в чтении чужого проекта.
Это проверка контракта потерянного ответа, не настоящий сетевой отказ браузера.
Промежуточные запросы identity подтверждают, что сессии продолжают действовать.
Учитель создаёт тестовый класс до начала измерения; setup не входит в задержки
измеряемого сценария. Куки, пароли, коды учеников и документы остаются в памяти.

Команды:

- `corepack pnpm test:capacity`: быстрые проверки профиля, защит запуска,
  процентилей и сравнения документов. Docker и БД не нужны.
- `corepack pnpm test:capacity:baseline`: настоящий сценарий только в явно
  выбранной временной среде GitHub. Обычный локальный запуск запрещается до
  подключения к БД; обычные test/access/data suites пропускают нагрузочный тест.

Повтор: Actions → Classroom Capacity Baseline → Run workflow на нужной версии.
Автоматический запуск идёт при изменениях самого сценария/профиля. Для проверки
другого runtime SHA используйте ручной запуск именно на нём. Общие gates и выпуск
остаются отдельными проверками. Рабочая установка и её база не используются.

## Как читать результат

Артефакт `classroom-backend30-<SHA>/backend30.json` содержит:

- точный SHA, идентификаторы и digest профиля, измеренную среду;
- запланированные/вошедшие независимые сессии, открытые проекты и достигнутую
  одновременность запросов, предложенные и завершённые операции;
- по типам операций: HTTP-статусы, ошибки, p50/p95/p99/max, отправленные и
  полученные байты; в процентили включены и неудачные попытки;
- подтверждённые сохранения, успешные проверки документа/ревизии, receipt retry,
  отклонённые stale writes и чтения чужого проекта;
- отдельные observed/target SLO, CPU/память процесса и редкие pool samples.

`correctness=PASS` требует30 независимых identity,60 подтверждённых сохранений,
62 корректных чтений (два дополнительных после конфликтов), две стабильные
квитанции повтора, два отклонённых stale writes и два отказа чужому читателю.
Это функциональный результат сценария. Задержки сравниваются отдельно с целями
capacity-контракта; зелёный job сам по себе не подтверждает performance SLO.
`capacityAcceptance=NOT_EVALUATED` остаётся таким при любом исходе малого теста.
При ошибке сохраняются имеющиеся агрегаты, job завершается FAIL. Не следует
уменьшать число участников или исключать неудачные попытки ради зелёного job.

## Пределы малого теста

API и генератор используют один Node process, PostgreSQL — отдельный контейнер.
Это closed-loop barrier workload: медленный ответ сдвигает следующую операцию,
поэтому такой генератор может скрывать перегрузку. Средний RPS — наблюдение, не
предел пропускной способности. Секундные pool samples могут пропустить короткий
пик; event-loop показатель общий у генератора и API. Ресурсы runner измеряются,
но не являются рекомендованным минимумом оборудования.

Нет браузерной Scratch VM, Caddy, загрузки MinIO-медиа, измерения статического
кэша/внешнего ingress, перезапусков контейнеров, полного распределения размеров
проектов или Learning/3D/Games journeys. Документы небольшие и синтетические.
Это **не** browser CLASS-30 из issue476 и **не**3000/5000 capacity acceptance.
Слой с неполным evidence нельзя объявлять здоровым по отсутствующим метрикам.
Списки Scratch assets пустые. Для создания обязательного S3-клиента заданы
синтетические настройки неработающего loopback endpoint; запросы к хранилищу
не выполняются, готовность MinIO этим не проверяется.

## Дальнейший масштаб

`tools/capacity/profile-v1.json` фиксирует C3000-PROFILE-V1: identity/admission/
module mix, группы классов/школ/NAT, arrival ramp, размеры документов/медиа,
cold/warm phases, save cadence/jitter, teacher bursts и перечень fault cases.
Это версия workload, не изменение долговременного архитектурного контракта.
Только вложенный CLASSROOM-API-30-V1 сейчас исполняется автоматически; остальные
профили требуют полного генератора и доказательств по всем слоям.

Порядок:30 →100 →300 →1000 →3000.5000 — отдельное исследование после3000.
Переход разрешается только после полной предыдущей ступени: SLO, реальная
выполненная нагрузка, запас генератора, отсутствие потери подтверждённых
сохранений/разлогиниваний/доступа к чужим данным и все обязательные метрики.
При недостающем evidence или исчерпании генератора — INCONCLUSIVE; при нарушении
корректности/SLO — FAIL, остановка на этой ступени и отдельная задача по причине.

Перед FIRST-C3000-BENCHMARK обязательны закрытие либо явный owner-defer blockers
из issue477. Без тестового сервера этот benchmark не запускается. Позднее
используется отдельный изолированный runner/сервер с собственной тестовой БД;
никакого прогрева рабочего школьного сервиса этот сценарий не разрешает.
FRP и live deployment остаются отдельными действиями владельца.
