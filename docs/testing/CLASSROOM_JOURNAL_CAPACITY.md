# Нагрузочный замер записи в журнале

**JOURNAL-ACTIVE-30-V3** проверяет один класс на временном GitHub runner. В нём 30
отдельных сессий StudentSeat и учитель с действующим аккаунтом. У каждого ученика свой
код. Для замера берётся уже созданный столбец и ученик с существующей оценкой.
Подготовка класса и вход участников в задержки записи не входят.

## Запуск

Workflow **Classroom Journal Capacity** выполняется для PR с подходящими путями.
После интеграции его можно запустить вручную на нужной ветке. Команда сценария
`pnpm exec playwright test --config playwright.classroom-journal-capacity.config.ts`
использует HTML и API из сборки выбранного коммита. Сценарий требует GitHub Actions,
точную loopback БД `asa_journal_capacity_test` и ограниченную роль `asalab_app`.
PostgreSQL и сервер создаются для одного запуска.

## Профиль

- Учитель меняет оценку и название столбца через обычный журнал и его реальные
  запросы. Проверка выполняется в Chromium при ширинах 1440 и 390 пикселей.
- Для каждой ширины есть контроль без активности учеников и две серии с нагрузкой.
  Первая волна из 30 ученических запросов запускается перед отправкой нажатия
  кнопки учителя. Следующие волны запускаются через 120 и 240 мс от первой.
  В каждой волне участвуют все 30 независимых сессий. В первой серии ученики
  читают списки заданий и результатов журнала.
- Во второй серии каждый из 30 учеников сохраняет свой проект Electronics в
  нулевой волне. Две следующие волны используют те же чтения, что и первая серия.
  Проекты создаются и открываются вне замера. Для редакций используется
  существующий синтетический документ из общего нагрузочного сценария с пятью
  резисторами (около 1,2 КБ в JSON без обёртки запроса).
  Перед следующим сохранением каждого ученика API должен вернуть ту же версию
  и тот же документ, которые были подтверждены его предыдущим сохранением.
- Встроенная диагностика Node фиксирует получение запроса сервером и завершение
  ответа по одним монотонным часам. Замер под нагрузкой засчитывается, когда
  хотя бы один запрос первой волны строго пересёк интервал запроса учителя.
  Для каждой волны отчёт показывает число пересечений, число ученических
  запросов в работе на момент входа запроса учителя и пик одновременно
  принятых сервером запросов. Это интервалы HTTP, которые могут включать
  ожидание соединения с БД. Отдельно отмечается число запросов, отправленных
  клиентом одновременно.
- При промахе синхронизации тест повторяет действие до двух раз с новой
  записью. По интервалам предыдущей попытки он выбирает смещение первой волны
  относительно отправки нажатия в пределах 60 мс в каждую сторону.
  Все попытки и интервалы сохраняются, а сводки задержек включают подтверждённые
  замеры. Промахи могут влиять на сравнимость сводок. Если за три попытки
  пересечение не подтверждается, проверка падает. Сервер обслуживает запросы
  без искусственных задержек для измерения.
- Измеряются браузерное время HTTP-запроса до полного ответа и интервал от
  пользовательского нажатия до появления верной оценки или названия в DOM и
  сообщения о сохранении. Второе измерение не включает доставку результата
  автоматизации обратно в драйвер.
- После каждого сохранения результат повторно читается через API, сверяются
  значение и ревизия. Первый запрос каждой группы повторяется с тем же
  идентификатором, чтобы подтвердить возврат той же сохранённой квитанции.
- Отдельное read-only соединение с PostgreSQL снимает приблизительно каждые
  100 мс число активных соединений приложения и ожиданий блокировок. Короткие
  пики между отсчётами могут не попасть в выборку.

## Чтение результата

Артефакт `classroom-journal-capacity-<SHA>/classroom-journal.json` содержит точный
SHA сборки, сведения о среде, число независимых участников, выборки отдельно для
каждой ширины, режима и операции, p50/p95/max и фактические размеры выборок.
Для каждой попытки сохранить проект артефакт содержит время записи и результат
проверки сохранённой версии.
Отклонения от заданного ритма видны по времени начала каждой волны. Секреты,
куки, личные данные и тела запросов не входят в отчёт. Частичные измерения
сохраняются и при ошибке.

Цель Learning NFR-004 для обычного API — p95 до 500 мс. На общем runner эти
цифры используются для диагностики. По четыре записи каждого вида в одной
группе достаточно для воспроизведения поведения, но недостаточно для устойчивой
оценки хвоста. Для сравнения до и после исправления нужны повторные замеры
того же профиля с отдельными результатами и тем же типом runner. Ошибки
сохранения, неполная нагрузка, противоречивая сверка результата или отсутствие
наблюдений PostgreSQL проваливают проверку.

В каждой из 12 групп четыре засчитанные записи педагога, всего 48. В четырёх
группах Electronics этим замерам соответствуют 480 подтверждённых сохранений
проектов и проверок чтения. Фактические числа включают дополнительные попытки,
если первая волна и запрос учителя не пересеклись. Внешний вход в школе, проекты Scratch,
активность в браузерных редакторах, первоначальная отрисовка журнала 30×100,
весь профиль CLASS-30 и больший масштаб проверяются отдельно.
