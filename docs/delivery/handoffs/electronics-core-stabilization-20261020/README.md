## 1. Назначение и граница готовности

Это пакет передачи требований владельца новому программному контроллеру. Он содержит полный объём СТ-00–СТ-24, известные дефекты, численные эталоны, визуальную приёмку, требования к Arduino, последовательную доставку и три конечных эксплуатационных проверки. Редакция 2.1 заменяет предыдущие редакции 1.0/2.0 этого пакета.

Пакет готов для чтения, выбора первого конкретного среза и организации реализации. Публикация документов сама по себе не означает запуск исполнителя, изменение электроники, зелёный CI, интеграцию в main, deployment или production-готовность.

Это отдельный пакет от ранее принятого `docs/product/electronics/ASA_ELECTRONICS_STABILIZATION_SPEC_V2.md`. Он передаёт новые цели владельца и не отменяет принятые результаты, аппаратные ограничения, действующие проверки или незавершённые задачи. Текущая выбранная задача, blockers и состояние работ читаются только из [current.yaml](../../../execution/current.yaml) на актуальном main. Копия этого файла внутри ветки документов является датированным состоянием базового коммита, а не текущим источником выбора задачи.

Эта ветка предназначена для документов. Продуктовую работу продолжать на актуальной принятой основе согласно действующей политике репозитория. Нельзя накопить реализацию всей программы в ветке ТЗ и удерживать готовые самостоятельные исправления до завершения остальных пакетов.

## 2. Первый вход контроллера

1. Прочитать актуальные `AGENTS.md`, `START_HERE_FOR_AI.md` и `docs/delivery/GITHUB_FIRST_DEVELOPMENT_PROTOCOL.md` из main. Учитывать `docs/delivery/AGENT_CHANGE_WORKFLOW.md` при публикации результата.
2. Один раз прочитать [SPEC.md](SPEC.md) полностью. Исполнителям передавать только выбранный пакет, относящиеся к нему инварианты и точные проверки.
3. Получить актуальные main, `docs/execution/current.yaml`, относящиеся к электронике кандидаты и CI соответствующих SHA. Не проводить повторный общий аудит всей платформы и не скачивать всю историю отчётов.
4. В существующем подготовленном checkout выполнить штатный вход:

```bash
pnpm agent:preflight --scope electronics --check
```

5. Сопоставить СТ-00–СТ-24 с уже принятой и незавершённой работой. Сохранить текущих исполнителей и их изменения. Уже подтверждённое требование закрывается существующим подходящим доказательством, без обязательного переписывания кода.
6. Если в текущем состоянии выбран подходящий исполняемый срез, продолжить его через точную task card и фактический lane. Если нужно выбрать новый срез в рамках порученной владельцем программы, контроллер оформляет этот выбор в каноническом состоянии main по действующим правилам до начала продуктовых правок. Ветка с продуктом не редактирует `current.yaml`, чтобы сама себе выдать разрешение.
7. Выполнить предусмотренную валидатором проверку конкретной выбранной task card. Требуемые ID брать из фактического канонического состояния, не придумывать и не копировать устаревшую задачу из чата.

Если preflight возвращает применимый blocker, сначала выполнить его `SAFE_ACTION` и классифицировать ограничение. Acceptance blocker не превращать в запрет любой диагностики; deployment blocker не превращать в остановку всей разработки. Реальные execution blockers и защищённые данные сохраняются. Устаревший CI, чужая задача или опубликованный план не являются доказательством текущей приёмки.

## 3. Поручение на реализацию после запуска владельцем

Ты — программный контроллер стабилизации электроники ASA Lab. Организуй и доведи существующую электронику до результатов полного ТЗ. Работай только в этом направлении и продолжай программу после каждого принятого самостоятельного среза.

Первый результат — доступное исправление воспроизведённого пользовательского отказа или подтверждение, что он уже исправлен, с точной версией и демонстрацией. Общий аудит, новый план или созданный тестовый каркас не заменяют этот результат.

Основной поток — корректная связность, параметры, DC/нелинейность/переходные процессы, общая граница ядра, настоящая компиляция и исполнение Uno, причинная связь с электрической схемой, достоверное изображение. Сохранение, жесты, читаемость и восстановление ресурсов ремонтируются по своим зависимостям без ожидания полного MCU.

Рано подтвердить два сквозных проекта: восемь LED с массивом/функцией/битовой маской и PWM → RC → ADC → изменение PWM. Оба должны использовать фактическую прошивку, общую шкалу времени и принятые состояния. До массовой приёмки зависимых Arduino-компонентов получить доказательство этой основы на целевом устройстве. Самостоятельные ранние исправления продолжают доставляться по §4.6 ТЗ.

Контроллер распределяет ограниченные срезы, исполнитель делает один срез, независимый рецензент проверяет конечный результат. Пересекающиеся файлы имеют одного согласованного писателя. Два неудачных исправления одной гипотезы требуют её пересмотра. Диагностический бюджет и конечный результат заданы в §4 ТЗ.

Не создавай новую платформу или второй редактор. Не меняй курсы, AI-чат, авторизацию или другие модули ради несвязанного CI. При независимом отказе общей проверки зафиксируй его причину и применимый путь разрешения; не объявляй весь продукт готовым при красном обязательном gate.

Принимай и интегрируй готовые самостоятельные результаты по действующим полномочиям. Различай проверенный исходник, main, установленную сборку и пользовательскую приёмку. Наличие всего ТЗ в GitHub не даёт разрешения на обновление установки, операции с рабочей БД или изменение сети. Уже предоставленные полномочия использовать без повторного запроса.

## 4. Что контроллер предъявляет после каждого результата

- Исправленный отказ и его контрольный проект.
- Шаги, позволяющие увидеть результат в существующем редакторе.
- Применённый независимый эталон, проверки и честные результаты.
- SHA, фактическое положение в main и доступный способ демонстрации.
- Сохранённые ранее принятые возможности и оставшийся конкретный дефект.
- Следующий выбранный зависимый срез либо точный внешний блокер.

Программа завершается по §11 ТЗ. Для готовности к эксплуатации дополнительно обязательны фактические доказательства §16: установленная версия и совместимое восстановление приложения, восстановление серверной копии, полный рабочий цикл класса 15 Electronics + 15 Scratch. Один общий итоговый прогон используется повторно там, где он действительно покрывает несколько критериев. Отсутствующее аппаратное или эксплуатационное доказательство остаётся открытым, но не удерживает независимые принятые исправления.

Пакет задания опубликован в ветке `docs/electronics-core-stabilization-20261020`, каталог `docs/delivery/handoffs/electronics-core-stabilization-20261020/`. Прочитай `README.md`, затем полностью `SPEC.md` редакции 2.1. Используй актуальные правила и `docs/execution/current.yaml` из main, сохрани уже принятую и незавершённую работу. Действуй как программный контроллер: выбери конкретный срез по каноническому порядку, назначь исполнителя и необходимую независимую проверку, доведи до видимого результата и разрешённой интеграции, затем продолжай следующие зависимые срезы до цели. Первые исправления должны доходить до main по мере готовности. Не повторяй большой аудит, не начинай реализацию заново и не отвлекайся на другие модули. Deployment, рабочая БД и сеть — только в пределах отдельно имеющихся полномочий. Статус ТЗ не выдавай за готовую электронику.
