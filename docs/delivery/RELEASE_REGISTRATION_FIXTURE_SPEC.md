# ТЗ: подготовка аккаунтов браузерного выпуска при ограничении запросов

**Идентификатор:** RELEASE-REGISTRATION-FIXTURE-SPEC

**Редакция:** 1.0

**Задача:** TASK-RELEASE-REGISTRATION-FIXTURE-001

## Причина и границы

Общий браузерный прогон использует один сервер и сетевой адрес. После большого числа мутаций подготовка последних аккаунтов может получить штатный HTTP 429 generic mutation protection: 900 запросов за пять минут. Это отдельный механизм от лимита регистрации 60 за час. Подготовка должна учитывать подтверждённое сервером окно, сохраняя настоящую регистрацию современного Account через API и последующие проверки доступа.

Исправление относится только к тестовому окружению выпуска. Рабочие ограничения, авторизация, прокси, origins, бизнес-логика и схема не меняются. Обход защиты, её отключение, увеличение квот, подмена адреса и замена личного Account на legacy-организацию запрещены.

## Требования

1. Повтор допускается только для подготовки `POST /api/auth/register`, если ответ HTTP 429 содержит `too_many_requests`, целый Retry-After от 1 до 300 секунд и точно совпадающий error.retryAfterSeconds.
2. Выдерживается указанное сервером окно; тот же request context, origin и исходный payload отправляются повторно ровно один раз. Другие endpoint и реальные сценарии входа/мутаций не получают автоматических повторов.
3. HTTP 201 возвращается сразу. Иные статусы, специальный лимит too_many_attempts, некорректные/несогласованные/слишком большие интервалы и повторный HTTP 429 остаются ошибкой исходного утверждения о HTTP 201. Бесконечные повторы запрещены.
4. Время теста расширяется только на фактическое ожидание квоты. Первоначальные бюджеты сценариев 90/120 секунд сохраняются; серверная задержка не превращается в дополнительный бюджет исполнения проверок.
5. Сохраняются все утверждения owner classroom flow и StudentSeat: 30 последовательных входов, 30 параллельных, 30×4 восстановления после опечаток, изоляция и допустимые отказы.
6. Минимальные пути: новый `e2e/registration-setup.ts`, два затронутых браузерных spec и `tests/portal/registration-setup.spec.ts`. Существующий `test:access-a` включает tests/portal, дополнительные package/workflow изменения не нужны.
7. Проверки с fake clock подтверждают строгий контракт Retry-After, исходную идентичность запроса, единственный повтор, сохранённый бюджет и отказ при постоянном/неправильном 429. Локально выполняются только эти проверки, форматирование и обнаружение браузерных сценариев.
8. Перед публикацией требуется независимый просмотр точного коммита. Полный General окончательного main, включая реальный общий браузерный прогон и БД, обязателен перед выпуском готовых образов и переключением основной установки.

Исходный полный браузерный сбой является доказательством до исправления; повторять тяжёлый исходный прогон не требуется. Эта задача не устанавливает реальную предельную нагрузку школьной сети и не означает выполнения оставшихся пунктов программы наблюдения.
