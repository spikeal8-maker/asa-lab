# ASA AI — задачи по замечаниям владельца

Это список требований и критериев результата, а не второе execution state.
Активный срез, статус исполнения, SHA и evidence ведутся только в
`docs/execution/current.yaml`. Наличие пункта здесь не означает его выполнения.

## Порядок выполнения

По поручению владельца от 26 октября 2026 года сначала объединяется в `main`
уже подготовленная работа AI после необходимых проверок. Только после этого
выбираются и реализуются следующие задачи. Этот документ сам по себе не
разрешает deployment, изменение рабочей БД или подключение платных сервисов.

## Задачи

| ID | Задача | Критерии результата |
| --- | --- | --- |
| AI-ADMIN-01 | Дашборд использования и порядок вкладок | Первый раздел — дашборд, второй — настройки. Реальные запросы, пользователи, входные/выходные токены, ошибки и использование инструментов за выбранный период; графики и разбивка по моделям. Неизвестный расход не показывать как нулевой. Пустые данные и недоступность источника различимы. |
| AI-ADMIN-02 | Живой каталог подключённых моделей | Получать доступные модели от каждого настроенного провайдера и локального сервера Ollama; показывать источник и время обновления. Удалённые, недоступные и устаревшие модели отмечать явно. Выбор по умолчанию и разрешения используют этот каталог. Сбой API не заменять выдуманным актуальным списком. |
| AI-ADMIN-03 | Доступ к моделям по категориям | Определить категории на существующей модели Account/Seat/учебных ролей; настраивать доступные модели и модель по умолчанию для каждой категории. Сервер проверяет права при каждом запросе. Изменения не смешивают личные аккаунты и школьный контекст. |
| AI-ADMIN-04 | Токенные бюджеты | Настраиваемые бюджеты по пользователям и категориям, период сброса, остаток и причины отказа. Учитывать все модельные этапы инструментального запроса, конкурентные запросы и неизвестный расход. Нужна проверка серверного применения, а не только полей формы. |
| AI-PROMPT-01 | Предпросмотр реального контекста | В админке показать подстановку переменных для вошедшего администратора: значение, источник, время вычисления, поведение при отсутствии. Отделить серверное время, часовой пояс профиля и данные устройства. Не раскрывать секреты или данные другого пользователя. |
| AI-PROMPT-02 | Расширенный пользовательский контекст | По разрешённым источникам добавить профиль, класс, проекты и прохождение курсов; для каждого поля определить назначение, доступ, актуальность и отсутствие значения. Пол, геопозицию, аватар и устройство добавлять только при наличии действительного источника; не угадывать. Доступ к подробностям через ограниченный серверный инструмент, если полного контекста не требуется. |
| AI-ANSWER-01 | Завершённые ответы без лишнего текста | Проверить длинный код и обычный диалог на поддерживаемых локальных и облачных моделях. Различать лимит токенов, таймаут, остановку владельцем и ошибку провайдера. При незавершённом ответе дать понятное продолжение с сохранением истории и без скрытого повторного списания. Краткость пояснений не обрезает запрошенный файл. |
| AI-TOOLS-01 | Единое поведение инструментов | Определить поддержку каждой модели/провайдера; подключать только реально исполнимые tools. Проверить запросы с вложениями, продолжение диалога, отказ инструмента, лимиты и отмену. Инструкции, параметры, результаты и ограничения в админке соответствуют реальным вызовам. Облачные модели не считать поддержанными только по наличию текста в промпте. |
| AI-SEARCH-01 | Погода и поиск изображений: итоговая приёмка | Проверить города разных стран, настоящую неоднозначность, отсутствие данных и время прогноза; карточки с понятными единицами. Поиск картинок показывает несколько проверенных миниатюр, источники и горизонтальную галерею на телефоне. Описать пределы фильтрации нежелательного контента и поведение при блокировке; не обещать абсолютную фильтрацию. |
| AI-IMAGES-01 | Удалённый ComfyUI и несколько моделей | Администратор задаёт разрешённое сетевое подключение к GPU-серверу, проверяет связь и совместимые модели/рецепты. Показать явный выбор модели и автоматический выбор среди разрешённых. Сохранить SSRF, ограничения адресов и секретов; SSH-туннель — только отдельно согласованная эксплуатационная настройка. Не добавлять платную генерацию. |
| AI-MODELS-01 | Управление локальными моделями | Отдельно определить безопасное скачивание и удаление моделей Ollama: место, прогресс, отмена, занятая модель и влияние на доступ пользователей. Не удалять существующие модели или задания автоматически. |
| AI-OLLAMA-01 | Возможность входа в Ollama Cloud | Проверить официальный поддерживаемый способ делегированного входа и ограничения. Если OAuth для стороннего приложения не предоставляется, явно описать это вместо имитации авторизации. API-ключ остаётся самостоятельным способом подключения; секреты не передавать браузеру. |
| AI-CHAT-01 | Итоговая визуальная приёмка чата | Проверить светлую/тёмную тему, меню плюсика, близкое расположение Auto, чип изображения и разрешение, иконки действий и подсказки, длинные названия чатов, предпросмотр нескольких изображений/файлов, фокус после ответа и плавную отмену. Проверить настольный и мобильный размеры в настоящем браузере. |
| AI-FILES-01 | Создание и скачивание файлов | Составить явную матрицу поддерживаемых форматов кода и документов; проверить MIME, имя, расширение, содержимое и фактическое скачивание. Отличать экспорт текста ответа от создания полноценного документа; не обещать все форматы без реализации. |
| AI-VIDEO-01 | Будущая генерация видео | Пока только обозначение «Скоро», без активного вызова. Реализацию начинать отдельным поручением с локальным исполнителем, лимитами и критериями качества. |

## Зависимости и проверка

Рекомендуемый порядок: AI-ADMIN-01 → AI-ADMIN-02 → AI-ADMIN-03 → AI-ADMIN-04;
AI-PROMPT-01 → AI-PROMPT-02. Проверка ответов и инструментов выделяется в
отдельные ограниченные срезы. Перед каждым срезом сверяется фактический `main`:
параллельная работа могла уже закрыть часть требований.

Для каждого результата нужны проверка серверного поведения, соответствующие
focused tests и визуальная проверка там, где меняется интерфейс. Общий CI,
публикация в `main`, обновление локального стенда и приёмка владельцем — разные
действия; одно не объявляется доказательством другого.
