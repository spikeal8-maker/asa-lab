# ASA Checkers — product rework execution plan

**Status:** ACTIVE IMPLEMENTATION
**Owner outcome:** превратить текущий учебный модуль шашек в понятную полноценную игру, где пользователь без обучения интерфейсу может сразу начать партию с ботом, другим человеком, одноклассником или перейти к задачам.
**Baseline:** существующее ядро правил, боты, учебные задачи, сохранение, разбор партий и classroom-механика сохраняются и переиспользуются; продуктовый слой и игровая воронка перерабатываются.

---

## 1. Цель программы

ASA Шашки должны перестать выглядеть как набор учебных экранов вокруг доски. Первый пользовательский вопрос должен быть не «что значит Продолжить?», а «с кем я хочу сыграть?».

Целевой первый экран:

```text
Шашки

[ Играть с ботом ]
[ Играть вдвоём ]
[ Играть с другом ]
[ Играть в классе ]

[ Задачи и обучение ]
[ Мои партии ]
```

Если у пользователя есть незавершённая партия, сверху допускается отдельная карточка:

```text
Продолжить партию
Искра · вы играете светлыми · ваш ход
[ Продолжить ]
```

Абстрактной кнопки «Продолжить» без контекста быть не должно.

Главное правило продукта:

> пользователь должен начать понятную партию максимум за два осознанных действия после входа в шашки.

## 2. Что сохраняем из текущей реализации

Не переписывать с нуля следующие части без доказанной технической причины:

- `contexts/checkers/domain/rules.ts` — правила русских шашек;

- систему задач, подсказок и учебных доказательств;
- сохранение состояния проекта и student state;
- classroom safety-механику и готовые реакции;
- разбор партий и существующие unit/E2E тесты правил;
- keyboard/accessibility поддержку доски.

Переработке подлежат прежде всего:

- информационная архитектура;
- главный экран;
- запуск партии;
- модель игровых режимов;
- визуальный renderer доски;
- online/friend multiplayer;
- realtime-обновление партий;
- структура UI-компонентов;
- понятность задач и обучения;
- состояние «продолжить партию»;
- визуальная иерархия мобильной версии.

## 3. Зафиксированные проблемы текущего продукта

### P0 — блокируют нормальное использование

1. Нет прямого понятного сценария «Играть».
2. Игра с ботом спрятана внутри лестницы ботов.
3. Сильные боты заблокированы учебной прогрессией даже в обычной свободной игре.
4. Нет режима двух игроков за одним устройством.
5. Нет простого режима «создать игру → отправить ссылку/код другу».
6. PvP фактически привязан к classroom-проекту.
7. Главная кнопка «Продолжить» не объясняет, что пользователь продолжает.
8. Визуально доска воспринимается как учебный виджет, а не как законченная игровая поверхность.

### P1 — ухудшают качество игры

1. Classroom active game обновляется polling-механикой вместо нормального realtime-потока.
2. Ход шашки визуально является перестановкой DOM-содержимого между клетками, а не движением фигуры.
3. Нет полноценной анимации перемещения, взятия и превращения.
4. Бот рассчитывает полезные объяснения хода, но пользователь почти не получает эту информацию.
5. UI-контроллер `CheckersModuleExperience.tsx` выполняет слишком много ролей одновременно.
6. Свободная игра, обучение, задания и classroom-партии смешаны в одном state-machine слое.
7. Победа над ботом должна учитывать сторону игрока; текущая логика прогрессии требует отдельной проверки и исправления для победы тёмными.

## 4. Продуктовая структура после переработки

### 4.1 Главная шашек — `CheckersLobby`

Главная не является учебным дашбордом.

Она содержит:

1. **Продолжить партию** — только если есть активная партия.
2. **Играть с ботом**.
3. **Играть вдвоём**.
4. **Играть с другом**.
5. **Играть в классе** — только когда classroom доступен.
6. **Задачи и обучение**.
7. **Мои партии / история**.

Не показывать пользователю одновременно десятки показателей освоения, заданий и педагогических сущностей выше основного игрового действия.

### 4.2 Свободная игра с ботом

Поток:

```text
Играть с ботом
→ выбрать уровень
→ выбрать сторону: светлые / тёмные / случайно
→ Начать
```

Требования:

- все уровни ботов доступны в свободной игре;
- лестница ботов остаётся отдельным режимом прогрессии/кампании;
- последний выбранный уровень можно запоминать;
- после завершения доступны: реванш, новый соперник, разбор, выход;
- победа корректно определяется относительно выбранной стороны пользователя;
- бот работает через существующий Web Worker;
- UI показывает состояние «бот думает», но не блокирует интерфейс целиком.

### 4.3 Игра вдвоём на одном устройстве

Новый режим `local`.

Поток:

```text
Играть вдвоём
→ новая партия
→ игра начинается сразу
```

Требования:

- никакой сервер или classroom не обязателен;
- после каждого хода сторона меняется по правилам;
- опциональная кнопка «повернуть доску после хода»;
- undo допускается только как явная настройка локальной дружеской партии;
- состояние можно сохранить локально/в личной истории;
- режим должен работать при временном отсутствии сети после загрузки приложения.

### 4.4 Игра с другом

Новый режим `friend`.

Минимальный поток:

```text
Играть с другом
→ Создать игру
→ система выдаёт ссылку и короткий код
→ второй пользователь открывает ссылку или вводит код
→ стороны назначаются
→ партия начинается
```

Минимальный R2 scope:

- private invite only;
- без глобального поиска случайных соперников;
- без обязательного рейтинга;
- без свободного чата;
- reconnect после краткого обрыва;
- сервер авторитетно проверяет каждый ход;
- каждый ход имеет sequence/version;
- повторная отправка одного хода идемпотентна;
- завершение партии хранится на сервере;
- ссылка не должна давать постороннему право управлять обеими сторонами.

### 4.5 Игра в классе

Существующий classroom PvP сохраняется как отдельный режим, а не как единственный способ играть с человеком.

Требования:

- вызов одноклассника;
- матч педагога;
- готовые безопасные реакции;
- педагогическое наблюдение;
- отсутствие свободного чата;
- серверная проверка ходов;
- активная партия использует тот же игровой renderer, что bot/local/friend;
- transport active game переводится на realtime-модель; polling допустим как fallback, но не как основной игровой канал.

### 4.6 Задачи и обучение

Обучение становится отдельной понятной зоной.

Первый экран обучения:

```text
Задачи
- Правила и первый ход
- Обязательное взятие
- Взятие назад
- Серия взятий
- Дамка
- Комбинации
- Полная партия

[ Продолжить обучение ] — только с подписью конкретной темы
```

Требования:

- пользователь всегда видит цель задачи до открытия доски;
- задача использует тот же renderer доски;
- объяснение → пример → самостоятельный ход → обратная связь;
- нельзя путать учебную задачу и обычную партию;
- прогресс не блокирует свободную игру;
- педагогические задания остаются отдельным подразделом «От преподавателя».

## 5. Целевая модель игрового состояния

`CheckersDocument` остаётся каноническим состоянием правил позиции.

Поверх него вводится явная сессия/матч, чтобы UI больше не определял тип игры косвенно через classroom, выбранного бота и текущую поверхность.

Рекомендуемая модель:

```ts
type CheckersMatchMode = 'bot' | 'local' | 'friend' | 'classroom';

type CheckersMatchStatus =
  | 'setup'
  | 'waiting'
  | 'active'
  | 'finished'
  | 'abandoned';

interface CheckersMatchSession {
  id: string;
  mode: CheckersMatchMode;
  status: CheckersMatchStatus;
  document: CheckersDocument;
  humanSide?: 'light' | 'dark';
  botId?: CheckersBotId;
  version: number;
  createdAt: string;
  updatedAt: string;
}
```

Это не обязательная финальная схема БД, а обязательный архитектурный принцип: режим партии должен быть явным и не зависеть от того, на каком экране оказался пользователь.

## 6. Новый renderer доски — Board V2

Текущий `CheckersBoard` сохраняет правила взаимодействия и accessibility, но визуальный слой перерабатывается.

### Обязательная структура

```text
BoardSurface
├── GridLayer
├── CoordinateLayer
├── MoveHintLayer
├── PieceLayer
├── AnimationLayer
└── InteractionLayer
```

Фигуры не должны физически жить только как содержимое кнопки клетки. Piece layer должен позволять анимировать переход между координатами.

### Обязательные эффекты

- плавный ход фигуры;
- отдельное визуальное взятие;
- серия взятий без визуального телепорта;
- превращение в дамку;
- last move highlight;
- selected piece;
- legal destination;
- forced capture indication;
- hover только там, где действие реально возможно;
- отсутствие layout shift.

### Визуальные требования

- убрать ощущение «учебной бирюзовой карточки»;
- уменьшить массивность рамки;
- отказаться от чрезмерных теней и градиентов;
- дамка не должна обозначаться случайным символом `◆`;
- использовать качественный CSS/SVG-векторный знак дамки;
- подготовить минимум 3 темы: Classic, Light, Dark;
- доска остаётся строго квадратной;
- фигуры читаются на desktop, tablet и mobile;
- мобильная доска занимает максимально полезную ширину без горизонтального scroll.

## 8. Realtime и серверная модель

### Правило

В online-партиях браузер не является источником истины.

Сервер должен:

1. проверить участника;
2. проверить version/sequence;
3. проверить ход через `applyCheckersGameMove`;
4. сохранить новое состояние атомарно;
5. опубликовать событие обоим клиентам;
6. вернуть подтверждённую версию.

### Transport

Использовать существующую инфраструктуру `realtime-gateway`, если она удовлетворяет требованиям. Не копировать шахматный domain-код, но допустимо переиспользовать общий транспортный шаблон reconnect/subscription.

События минимального контракта:

```text
match.created
match.joined
match.started
move.accepted
move.rejected
match.finished
match.resigned
connection.restored
```

Polling 2500 ms остаётся только как аварийный fallback или список lobby, но не как основной канал активной партии.

## 9. Порядок реализации

### CK-000 — activation and baseline

**Цель:** зафиксировать текущую работу и защитить существующее ядро от случайной переписки.

Deliverables:

- этот execution plan;
- список текущих routes/screens;
- текущий E2E smoke: задача → бот → ход → ответ бота;
- regression тест победы игрока светлыми и тёмными;
- baseline screenshots desktop/tablet/mobile;
- список таблиц/API classroom checkers;
- подтверждение текущего realtime/polling поведения.

**DoD:** существующие правила, боты и classroom tests зелёные; план принят как source of truth.

### CK-101 — новый Checkers Lobby

**Цель:** убрать непонятный стартовый экран.

Сделать:

- новый игровой lobby;
- карточки Bot / Local / Friend / Classroom / Learning / History;
- contextual Resume Card;
- удалить generic «Продолжить» без описания;
- обучение не должно занимать главный CTA;
- сохранённая партия должна открываться одним действием.

**Acceptance:** новый пользователь без инструкции видит все целевые режимы и может начать доступную bot-партию максимум за два действия. Local / Friend / History до своих этапов должны быть явно недоступны, а не имитировать рабочую функцию. Рабочий Local активируется только в CK-103.

**Checkpoint 2026-09-12:** game-first Lobby реализован. Bot / Learning / Classroom ведут в существующие рабочие сценарии; Local / Friend / History показаны как будущие режимы и disabled. Generic «Продолжить» удалён. Resume отображается только с конкретным контекстом незавершённой партии. Для bot-resume сторона игрока сохраняется локально; legacy-партия без достоверной стороны fail-closed и не запускает автоматический ход бота. Focused gate требуется зелёный; свежий browser gate остаётся отдельным evidence-action на изолированной `*_test` БД.

### CK-102 — Bot Free Play

**Цель:** сделать существующих ботов реально доступной игровой функцией.

Сделать:

- отдельный setup;
- все боты доступны в free play;
- сторона light/dark/random;
- campaign progression отделена от free play;
- исправить определение победы относительно стороны пользователя;
- реванш;
- выбор нового бота;
- понятный game result.

**Acceptance:** игрок может начать, закончить и повторить полноценную партию ботом за обе стороны.

**Checkpoint 2026-09-12:** CK-102 реализован. Свободная игра отделена от учебной лестницы через сохраняемый ctiveBotMode=free|campaign; все шесть ботов доступны без unlock в free play; доступны светлые, тёмные и случайная сторона; победа кампании считается относительно стороны человека, включая  -1 за тёмных; free play не меняет ladder progression. После завершения показаны результат, реванш, выбор другого соперника и переход в разбор. Старые документы без ctiveBotMode принимаются как campaign для сохранения прежней семантики. gate:checkers-m1 PASS без Nx cache: 20 test files / 81 tests, общий typecheck и production build 26 проектов. Browser E2E обновлён, но свежий запуск не заявляется без изолированной *_test БД.

### CK-103 — Local Two Player

**Цель:** два человека могут просто играть на одном устройстве.

Сделать:

- `mode=local`;
- отсутствие bot effect;
- корректная смена стороны;
- опциональный auto-flip;
- restart/resign/draw controls;
- локальное восстановление незавершённой партии.

**Acceptance:** два пользователя могут провести полную партию без classroom и без второго аккаунта.

### CK-104 — Board V2

**Цель:** заменить визуально слабую доску, не затрагивая правила.

Сделать renderer, темы, анимации, vector king marker, last move, forced capture и responsive polish.

**Acceptance:** одинаковая позиция и все legal moves совпадают с Board V1; E2E проверяет desktop/tablet/mobile; никаких телепортов фигуры при обычном ходе.

### CK-105 — Match Session refactor

**Цель:** убрать смешивание surface state и domain game state.

Сделать:

- явный `mode/status`;
- общий match controller;
- общий result flow;
- общий resume flow;
- общий history model;
- адаптер старого personal project state.

**Acceptance:** bot/local/classroom используют одну игровую surface, но разные opponent/session adapters.

### CK-106 — Friend Invite backend

**Цель:** private online game между двумя пользователями.

Сделать:

- создать private match;
- короткий код + invite URL;
- join;
- side assignment;
- server-authoritative move;
- optimistic concurrency/version;
- idempotency;
- finish/resign;
- permissions.

**Acceptance:** два браузерных контекста проводят партию друг против друга и не могут сделать ход за чужую сторону.

### CK-107 — Checkers Realtime

**Цель:** активная online-партия не зависит от 2.5-second polling.

Сделать:

- subscription;
- move push;
- reconnect;
- duplicate event handling;
- stale version recovery;
- degraded polling fallback.

**Acceptance:** второй клиент видит подтверждённый ход без ручного refresh; reconnect восстанавливает каноническое состояние.

### CK-108 — Classroom convergence

**Цель:** сохранить школьную безопасность, но перевести classroom на новый match UX.

Сделать:

- существующие вызовы;
- teacher event;
- safe reactions;
- moderation/reporting;
- Board V2;
- общий match surface;
- realtime active game.

**Acceptance:** текущие classroom capabilities не потеряны, а ученик больше не попадает в отдельную визуально чужую игру.

### CK-109 — Learning UX rework

**Цель:** задачи становятся понятным вторичным режимом.

Сделать:

- learning home;
- явные темы;
- отдельный teacher assignments block;
- contextual «Продолжить тему …»;
- Board V2 в задачах;
- сохранить hints/evidence/mastery;
- свободная игра не блокируется учебным прогрессом.

**Acceptance:** пользователь понимает разницу между задачей, уроком и обычной партией до входа на доску.

### CK-110 — History and Review

**Цель:** партии имеют понятное продолжение после окончания.

Сделать:

- список последних партий;
- opponent/mode/result/date;
- reopen review;
- rematch where applicable;
- last active session;
- review не маскируется под active play.

### CK-111 — Responsive, accessibility and game feel

Сделать:

- desktop/tablet/mobile evidence;
- keyboard board regression;
- touch targets;
- reduced-motion variant;
- aria live только для реально важных game events;
- отсутствие horizontal overflow;
- стабилизация layout при появлении game controls;
- визуальное различие player/opponent/turn/result.

### CK-112 — final acceptance gate

Программа принимается только после прохождения полного набора сценариев ниже.

| R3 Classroom + Learning | classroom на общем match UX, понятные задачи | CK-108–109 |
| R4 Product completion | history/review/responsive/final gate | CK-110–112 |

Не переходить к следующему release, если текущий не имеет рабочей вертикали в браузере.

## 11. Обязательные пользовательские acceptance scenarios

### Scenario A — новый пользователь играет с ботом

```text
Игры → Шашки
→ Играть с ботом
→ выбрать уровень/сторону
→ Начать
→ сделать ход
→ получить ход бота
→ закончить партию
→ Реванш
```

### Scenario B — два человека за одним компьютером

```text
Игры → Шашки
→ Играть вдвоём
→ Начать
→ светлые делают ход
→ тёмные делают ход
→ партия корректно завершается
```

### Scenario C — игра с другом

```text
Игры → Шашки
→ Играть с другом
→ Создать
→ скопировать код/ссылку
→ второй пользователь присоединяется
→ оба видят одинаковую позицию
→ чужой ход заблокирован
→ reconnect не теряет партию
```

### Scenario D — задача

```text
Игры → Шашки
→ Задачи и обучение
→ выбрать конкретную тему
→ прочитать цель
→ пример
→ свой ход
→ результат
→ вернуться в список
```

### Scenario E — продолжение

Если активной партии нет — карточки `Продолжить` нет.

Если есть:

```text
Продолжить партию
Следопыт · вы тёмными · ход соперника
```

После нажатия пользователь попадает именно в эту партию.

### Scenario F — classroom

```text
ученик → Шашки → Играть в классе
→ вызвать одноклассника
→ второй принимает
→ партия проходит на общей match surface
→ реакции безопасны
→ педагог видит разрешённые данные
```

## 12. Tests and gates

Каждая задача, которая меняет поведение, добавляет или обновляет тесты.

Минимальные команды после внедрения задач должны включать:

```text
pnpm test:checkers
pnpm typecheck:checkers
pnpm nx run web:typecheck
pnpm nx run web:build
pnpm e2e:checkers
```

После появления friend/realtime должны быть отдельные focused tests, а `gate:checkers-m1` необходимо расширить или заменить новым checkers release gate.

Нельзя считать этап завершённым только по unit tests. Для каждого release нужен Playwright browser proof.

## 13. Non-regression правила для ботов-разработчиков

1. Не переписывать rules engine ради UI.
2. Не копировать правила в React-компоненты.
3. Не создавать второй источник истины позиции.
4. Не менять Chess/Electronics/3D без необходимости для shared infrastructure.
5. Не превращать classroom API в generic public multiplayer простым снятием authorization checks.
6. Не использовать client state как авторитет в online game.
7. Не объявлять realtime готовым, если активная партия всё ещё зависит от polling.
8. Не считать Board V2 готовой без мобильного browser proof.
9. Не скрывать ошибки save/reconnect за optimistic UI.
10. Не удалять существующие тесты, чтобы получить зелёный gate.
11. Не блокировать free play учебной прогрессией.
12. Не возвращать generic «Продолжить» без объекта продолжения.

## 14. Что не входит в первый цикл

До завершения R2 не являются обязательными:

- публичный matchmaking со случайными пользователями;
- рейтинг/ELO;
- турниры;
- глобальный leaderboard;
- spectator mode;
- свободный чат;
- сложные часы и time controls;
- античит уровня соревновательной платформы.

Сначала должна быть безупречно понятная базовая игра.

## 16. Definition of Done всей программы

ASA Шашки считаются приведёнными в нормальное продуктовое состояние, когда одновременно верны все утверждения:

- пользователь сразу понимает, как начать игру;
- с ботом можно играть без прохождения курса;
- можно выбрать любую доступную сложность в free play;
- можно играть вдвоём на одном устройстве;
- можно создать private online game и пригласить друга;
- classroom остаётся безопасным специализированным режимом;
- задачи и обучение находятся отдельно и понятны;
- «Продолжить» всегда указывает конкретную незавершённую активность;
- доска визуально выглядит как игровая доска, а не учебный прототип;
- ходы, взятия и превращения анимируются без нарушения domain state;
- online game сервер-авторитетна;
- reconnect не теряет партию;
- active online game не зависит от постоянного polling;
- результат правильно учитывает сторону игрока;
- desktop/tablet/mobile проходят browser acceptance;
- существующие правила русских шашек и regression tests не деградировали.

После достижения этих условий шашки можно считать не «модулем с возможностью двигать фигуры», а полноценной игровой частью ASA Lab.
