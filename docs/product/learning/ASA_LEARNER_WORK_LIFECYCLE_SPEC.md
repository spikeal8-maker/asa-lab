# ASA Lab — жизненный цикл учебного проекта ученика

**Идентификатор:** LRN-LEARNER-WORK-01  
**Статус:** нормативная детализация E1  
**Дата:** 21 сентября 2026 года  
**Связанная задача:** #371  
**Каноническая ссылка:** `ASA_INTEGRATED_IMPLEMENTATION_SPEC.md §4.2.4`

## 1. Назначение

Проект, который ученик создал из задания преподавателя или практического блока курса, является не обычным личным проектом, а **учебной работой с неизменяемым происхождением**.

Цели:
- ученик не может случайно потерять действующую работу через «Архив» или «Корзину»;
- исходная учебная работа не публикуется в Сообщество;
- сдача, оценка и история проверки не зависят от того, как ученик позднее организует список своих проектов;
- после завершения обучения работа не захламляет активный список;
- после связывания StudentSeat с Account правила не меняются;
- для самостоятельного продолжения можно создать отдельную личную копию, не превращая исходную учебную работу в личную.

## 2. Основной принцип

Учебное происхождение определяется серверной учебной цепочкой, а не внешними признаками проекта.

Нельзя определять учебную работу по:
- `project.scope`;
- `classroomId`;
- названию проекта;
- текущему экрану;
- способу входа StudentSeat/Account;
- наличию слова «курс»;
- тому, опубликован проект или нет.

Каноническая связь:

```text
LearningActivityVersion
        ↓
ActivityRun
        ↓
ActivityParticipation
        ↓
Attempt
        ↓
учебный Project
        ↓
Submission → exact ProjectVersion
```

Для совместимости старых назначений допустима существующая связь `classroom_assignment_work`, но новый продуктовый контракт обязан разрешаться до канонического `ActivityParticipation`.

Проект E1 принадлежит не «курсу вообще», а конкретному учебному вхождению конкретного ученика.

## 3. Неизменяемое происхождение

После первого успешного Start сервер фиксирует учебное происхождение проекта.

Минимально оно позволяет определить:
- learner identity;
- ActivityParticipation;
- ActivityRun;
- exact LearningActivityVersion;
- direct assignment или Course Activity occurrence;
- classroom/course run, если применимо.

Происхождение append-preserved/immutable:
- нельзя «отвязать проект от задания»;
- нельзя заменить его другим классом/учеником;
- связывание StudentSeat → Account не создаёт новое происхождение;
- повторная попытка/доработка использует тот же учебный проект, если это текущий контракт задания;
- личная копия получает новый project id и **не наследует учебную runtime-связь**.

## 4. Два независимых жизненных цикла

Нельзя смешивать:

```text
Project status:
active / archived / trashed

Academic workflow:
in progress / submitted / changes requested / accepted / withdrawn / ...
```

Для исходной учебной работы обычные `archived/trashed` не являются способом закончить обучение.

Над проектом вводится server-derived учебное представление:

```text
learningWork:
- origin
- workflowState
- protectionState
- attentionState
- learnerCollectionState
- allowedActions
```

`learnerCollectionState` относится только к организации списка ученика:

```text
active
learning_archive
```

Перенос в учебный архив не изменяет Attempt/Submission/Result и не переводит сам project в обычную корзину.

## 5. Состояния, которые видит ученик

Минимальный набор:

```text
🎓 Учебная работа · В работе
🎓 Учебная работа · Сдано, ждёт проверки
🎓 Учебная работа · Требуется доработка
🎓 Учебная работа · Выполнено
🎓 Учебная работа · Участие завершено
🎓 Учебная работа · В учебном архиве
```

Статус берётся из канонического Learning workflow. Проектный `status` не подменяет учебный статус.

## 6. Карточка в списке работ

Для Account:

```text
┌────────────────────────────────────┐
│ Электроника                        │
│ Закон Ома                          │
│                                    │
│ 🎓 Учебная работа                  │
│ Основы электроники · Урок 4        │
│ Требуется доработка                │
│                                    │
│ [Продолжить]  [Посмотреть задание] │
└────────────────────────────────────┘
```

Для выполненной:

```text
┌────────────────────────────────────┐
│ Закон Ома                          │
│ 🎓 Учебная работа                  │
│ ✓ Принято преподавателем           │
│ 21 сентября 2026                   │
│                                    │
│ [Посмотреть] [Убрать из активных]  │
└────────────────────────────────────┘
```

Account-проекты получают фильтрацию:

```text
Все | Личные | Учебные
```

Внутри «Учебные»:

```text
Активные | Выполненные | Архив
```

StudentSeat сохраняет отдельный раздел «Мои учебные работы» и использует тот же серверный lifecycle.

## 7. Защита от случайной потери

Исходная учебная работа не должна использовать обычные destructive actions.

Для неё сервер запрещает:
- перенос в обычный `archived`, если это обход учебного lifecycle;
- перенос в `trashed`;
- удаление учебного происхождения;
- публикацию исходной работы в Сообщество;
- замену owner/learner lineage;
- destructive duplicate, который выдаётся за продолжение той же работы.

Это не только скрытые кнопки. Прямой API-запрос обязан получить явный отказ с причиной.

Пример сообщения:

```text
Эта работа связана с учебным заданием.
Её нельзя удалить или отправить в обычную корзину.
```

## 8. Когда работа требует защиты

`protectionState = protected`, если работа ещё участвует в живом учебном процессе, в том числе:

- attempt `in_progress`;
- Submission ждёт проверки/evaluation;
- `changes_requested`;
- разрешена повторная сдача и от ученика ожидается действие;
- существует иная server-derived learner action, требующая сохранить рабочий проект.

Простое закрытие браузера, переход в другой раздел или окончание календарного дня ничего не освобождает.

## 9. Когда работа может уйти из активных

Сервер может вернуть `mayMoveToLearningArchive=true`, когда от ученика больше не требуется текущего действия.

Типовые основания:
- работа принята/завершена;
- participation окончательно withdrawn;
- ActivityRun отменён/архивирован;
- проведение окончательно закрыто и новая сдача невозможна;
- иное терминальное состояние, явно определённое Learning contract.

Сам факт «курс закончился» недостаточен, если остаётся:
- `changes_requested`;
- незавершённая разрешённая попытка;
- иной learner action.

Сданную работу, которая ещё ждёт решения преподавателя, E1 по умолчанию оставляет в активных, чтобы результат не потерялся для ученика из виду.

## 10. Учебный архив — не корзина

Действие ученика:

```text
[Убрать из активных]
```

или:

```text
[В учебный архив]
```

меняет только `learnerCollectionState`.

Оно НЕ:
- удаляет project;
- меняет project owner;
- удаляет draft/version;
- удаляет Submission;
- удаляет AssessmentResultRevision;
- удаляет ResultSelection;
- меняет журнал;
- скрывает работу от преподавателя, имеющего законное право review.

Ученик может открыть учебный архив и вернуть завершённую работу в свой активный список.

## 11. Повторное появление после возврата на доработку

Учебный архив — только пользовательское представление.

Если после архивирования серверный workflow снова требует действия ученика, например преподаватель оформил законный `changes_requested`, то:

```text
learning attention overrides archive preference
```

Работа снова появляется:
- в «Моём обучении»;
- среди активных учебных работ;
- с состоянием «Требуется доработка».

Для этого не нужно создавать новый проект и нельзя терять прежнюю историю.

## 12. Выход из курса или прекращение участия

Выход/withdrawal не удаляет учебный проект.

После окончательного withdrawal:
- новые учебные действия запрещены согласно Learning contract;
- проект остаётся доступен ученику для просмотра;
- его можно убрать в учебный архив;
- Submission/Result/history остаются;
- исходный проект всё равно остаётся учебным по происхождению.

Если участие восстановлено допустимым новым процессом, система не должна молча присоединять старый проект к новой Participation без явного canonical правила.

## 13. Завершение курса

CourseRun/курс и Project имеют разные жизненные циклы.

После завершения курса:
- активные требования конкретных Activity occurrences разрешаются по их canonical state;
- выполненные работы можно убирать в учебный архив;
- незаконченные/возвращённые работы следуют фактической возможности продолжения;
- оценки и submissions сохраняются независимо.

Нельзя массово переводить все проекты курса в обычную корзину только потому, что CourseRun закрыт.

## 14. Публикация в Сообщество

Исходная учебная работа:

```text
mayPublishOriginal = false
```

для StudentSeat и для связанного Account одинаково.

Причины:
- сохранение границы между учебной и личной работой;
- защита контекста класса/задания;
- невозможность случайно опубликовать работу ребёнка;
- точная история того, что было сдано преподавателю.

Нельзя реализовать это только проверкой `viewer.isSeat`: после Seat→Account linking защита должна сохраниться по provenance проекта.

## 15. Личная копия

После терминального состояния сервер MAY разрешить:

```text
[Создать личную копию]
```

Требования к копии:
- новый project id;
- обычное personal происхождение;
- нет ActivityParticipation/Attempt/Submission linkage;
- действия над копией никак не меняют учебный оригинал;
- публикация оценивается уже по обычным правилам личного проекта;
- класс, ученик, assignment id и другие private learning identifiers не переносятся в public metadata.

Если права на starter/reference content не разрешают personal copy, сервер возвращает `mayCreatePersonalCopy=false` и понятную причину. Клиент не предполагает право копирования сам.

## 16. Что именно сохраняется для преподавателя

Учитель проверяет Submission, а не «живой проект ученика».

Submission закрепляет exact project version/evidence. Поэтому:
- последующее редактирование черновика не меняет прошлую сдачу;
- перенос работы учеником в учебный архив не меняет review;
- личная копия не меняет review;
- будущая очистка пользовательского представления не меняет историю.

Преподавательский preview из LRN-WORK-SHELL-01 всегда использует exact submitted evidence.

## 17. Серверные разрешения действий

API проекта должен возвращать server-derived возможности, достаточные UI:

```text
learningOrigin: null | {...}
learningWorkflowState
learningCollectionState
allowedActions:
  open
  continue
  submit
  moveToLearningArchive
  restoreFromLearningArchive
  createPersonalCopy
  publishOriginal
  changeGenericProjectStatus
```

Названия полей implementation-specific, но решение не может вычисляться только на клиенте.

Минимально сервер обязан guard:
- generic project archive/trash;
- gallery publish;
- personal-copy operation;
- изменение learning archive state.

## 18. Хранение происхождения

Предпочтительная E1-модель — одна явная связь project ↔ canonical ActivityParticipation.

Она должна быть:
- tenant/school coherent;
- immutable;
- inspectable;
- совместима с direct и Course Activity occurrences;
- не зависеть от current assignment title;
- не выводиться ретроспективно из догадок по старым данным.

Для legacy rows допускается compatibility projection с честным `origin=legacy/unknown`, а не fabricated canonical lineage.

## 19. Физическое удаление

Hard delete исходной учебной работы и её исторических evidence **не входит в E1**.

Если в будущем появится право на окончательное удаление пользовательского Project payload, оно требует отдельной retention/privacy policy и обязано доказать, что:
- обязательная академическая история остаётся законно сохранённой либо удаляется по отдельному разрешённому процессу;
- FK/audit/evidence не становятся повреждёнными;
- преподаватель не видит «работа исчезла» вместо точной исторической сдачи.

В E1 пользовательское «убрать» означает учебный архив, а не физическое удаление.

## 20. Матрица действий

| Состояние | Продолжить | Сдать | Учебный архив | Обычная корзина | Опубликовать оригинал | Личная копия |
|---|---:|---:|---:|---:|---:|---:|
| В работе | да | по правилам | нет | нет | нет | нет |
| Сдано / ждёт проверки | просмотр | нет | нет | нет | нет | нет |
| Требуется доработка | да | по правилам | нет | нет | нет | нет |
| Принято / выполнено | просмотр | нет | да | нет | нет | по server policy |
| Participation withdrawn | просмотр | нет | да | нет | нет | по server policy |
| Run отменён/архивирован | просмотр | нет | да | нет | нет | по server policy |
| Учебный архив | просмотр | нет | вернуть | нет | нет | по server policy |

## 21. Приёмка

Обязательные сценарии:

1. Direct assignment → Start → project помечен как учебный.
2. Course Activity occurrence → Start → exact occurrence provenance.
3. Активную работу нельзя отправить в обычный архив/корзину через API.
4. Активную работу нельзя опубликовать в Сообщество через Account.
5. Seat→Account linking не снимает protection.
6. Submitted waiting review остаётся видимой и protected.
7. Changes requested возвращает возможность Continue/Resubmit.
8. Accepted позволяет «В учебный архив».
9. Учебный архив не меняет exact Submission/Result.
10. Returned-after-archive работа снова появляется среди активных.
11. Withdrawal позволяет учебный архив, но не стирает history.
12. Personal copy имеет новый id и не имеет learning runtime linkage.
13. Изменение/удаление personal copy не меняет оригинальную сдачу.
14. Teacher exact review работает после learner archive.
15. Account список различает personal/learning без client-side guessing.

## 23. Архитектурные уточнения после критического анализа

Этот документ реализуется совместно с ASA_LEARNING_WORK_ARCHITECTURE_PLAN.md.

### 23.1 Проект не создаётся отдельно от учебного происхождения

Новый продуктовый Start не выполняет две независимые клиентские mutation createProject → startAssignment.

Project, Learning Project Origin и Attempt создаются/reuse одной идемпотентной server operation. Частичный сбой не должен оставлять обычный personal project, который на самом деле был началом задания.

### 23.2 Защита охватывает обычное дублирование

Generic Duplicate Project не является обходом запрета публикации учебного оригинала.

Для protected learning work:
- обычное duplicate либо запрещено, либо перенаправляет пользователя на отдельное действие «Создать личную копию»;
- eligibility личной копии возвращает сервер;
- active/submitted/changes_requested original по умолчанию не копируется в personal space;
- terminal accepted/withdrawn может разрешить personal copy по policy.

### 23.3 Принятая исходная работа read-only

После accepted/completed:
- исходный learning project доступен для просмотра;
- generic edit запрещён;
- learning archive разрешается по policy;
- дальнейшее экспериментирование выполняется в personal copy.

Если canonical workflow позже становится changes_requested, исходная работа снова получает edit/resubmit actions.

### 23.4 Один policy resolver

Allowed actions для project lifecycle вычисляются одной Learning Work Policy и используются:
- Projects status mutation;
- duplicate;
- gallery publish;
- learning archive;
- personal copy;
- editor write authorization.

Запрещено поддерживать пять расходящихся списков условий.

### 23.5 Список проектов читает server-derived provenance

Account project list не должен определять badge «Учебная работа» по classroomId, title или client-side lookup assignments.

Project list API/projection получает server-derived learning origin/state/allowed actions либо присоединяет canonical Learning Work Context проекцию на сервере.
