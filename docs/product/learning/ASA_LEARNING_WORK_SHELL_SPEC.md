# ASA Lab — универсальная оболочка учебной работы

**Идентификатор:** LRN-WORK-SHELL-01
**Статус:** нормативная детализация E1
**Дата:** 21 сентября 2026 года
**Каноническая ссылка:** `ASA_INTEGRATED_IMPLEMENTATION_SPEC.md §4.2.2–4.2.5`  
**Архитектурный контракт:** `ASA_LEARNING_WORK_ARCHITECTURE_PLAN.md`

## 1. Назначение

Ученик не должен терять задание после перехода из курса/назначения в предметную лабораторию. Преподаватель не должен открывать полноэкранный предметный редактор для последовательной проверки 20–30 работ.

Решение состоит из двух общих поверхностей:

1. **Оболочка задания ученика** — поверх любого subject editor.
2. **Рабочее место проверки преподавателя** — отдельный review workspace с очередью учеников.

Обе поверхности являются частью Learning, а не частью Electronics/3D/Scratch/Chess/Checkers.

## 2. Архитектурный принцип

```text
Учебное назначение / Course Activity occurrence
                    │
                    ▼
         Общая учебная оболочка
         ├─ exact assignment context
         ├─ карточка задания
         ├─ статус / сдача
         └─ возврат в обучение
                    │
                    ▼
        Предметный редактор проекта
        ├─ Electronics
        ├─ 3D
        ├─ Blocks / Scratch
        ├─ Chess / Checkers
        └─ будущий module
```

Предметный редактор не:
- читает CourseRun;
- решает, какое задание назначено;
- хранит копию текста задания;
- создаёт собственный Submission/Assessment workflow;
- определяет, кому разрешено видеть работу.

Новая лаборатория подключается через общий host/adapter. Если runtime технически внешний или iframe-подобный, адаптер обязан сохранить тот же учебный контракт.

## 3. Источник задания

Оболочка разрешает контекст по `projectId`.

Поддерживаются:
- direct assignment;
- lesson-level legacy assignment;
- конкретный Course Activity block occurrence.

Для Course Activity связь определяется по exact occurrence, а не только по `LearningActivityVersionId`.

Содержание задания читается из закреплённой опубликованной версии. Текущий авторский draft не может задним числом менять уже выданное задание.

## 4. Содержимое задания

Одна модель чтения используется:
- в курсе;
- в карточке поверх лаборатории;
- у преподавателя рядом с работой;
- в предпросмотре автора.

Минимум:
- название;
- цель;
- инструкция;
- образец/схема;
- срок;
- состояние работы.

Целевая последовательность безопасных блоков:

```text
heading
paragraph
list
callout
image
video
file
link
```

До перехода на блочную модель существующие поля `goal / brief / sampleImage` проецируются в этот reader. Второй параллельный формат задания запрещён.

### Медиа

Изображение:
- видно внутри задания;
- открывается крупно;
- может быть закреплено как отдельный reference-window.

Видео:
- воспроизводится внутри карточки или отдельного безопасного viewer;
- не запускается автоматически;
- сохраняет controls и доступный fallback.

Файл:
- показывает имя/тип;
- открывается/скачивается штатным разрешённым способом;
- отсутствие файла даёт явную ошибку.

## 5. Ученик — desktop

### 5.1 Первое открытие

Новое задание впервые открывается развёрнутым в безопасном размере. Это гарантирует, что ученик хотя бы один раз увидит условия работы.

Свёрнутое состояние другого задания не наследуется.

### 5.2 Свёрнутое состояние

```text
[ ▣ Задание ]
```

Компактная кнопка:
- плавающая;
- имеет высокий, но не максимальный слой;
- не блокирует взаимодействие с лабораторией вокруг себя;
- может менять допустимый край/позицию без выхода за viewport.

### 5.3 Развёрнутая карточка

```text
┌──────────────────────── Задание ────────────────────────┐
│ ⠿  Закон Ома                                    [ — ]  │
├─────────────────────────────────────────────────────────┤
│ Цель                                                    │
│ Исследовать зависимость тока от сопротивления.          │
│                                                         │
│ 1. Добавьте источник                                    │
│ 2. Добавьте резистор         ┌─────────────────────┐     │
│ 3. Соедините цепь            │  схема / образец    │     │
│                              └─────────────────────┘     │
│                         [увеличить] [закрепить]          │
│                                                         │
│ Статус: В работе                         [Сдать работу]  │
└─────────────────────────────────────────────────────────┘
```

### 5.3.1 Читаемость заголовка

В раскрытом состоянии полное смысловое название задания должно быть доступно визуально. Допустимый ellipsis в компактной строке не может быть единственным местом, где ученик узнаёт название.

Если header не помещает одновременно title/status/reset/submit, layout перестраивается: перенос строки, отдельная строка действий или полный title в body. Нельзя жертвовать смыслом задания ради плотности toolbar.

### 5.4 Перемещение

Карточка перемещается только за явный drag-handle.

Требования:
- pointer/mouse/touch на совместимом устройстве;
- карточка не уходит за viewport;
- после resize/rotate viewport координаты корректируются;
- drag не запускается при нажатии кнопок/ссылок/медиа;
- Esc не закрывает лабораторию, если фокус в карточке.

### 5.5 Размер

На desktop карточка меняет ширину/высоту.

Ориентиры:
- минимальная ширина: 320 px;
- нормальная начальная: около 420–520 px;
- максимальная: не более 70% ширины viewport;
- минимальная высота должна оставлять читаемое содержимое;
- максимальная: не более 80% доступной высоты.

При уменьшении контент получает внутренний scroll; текст не сжимается до микроскопического размера.

### 5.6 Закрепление

Целевые режимы:
- свободное окно;
- закреплено слева;
- закреплено справа;
- свёрнуто.

Закрепление не перестраивает предметный редактор. Это overlay, а не новая колонка внутри конкретной лаборатории.

### 5.7 Сохранение представления

Разрешено локально хранить:
- положение;
- размер;
- режим закрепления;
- последний viewport-class.

Не хранить в этих настройках:
- текст задания;
- оценку;
- статус Submission;
- права.

Open/seen state относится к конкретному назначению/работе.

## 6. Отдельное окно схемы/образца

Изображение может отделяться от полной карточки:

```text
┌──── Схема ────┐
│                │
│   reference    │
│                │
│        [×]     │
└────────────────┘
```

Reference-window:
- перемещается;
- меняет размер;
- остаётся поверх editor;
- не дублирует submit/status controls;
- закрывается обратно в карточку задания.

Это особенно важно для Electronics, 3D и будущих визуальных лабораторий.

## 7. Телефон

Desktop-card не уменьшается механически.

### 7.1 Свёрнуто

```text
┌──────────────────────┐
│                      │
│      лаборатория     │
│                      │
│                 [▣]  │
└──────────────────────┘
```

### 7.2 Открыто

Нижняя выдвижная панель:

```text
┌──────────────────────┐
│      лаборатория     │
│                      │
├──────────────────────┤
│ ───                  │
│ Задание              │
│ Цель                 │
│ Инструкция           │
│ Схема / видео / файл │
│                      │
│        [Сдать работу]│
└──────────────────────┘
```

Состояния:
- collapsed;
- примерно половина экрана;
- почти полный экран.

Требования:
- собственный вертикальный scroll;
- safe-area;
- лаборатория сохраняет своё состояние под панелью;
- resize-handles desktop отсутствуют;
- положение desktop не переносится на mobile;
- при клавиатуре/вводе панель не должна оставлять недоступные controls.

Контрольные ширины: 320 и 390.

## 8. Доступность

- кнопка «Задание» имеет понятный accessible name;
- состояние раскрытия — `aria-expanded`;
- drag не единственный способ вернуть окно: есть «Сбросить положение»;
- все действия доступны с клавиатуры;
- resize не должен быть единственным способом получить читаемую карточку;
- focus не уходит под закрытую карточку;
- reduced motion соблюдается;
- статус не кодируется только цветом.

## 9. Преподаватель — выбор практики

В CourseRun преподаватель сначала выбирает конкретную практику:

```text
Урок 3

Практика: Закон Ома
18 учеников · 7 ждут проверки      [Открыть проверку]

Практика: Последовательная цепь
18 учеников · 3 ждут проверки      [Открыть проверку]

Практика: 3D-модель
18 учеников · 11 ждут проверки     [Открыть проверку]
```

Lesson-level legacy assignment остаётся совместимым.

## 10. Поточная проверка — desktop

```text
┌────────────────┬──────────────────────────────────┬──────────────────────┐
│ Ученики        │ Работа ученика                   │ Проверка             │
│                │                                  │                      │
│ ! Катя         │                                  │ Закон Ома            │
│ ✓ Миша         │       exact submitted            │                      │
│ ● Петя         │       snapshot / preview         │ Оценка [ 8 / 10 ]    │
│ ○ Саша         │                                  │ Комментарий          │
│ ↩ Лена         │                                  │ [.................]  │
│                │ [Открыть полностью]              │                      │
│                │                                  │ [Вернуть] [Принять] │
└────────────────┴──────────────────────────────────┴──────────────────────┘
                 [← предыдущий]       [следующий →]
```

Рекомендуемые desktop-размеры:
- список: 240–300 px;
- review controls: 320–380 px;
- preview: всё оставшееся пространство.

## 11. Список учеников

Состояния:

```text
○ не начал
● в работе
! ждёт проверки
↩ возвращено
✓ проверено / принято
```

Фильтры:
- Все;
- Ждут проверки;
- В работе;
- Возвращены;
- Проверены.

После успешного решения интерфейс SHOULD автоматически открыть следующую работу в текущем фильтре. Если следующей нет — показать завершённую очередь, а не прыгнуть в другой класс/задание.

## 12. Preview работы

По умолчанию преподаватель видит облегчённый exact preview.

Приоритет:
1. snapshot exact submitted revision;
2. module-specific read-only preview;
3. безопасное summary, если preview невозможен.

Нельзя показывать latest personal draft вместо Submission.

Полный editor открывается только по явному действию:

```text
[Открыть работу полностью]
```

Возврат должен привести обратно к тому же ученику и той же очереди проверки.

## 13. Проверка и оценивание

Справа показываются:
- exact задание;
- состояние сдачи;
- оценка, если схема оценивания балльная;
- комментарий;
- «Вернуть на доработку»;
- «Принять».

Для completion/ungraded не изобретать баллы.

При correction/re-review сохраняется история решений; stale reviewer не перезаписывает более новую редакцию молча.

## 14. Планшет и телефон преподавателя

На планшете:
- список учеников может быть drawer;
- review controls могут быть drawer;
- work preview остаётся основной областью.

На телефоне:
- шаг 1 «Ученики»;
- шаг 2 «Работа»;
- шаг 3 «Проверка».

Выбранный ученик и фильтр сохраняются между шагами.

Трёхколоночный desktop-layout не ужимается до 320 px.

## 15. Подключение новых лабораторий

Минимальный контракт нового module:

- проект открывается через общий host либо адаптер;
- host знает `projectId` и resolved `moduleKey`;
- учебная оболочка может разрешить assignment context;
- module предоставляет snapshot или preview capability, если это возможно;
- module не реализует собственный AssignmentBrief/submit UI.

Приёмка новой лаборатории обязательно включает:
- direct assignment;
- Course Activity occurrence;
- открыть задание поверх editor;
- сохранить работу;
- вернуться и продолжить;
- сдать;
- teacher preview/review.

## 16. Порядок реализации после архитектурного пересмотра

### A0 — фундамент общей оболочки

Этот срез не зависит от предметного содержания задания и может быть завершён отдельно.

Обязательно:
- platform layer выше fullscreen/iframe/canvas предметной среды;
- desktop pointer capture для drag/resize;
- max width ≤ 70% viewport;
- max height ≤ 80% usable viewport;
- reset без drag;
- 1440/390/320;
- browser evidence минимум Electronics, 3D и Blocks/Scratch;
- предметные редакторы не получают Learning UI.

### A1 — единый Learning Work Context

До rich UI карточка переводится на один server resolver по projectId.

Обязательно:
- direct assignment;
- legacy lesson assignment;
- Course Activity occurrence;
- exact learningActivityVersionId;
- courseBlockId для block occurrence;
- canonical workflow;
- server-derived allowed actions;
- состояния resolving / not_learning / ready / denied / unavailable.

После A1 AssignmentBrief не перебирает списки назначений/курсов.

### A2 — полный immutable task snapshot

До video/file/pinned-image UI опубликованная версия должна реально замораживать:
- title;
- goal;
- упорядоченное learner-facing content;
- immutable media refs;
- starter project version;
- digest.

Текущий mutable sample/media автора не может подмешиваться в старую published version.

### A3 — learning capabilities модулей

Module registry сообщает, пригоден ли модуль для:
- назначения;
- редактируемого учебного evidence;
- сдачи ProjectVersion;
- snapshot/interactive/summary preview.

Course Builder и Learning используют capabilities, не конкретные имена модулей.

### A4 — атомарный старт и immutable origin

Новый learner Start является одной idempotent server operation:
- разрешить Participation;
- создать/reuse Project;
- зафиксировать Project↔Participation origin;
- создать/reuse Attempt;
- вернуть projectId/context.

Клиентская пара createProject → startAssignment не остаётся конечной архитектурой.

### A5 — защита и список учебных работ

- единая server policy для archive/trash/duplicate/publish/edit/copy;
- учебные badges/filters;
- accepted original read-only;
- отдельный learning archive;
- changes_requested автоматически возвращает работу в active attention.

### A6 — rich task shell

Только после A2:
- image zoom;
- pinned reference;
- video;
- file/link;
- desktop/mobile refinement.

### A7 — personal copy

- отдельная server command;
- новый personal project id;
- нет Learning runtime linkage;
- нет private classroom/learner provenance в public metadata.

### A8 — поточная проверка преподавателем

- activity occurrence queue;
- exact submitted evidence;
- filter/order;
- previous/next;
- assessment;
- optional full editor.

## 17. Критерии приёмки

Оболочка ученика считается готовой, когда:

1. задание остаётся доступно после открытия лаборатории;
2. subject editor не содержит отдельной копии Assignment UI;
3. карточка можно свернуть и вернуть;
4. desktop-положение не уходит за экран;
5. mobile не является уменьшенной desktop-карточкой;
6. exact assignment version сохраняется после изменения авторского draft;
7. Course Activity block показывает своё задание, а не соседнюю activity того же lesson;
8. изображение читаемо в увеличении;
9. сохранение/сдача не зависит от того, открыта карточка или свернута;
10. новая лаборатория подключается без копирования Learning UI.

Review workspace считается готовым, когда:

1. преподаватель видит очередь именно выбранной практики;
2. exact submission не подменяется latest draft;
3. можно принять/вернуть/оценить без полноэкранного editor;
4. следующий ученик открывается без возврата в список;
5. состояние очереди обновляется после решения;
6. full editor остаётся доступным как дополнительное действие;
7. narrow UI сохраняет все действия без трёх нечитаемых колонок.


## 18. Жизненный цикл учебного проекта

Оболочка задания работает не с абстрактным personal project, а с учебной работой, происхождение которой защищено отдельным нормативным контрактом:

[ASA_LEARNER_WORK_LIFECYCLE_SPEC.md](ASA_LEARNER_WORK_LIFECYCLE_SPEC.md).

Для этой оболочки обязательны следующие правила:

- открытый из задания проект сохраняет canonical Learning provenance;
- сворачивание/перемещение карточки никак не меняет academic lifecycle;
- submit закрепляет exact ProjectVersion/evidence;
- исходная учебная работа не публикуется в Сообщество;
- generic archive/trash не используются для активной учебной работы;
- после терминального состояния «Убрать из активных» означает учебный архив, а не разрушение Project/Submission;
- если преподаватель законно возвращает работу на доработку, learner attention снова выводит её в активные;
- личная копия, если разрешена, имеет новый project id и не наследует Participation/Attempt/Submission linkage.

В `ModuleEditorHost` и `AssignmentBrief` запрещено вычислять эти разрешения локально по маршруту, роли или типу модуля. UI использует server-derived lifecycle/allowed actions.

Для V1 обязательны exact-HEAD screenshots:
- Electronics expanded desktop;
- Electronics moved desktop;
- 3D desktop;
- Blocks/Scratch overlay desktop;
- mobile 390;
- mobile 320.

A0 integration test не доказывает штатное authoring/assignability конкретного нового module, если activity fixture подготовлен напрямую. Такая поддержка доказывается отдельно в V5.
