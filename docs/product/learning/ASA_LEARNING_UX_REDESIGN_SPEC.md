# ASA Lab — UX-пересборка Learning после ручного staging-review

**Issue:** #385
**Статус:** нормативный UX-план
**Основание:** ручная проверка test school №374 на Ali_Robs; дополнено отзывом владельца 2026-10-07 о прохождении урока и загрузке материалов.

**Читать сначала:** §§35–39 — уточнённый продуктовый контракт, проверяемые сценарии и исследование официальных продуктов. Это требования, а не заявление о реализации. Текущая задача, checkpoint и разрешения остаются только в `docs/execution/current.yaml` и AGENTS.md. Уточнённые ниже правила заменяют прежнюю обязательность боковых настроек и приёмки каждого изолированного списка; академические, security и versioning-инварианты не отменяются.

## 1. Что признано проблемой

Наличие работающих частей Learning не доказывает готовность целого курса. Выявленная проблема UI — необходимость понимать внутренние сущности ASA Lab вместо понятного учебного действия.

Нужно перестраивать видимые сценарии, а не косметически украшать существующие формы.

Порядок работ:

1. UX0 — ученическая бирка и панель задания;
2. UX1 — неизменяемое rich-content задание с изображениями/схемами;
3. UX2 — новый редактор задания преподавателя;
4. UX3 — новый визуальный Course Builder;
5. UX4 — Teacher Home / Journal / Review.

Каждый этап даёт проверяемый видимый результат. Контролёр явно порученной программы продолжает согласованные зависимые этапы по AGENTS.md; промежуточный снимок не завершает программу. Точки визуального согласования и итоговая приёмка — в §§38–39.

## 2. UX0 — минимальная бирка ученика

Collapsed anchor по умолчанию:

```text
[ Задание  ˄ ]
```

Не показывать в anchor:
- длинный title;
- тип назначения;
- слова «индивидуально»;
- срок;
- save state;
- текст «результат ещё не опубликован».

Если canonicalState.selectedResult уже опубликован и доступен learner projection, допустим короткий результат:

```text
[ Задание · 8/10  ˄ ]
[ Задание · ✓     ˄ ]
```

Не вычислять оценку на клиенте. Использовать только canonical selectedResult.

## 3. UX0 — открытая panel

Header:

```text
Название задания                         [↗] [⋯]
Короткий статус
```

Header не содержит Submit и Reset.

Body:
- instruction/brief;
- компактный deadline, если он есть;
- teacher feedback, если canonical contract его уже предоставляет;
- без технических revision/debug labels.

Footer зависит от workflow.

### in_progress

```text
Сохранено                    [Отправить на проверку]
```

### submitted / waiting_review

```text
На проверке
```

UX0 НЕ добавляет добровольную кнопку «Доработать», если нет безопасного server command для новой canonical submission.

### changes_requested

```text
Нужна доработка                     [Продолжить]
```

После возобновления:

```text
Сохранено                    [Отправить повторно]
```

### completed + published selected result

Graded:

```text
Выполнено                              8/10
```

Completion:

```text
Выполнено                           ✓ Принято
```

Если selectedResult отсутствует, результат не выдумывать.

## 4. Что UX0 не делает

- не подключает Course Activity через A1;
- не меняет Submission/Attempt lifecycle;
- не добавляет voluntary rework до оценки;
- не добавляет изображения;
- не меняет teacher authoring;
- не меняет Course Builder;
- не меняет backend или migrations без отдельного доказанного blocker.

## 5. UX1 — изображения и схема

Изображение/схема — first-class task content.

Историческая причина UX1 — недостаток rich-content и точных media refs. Не считать это описанием текущего HEAD: фактические возможности проверяются по коду. Целевой контракт требует server-side immutable task snapshot/media refs, а не только CSS; пользовательская загрузка и подготовка медиа уточнены в §37.

Целевой published snapshot:

```text
title
goal?
blocks[]
mediaRefs[]
contentDigest
```

Минимальные blocks:
- paragraph;
- list;
- callout;
- image;
- video;
- file;
- link.

Image в лаборатории:
- адаптируется к panel;
- увеличивается;
- может открываться как отдельный reference;
- reference можно расположить рядом с Electronics/3D;
- mobile использует sheet/lightbox.

## 6. UX2 — преподаватель создаёт «Задание», а не внутренний material root

Основная IA преподавателя:

```text
Задания
Курсы
Библиотека
```

### 6.1 UX2A — единый вход учителя в задания

Видимый teacher entry «Курсы и задания» ведёт в `#/challenges`. По умолчанию открывается `Задания` — существующий canonical Learning authoring.

Нормативная граница:
- **новые задания** создаются только через canonical Learning authoring;
- `teacher_assignments` — только legacy/history/compatibility;
- «Ранее созданные задания» не является основной вкладкой и не конкурирует с canonical authoring;
- новые продуктовые функции не добавляются в legacy `AssignmentEditorDialog`;
- новые задания не создаются через legacy `AssignmentEditorDialog`;
- существующие legacy-задания, их выдачи, работы учеников и история остаются доступными для совместимости и не удаляются этим UX-срезом.

Из класса:
- «Назначить задание» сохраняет canonical flow выбора опубликованного Learning Activity, аудитории и срока;
- «Создать задание» переводит в `#/challenges` → `Задания` и не открывает legacy editor.

Новый assignment editor строится вокруг блока «Что увидит ученик».

Основные действия:
- название;
- текст;
- изображение/схема;
- видео;
- файл;
- ссылка;
- среда выполнения;
- способ проверки;
- сроки;
- preview;
- publish;
- assign.

Rare settings скрываются progressive disclosure.

## 7. UX3 — Course Builder

Course Builder должен выглядеть как редактирование готового урока.

Левая колонка — компактное содержание курса.

Центр — page-like lesson canvas.

Одна кнопка:

```text
+ Добавить содержимое
```

открывает menu:
- текст;
- заголовок;
- изображение;
- видео;
- файл;
- формула;
- таблица;
- врезка;
- задание.

Задание выбирается через picker/card, а не через технический select published activity.

Duplicate/hide/move остаются, но уходят в contextual menu конкретного блока.

## 11. Owner UX decision 2026-10-04 — modern editor-first system

После owner review свежего Learning preview зафиксировано:

- функциональная глубина backend не считается видимым product result сама по себе;
- teacher authoring не должен выглядеть как длинная административная форма;
- Google Classroom / legacy LMS-паттерн не является визуальным целевым референсом;
- постоянная трёхколоночная компоновка «список + форма + preview» отклонена;
- крупные hero-блоки, нумерация 01/02/03/04 и карточки внутри карточек отклонены;
- постоянный preview, занимающий треть editor viewport, отклонён;
- новый Learning UX должен быть editor-first, content-first, progressive-disclosure и визуально современным;
- внутренняя сложность Learning (Attempt, Origin, Submission, immutable version, policy resolver) остаётся под капотом и не переносится в основной UI.

### 11.1 Отклонённый эксперимент

Draft PR #495 «Learning UX: visible teacher assignment editor» является **отклонённым визуальным экспериментом** и не является базой для дальнейшего UX.

Причины отклонения:
- слишком много постоянных областей одновременно;
- перегруженная композиция;
- большая декоративная шапка не помогает выполнить задачу;
- постоянные library и preview уменьшают рабочую область;
- настройки и основной контент визуально конкурируют;
- интерфейс требует изучения вместо естественного сценария;
- экран выглядит как dashboard/admin UI, а не как современный content editor.

Новые implementation slices не должны продолжать эту композицию.

## 12. Главный UX-инвариант

Learning разделяет три разные пользовательские задачи:

~~~text
Создать содержание
        ↓
Назначить людям
        ↓
Проверить результат
~~~

Они **не объединяются в один экран**.

Основное правило:

> Один экран = одна основная пользовательская задача.

Следствия:
- список не является частью постоянного editor layout;
- settings не являются постоянной колонкой;
- preview не является постоянной колонкой;
- assignment не смешивается с authoring;
- review не смешивается с authoring;
- список учеников не показывается в editor задания;
- служебные сущности backend не становятся видимыми controls.

## 13. Информационная архитектура преподавателя

Основной раздел:

~~~text
Курсы и задания
├─ Задания
├─ Курсы
└─ Библиотека
~~~

Проверка работ открывается контекстно:
- из Teacher Home;
- из конкретного задания;
- из класса;
- из курса;
- из learner profile.

Не добавлять вкладку «Проверка» только ради дублирования уже существующего контекста.

## 14. Задания — основной список

Экран отвечает только на вопрос:

> Какие задания у меня есть и что требует внимания?

Целевая структура:

~~~text
Задания                                      [+ Новое задание]

[ Поиск ]                    [Статус ▾] [Среда ▾] [Сортировка ▾]

Автоматический ночник
Электроника
Опубликовано · назначено 3 классам
7 ждут проверки
                                               [Открыть] [⋯]

Светофор
Электроника
Черновик · изменено сегодня
                                               [Открыть] [⋯]
~~~

Обязательная информация строки: название, понятный статус и действие открытия. Предмет/среда конкретной практики, аудитория, ожидающие проверки работы и дата показываются только при наличии корректной авторизованной проекции. Отсутствие этих дополнительных полей не разрешает выдумывать значения и не блокирует весь путь урока. У курса может быть несколько сред; не сворачивать их в одну.

Не показывать ids, version UUID, Attempt, Origin, policy JSON, technical revision и compatibility labels.

Контекстное меню ⋯ содержит только реально поддерживаемые команды: редактирование, копия, история или архивирование по доступным правам. Если вторичных команд нет, пустое меню не рисуется.

Danger action отделяется визуально. Назначение не прячется в ⋯, если это основное следующее действие.

Editor — отдельный экран и выглядит как редактирование самого задания, а не как заполнение карточки базы данных.

~~~text
← Задания

Автоматический ночник                 Сохранено
                         [Предпросмотр] [Назначить →]


Автоматический ночник

Добавьте цель задания…


Соберите схему автоматического ночника.
Светодиод должен включаться при уменьшении освещения.


┌──────────────────────────────────────────────┐
│                изображение                   │
└──────────────────────────────────────────────┘

📄 Справочник по фоторезистору.pdf

＋ Добавить блок


───────────────────────────────────────────────
~~~

Доминирует content canvas. Inline редактируются:
- название;
- goal;
- instruction;
- content blocks.

Не открывать modal для обычного изменения текста.

Header содержит Back, достоверный saved/unsaved state, Preview и основное действие Assign. Явное сохранение сохраняется, пока надёжное автосохранение не реализовано и не проверено. Контентные поля растут по тексту, а не имеют декоративную минимальную высоту; детали §36.

Publish может быть отдельной action либо частью Assign confirmation. Не показывать 4–6 равнозначных CTA.

Внизу допустима компактная meta strip:
- module;
- attempts;
- result mode;
- deadline summary;
- кнопка «Настройки».

## 16. Добавление content block

Одна команда:

~~~text
+ Добавить блок
~~~

открывает небольшой contextual popover рядом с местом вставки:

~~~text
Aa  Текст
H   Заголовок
☷   Список
▣   Примечание

🖼  Изображение
▶   Видео
📄  Файл
🔗  Ссылка

⚡  Проект / лаборатория
~~~

После выбора block вставляется прямо в document flow.

На hover/focus:

~~~text
⠿                                               ⋯
~~~

⠿ — drag/reorder desktop.

Меню ⋯:
- Duplicate;
- Move up;
- Move down;
- Hide, если поддерживается contract;
- Delete.

На mobile drag не обязателен; move up/down обязателен.

## 17. Компактные параметры практики

Параметры не занимают постоянную колонку. По отзыву владельца 2026-10-07 обязательный right drawer отменён: на desktop используется компактное отдельное диалоговое окно, на mobile — полноэкранное адаптивное представление.

Среда выбирается для конкретной проектной практики («Где выполнять практику»), не для курса и не для обычного материала. У курса/урока могут быть несколько практик разных сред. Используются существующие activity/version/occurrence-модели; новая многопроектная сущность не вводится только ради смешанного курса.

В параметрах практики: оценивание, попытки и действующие правила выполнения. Срок и получатели — в назначении; публикация и история версий — отдельные вторичные команды, не часть параметров. Редкие политики раскрываются в «Дополнительных настройках» без raw policy names. Закрытие/отмена имеют явную семантику, не теряют ввод и не публикуют данные. Требования к focus, Escape, возврату фокуса и dirty-navigation сохраняются.

Это выбор ASA по обратной связи владельца, а не утверждение, что конкуренты используют такое же окно.

## 18. Preview

Preview открывается **по требованию**, а не занимает постоянную колонку.

Desktop:
- right sheet / large drawer;
- editor остаётся позади;
- закрытие возвращает пользователя в то же место.

Mobile:
- full-screen sheet.

Preview показывает тот же content model, который увидит learner.

~~~text
Как увидит ученик                             ×

Автоматический ночник

Соберите схему...

[изображение]

📄 Справочник.pdf

Электроника · 2 попытки

                         [Начать работу]
~~~

Если draft не сохранён:
- local representation может называться «Несохранённый предпросмотр»;
- exact preview явно требует save;
- local preview нельзя выдавать за exact published version.

## 21. Visual Course Builder

1. compact outline слева;
2. lesson/page canvas по центру.

Третьей постоянной панели нет.

~~~text

┌───────────────┬────────────────────────────────────────────┐
~~~

## 30. Anti-absurd UX invariants

Эти правила нормативны для Learning UX:

1. Один экран — одна основная задача.
2. На экране одна primary CTA; вторая допустима только как очевидная парная операция.
3. List, editor, settings и preview не показываются одновременно как равноправные постоянные панели.
4. Rare settings скрыты progressive disclosure.
5. Backend concepts не показываются пользователю без продуктового смысла.
6. Не делать card-inside-card-inside-card.
7. Не использовать modal для обычного редактирования.
8. Не использовать отдельную страницу для маленького contextual action.
9. Не заставлять повторно выбирать один объект в одном flow.
10. Content creation, assignment и review остаются разными задачами.
11. Desktop content canvas получает большую часть useful viewport.
12. Mobile проектируется отдельно.
13. Любой state label отвечает «что делать дальше?».
14. Если control нельзя понять без инструкции, control требует redesign.
15. Empty state объясняет следующий шаг и содержит не более одной primary CTA.
16. Success не закрывается modal, если достаточно inline confirmation.
17. Destructive action никогда не является primary.
18. Hover-only action имеет keyboard/touch alternative.
19. Никаких декоративных hero-блоков, если они отнимают рабочую площадь без выполнения задачи.
20. Промежуточный visible result обязателен, но не равен owner acceptance и не завершает порученную программу; конкретные точки согласования — §38 и AGENTS.md.

## 31. Корректировки и error states

Каждый основной flow обязан иметь:
- loading;
- empty;
- success;
- validation error;
- permission denied;
- stale/revision conflict;
- missing media;
- network retry;
- archived/historical read-only, если применимо.

Ошибки:
- показываются рядом с объектом действия, когда возможно;
- не используют raw backend code как основной текст;
- не уничтожают введённый draft;
- дают понятное действие: исправить, повторить, обновить, вернуться.

Revision conflict:
- не молча перезаписывает изменения;
- предлагает reload/latest или explicit recovery.

### 35.2 Обзор обучения и открытый урок — разные представления (LRN-UX-01)

- Обзор показывает назначенные курсы и отдельные задания: название, осмысленный прогресс, срок при наличии и «Начать»/«Продолжить». Не повторять ту же работу одновременно в нескольких равноправных карточках.
- Открытие курса переводит в фокусное представление урока. Повторные заголовки «Моё обучение», верхние фильтры обзора, объяснение устройства платформы и общая лента результатов не остаются над/под уроком. Возврат к обзору сохраняет его фильтр и позицию.
- В начале урока видны название, короткая цель/инструкция, структура объяснения и практик, текущее состояние и следующее действие. Крупное изображение не должно прятать само наличие обязательной практики за несколькими экранами прокрутки.
- Desktop: одна компактная структура курса рядом с содержимым; глобальная навигация ASA сворачивается только в этом контексте, остаётся доступной вместе с помощью и выходом. Не переписывать глобальный портал ради локального экрана. Mobile: содержание урока на всю ширину; структура открывается по явной кнопке, выбранный пункт и положение сохраняются.
- В структуре показаны вложенные практики с человеческими названиями и отдельными состояниями. Переход ведёт к соответствующему блоку/редактору, не создаёт второй Project/Attempt. Источник идентичности — точное occurrence, не только одинаковый title или activity root.
- «Следующий шаг» ведёт к доступной обязательной работе: незавершённая доработка/начатая практика или следующая по порядку доступная. Не обходить teacher prerequisites, сроки, аудиторию или закрытый курс; при блокировке указать причину. Если все работы ждут review, показать «Ожидайте проверки», не фиктивное «Продолжить».

### 35.3 Прочтение, сдача и принятие — разные состояния (LRN-UX-02)

- «Материал прочитан» отражает только прочтение. Ручная отметка не сдаёт практику, не принимает её и не завершает весь смешанный урок.
- Практика: «Не начато» → «В работе» → «На проверке» → «Нужна доработка» / «Принято». Приёмка/баллы и допустимые действия берутся из canonical server state; отсутствие оценки не превращать в ноль. Для режима без ручного review использовать существующую completion policy и объяснимое «Выполнено».
- Вместо отключённой кнопки «Работа сдана» показывать статус «На проверке». Для принятой работы — «Принято» и вторичное «Посмотреть работу». Не дублировать статус ещё одной бессмысленной кнопкой.
- Целевой смешанный урок завершён, когда выполнено требуемое чтение и удовлетворены completion policies ВСЕХ назначенных обязательных практик этого урока. `submittedAt` не заменяет accepted result там, где нужна проверка. Неназначенные/опциональные/освобождённые элементы не создают ложную задолженность; освобождение объясняется явно.
- Курс завершён, когда завершены все обязательные уроки закреплённой версии для этого ученика. Нулевой знаменатель отображается как «Нет обязательных занятий», не «0 из 0 выполнено». Скрытые в НОВОЙ авторской версии уроки не удаляют требования уже назначенной старой версии.
- Счётчики называют единицу: «Уроки: 0 из 3» и «Практики: 1 из 2», а не безымянное «0 из 1». Общий урок может быть не завершён при одной принятой практике — UI объясняет оставшуюся работу.
- Клиент/сервер должны согласованно рассчитывать эти состояния. В implementation-срезе проверить endpoints отметки материала, read projections, frontend helper и права Seat/Account; не чинить только подпись. Повтор отметки/сдачи идемпотентен. Не менять исторические Results/Attempts и не переписывать задним числом принятые completion policies; для старых неоднозначных mixed-уроков нужен проверенный совместимый переход без удаления истории. Если новая агрегация требует изменения академического контракта, согласовать его до runtime-правки.

Целевой пример, не новая сущность БД:

```text
← Мои курсы
Автоматический ночник / Урок 1. Свет и сопротивление
Материал прочитан · Практики: 1 из 2

Объяснение                    Прочитано
Схема в Электронике            Принято учителем
Модель корпуса в 3D            Не начато

Следующий шаг: создайте модель корпуса.
[Начать практику в 3D]
```

## 36. Редактор и читаемая композиция (LRN-UX-03)

- Редактор редактирует документ, но большой белый прямоугольник сам по себе не делает его удобным. Однострочная инструкция не получает фиксированную пустую высоту 200–300 px; текстовое поле растёт по содержимому. Название не дублируется в двух крупных шапках.
- Базовый текст ориентировочно 16–18 px, заголовок урока 24–32 px, вторичная подпись не теряет читаемость. Это проектные ориентиры, не повод принимать экран по числам. Сохранить доступность при 200% zoom, перенос длинных русских названий, видимый focus и доступные touch targets.
- Ширина текстового чтения ограничена для читаемости; схема может раскрыться шире/в lightbox. Запрещены обрезка схемы, растягивание маленького растра и «уменьшение всего интерфейса» как исправление плотности. Не заставлять схему занимать полную высоту экрана по умолчанию; увеличение явно доступно.
- Один вход «Добавить содержимое» для текста, изображения, файла, видео/ссылки и существующей практики. Выбор файла, drag-and-drop и вставка изображения из буфера ведут в один pipeline; разрешённые типы и ошибки одинаковы. Нативный file input остаётся доступным техническим механизмом, но не единственным user-facing control.
- Вложение отображается там, куда добавлено; есть понятные «Заменить», «Удалить», имя/тип/размер и «Скачать» по правам. Несколько изображений/файлов не должны заменять друг друга молча. Целевой минимум — 10 медиа-вложений в уроке в пределах существующего общего лимита блоков; это не обещание бесконечной загрузки.
- Вторичные действия блока — по focus/touch/context menu, не ряд из десятка кнопок. Интерактивность текста заметна при наведении/focus, не только по наличию каретки. Не требуется конкретная rich-text библиотека.
- Пример пустого курса не оценивается по проценту незанятой площади. Убирается бесполезный chrome, а не полезный воздух; не добавлять фиктивные записи или декоративные виджеты.

## 37. Материалы без внешней «сжималки»

### 37.1 Целевой профиль загрузки (LRN-MEDIA-01)

Эти значения — выбранные проектные требования данной редакции, не текущая возможность preview и не универсальная норма отрасли. MB здесь = 1 000 000 байт; лимиты проверяются одинаково в UI, API, proxy и storage. Административное снижение лимита не должно быть скрытым: профиль и сообщение видимы до загрузки; базовый продуктовый тест проводится на значениях таблицы.

| Тип | Целевой входной размер | Поведение |
|---|---:|---|
| Изображение PNG/JPEG/WebP | до 20 000 000 байт включительно | автоматическая ориентация и экранные варианты; увеличение для чтения схемы |
| PDF | до 25 000 000 байт включительно | исходный документ сохраняется; просмотр по поддержке и скачивание без потери страниц |
| Обычное учебное вложение | до 50 000 000 байт включительно | безопасное скачивание оригинала; встроенный просмотр не обещается для каждого формата |

Минимальный allowlist учебных вложений: PDF, DOCX, PPTX, XLSX, TXT, CSV, SB3, STL, INO, ZIP. Для каждого типа до включения реализуются проверка типа/контейнера и безопасная выдача. SB3/ZIP/OOXML как загрузки не распаковываются и не исполняются автоматически; наличие SB3-файла не означает готовность учебной интеграции Scratch. Исполняемые файлы, HTML, SVG и макросодержащие документы не входят в этот базовый профиль.

Лимит 400 000 байт для принимаемого изображения/PDF отменяется как TARGET-поведение, но не одной заменой числа в UI. Перед implementation проверить все ограничения API, схем/SQL/media roles, транспорт/base64, request body, reverse proxy, копирование и версионирование. Входной файл не обязан совпадать с лёгкой экранной копией по размеру. Большой base64 в JSON не должен бесконтрольно увеличивать память; выбрать ограниченный upload-path на существующем хранилище, не новый медиасервис по умолчанию.

### 37.2 Автоматическая обработка изображения (LRN-MEDIA-02)

- Выбор/вставка → загрузка → проверка/обработка → готовое вложение. Состояния видимы; отмена и повтор не теряют документ и не создают дубликат. «Сохранено» означает подтверждённый сервером документ со всеми нужными готовыми ссылками, не только локально прочитанный файл.
- Сервер авторитетно проверяет формат/сигнатуру/декодирование; расширения и browser MIME недостаточно. Ограничить decoded pixels, стороны, время/память/параллелизм. Исходный проектный профиль: не более 64 Мп и 16 384 px по стороне; при превышении — понятная причина, не ошибка про 400 КБ. Значения подлежат проверке ресурсным тестом до выпуска.
- Для экранного показа создавать варианты по реальному viewport, сохранять пропорции и EXIF-ориентацию, не увеличивать малое изображение, не обрезать текст/схему, сохранять прозрачность. Удалять ненужные EXIF/GPS из выдаваемых производных. Никакой цели «любой ценой меньше 400 КБ».
- Оригинал и производные хранить как различимые объекты; скачивание оригинала только по тем же правам/версии. Учителю не требуется искать компрессор. Проверить PNG-схему с мелким текстом, JPEG-фото с ориентацией, прозрачный WebP и большое изображение; формальный размер не заменяет визуальную читаемость.
- Медиа загружать по необходимости: thumbnails для списков, подходящий вариант для урока, оригинал/крупный вариант по запросу. Один список не скачивает все 20-МБ оригиналы. Подготовить ограниченный параллельный тест существующего сценария класса, без новой общей программы масштабирования.

### 37.3 Сохранность, безопасность и история (LRN-MEDIA-03)

- Использовать существующие version/media-ref/tenant/RLS contracts. Опубликованная версия закрепляет конкретные байты и ссылки. Замена в черновике/v2 не меняет материал назначенной v1. При смене алгоритма производных нельзя молча перезаписать старое опубликованное изображение.
- Права проверяются при каждой выдаче, включая оригинал, thumbnail, производную, PDF и download; hash или URL не является разрешением. Копия курса сохраняет валидную самостоятельную связь с материалами и не расширяет доступ к исходной школе.
- Квоты и orphan cleanup учитывают оригиналы/производные и незавершённые загрузки; не удалять blob, на который ссылается опубликованная/назначенная версия. Никакой destructive cleanup существующего preview в этом docs-срезе.
- Allowlist, byte/pixel limits, безопасные имена, generated storage keys, авторизация/CSRF и безопасные Content-Type/Content-Disposition/nosniff применяются совместно. Документы проверяются на вредоносное содержимое доступным согласованным механизмом; не отправлять ученические файлы в публичный сторонний сканер без разрешения. Проверка/карантин не выдаётся за успешную публикацию.
- Успешное скачивание PDF подтверждает читаемый настоящий документ, а не только пять байт `%PDF-`. Для обычных вложений проверять совпадение скачанных байтов, Unicode-имена и отказ постороннему ученику.

### 37.4 Видео — не переименованная ссылка (LRN-MEDIA-04)

У UI различаются «Видео» (фактическое воспроизведение в уроке) и «Внешняя ссылка» (переход на сайт). Одно не засчитывается за другое. Целевой первый video-path — согласованный HTTPS provider/embed либо прямой поддерживаемый медиа-ресурс с действующим плеером, sandbox/CSP и fallback «Открыть источник». Не вставлять произвольный HTML/iframe и не делать серверный fetch произвольного URL без SSRF-защиты. Проверять доступность в используемой школьной сети, без предположения, что зарубежный provider доступен всем.

Загрузка видео на сервер — отдельная явно оцениваемая возможность с codec/size/quota-профилем; эта редакция не приказывает строить перекодирование или видеохостинг. Пока доступна только ссылка, кнопка и отчёт так и называются, video requirement остаётся TARGET. Недоступный provider не блокирует загрузку текста, изображения и остальных частей урока. По внешней ссылке не выдумывается процент просмотра.

## 38. Приёмка и порядок ремонта без новой полной переписки

### 38.1 Три обязательных результата

1. Понятный ученический маршрут и согласованный прогресс (§35).
2. Обычные изображения и учебные документы без ручного сжатия (§37.1–37.3).
3. Компактный редактор и осмысленная демонстрация (§36, сценарии ниже).

Перед пакетной реализацией показать один согласованный набор целевых состояний: обзор курсов, открытый смешанный урок и редактор с обычными вложениями. Это один дизайн-checkpoint, не отдельная приёмка каждой кнопки. После него контролёр выполняет связанные bounded repairs через исполнителей/рецензентов по AGENTS.md и показывает промежуточный результат, не превращая каждый CI в повод заново переписать UI. Список заданий, который уже пригоден, не реализуется повторно.

Изменение ТЗ не изменяет автоматически current task, не снимает blockers, не разрешает merge/rebase PR #511, смену baseline, обновление Docker или рабочей БД. Существующий owner-preview и его данные сохраняются до отдельного разрешённого действия; отзывы не означают «просмотр завершён». Развёртывание ремонта — отдельный явно названный кандидат после разрешения владельца.

### 38.2 Приёмочный учебный материал (LRN-UX-04)

Курс «Автоматический ночник», урок «Свет и сопротивление»: понятное объяснение, схема с читаемыми подписями, настоящий PDF, обычный учебный файл, практика «Соберите схему» в Электронике и «Создайте корпус» в 3D. Отдельно проверяется Scratch по готовому обычному контракту; наличие кнопки/тестового override не закрывает его зависимость. Видео проверяется только реально поддерживаемым способом и отдельно от внешней ссылки.

В названиях и инструкции нет SHA, timestamp, `Owner Learning demo`, `Mixed v1`, `Exact instructions`; они остаются в техническом evidence. Используются синтетические педагогические данные, не реальные данные детей. Полезные схемы/документы не заменяются скриншотами другого интерфейса ASA. Нужны оба состояния: ученик, ещё ничего не выполнивший, и тот же ученик после одной принятой практики. В последнем шаге тот же ученик завершает обе практики; выполнение разных практик двумя разными учениками не доказывает завершение курса одним.

### 38.3 Планируемые проверки; не существующие PASS (LRN-UX-05)

| Сценарий | Обязательный наблюдаемый результат |
|---|---|
| U01 — вход нового ученика | без устных подсказок находит курс, объяснение и первую практику; может вернуться к обзору |
| U02 — чтение + Электроника принята, 3D не начата | «Материал прочитан», «Практики: 1 из 2», явный переход к 3D; смешанный урок/курс не завершён |
| U03 — отметка чтения, reload, второй tab, повтор API | практика не становится принятой/сданной; клиент и сервер согласованы; нет новых Attempts |
| U04 — та же практика ждёт review / возвращена / принята | правильные подпись, следующее действие, точная работа и версия; submitted не маскируется accepted |
| U05 — две практики одного ученика приняты | урок/курс завершён по закреплённой политике; баллы не выдумываются; различимые знаменатели |
| U06 — optional/excused/named/hidden-v2/пустой курс | нет ложных долгов или доступа; старая v1/история неизменны; 0/0 не является успехом |
| M01 — PNG 3–8 МБ и JPEG 10–20 МБ | выбор, drag/drop и paste не требуют компрессора; подписи читаемы, ориентация правильна |
| M02 — 400 001 байт; границы 20 МБ/25 МБ/50 МБ | бывший порог не отклоняет допустимый файл; точные верхние границы и понятный отказ выше них |
| M03 — повреждённый формат, чрезмерные pixels, замаскированный executable, недопустимый ZIP | безопасный отказ/карантин; текст задания сохранён; никаких inline execution или распаковки |
| M04 — отмена, прерывание upload, retry и 10 вложений | нет потерянных блоков, silent replacement и дубликатов; правильный server-ACK статус |
| M05 — v1 опубликована, затем замена/v2, copy, удаление черновика | старые оригинал/производные/PDF доступны только своему ученику и не изменены |
| M06 — PDF 5–25 МБ и DOCX/ZIP/SB3 в пределах профиля | обычные файлы скачиваются с правильными байтами/именем; настоящий PDF открывается; SB3 не выдаётся за интеграцию |
| V01 — внешний provider недоступен | текст/файлы работают, честный fallback; видео не засчитано просмотренным |
| UI01 — 1440×900, 1024×768, 390×844, 320×568, keyboard/200% zoom | текст, фокус, названия практик и следующее действие читаемы; sticky chrome не перекрывает контент |
| UI02 — краткая и длинная инструкция в редакторе | поле растёт по тексту, загрузка видима, нет лишних карточек/пустых min-height; preview той же версии |

Реализация добавляет проверки в существующие canonical unit/API/PG/E1 suites; таблица не подменяет их выполнение. Каждый receipt связывает сценарий, exact SHA и результат. Реальные пользовательские проверки преподавателем и учениками записываются как наблюдения, а не имитируются ботом. До их выполнения usability acceptance — NOT_RUN. Число снимков, отсутствие overflow, размер padding и зелёный CI сами по себе не дают owner acceptance. Невозможность понять следующий шаг или нечитаемая схема — FINDING даже при зелёных технических тестах.
