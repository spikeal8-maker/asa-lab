# ASA Lab — UI layout acceptance contract

**Статус:** NORMATIVE / TARGET  
**Редакция:** 1.0  
**Область:** все пользовательские интерфейсы ASA Lab, включая Account/Settings, Learning, Classes, Courses, Games, Electronics, 3D и будущие модули.

## 1. Зачем существует этот контракт

Функционально зелёный тест не означает, что интерфейс пригоден пользователю. Любая правка пользовательского экрана считается незавершённой, пока не проверены компоновка, читаемость, адаптивность и соседние поверхности, которые используют изменённый CSS/компонент.

Этот документ усиливает существующий `UI-AC-27` из `ASA_USERS_ACCESS_AND_SETTINGS_SPEC.md`. Требование 1440/1024/390/320 сохраняется, но теперь оно является только частью полной layout-приёмки.

## 2. Когда контракт обязателен

Layout-review обязателен, если изменение затронуло хотя бы одно из:

- JSX/HTML пользовательского экрана;
- CSS/grid/flex/container/breakpoint;
- общий визуальный компонент;
- label, title, help text, button text или другое содержимое, способное изменить размеры;
- empty/loading/error/permission state;
- navigation, sidebar, tabs, dialogs, forms, cards, tables;
- отображение данных после backend/API изменения.

Изменение shared CSS-класса или shared-компонента требует проверки **всех его реальных consumers**, а не только страницы, ради которой вносилась правка.

## 3. Обязательные размеры

Каждая затронутая surface проверяется минимум на:

- 1440 px — desktop;
- 1024 px — compact desktop/tablet landscape;
- 390 px — основной mobile;
- 320 px — узкий mobile.

Если у компонента есть существенный breakpoint между ними, дополнительно проверяется сам breakpoint или ближайшая ширина, на которой меняется layout.

## 4. Layout invariants

Для каждой затронутой surface обязательны все условия:

1. Нет горизонтального scroll страницы, кроме явно спроектированного локального scroll-container (например, большая матрица журнала).
2. Текст не сжимается до min-content: запрещены колонки, где обычная фраза переносится по 1–4 символа на строку.
3. Grid/Flex slot обязан соответствовать фактической DOM-семантике. Нельзя применять layout `icon | text | action` к DOM `text | action`.
4. Основной текст остаётся читаемым без `overflow:hidden` как способа скрыть ошибку компоновки.
5. Заголовки и названия важных сущностей допускают перенос; обрезка допустима только там, где есть полный доступный текст/tooltip и это не основной идентификатор страницы.
6. Primary action сохраняет текстовую подпись на desktop и mobile; превращение основного действия только в иконку требует отдельного решения и `aria-label`.
7. Button/select/input не вытесняет описательный текст в нечитабельную колонку.
8. Long Russian labels, длинное имя пользователя/класса/курса и длинный status text не ломают layout.
9. Empty state не дублируется одновременно в select, help text и отдельной большой карточке. Один state — одно основное объяснение и один следующий CTA.
10. Secondary settings не занимают главный визуальный поток над основной задачей страницы. Вторичные параметры сворачиваются, уходят в settings или показываются рядом с контекстом.
11. Соседние блоки используют согласованные spacing, heading hierarchy и action placement.
12. Исправление одного viewport не считается PASS, если ухудшился другой обязательный viewport.

## 5. Состояния, которые необходимо проверить

Для изменённой страницы проверяются все применимые состояния:

- populated/normal;
- empty;
- loading;
- error/retry;
- disabled/permission-limited;
- long-content;
- active/editing;
- success/notice после действия.

Не требуется искусственно создавать состояния, которых у surface нет.

## 6. Проверка impact radius

Перед завершением UI-шага исполнитель обязан:

1. перечислить изменённые CSS-классы/shared-компоненты;
2. найти все их consumers;
3. разделить consumers на `directly affected`, `potentially affected`, `not affected with reason`;
4. визуально/браузерно проверить все `directly affected` и все shared-layout consumers;
5. при изменении общего примитива проверить минимум один representative screen каждого типа consumer.

Запрещено считать изменение локальным только потому, что изменён один CSS-файл.

## 7. Browser evidence

Для L0/L1 UI-изменения минимум:

- browser screenshot/evidence для desktop 1440 и mobile 390;
- автоматическая проверка `document.documentElement.scrollWidth <= document.documentElement.clientWidth`, если страница не имеет разрешённого page-level horizontal scroll;
- проверка 1024 и 320 без обязательного screenshot, если assertions и visual review подтверждены;
- для найденного layout defect — regression assertion по конкретной причине дефекта, а не только snapshot.

Для milestone/release candidate screenshots обязательны на 1440/1024/390/320 для всех изменённых основных surfaces.

## 8. Правила CSS и компонентов

- Shared visual primitive должен иметь описанный slot contract.
- Семантически другой компонент не должен переиспользовать старый CSS-класс только ради похожего фона/границы.
- `min-width: 0` применяется осознанно для shrinkable content, но не используется для маскировки неправильной grid-колонки.
- `overflow:hidden`, `text-overflow:ellipsis` и `white-space:nowrap` не являются исправлением layout defect сами по себе.
- Breakpoint должен менять структуру предсказуемо: 3 columns → 2 → 1, а не оставлять пустую колонку от исчезнувшего элемента.
- Form actions используют единый footer/layout pattern; primary и cancel не должны визуально разрываться без причины.

## 9. Информационная архитектура

При layout-review проверяется не только CSS:

- одна страница должна иметь одну основную пользовательскую задачу;
- настройки не смешиваются с основным рабочим потоком без необходимости;
- повторяющиеся заголовки/объяснения удаляются;
- secondary controls не выглядят важнее primary content;
- рядом расположенные tabs/cards должны соответствовать одному уровню иерархии;
- CTA находится рядом с объектом, которым управляет.

## 10. Найденные владельцем обязательные regression cases

Следующие дефекты считаются P0/P1 evidence и должны иметь явную проверку после исправления:

### UI-LAYOUT-R01 — Account / Возможности

Карточка `Создавать материалы` не может использовать grid-slot под отсутствующую иконку. Описание не должно сжиматься до узкой вертикальной колонки. Проверить обе карточки: `Создавать материалы` и `Преподавание`.

### UI-LAYOUT-R02 — Account / Уведомления

Категории, master switch, per-class overrides и actions должны иметь устойчивую иерархию. `Сохранить` и `Отменить` размещаются в одном action-footer; длинные категории не разъезжаются.

### UI-LAYOUT-R03 — Classroom / Обучение / Курсы

Назначение курса, срок и CTA должны оставаться компактным единым блоком. `Аудитория курса` не должна превращаться в огромный пустой fieldset с разнесёнными radio-control.

### UI-LAYOUT-R04 — Classroom / empty course state

При отсутствии опубликованных курсов пользователь получает одно объяснение и один следующий CTA. Не допускаются три одновременных сообщения `нет курсов` в select/help/empty-card.

### UI-LAYOUT-R05 — Classroom / учебные оповещения

Настройки оповещений являются secondary control и не должны визуально заслонять основной контент вкладки `Обучение`.

## 11. Definition of done для UI-правки

UI-изменение нельзя объявлять `DONE`, `CI_VERIFIED`, `DEMONSTRATED` или `OWNER_ACCEPTED`, если:

- не перечислен impact radius;
- не проверены обязательные viewport;
- известен text squeeze/overflow/overlap;
- нарушена иерархия primary/secondary действий;
- shared CSS изменён без проверки consumers;
- screenshot демонстрирует визуальный дефект, даже если functional tests зелёные.

Функциональные тесты и layout acceptance дополняют друг друга; одно не заменяет другое.
