## Checks performed

- R0 prerequisites: 7/7 accepted.
- User value: one complete private online Checkers match between two real ASA users.
- Scope isolation: Quick, Rated, Social, Chess, Arena, Creator and tournaments excluded.
- Identity/security: consumes GP-R0-001/002; no client identity authority and no classroom dependency.
- Match model: consumes GP-R0-003/004/005; duel uses zero team rows while canonical team storage is not postponed.
- Capability/error semantics: consumes GP-R0-006/007.

- Hygiene: legacy hard-limit Checkers files are protected from new responsibilities; audit cadence is explicit.
- Cost: default new dependency count is zero and hidden infrastructure expansion is a stop condition.

## Challenge cases

1. **Invite accepted twice** -> same semantic result/replay or terminal rejection; never a second match/seat.
2. **One user opens own invite** -> cannot obtain both participant authorities.
3. **Lost move response** -> retry with same command id replays; stale different command conflicts.
4. **Second tab/stale version** -> server rejects stale command without duplicate game effect.
5. **Disconnect during opponent turn** -> reconnect snapshot, not client cache, determines canonical state.
6. **Finish followed by downstream failure** -> transactional finalization/outbox preserves durable result for retry/recovery.
7. **Polling load concern** -> bounded cadence/long-poll is an implementation tuning problem; it does not authorize a realtime service in R1.
8. **Checkers UI hotspot touched** -> extract only the online seam; no broad Checkers rewrite.

## Residual implementation risks

- Exact invite-code entropy/TTL/lookup indexing must be proven in R1B tests.
- Exact update-delivery cadence/load limits must be measured in R1C.
- Physical SQL/outbox design must pass RLS/fault-path tests in R1A/R1D.
- Fresh file-size baseline must be generated by the first hygiene tool run.

These are implementation evidence items, not architecture blockers.
