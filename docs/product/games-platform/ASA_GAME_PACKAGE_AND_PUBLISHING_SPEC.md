# ASA Game Package & Publishing System

**Status:** Draft product/developer specification  
**Depends on:** `ADR-GAME-001`, `ADR-GAME-002`  
**Purpose:** define how a game created outside ASA becomes a validated, versioned and publishable ASA game.

## 1. Product goal

A creator should be able to build a game without understanding ASA internals.

The creator supplies:

```text
game package manifest
client artifact/source
optional managed rules artifact
optional verified realtime runtime artifact
assets/content
metadata
```

ASA supplies, subject to declared/granted capabilities:

```text
identity
Games Hub integration
private/classroom/public publishing
invites/party
matchmaking
match lifecycle
reconnect
history
common statistics
ratings/leaderboards when authoritative
notifications
moderation/reporting
telemetry
version/release management
```

If a creator must query ASA account/classroom tables or implement their own generic matchmaking/rating stack, the package contract has failed.

## 2. Terms

### Game

Stable creator-owned product identity.

### Source revision

Immutable source snapshot, such as Git commit SHA or uploaded archive digest.

### Build

Immutable output produced from one source revision.

### Release

One approved build with pinned protocol/rules/schema compatibility.

### Channel

Named pointer to a release (`private`, `preview`, `classroom`, `beta`, `stable`).

### Publication

Audience/discovery decision independent from channel.

### Capability request

What the package wants to use.

### Capability grant

What ASA policy actually permits for the release/audience.

## 3. Package layout

Source repository MAY use any internal layout. For the standard web creator path, recommended layout is:

```text
my-game/
├── asa-game.yaml
├── package.json
├── src/
├── public/
├── tests/
└── README.md
```

Build output contract:

```text
dist/
├── index.html
├── assets/
└── optional metadata generated by SDK tooling
```

The build system never assumes the source repository itself is the runtime artifact.

## 4. Manifest v1 proposal

Illustrative draft:

```yaml
apiVersion: games.asa-lab/v1
kind: GamePackage

metadata:
  gameKey: space-cats
  displayName: Space Cats
  packageVersion: 1.2.0

compatibility:
  gameSdk: "^1.0"
  clientBridge: "1"

client:
  kind: web
  entry: dist/index.html
  buildOutput: dist

runtime:
  kind: none

players:
  min: 1
  max: 1
  topology: solo

capabilities:
  request:
    - player.public_profile.read
    - storage.private
    - achievements.personal

publication:
  requestedAudience: private
```

Manifest MUST NOT contain:

- database credentials;
- GitHub tokens;
- ASA session cookies;
- raw PostgreSQL table/connection details;
- Kubernetes/Agones resources;
- arbitrary environment secrets;
- self-issued capability grants.

## 5. Multiplayer command package example

```yaml
apiVersion: games.asa-lab/v1
kind: GamePackage

metadata:
  gameKey: classroom-grid-battle
  displayName: Grid Battle
  packageVersion: 0.4.0

compatibility:
  gameSdk: "^1.0"
  clientBridge: "1"
  commandProtocol: "1"

client:
  kind: web
  entry: dist/index.html
  buildOutput: dist

runtime:
  kind: managed-command
  rulesArtifact: build/rules.wasm
  rulesVersion: classic-v2
  stateSchemaVersion: 2

players:
  min: 2
  max: 2
  topology: duel

capabilities:
  request:
    - multiplayer.private_invites
    - multiplayer.quick_match
    - reconnect
    - match.history
    - statistics.common

publication:
  requestedAudience: classroom
```

`rules.wasm` is illustrative; ADR does not yet mandate WASM as the only managed-command implementation.

## 6. Verified realtime room example

```yaml
apiVersion: games.asa-lab/v1
kind: GamePackage

metadata:
  gameKey: robot-arena
  displayName: Robot Arena
  packageVersion: 2.0.0

compatibility:
  gameSdk: "^1.0"
  clientBridge: "1"
  roomProtocol: "1"

client:
  kind: web
  entry: dist/index.html
  buildOutput: dist

runtime:
  kind: isolated-room-runtime
  imageArtifact: runtime-image
  tickRateHz: 30
  maxPlayersPerRoom: 8
  recovery: non-recoverable

players:
  min: 4
  max: 8
  topology: free-for-all

capabilities:
  request:
    - multiplayer.party
    - multiplayer.quick_match
    - runtime.realtime
    - input.pointer_lock
    - ui.fullscreen
    - reconnect

publication:
  requestedAudience: event
```

Custom realtime runtime packages are not available to unreviewed student/classroom trust by default.

## 7. Integration kinds

### `platform-native`

First-party code compiled with ASA repositories/services.

Use for mature built-in games during transition.

### `sandbox-web`

Default external/student package.

Client-only or platform-service-backed web application running in isolated iframe/origin.

### `managed-command`

Game supplies restricted rules/state transition module. ASA owns command persistence, match lifecycle, networking and authoritative execution shell.

### `isolated-room-runtime`

Game supplies a server runtime artifact speaking ASA Room Runtime Protocol. Reserved initially for platform/verified trust.

## 8. Source connector workflow

### GitHub v1

Creator chooses:

```text
Developer Portal
→ New Game
→ Connect GitHub
```

ASA GitHub App is installed only on selected repositories.

Recommended minimum repository access:

```text
Metadata: read
Contents: read
```

Webhook subscriptions are added only for required events, such as push/release/manual trigger.

No `Workflows: write`, repository administration or secrets access by default.

GitHub App installation credentials stay inside Source Connector.

Build receives an exported source snapshot pinned by commit SHA.

### Other future source providers

Same pipeline can accept:

```text
ZIP archive digest
ASA Creator project revision
GitLab commit
school repository revision
```

Source provider does not change package/release semantics.

## 9. Build states

```text
queued
importing
building
validating
passed
failed
quarantined
```

A build that fails security/conformance never becomes a releasable artifact.

## 10. Isolated build process

Build steps conceptually:

```text
source snapshot
  ↓
manifest parse/schema validation
  ↓
SDK compatibility validation
  ↓
restricted dependency/build process
  ↓
tests
  ↓
artifact validation
  ↓
license/SBOM/security checks
  ↓
content digests/provenance
  ↓
GameBuild record
```

Builder has:

```text
NO production DB credentials
NO ASA session secrets
NO GitHub installation token after import
NO host Docker socket
NO privileged mode
```

Resource policy includes CPU, memory, PIDs, wall time, output size and artifact size.

Network is denied by default or restricted to approved dependency mirrors/proxies.

## 11. Build output

Every successful build records at minimum:

```text
build_id
game_id
source_revision
source_digest
manifest_digest
builder_version
sdk_version
client artifact digest nullable
rules artifact digest nullable
runtime artifact digest nullable
SBOM/license status
scan status
created_at
```

Artifacts are immutable/content-addressed.

## 12. Release workflow

Build does not equal release.

```text
Passed build
   ↓
Preview
   ↓
Capability review
   ↓
Content/moderation review by scope
   ↓
Certification when needed
   ↓
Approved GameRelease
```

Release pins exact protocol/schema versions.

## 13. Release channels

Initial channels:

```text
private    author-only current release
preview    invited testers/reviewers
classroom  approved classroom release
beta       wider pre-stable cohort
stable     normal production release
```

An event campaign can pin its own exact release or channel.

Promotion changes channel pointer. Old build/release remains immutable.

Rollback therefore does not rebuild source.

## 14. Publication scopes

### Author only

Default. Creator can test safe build.

### Classroom

Teacher/moderator approves. Discoverable only for allowed classroom scope.

### Workspace/school

Organization-admin/policy approval.

### ASA Community

Platform moderation and required safety/conformance checks.

### Featured/rated

Stricter certification, competitive integrity and operational requirements.

### Event

Availability is tied to campaign start/end, while match history remains durable after event closes.

## 15. Capability request model

Example manifest request:

```yaml
capabilities:
  request:
    - player.public_profile.read
    - storage.private
    - multiplayer.private_invites
    - multiplayer.quick_match
    - input.pointer_lock
```

Platform grant may be narrower:

```text
granted:
  player.public_profile.read
  storage.private
  multiplayer.private_invites

denied:
  multiplayer.quick_match
  input.pointer_lock
```

Runtime only sees granted capabilities.

## 16. Client isolation

External web game is loaded from a dedicated game-content origin into a sandboxed iframe.

Conceptual:

```html
<iframe
  src="https://<game-content-origin>/<release>/index.html"
  sandbox="allow-scripts ...minimal-required-flags..."
></iframe>
```

Exact flags depend on granted capabilities.

Controls:

- dedicated origin;
- strict CSP;
- Permissions Policy;
- no ASA authentication cookies;
- no direct parent DOM access;
- external network restricted by `connect-src`/gateway policy;
- top navigation/popups/forms disabled unless separately justified;
- service-worker/storage policy explicitly controlled.

Do not serve untrusted game code as normal `/assets` under the authenticated ASA Web origin.

## 17. Client bridge

The parent platform and game communicate through versioned RPC/events.

Handshake example:

```text
GAME_HELLO
PLATFORM_HELLO
CAPABILITIES_GRANTED
GAME_READY
```

Request example:

```json
{
  "protocol": 1,
  "id": "req-42",
  "type": "storage.get",
  "payload": { "key": "save-1" }
}
```

Response:

```json
{
  "protocol": 1,
  "replyTo": "req-42",
  "ok": true,
  "payload": { "value": "..." }
}
```

Bridge validates:

- exact source/origin/window;
- protocol version;
- message schema;
- granted capability;
- payload size/rate;
- request correlation/timeout.

## 18. Suggested Client SDK families

Creator-friendly surface can wrap bridge details:

```ts
const asa = await createAsaGameClient();

const me = await asa.player.getPublicProfile();
await asa.storage.private.set('save', value);
asa.ui.openInvitePicker();
asa.match.on('found', ...);
```

API must expose stable product concepts, not NestJS/SQL/Redis implementation.

## 19. Storage classes

External games SHOULD use platform storage capabilities rather than raw browser/DB access when durable data matters.

Initial classes:

```text
storage.local_ephemeral
storage.private_player
storage.game_shared limited/verified
```

Each has quotas/retention/schema rules.

No game receives arbitrary database credentials.

## 20. Scores, stats and competitive integrity

### Client-only game

May produce:

```text
personal progress
personal achievements
unverified/classroom score
```

It MUST NOT affect verified competitive rating solely on client claims.

### Managed command / authoritative room game

Server/runtime produces final outcome and custom metrics.

Those may feed:

```text
verified match history
rating
leaderboards
public W/L/D
competition progression
```

## 21. Student publishing lifecycle

Recommended default:

```text
Draft
  ↓ safe build
Private Playtest
  ↓ teacher approval
Classroom
  ↓ platform moderation/certification
Community
  ↓ optional editorial selection
Featured
```

A student does not accidentally publish code globally by pushing to GitHub.

## 23. Admin/Moderator views

Admin can:

- inspect manifest/build/release;
- review requested capabilities;
- run preview;
- approve/deny publication scope;
- suspend game/release;
- rollback channel;
- view crash/security/abuse signals;
- revoke capability;
- disable matchmaking admission independently from history.

Admin does not edit source code as part of normal publication.

## 24. Kill switch and revocation

Platform can separately:

```text
disable discovery
disable new sessions
disable matchmaking
disable a capability
disable exact release
disable entire game
```

Historical matches/statistics remain according to retention policy.

For a dangerous realtime runtime, runtime allocation can be stopped while client/catalog metadata remains available for administrators.

## 25. Version compatibility

A release pins:

```text
Game Package schema version
ASA Game SDK version range
Client Bridge protocol
Command/Room protocol where applicable
rules version
state schema version
```

Active matches never silently jump to incompatible rules/runtime version.

## 27. Definition of package readiness

A package system is ready for creator pilot when:

1. GitHub repo can be connected with least-privilege app access.
2. Exact commit produces an immutable build.
3. Build is isolated from production credentials/network.
4. Sandboxed web client launches without ASA cookie/DOM access.
5. Client SDK provides at least profile, storage and exit/error lifecycle.
6. Manifest requests cannot self-grant capabilities.
7. Release can be promoted private → classroom without rebuild.
8. Release can roll back to previous build.
9. Teacher can approve classroom visibility.
10. Deleting/disabling source repository does not corrupt already-recorded release metadata/history.

## 28. Non-goals for v1

Do not require initially:

- arbitrary student dedicated-server containers;
- marketplace monetization;
- native Windows/macOS game installation;
- Steam-like DRM;
- public mod workshop;
- unrestricted external networking;
- arbitrary filesystem access;
- Kubernetes/Agones.

These can be revisited after the secure web creator path works.
