# Техническое задание: публичный раздел «Проекты» AsaLab

**Статус:** Implementation-ready  
**Репозиторий:** `spikeal8-maker/asa-lab`  
**Рабочая ветка спецификации:** `docs/projects-ui-ux-spec-v3`  
**Область:** frontend, backend, data, security, testing, rollout  
**Источник истины:** существующий домен проектов AsaLab

---

## 1. Цель

Реализовать публичный раздел «Проекты» AsaLab: каталог пользовательских проектов, поиск и фильтрацию, страницу просмотра проекта, публикацию/снятие с публикации, а также социальные функции там, где они уже поддерживаются системой или где их необходимость подтверждена AS-IS аудитом.

Ключевое требование: публичный раздел не является новым проектным движком и не должен создавать параллельную архитектуру.

> **Не создавать второй Project Hub, вторую модель проектов, отдельную систему публикации или параллельную систему версий. Общественный раздел «Проекты» строится поверх существующего проектного ядра AsaLab. Любая новая сущность вводится только после доказанного отсутствия подходящей существующей реализации.**

---

## 2. Архитектурные инварианты

1. Существующая сущность проекта является source of truth.
2. Сохраняется существующий канонический идентификатор проекта (`project_id` или фактический аналог из кода).
3. Существующий механизм snapshot/version/history является единственным механизмом версий.
4. Публикация должна быть состоянием/метаданными существующего проекта либо ссылкой на существующую версию/снимок. Создание отдельной копии payload проекта запрещено без ADR.
5. Все операции записи авторизуются на сервере на уровне конкретного объекта.
6. UI-проверки прав не считаются механизмом безопасности.
7. Изменения схемы БД — additive, обратно совместимые и по возможности обратимые.
8. Запрещено дублировать проект, snapshot, version или media payload только ради публичного каталога.
9. Необходимо переиспользовать существующие API-конвенции, маршрутизацию, дизайн-систему, хранилище, медиа-пайплайн, ACL/RBAC и логирование.
10. Если фактическая архитектура репозитория конфликтует с предположением этого ТЗ, фактический инвариант кода имеет приоритет. Конфликт фиксируется в AS-IS матрице и, если нужно, в ADR/PR note; обходить его молча запрещено.

## 4. Публичный каталог `/projects`

Если маршрут `/projects` или эквивалент уже существует, он расширяется. Конкурирующий маршрут для того же продукта не создаётся.

### 4.1. Функциональность

Каталог должен поддерживать:

- просмотр публично доступных проектов гостем;
- поиск по доступным индексируемым полям;
- категории и теги только из реальных данных;
- фильтры, которые имеют backend-семантику;
- сортировку;
- серверную пагинацию/cursor pagination по существующей конвенции проекта;
- открытие карточки в канонический viewer проекта;
- сохранение состояния поиска/фильтров/сортировки в URL;
- корректную работу browser Back/Forward и deep link.

### 4.2. Поиск

- запрос должен иметь debounce на клиенте;
- backend обязан валидировать длину и допустимые параметры;
- поиск не должен возвращать private/unpublished объекты;
- при наличии полнотекстового поиска/индекса — переиспользовать его;
- если полнотекстового поиска нет — реализация должна быть ограниченной и прозрачной, без декоративной имитации.

### 4.3. Сортировка

Допускаются только реально поддерживаемые режимы. Например: `newest`, `updated`, `popular`, но название enum берётся из существующего кода.

`popular` разрешён только при наличии настоящей измеряемой метрики. Фиктивные просмотры, лайки, рейтинги и случайные значения запрещены.

### 4.4. Карточка проекта

Карточка может показывать только реально существующие данные:

- canonical project id;
- title;
- cover/preview;
- автора/владельца в разрешённом объёме;
- тип/категорию;
- теги;
- дату публикации/обновления;
- реальные социальные счётчики, если соответствующий backend существует.

Никакие mock/fake данные не допускаются в production.

### 4.5. Состояния UI

Обязательны:

- loading/skeleton;
- empty catalog;
- no search results;
- recoverable error + retry;
- permission denied, если сценарий допускает его;
- unsupported project type;
- broken/invalid project payload без падения всей страницы.

---

## 5. Страница проекта / Viewer

### 5.1. Каноничность

Viewer получает существующий проект по его каноническому идентификатору. Новый идентификатор «публичного проекта» не вводится без отдельного обоснования.

### 5.2. Доступ

До передачи payload клиенту сервер обязан проверить:

1. существование проекта;
2. visibility/publication state;
3. object-level ACL;
4. дополнительные ограничения фактической модели доступа AsaLab.

Запрещено сначала отдавать данные проекта, а затем скрывать их интерфейсом.

### 5.3. Рендеринг

Viewer должен переиспользовать существующие production renderer/read-only adapter/editor renderer там, где это технически возможно.

Запрещено создавать второй renderer для одного и того же формата только потому, что экран называется публичным.

### 5.4. Ошибочные состояния

Viewer обязан корректно обрабатывать:

- 404;
- 403 либо скрытый 404 — в соответствии с действующей политикой проекта;
- неподдерживаемый тип проекта;
- повреждённую/несовместимую версию;
- отсутствующий media asset;
- ошибку загрузки renderer.

### 5.5. Действия пользователя

Гость/не-владелец не получает mutating editor actions.

Если в системе уже существует copy/remix/fork workflow, публичный viewer должен использовать его. Новый дублирующий механизм копирования запрещён.

## 6. Жизненный цикл публикации

Минимальные операции:

- publish;
- unpublish;
- republish;
- изменение допустимых publication metadata, если такие metadata действительно существуют или подтверждены AS-IS аудитом.

### 6.1. Критические правила

1. Публикация не клонирует проект.
2. Сохраняется canonical project id.
3. Unpublish не удаляет проект и его историю.
4. После unpublish проект немедленно исчезает из публичного каталога/поиска после предусмотренной системой инвалидации.
5. Поведение direct URL после unpublish определяется ACL.
6. Публикация/снятие с публикации должна инвалидировать связанный cache/search index, если они существуют.

### 6.2. Версии

Поведение публикации должно следовать существующей модели версий:

- если система публикует immutable snapshot — publication указывает на существующий snapshot/version;
- если система намеренно показывает current HEAD — сохраняется эта модель;
- запрещено создавать второй стек snapshot/version для публичного раздела.

## 7. ACL / матрица прав

Точные названия ролей берутся из кода. Не допускается придумывать `admin`, `moderator`, `teacher` и иные роли, если они не соответствуют фактической модели AsaLab.

Перед реализацией необходимо заполнить матрицу реальными ролями:

| Операция | Guest | Authenticated non-owner | Owner | Privileged role |
|---|---:|---:|---:|---:|
| Открыть каталог | ✓ | ✓ | ✓ | ✓ |
| Открыть public project | ✓ | ✓ | ✓ | ✓ |
| Открыть unlisted, если существует | по фактической ACL | | | |
| Открыть private | ✗ | по фактической ACL | ✓ | по фактической ACL |
| Publish/unpublish | ✗ | ✗ | ✓/по политике | по политике |
| Изменить metadata | ✗ | ✗ | ✓/по политике | по политике |
| Сменить владельца | ✗ | ✗ | только если разрешено | по политике |
| Copy/remix | по фактическому workflow | | | |
| Social write | ✗ | ✓ при разрешении | ✓ | ✓ |
| Moderation action | ✗ | ✗ | ✗, если не privileged | ✓ |

Каждая mutation проверяет права на сервере после разрешения project id. Это обязательная защита от IDOR.

## 8. API

### 8.1. Принцип

Сначала используются или расширяются существующие endpoints.

Запрещено создавать параллельный `/api/public-projects` только потому, что экран в UI называется «Проекты», если существующий `/api/projects` или его фактический аналог способен корректно представить публичную выборку.

### 8.2. Логические операции

ТЗ требует наличие операций, но не навязывает URL:

- list public projects;
- get project detail;
- publish;
- unpublish;
- update publication metadata;
- copy/remix — если существует;
- social mutation — если модуль существует или подтверждён как BUILD.

### 8.3. Контракты

- query/body валидируются на сервере;
- page size ограничен;
- errors следуют фактической конвенции проекта (`400/401/403/404/409/422` там, где применимо);
- расширение response должно быть additive;
- OpenAPI/contract-schema обновляется, если проект её использует;
- list endpoint не допускает N+1 по author/tags/metrics;
- private metadata не попадает в public DTO.

## 9. Данные и миграции

1. Project остаётся source of truth.
2. Новые поля БД добавляются только для подтверждённого gap.
3. Миграции additive и backward-compatible.
4. Миграция должна быть безопасна на существующих данных.
5. Для новых hot-query полей создаются индексы на основании фактических запросов.
6. Запрещено копировать payload в `public_projects` либо аналогичную параллельную таблицу без ADR.
7. Денормализованные counters допустимы только с описанным source of truth и механизмом атомарного обновления/rebuild.
8. Если проект уже имеет audit/event mechanism, publication/moderation должны использовать его.
9. Для любой миграции документируется rollback/forward-fix стратегия.

---

## 10. Социальный слой

Социальные функции не должны превращать первый этап в создание второй социальной платформы.

Перед реализацией отдельно проверяются:

- reactions/likes;
- saves/favorites;
- collections;
- comments;
- follows, если они вообще присутствуют в домене;
- counters;
- moderation hooks.

### Правила

- UI не показывает кнопку/счётчик, если нет настоящего persistent backend;
- реакция должна быть идемпотентной;
- уникальность реакции должна обеспечиваться на backend/DB по фактической модели;
- optimistic UI обязан reconcile с server truth;
- guest не выполняет social mutation, если модель безопасности прямо этого не допускает;
- существующее хранилище saves/collections переиспользуется;
- существующая система comments/moderation переиспользуется;
- если comments отсутствуют, они выносятся в P2 и отдельный ADR/подзадачу вместо скрытого создания большого нового подсистемного блока.

---

## 11. Модерация

Если модерация уже существует — использовать её.

Минимальные требования при наличии публичного UGC:

- hide/takedown не выполняет destructive delete;
- скрытый проект исключается из public discovery;
- moderation mutation доступна только фактической privileged role;
- действие логируется существующим audit mechanism либо минимально необходимым журналом, если gap доказан;
- причина/статус показываются владельцу в соответствии с принятой политикой продукта;
- запрещено hardcode-ить новую роль `admin` ради этого экрана.

---

## 12. Frontend

1. Переиспользовать существующие design tokens, layout primitives и UI-components.
2. Не создавать отдельные версии Card/Viewer без доказанной необходимости.
3. Search/filter/sort state хранится в URL.
4. Состояния loading/error/empty реализуются явно.
5. Media preview грузится лениво.
6. Не prefetch-ить тяжёлый проектный payload всех карточек.
7. Никакие secrets/config tokens не попадают в client bundle.
8. Ошибка renderer отдельного проекта не должна ломать весь каталог.
9. Desktop, tablet и mobile должны использовать одну функциональную модель, а не разные наборы возможностей без продуктовой причины.

---

## 13. Accessibility

Цель: WCAG 2.1 AA для пользовательского сценария раздела.

Обязательно:

- keyboard-only navigation;
- логичный focus order;
- видимый focus;
- labels для controls;
- semantic headings;
- alt text для содержательных изображений;
- корректная семантика статусов/ошибок;
- focus trap + restore для modal/dialog;
- достаточные touch targets;
- контраст через действующие design tokens;
- учёт `prefers-reduced-motion`, если присутствуют анимации.

---

## 14. Безопасность

Перед готовностью feature обязательны проверки:

- IDOR / object-level authorization;
- XSS в title/description/comments/markdown/html;
- media/file validation через существующий upload pipeline;
- ограничения MIME/type/size;
- CSRF, если используемая cookie-auth архитектура этого требует;
- rate limiting для mutation/search, если инфраструктура уже поддерживает его;
- whitelist и bounds для query/filter/sort;
- отсутствие утечки private data через search, count, preview, log или cache;
- SSRF protection, если поддерживаются remote URLs/imports;
- разделение public/private cache keys;
- отсутствие secrets/PII в telemetry и client logs.

---

## 15. Производительность

- каталог всегда пагинирован;
- тяжёлые previews lazy-load;
- используется существующая thumbnail/variant система;
- запрещены N+1 запросы;
- hot listing/filter/sort запросы проверяются по query plan;
- до/после реализации фиксируются измерения ключевых запросов;
- если в репозитории есть performance budget — использовать его;
- произвольный SLA без существующего продуктового основания не придумывать.

---

## 16. Наблюдаемость

При наличии инфраструктуры AsaLab использовать:

- structured application logs;
- request/user/project correlation ids в допустимом формате;
- endpoint latency/status metrics;
- domain events для publish/unpublish/moderation;
- существующий error tracking.

Запрещено писать в logs приватный project payload, secrets и лишние персональные данные.

## 17. Тестирование

### 17.1. Unit

- ACL decisions;
- publication transition validation;
- filter/sort/query parsing;
- social idempotency, если social layer реализован;
- DTO/public projection sanitization.

### 17.2. API / integration

- guest/member/owner/privileged access matrix;
- private project не утечёт через list/detail/search;
- поведение 403/404 соответствует действующей политике;
- publish/unpublish;
- pagination boundaries;
- filter/sort;
- cache/search invalidation, если применимо;
- реальное project persistence хотя бы в одном интеграционном сценарии без mock core domain.

### 17.3. DB

- миграция на непустой базе;
- uniqueness constraints;
- indexes;
- rollback/forward-fix сценарий.

### 17.4. E2E

Обязательные сценарии:

1. Guest открывает каталог и публичный проект.
2. Guest не получает private/unpublished project прямым URL/API.
3. Owner публикует проект; проект появляется в публичном каталоге.
4. Owner снимает публикацию; проект исчезает из public discovery.
5. Фильтры/поиск/сортировка сохраняются после reload и Back/Forward.
6. Mobile critical flow проходит без функциональной деградации.
7. Unsupported/corrupt viewer показывает контролируемое состояние.
8. Существующий Project Hub/editor/save/upload/version/snapshot flow остаётся рабочим.

### 17.5. Accessibility

- автоматизированная проверка;
- ручной keyboard smoke test критического пути.

### 17.6. Regression

Нельзя считать feature готовой, если для неё пришлось ломать существующие project/editor/version/upload сценарии или отключать тесты.

## 18. Acceptance Criteria

**AC-01.** Guest catalog отображает только проекты, разрешённые для публичного просмотра.  
**AC-02.** Private/unpublished проект невозможно получить подменой ID, query params, прямым API, cached URL или поиском.  
**AC-03.** Search/filter/sort state кодируется в URL и восстанавливается.  
**AC-04.** Detail page использует существующий canonical project id и существующие project data.  
**AC-05.** Viewer переиспользует production rendering path/read-only adapters там, где это поддерживается.  
**AC-06.** Owner может publish/unpublish проект только через server-authorized flow.  
**AC-07.** Publish/unpublish не дублирует project payload/model/version history.  
**AC-08.** Каждая mutation имеет server-side role/ownership/object ACL check.  
**AC-09.** Publication version behavior использует существующий snapshot/version subsystem.  
**AC-10.** Social counters/actions появляются только при наличии реального persistent backend.  
**AC-11.** List API пагинирован и не имеет выявленного N+1.  
**AC-12.** Desktop/mobile и keyboard critical flow проходят тестирование.  
**AC-13.** Unit/integration/E2E regression suite проходит.  
**AC-14.** Existing Project Hub/editor behavior не изменён вне явно требуемого scope.  
**AC-15.** `main` не изменяется напрямую; реализация проходит через branch/PR workflow.  
**AC-16.** Все новые domain entities/endpoints имеют доказательство отсутствия подходящей существующей реализации в AS-IS матрице.  
**AC-17.** Production UI не содержит mock counters, fake popularity, test projects или декоративных backend-less действий.

## 19. Этапы реализации

### P0 — Audit / Design Gate

Результаты:

- заполненная AS-IS матрица;
- карта существующих routes/API/entities;
- карта ACL;
- карта snapshot/version semantics;
- список `REUSE / MODIFY / BUILD / DO-NOT-TOUCH`;
- ADR только для действительно новых domain concepts.

**P0 не должен менять production behavior.**

### P1 — Core Projects

Реализуются:

- catalog/query;
- project detail/viewer;
- publish lifecycle;
- ACL/security;
- production states;
- unit/integration/E2E tests;
- необходимая документация API.

P1 должен быть самостоятельным релизным этапом без обязательной зависимости от нового social layer.

### P2 — Social / Moderation / Discovery enrichment

Только после P1 и AS-IS аудита:

- недостающие reactions/saves/collections;
- comments, если одобрены отдельным решением;
- moderation improvements;
- advanced ranking/search;
- дополнительные discovery-механики.

Каждый этап должен быть совместим с существующим Project Hub.

---

## 20. Явно запрещено

- создавать второй/параллельный Project model;
- создавать дублирующую таблицу public project payload без ADR;
- создавать второй snapshot/version stack;
- полагаться на client-only ACL;
- hardcode-ить роли, которых нет в фактической модели доступа;
- показывать fake likes/views/popularity;
- создавать новый endpoint только потому, что так называется экран в макете;
- проводить destructive migration без отдельного migration plan;
- выполнять широкий рефакторинг, не относящийся к scope;
- отключать, удалять или ослаблять тесты ради зелёного CI;
- напрямую пушить реализацию в `main`;
- заменять существующий project editor/service новой подсистемой;
- публиковать private payload в public cache/search;
- делать «временный» обход authorization;
- использовать mock/test data в production UI;
- копировать бизнес-логику ACL/versions между frontend и backend вместо единого server source of truth.

## 21. Definition of Done

Feature считается выполненной только если:

- [ ] AS-IS матрица заполнена конкретными путями/symbols/API;
- [ ] каждое изменение имеет решение `REUSE / MODIFY / BUILD`;
- [ ] нет параллельной модели проекта;
- [ ] нет параллельной системы версий;
- [ ] server-side ACL покрывает все mutations;
- [ ] private/unpublished data не утечёт через list/detail/search/cache;
- [ ] API contracts/OpenAPI обновлены, если они используются проектом;
- [ ] migrations проверены на существующих данных;
- [ ] rollback/forward-fix описан;
- [ ] unit/integration/E2E tests проходят;
- [ ] lint/typecheck/build проходят;
- [ ] keyboard/mobile critical flows проверены;
- [ ] performance check выполнен;
- [ ] observability переиспользована/добавлена в соответствии с архитектурой;
- [ ] существующие Project Hub/editor/version/upload сценарии не регрессировали;
- [ ] документация скорректирована по фактическим route/API semantics;
- [ ] изменения прошли branch/PR workflow без прямого изменения `main`.

## 22. Правило для исполнителей и кодовых агентов

> **UX-спецификация описывает желаемое поведение, но не является доказательством существования backend-функции. Перед реализацией каждого требования исполнитель обязан найти существующую реализацию в коде. Если она есть — использовать её. Если частичная — расширить. Если отсутствует после проверки релевантных модулей — только тогда проектировать дополнение.**

Перед каждым `BUILD` исполнитель обязан показать доказательство, что `REUSE` и `MODIFY` невозможны или некорректны.

Если документация противоречит устойчивому инварианту уже работающего кода, запрещено молча обходить код. Необходимо зафиксировать конфликт в ADR/PR note и принять явное архитектурное решение.

---

## 23. Обязательные доказательства в implementation PR

PR должен содержать:

1. заполненную AS-IS матрицу;
2. список затронутых файлов/модулей;
3. schema/API diff;
4. объяснение каждого `BUILD`;
5. permission-test matrix;
6. результаты unit/integration/E2E;
7. lint/typecheck/build status;
8. query-plan/performance evidence для каталога;
9. desktop/mobile screenshots или короткое подтверждение E2E;
10. migration + rollback/forward-fix note, если менялась БД;
11. перечень переиспользованных существующих Project Hub/renderer/version/media/ACL механизмов;
12. подтверждение отсутствия прямого изменения `main`.

## 24. Итоговый критерий архитектурного качества

Новый раздел должен выглядеть для пользователя как отдельный общественный продукт, но для архитектуры AsaLab оставаться **ещё одной проекцией существующего домена проектов**, а не второй системой проектов.

Если для реализации публичного каталога приходится копировать project payload, version history, ACL, renderer или upload logic, решение считается архитектурно неверным до отдельного доказанного ADR.
