# ASA Lab: оптимизация и обновление рабочей Главной

Согласованный план реализации. Это требования, а не отчёт о готовности интерфейса.
Создание документа не разрешает публикацию пользовательских данных, подключение
сторонних сервисов, изменение working database или обновление production.
Активные задачи, ограничения и состояние направлений читаются только из
`docs/execution/current.yaml`. Статусы реализации здесь не дублируются.

Короткий маршрут реализации: требования — §1.1, навигация — §3,
последовательность — §4.3, состояния страницы — §4.4, оптимизация и замеры —
§4.5, приёмка — §4.6 и §11. Это один пакет продукта, разделённый на проверяемые
срезы, а не поручение переписать весь портал. Разделы 5–9 — дальнейшее развитие;
публичная социальная платформа не является условием выпуска новой Главной.

Переходный первый выпуск: «Проекты» открывает существующую галерею с её
текущими правами. Публичный доступ к работам не расширяется переименованием
кнопки. Общедоступные курсы появляются в шапке вместе с работающим каталогом,
не как заглушка. Проверки БД выполняются в отдельном временном PostgreSQL, а не
в дополнительной базе рабочего кластера: provision-скрипт меняет роль кластера.

## 1. Цель и границы

Пользователь должен понимать три самостоятельных действия:

1. **Создавать:** работать со своими моделями, схемами и будущими средами.
2. **Исследовать:** открывать опубликованные проекты, пробовать, сохранять,
   обсуждать и брать за основу.
3. **Учиться:** выбирать общедоступные курсы и продолжать своё обучение.

Верхняя навигация открывает общедоступные каталоги, боковая — личную работу.
Авторизация нужна для персональных действий, но не должна быть обязательной
для просмотра материалов, явно разрешённых к открытому распространению.
Обычный вход с начальной страницы приводит на личную Главную.

В первый пакет не входят Scratch, инженерный CAD, ИИ, личные сообщения,
подписки на авторов, платёжная система и перенос production. Они не должны
задерживать исправление навигации и создания проектов.

### 1.1. Полный обязательный пакет Главной после входа

Ближайший результат — качественная рабочая Главная на компьютере и телефоне,
а не реализация всей социальной платформы. Для этого пакета агент читает этот
раздел, разделы 3–4 и проверки раздела 11. Разделы 5–9 задают будущие границы,
но не являются условием для завершения личной Главной.

| Требование владельца | Принятое правило первого пакета |
| --- | --- |
| После входа попадать на Главную | Обычный вход через любой доступный канал и регистрация ведут на `#/home`, не в настройки. Reload редактора и прямое приглашение — отдельные сценарии |
| Компьютерная верхняя панель остаётся | Сохраняются шапка, бренд, действия создания и аккаунта. Публичные направления сверху, личные слева; не удалять шапку ради мобильной версии |
| На телефоне нужен понятный «Создать» | Слово не скрывается. Плюс допустим рядом с текстом, не вместо него |
| Разделы на телефоне раскрываются | Кнопка меню у логотипа открывает вертикальную панель, горизонтальная полоса разделов убрана |
| Убрать кружок на левой аватарке | Левое фото и имя остаются. Убираются накладной кружок со стрелкой и открытие того же account menu из левой фотографии |
| Оставить доступ к настройкам | Меню аккаунта открывается маленькой правой аватаркой. На телефоне настройки также доступны в раскрытой навигации |
| Заменить ASA 3D понятным названием | Название среды — «3D-моделирование», название создаваемого документа — «3D модель N». Внутренний `three-d` и существующие имена не меняются |
| Создавать без посредника | Верхняя кнопка открывает только два доступных типа; выбор сразу создаёт проект и открывает редактор. Большой диалог с именем и плитками не показывается |
| Не показывать недоделанные среды | Никаких «Скоро», Scratch/CAD/ИИ-заглушек в меню создания |
| Последовательные имена | Сервер назначает «Электрическая цепь N» / «3D модель N» отдельно по владельцу и среде, начиная с 1 для владельца без таких работ |
| Плюс на полке сразу открывает нужную среду | Одна и та же операция создания с заранее выбранной средой, без повторного выбора |
| Создание доступно при любом числе проектов | Плитка/действие не исчезает при четырёх работах; не ломает сетку при заполненной полке |
| Главная не перегружена | Небольшой заголовок и две полки недавних работ, без повторной рекламы, больших пустот и социальных счётчиков |
| Все проекты нужного типа доступны | «Все модели»/«Все схемы» открывают список с фильтром; сохраняются Back, фильтр и место просмотра |
| Игры не возвращаются в проекты | Шахматы/шашки остаются в Играх; игры не засчитываются в видимые полки и их число |
| Дальнейшие страницы предусмотрены | Исследовать, Курсы, Сохранённое, Моё обучение имеют разные назначения. Пустые новые страницы и ложные публичные обещания не выпускаются |
| Сохранность и надёжность | Не теряются существующие проекты, права, классы, админ-доступ; нет двойного создания, ложного «Сохранено» или подмены аккаунта при смене контекста |

Кнопку подтверждения MAX не возвращать пользователю с уже связанной учётной
записью. Проверить этот сценарий в общем переходе после входа, не переделывая
каналы авторизации в рамках визуальной задачи. Индикатор подтверждения аккаунта
не путать с удаляемым кружком-стрелкой на левой фотографии.

## 3. Информационная архитектура

### 3.1. Верхняя панель

Рекомендуемые названия: **Исследовать** и **Курсы**.

- Логотип ASA Lab: для гостя — публичная главная, для вошедшего — личная Главная.
- Исследовать: проекты, явно опубликованные для открытого просмотра.
- Курсы: открытый каталог учебных курсов, не авторская библиотека преподавателя.
- Создать: меню реально доступных сред с кратким описанием каждой.
- Уведомления: только после появления действующей системы; не показывать фиктивный ноль.
- Аватар и меню аккаунта; для гостя вместо них — вход/регистрация.

На главных страницах каталогов поясняющий заголовок устраняет неоднозначность:
«Проекты сообщества» и «Каталог курсов». В верхней панели достаточно коротких слов.
Не добавлять постоянные пункты «3D», «Электроника», «Scratch», «ИИ», «CAD»:
типы сред живут в фильтрах и меню создания, иначе шапка не выдержит расширения.

Поиск в первом пакете локальный: проекты ищутся в Исследовать, курсы — в Курсах,
личные работы — в Моих проектах. Общий поиск допустим позже, когда реально ищет
по нескольким типам и явно группирует результаты. Нынешнюю лупу-переход убрать.

Для компьютера шапка — три устойчивые области: бренд, общие направления,
создание/аккаунт. Не удерживать центральную колонку жёстким минимумом 480 px,
как сейчас: на промежуточных ширинах она конкурирует с остальными кнопками.
При нехватке места навигация сворачивается целиком, а текст кнопок не мельчает.
На широком экране сохраняется постоянный sidebar; на узком — drawer. Его ширина,
высота шапки и отступ содержимого должны использовать общие layout-параметры,
а не несколько независимых фиксированных значений в разных CSS-файлах.

Предварительный ориентир: шапка 56–64 px, боковая панель 220–240 px; окончательно
подтвердить на реальном интерфейсе. Область контента не прячется под шапкой и
не оставляет лишний отступ после сворачивания sidebar. Полки идут друг под другом:
3D, затем электроника, а не две узкие колонки разных сред рядом.

### 3.2. Личная боковая панель

Основные пункты: Главная, Мои проекты, Моё обучение, Классы, Сохранённое, Игры.
Преподавателю дополнительно доступна группа авторских инструментов «Курсы и
задания». Админка показывается только при подтверждённых сервером полномочиях.
Внизу — помощь. Настройки и выход находятся в меню аккаунта; на телефоне они
также доступны в нижней группе общей раскрывающейся панели.

Левый профиль — компактная идентификационная область с фото и именем без
выпадающего account menu. Правый аватар — единственный desktop-триггер этого
меню. Удалить слева `portal-avatar-upload-badge`, соответствующий обработчик
и невидимую фокусируемую кнопку, а не только скрыть нарисованную стрелку.
Полностью удалять левую аватарку владелец не просил. Загрузку/смену фотографии,
выход и переключение личного/школьного пространства сохранить в настройках
и правом меню. Оба отображения используют один подтверждённый источник аватара.

Не дублировать Исследовать/Курсы слева на компьютере. «Моё обучение» означает
мои занятия и прогресс, а «Курсы» сверху — выбор из общего каталога.
«Сохранённое» содержит мои подборки, а не второй экземпляр галереи.
«Мои публикации» — фильтр/вкладка в Моих проектах, не ещё один верхний раздел.

Гость видит публичные каталоги, но не пустые личные разделы. Переход к личному
действию объясняет необходимость входа и запоминает намерение без выполнения
действия до авторизации.

### 3.3. Телефон и планшет

- Верхняя строка: кнопка меню, логотип, подписанная кнопка «Создать» и компактный аккаунт.
- Когда доступны реальные уведомления, не втискивать пятую кнопку: на узком
  экране отдельный пункт уведомлений переносится в меню, индикатор — к его кнопке.
- Меню открывает одну боковую панель поверх страницы. В ней две короткие группы:
  «Открыть» (Исследовать, Курсы) и «Моё» (личные разделы).
- После выбора панель закрывается, текущий раздел выделен; состояние раздела
  и прокрутка восстанавливаются при возврате.
- Никакого второго горизонтального списка разделов и дополнительной нижней
  навигации в первом пакете: не создавать сразу три способа перехода.
- Работа клавиатурой, Escape, закрытие по фону, возврат фокуса, блокировка
  прокрутки фона. Для навигационных пунктов — настоящие ссылки; при использовании
  модального drawer — корректное управление фокусом и недоступный фон.
- Проверить 320, 360, 390, 768, 1024 и 1440 CSS px, портрет/альбом, 200% zoom,
  длинные имена, экранную клавиатуру и safe-area. Основные touch targets — 44 px.
- Спокойная анимация без прыжков контента; учитывать reduced motion. Цвет,
  шрифт, отступы и фокус общие для публичного и личного пространства.

Современность означает ясную и быструю работу, а не больше карточек, градиентов,
баннеров, счётчиков и анимированных украшений.

## 4. Главная и быстрое создание

На личной Главной — две полки: «3D-моделирование» и «Электроника».
В каждой недавние работы и постоянное действие создания. На компьютере
количество карточек определяется доступной шириной, на узком телефоне — один
читаемый столбец, на более широком экране допустимы два. Большой пустой баннер
не нужен. Ошибка загрузки не должна отображаться как отсутствие проектов.

Меню «Создать» содержит только рабочие варианты:

- 3D-модель — моделирование из объёмных фигур;
- Электрическая цепь — сборка и проверка электронных схем.

Выбор типа сразу создаёт личный черновик и открывает редактор. Плитка внутри
полки вызывает тот же механизм с уже выбранным типом. Имя назначает сервер:
«3D модель 1», «Электрическая цепь 1» и далее отдельно по владельцу и среде.
В классе сохраняется отдельный явный контекст создания; глобальная кнопка не
должна незаметно создавать работу в случайном классе или аккаунте.

Переиспользовать серверную нумерацию и блокировку транзакции. Проверить повторы
с одинаковым idempotency key, два устройства, сбой ответа после успешной записи,
архивирование, корзину и пользовательское переименование. Номер не считать
по длине списка в браузере. Не обещать уникальность произвольных названий:
название не является идентификатором проекта.

Результат операции — project ID и фактическое имя от сервера. До получения
результата показывать «Создаём…», исключать повторное создание, а при ошибке
давать понятный повтор той же операции. Просмотр публикации не создаёт черновик.
Переименование существующих работ, смена moduleKey, формата документа и
редакторного ядра для этой задачи не нужны.

«Все модели»/«Все схемы» сохраняют фильтр в адресе. Возврат из редактора ведёт
на исходную полку или список. Обычный новый вход через доступный способ приводит
на Главную. Reload редактора и восстановление сессии не должны выбрасывать
из работы; приглашения и прямые ссылки обрабатываются как отдельное намерение.

### 4.1. Найденные риски первого пакета

По чтению текущей реализации, без инъекции ошибок в production:

- В `CreatorHomePage` одна ошибка используется для загрузки и действий карточек.
  Неуспешная публикация/архивация может заменить всю полку экраном ошибки.
  Разделить page load error и локальную ошибку действия, сохраняя видимые работы.
- `load()` сбрасывает проекты в `null` даже при повторном обновлении. Это
  снова включает skeleton и может создавать ненужное мигание после действий.
  При фоновой сверке оставлять уже известные карточки, менять только нужные.
- В `load()` результат `myGalleryProjects` применяется до проверки
  `loadSequence`. Поздний ответ старого контекста может обновить метки публикаций.
  Проверять актуальность до любого setState; смена principal/workspace отменяет
  старые чтения. Ответ уже отправленной записи не применять к новому аккаунту.
- Главная ждёт `Promise.all` с дополнительными метками публикаций. Задержка
  необязательного запроса не должна удерживать показ личных проектов.
- `listForActor` возвращает все активные работы, а клиент оставляет четыре на
  среду. Это риск роста нагрузки, не измеренное утверждение о текущей медленности.
- Диалог создаёт новый idempotency key при каждом submit. Серверная поддержка
  повторов существует, но клиент не сохраняет один ключ для повтора после
  неопределённого сетевого исхода.
- В `e2e/creator-portal.spec.ts` ещё есть ожидание шахматной полки на Главной.
  Оно противоречит принятому переносу игр. Обновить сценарий по требованиям,
  не удалять проверку целиком и не объявлять старый gate достаточной приёмкой.
- Дублирование карточки на Главной вызывает `crypto.randomUUID()` напрямую,
  хотя есть совместимый `newClientId()`. Проверить этот путь на HTTP-адресе
  школьной LAN: не все контексты браузера предоставляют randomUUID. Использовать
  существующий безопасный helper, а не Math.random и не новое глобальное решение.
- Редакторы уже загружаются через lazy в `ModuleEditorHost`, а оболочка первого
  кадра и error boundaries уже существуют. Не реализовывать их второй раз.
  В `App.tsx` многие второстепенные страницы импортируются статически — это
  кандидат на измерение стартового набора, не доказанное число лишних килобайт.
- `bundle:check` проверяет размеры отдельных JS-файлов, но не сумму всего
  загружаемого при открытии Главной графа зависимостей. Одного зелёного результата
  недостаточно, чтобы доказать ускорение: перенос байтов в ещё один стартовый
  chunk сам по себе ничего не экономит.

Отдельный приоритетный риск сохранности: `recordClassroomActivity` подавляет
исключение SQL внутри той же транзакции, где создаётся/сохраняется проект;
`withTenantContext` затем вызывает COMMIT и возвращает результат callback.
После ошибки SQL обычный JavaScript catch не восстанавливает транзакцию
PostgreSQL. Поэтому нельзя считать эту запись действительно независимой от
сохранения: возможен откат либо ложное подтверждение результата. Это вывод
о риске по коду, не установленная причина прежних потерь и не обнаруженная
потеря текущих данных. Первый технический шаг — fault-injection тест на
изолированной БД, затем минимальная правка границы транзакции: проверяемый
commit и savepoint/отдельная надёжная доставка необязательного события.
Ошибки журналирования нельзя скрывать без диагностического следа.

### 4.2. Серверные контракты, которые нужно сохранить и усилить

1. **Владелец из сессии.** Аккаунт и StudentSeat используют существующий
   principal/context. Не принимать владельца/tenant из тела запроса. Права
   проверяются на каждом чтении, создании, сохранении и получении изображения,
   а не только наличием кнопки в меню.
2. **Одна операция создания.** Переиспользовать `POST /api/projects`, не вводить
   разные реализации для главной, шапки и мобильного интерфейса. Для
   `automaticTitle=true` разрешить отсутствие имени в новом клиенте и назначать
   его сервером; существующий ручной контракт сохранить совместимым. Проверить
   режим автоматического имени до требования непустого пользовательского title.
3. **Повторы и два устройства.** Один ключ на намерение; повтор с тем же телом
   возвращает тот же project ID, другое тело с тем же ключом даёт конфликт.
   Неопределённый исход после обрыва проверяется повтором того же запроса.
   При необходимости пережить reload хранить только несекретное описание
   незавершённой операции в привязке к аккаунту/контексту, не токены сессии.
4. **Атомарная запись.** Проект, начальный черновик и необходимые связанные
   данные создаются полностью либо не создаются. Успех выдаётся после
   подтверждённого commit. Нельзя показать «Готово», если PostgreSQL откатил запись.
5. **Конкурентное сохранение.** Сохранить `baseRevision`/`mutationId` и текущую
   проверку версии. Конфликт двух вкладок не разрешать молчаливой перезаписью;
   несохранённый локальный документ не терять при навигации.
6. **Ограниченная выдача Главной.** Добавить совместимый ограниченный read model:
   по каждой активной среде до четырёх работ плюс `hasMore` или точный total.
   Не применять общий LIMIT ко всем средам, иначе одна вытеснит вторую.
   Для полного списка — фильтр модуля и стабильная пагинация по времени + ID.
   Не добавлять SQL-запрос на каждую карточку; не загружать полные документы
   редакторов ради полок. Индексы вводить по измерению плана запроса на тестовых данных.
7. **Единый реестр.** Тип, пользовательское название, доступность и стартовый
   документ берутся из существующего module-sdk. Новый viewer/Scratch не нужен
   для ускоренного создания 3D/электроники. Недоступный тип сервер отклоняет,
   даже если запрос отправлен вручную.
8. **Ограничение злоупотреблений.** Проверить действующие CSRF/origin и лимиты
   записей; при необходимости добавить ограничения по principal и операции,
   а не считать всех учеников за школьным NAT одним ботом. Логи без токенов
   и полных пользовательских документов. Идемпотентность не заменяет rate limit.
9. **Наблюдаемость.** Учитывать один успешный create после commit; повторы не
   удваивают счётчики. Отделять ошибки создания, загрузки списка, конфликты
   сохранения и запуск среды. Подробная аналитика и новый dashboard не входят
   в визуальный пакет, но существующие события не должны пропасть.

активного состояния. Каждый срез проверяется до следующего; косметические правки
не откладывают исправление подтверждённого дефекта сохранности.

| Подэтап | Реализация | Доказательство завершения |
| --- | --- | --- |
| 0. Исходное состояние | Зафиксировать SHA, desktop/mobile кадры, переходы, размеры и запросы по §4.5; подготовить синтетические данные и воспроизводящие тесты | Отделены подтверждённые дефекты, гипотезы и уже работающие механизмы; production не используется как тестовая база |
| 1. Запись и повтор | Воспроизвести транзакционную ошибку в изолированном PostgreSQL; исправить границу ошибки/commit; совместимо усилить automaticTitle и повторы | После успешного ответа независимое чтение видит тот же проект/документ; rollback не выдаёт успех; два повтора дают один ID, два разных намерения — два проекта |

| 5. Измеренная оптимизация | По исходным замерам облегчить стартовую загрузку, миниатюры, CSS и повторные чтения; проверить освобождение ресурсов | Есть сравнение до/после на одинаковых условиях; улучшено найденное узкое место, соседние сценарии не ухудшены; бюджеты не подняты ради PASS |
| 6. Общая приёмка | Обновить устаревшие тесты, прогнать контракты, реальную БД и браузерные сценарии, показать результат владельцу | Пройден §4.6; есть реальные desktop/mobile кадры, а не только макет; непроверенные каналы/устройства явно отмечены |

Срезы 1–5 не меняют документы, ядра и алгоритмы электроники/3D. Общие
`App.tsx`, `api.ts`, карточки и CSS затрагивать только после проверки пересечений
с работой других исполнителей. Не превращать изменение Главной в чистку всей
кодовой базы, замену роутера, дизайн-системы, сборщика или библиотек состояния.

### 4.4. Контракт состояний и отсутствие мерцания

| Состояние | Что видит пользователь | Чего быть не должно |
| --- | --- | --- |
| Первый запуск, сессия ещё не проверена | Уже существующая нейтральная оболочка; после проверки — нужный маршрут | Вспышка старой landing/login страницы или предыдущего аккаунта |
| Первая загрузка проектов | Шапка, навигация и skeleton внутри полок с устойчивыми размерами | Вся страница исчезает; ошибка ошибочно названа пустым списком |
| Проектов нет | Название среды, короткое приглашение и понятное создание | Большой рекламный баннер или отключённая среда «Скоро» |
| Проекты есть | Недавние карточки, создание и отфильтрованный полный список | Игры в полках, исчезновение создания, только hover-действия на телефоне |
| Повторная сверка | Существующие карточки того же аккаунта остаются; обновляется нужная область | Полный skeleton и скачок прокрутки после каждого действия |
| Ошибка действия или вторичного запроса | Сообщение рядом с действием, безопасный повтор; остальные карточки доступны | Удаление всей полки, ложная отметка публикации, автоматическое повторение записи с новым ключом |
| Открытие среды | Загрузка только выбранного редактора; при сбое доступен возврат | Старая главная в промежуточном кадре, бесконечная перезагрузка, исчезновение сохранённой работы |
| Смена аккаунта/пространства, logout, 401 | Старые персональные данные очищены; поздние ответы отброшены | Сохранение старых карточек ради плавности или использование чужого pending-create |

Обычный логин, возвращение на открытую вкладку и прямое приглашение различаются
в маршрутизации. Авторизация по прямому намерению не должна автоматически
повторять запись/публикацию. Ошибка сети не равна подтверждённому logout.

Не удалять `seo-fallback` целиком только потому, что раньше он мерцал: проверить
первый кадр, noscript и публичный HTML отдельно. Сохранить действующую защиту
первого кадра. При недоступном начальном JS или chunk после обновления нужен
понятный выход из ошибки, а не бесконечный логотип. Повтор/обновление не должны
молчаливо уничтожать несохранённый документ; автоматический reload-цикл запрещён.

### 4.5. Оптимизация как измеряемая часть реализации

**Протокол исходного замера.** Использовать локальную production-сборку
с изолированными тестовыми данными, не скорость Vite HMR и не публичный маршрут
через VPN как доказательство качества кода. Порты и запуск — по AGENTS.md;
не останавливать работающий Docker ради замера. Если безопасного стенда нет,
вынести проверку в изолированный CI, а не подключить тесты к live БД.

Зафиксировать revision, браузер/устройство, viewport, CPU/network-профиль,
набор данных и состояние кэша. Сравнить не менее пяти холодных и пяти тёплых
проходов до/после: медиана и диапазон, а не самый удачный кадр. Отдельно:
восстановленная сессия → Главная, обычный вход → Главная, возврат из редактора,
создание каждого типа. Внешнюю задержку MAX не приписывать рендерингу Главной.

| Направление | Что измерить | Изменение при подтверждённой проблеме |
| --- | --- | --- |
| Стартовый JS/CSS | Полный граф запросов до готовых полок, несжатые и переданные байты, выполнение JS, long tasks | Отложить второстепенные страницы, не заставляя Главную ждать аккаунт/галерею/авторские инструменты. Сохранить существующий lazy редакторов; не делать eager preload всех сред |
| API и запросы | Число запросов, время/размер ответа, холодный и повторный вход, блокирующие зависимости | Основные данные отдельно от меток публикаций; дедупликация чтений в одном контексте; компактная выдача полок без загрузки всех работ |
| База | План SELECT и время на малом/большом синтетическом наборе, ограниченность ответа, отсутствие N+1 | Индексы только под подтверждённый план; параметры, допустимые сортировки, серверный предел limit и стабильный cursor; без изменения tenant/RLS |
| Миниатюры/аватар | Какие изображения действительно запрошены Главной, их размеры/байты, скачки сетки | Разрешённые миниатюры подходящего разрешения, width/height или aspect-ratio, lazy ниже первого экрана. Не задерживать видимую основную картинку; не менять owner assets/SVG и исходные пользовательские документы |
| Повторные переходы | Главная → 3D/электроника → Главная, 20 циклов после прогрева; Workers, таймеры, WebGL и память | Устранить конкретно воспроизведённые незакрытые ресурсы; не считать нормальный одноразовый кэш утечкой и не переписывать редактор без доказательства |
| Обновление и кэш | Старый открытый браузер + новая сборка, истёкшая сессия, смена пользователя | Совместимость запросов, безопасная обработка отсутствующего chunk; приватные API/медиа не попадают в общий кэш. Не вводить service worker или хранение приватных списков в localStorage ради баллов |

Общую `ProjectCard` переиспользовать. Изменение её размеров/действий проверить
также в Моих проектах и классах; стили новой Главной ограничить её оболочкой.
Удалять старый CSS/компонент только после проверки импортов, прямых ссылок,
динамических классов и ролей. Не добавлять `memo`, виртуализацию восьми карточек,
новую cache-библиотеку или глобальную очистку зависимостей без измеренного повода.

**Измеряемые ориентиры, не обещание уже достигнутых показателей:**

- Для полной загрузки страницы: LCP ≤ 2,5 с, CLS ≤ 0,1; для взаимодействий
  ориентир INP ≤ 200 мс. Это ориентиры Core Web Vitals; полевой результат
  оценивается по p75 отдельно для desktop/mobile. Пять лабораторных прогонов
  не доказывают полевой p75, Lighthouse TBT не является измеренным INP.
- Для SPA-перехода измерять отдельно время до видимых и доступных действий
  полок: один LCP загрузки документа этого не подтверждает. Открытие меню и
  создание проекта проверять взаимодействием, а не только screenshot.
- До начала оптимизационных правок записать числовые бюджеты стартовых байтов,
  API и готовности полок по baseline. Сохранить существующие лимиты
  `tools/check-web-bundle-budget.mjs`; если меняются chunk-границы, дополнить
  проверку суммарного стартового графа, а не спрятать размер за новым именем.
- Рабочие данные: 0, 1, 4, 5 и 1000 личных работ с неравным распределением по
  двум средам, отдельно архив/корзина/игры. На Главной максимум четыре работы
  на среду плюс создание. Размер списка не должен расти пропорционально всей
  истории. Для «есть ещё» предпочтителен ограниченный запрос, не дорогой total.
- Школьная проверка: до 20 синтетических сессий с постепенным увеличением
  нагрузки на изолированном стенде; число успешных уникальных созданий совпадает
  с числом записей. Сравнить задержки и ошибки; p95 указывать только с числом
  запросов и достаточной выборкой, не вычислять над пятью посещениями.

Лабораторный HTTP LAN нужен в дополнение к localhost: они различаются доступными
браузерными API. Не менять системный bind, VPN, DNS или FRP ради этой проверки.
Школьный IP не заменяет идентификатор пользователя; существующие события
запуска/создания не исчезают после оптимизации, повторы не увеличивают счётчик.

### 4.6. Когда первый пакет действительно готов

1. Выполнена вся таблица §1.1, включая левую аватарку, слово «Создать», оба
   способа прямого создания и отфильтрованные списки. Показаны реальная пустая
   и заполненная Главная на телефоне и компьютере, открытое меню и drawer.
2. Fault-injection на настоящем тестовом PostgreSQL проверяет ошибку побочного
   события и commit, независимое повторное чтение, двойной запрос и потерянный
   ответ. Unit mock не подменяет эту проверку. Несохранённые правки и конфликты
   двух вкладок не исчезают при переходах.
3. Замедленные/переставленные ответы, недоступные метки, 401, сбой chunk и
   повторная загрузка не приводят к старому экрану, чужим данным, дублям или
   бесконечному loader. Фоновое сохранение карточек допустимо только в том же
   авторизованном контексте.
4. Есть таблица замеров до/после и артефакты. Если выигрыш не измерен, так и
   написать; нельзя заменить результат новым размером кнопок или PASS unit-тестов.
5. Проверены роли, открытие прежних проектов, save/reload, Игры, классы, задания,
   админка, Back и прямые ссылки. Доступные способы входа проверены; если MAX
   проверен только mock-сценарием, это не живой end-to-end вход владельца.
6. После отдельного разрешения на поставку есть финальный CI и подтверждение
   фактического runtime. До этого результат называется локальным, даже если
   он уже находится в GitHub. Никакого обещания «падений больше не будет»:
   выпуск подтверждает конкретные сценарии, данные, бюджеты и способ восстановления.

## 5. Исследовать: от картинки к действующему проекту

### 5.1. Лента

- Сетка обложек с единым соотношением сторон, названием, публичным именем автора
  и типом среды. Карточка целиком понятна как переход, отдельные реакции не
  должны случайно открывать страницу.
- Фильтры по среде и теме, поиск, сортировки «Новые», «Популярные», «Выбор редакции».
- Пагинация/«Показать ещё» с сохранением фильтра и места при возврате. Не
  устанавливать бесконечную прокрутку без доступного конца и восстановления.
- В ленте лёгкие миниатюры с заданными размерами и ленивой загрузкой, а не
  десятки запущенных редакторов, WebGL-контекстов или симуляторов.
- Никакой пустой карточки экспериментальной среды. Ошибки API и недоступная
  публикация отображаются отдельно от пустых результатов поиска.

### 5.2. Страница опубликованной работы

Главное место занимает интерактивный просмотр, а не текстовая боковая колонка.
Рядом/ниже — название, автор, описание, инструкция, лицензия, исходный автор
ремикса и действия. На телефоне viewer первым, затем компактные действия,
описание и обсуждение; fullscreen возвращается в ту же публикацию.

| Тип | Просмотр | Действие «Взять за основу» |
| --- | --- | --- |
| 3D | Вращать, приближать, осматривать опубликованную модель | Свой независимый проект из опубликованной версии |
| Электроника | Осматривать схему, запускать/останавливать расчёт, пользоваться поддерживаемыми входами | Своя схема с исходным авторством |
| Блочное программирование, позже | Запуск/стоп сцены, управление и просмотр блоков | Свой проект с сохранённой цепочкой происхождения |
| Будущая среда | Только явно заявленные и проверенные возможности viewer | Только если формат, права и копирование поддержаны |

Не открывать чужой редактор с правом записи. Viewer работает с разрешённым
опубликованным снимком; локальные изменения входов симуляции исчезают после
сброса и не вызывают autosave оригинала. Копирование — отдельное явное действие,
после которого открывается собственный редактор. Личные исходники, история
черновика и данные класса не попадают в публичный ответ.

Принцип Scratch, который стоит перенять: посмотреть результат, разобраться,
создать свою версию с указанием происхождения. Не требуется копировать его
дизайн, персонажей или все социальные функции.

### 5.3. Публикация и доступ

Разделить состояния доступа и модерации. Черновик, опубликованная версия,
ограничение «по ссылке», публичная видимость и скрытие модератором — не одно поле.

- Сам факт создания, сохранения или копирования не публикует работу.
- Обновление черновика не заменяет опубликованную версию без явного действия.
- Уже размещённые внутри ASA Lab работы не открывать всему интернету автоматически:
  нужна отдельная проверка/подтверждение новой аудитории.
- «По ссылке» не равнозначно «только авторизованным». Перед внедрением определить
  точную аудиторию и доступ к документу/медиа; по умолчанию не индексировать.
- Отзыв публикации должен закрывать выдачу документа и медиа и инвалидировать
  управляемый кэш. Уже скачанные третьими лицами данные гарантированно отозвать нельзя.
- Копия принадлежит новому автору; её жизненный цикл отличается от закладки.
  Снятая с публикации работа не доступна по старой закладке, но это не удаляет
  ранее разрешённую независимую копию. Исходное авторство не теряется.

Существующие session/educator/RLS guards не снимать. Для анонимного просмотра
спроектировать ограниченную выдачу опубликованных данных и отдельные DTO,
проверяемые на сервере. Не менять tenant-модель и не ослаблять текущие политики.
Необходимые изменения доступа/аддитивные миграции — отдельный согласованный срез;
при конфликте с политикой репозитория до реализации требуется решение владельца.

### 5.4. Реакции, закладки и просмотры

- Сердце: публичное «Нравится», один голос от одного вошедшего участника,
  серверная уникальность; повтор запроса не удваивает голос.
- Закладка/звезда: личное сохранение в подборку. Не вторая одинаковая реакция.
  В первом варианте число чужих сохранений не показывать.
- «Выбор редакции»: отдельная редакционная отметка с ограниченной ролью,
  не право любого преподавателя распоряжаться всей платформой.
- Публичный отрицательный рейтинг не включать в первый запуск; проблемы
  отправляются через жалобу. Судьбу существующей реакции «Ого» определить явно,
  не удалять накопленные данные молча.
- Просмотр считать после успешной загрузки страницы публикации и её содержимого,
  не по попаданию карточки в ленту. Запуск симуляции — отдельное событие.
- Предлагаемое правило дедупликации просмотров: публикация + viewer key + сутки UTC.
  Для вошедшего это внутренний principal, для гостя — ограниченный first-party
  идентификатор без fingerprinting. Это оценка просмотров, не доказательство
  количества уникальных людей; отсутствие cookie снижает точность.
- Один школьный IP не означает одного пользователя. IP не является ключом
  уникальности; технические сведения не показываются в публичном профиле.
- Не считать собственные просмотры/проверки автора в рейтинге, отделять известные
  crawler/автоматические запросы. Антинакрутка не даёт абсолютной гарантии.
- Популярность считать за явно заданный период, а не только за всё время.
  Сначала Новые/редакционный выбор/простая прозрачная сортировка; персональные
  рекомендации и непрозрачный ИИ-рейтинг не нужны для первого выпуска.

## 6. Курсы: общий каталог и личный прогресс

Общий каталог курсов и библиотека материалов преподавателя остаются разными
входами в существующую учебную модель, а не двумя независимыми LMS.

Публичная карточка: название, обложка, авторское публичное имя, предмет/среда,
уровень, ожидаемые навыки и продолжительность только при наличии данных.
Фильтры: тема, среда, уровень. Не придумывать отзывы, часы и число учеников.

Страница курса: чему научусь, что нужно знать, программа, доступные для
предпросмотра уроки, автор, условия доступа, действие «Начать курс».
Для уже записанного участника — «Продолжить». После начала курс появляется
в «Моём обучении», а прогресс не хранится в общем каталоге.

Нужно определить и реализовать самостоятельную запись без фиктивного класса,
с опорой на существующие CourseVersion/CourseRun/участие/прогресс и контракт
`COURSES_AND_LEARNING_IMPLEMENTATION_PLAN.md`. Повторная запись идемпотентна.
Изменение авторского черновика не переписывает курс, который уже проходит ученик.
Для места ученика без самостоятельного аккаунта отдельно определить разрешённые
курсы и политику преподавателя; не обходить права созданием произвольного аккаунта.

Каталог преподавателей не превращать в публичный удалением проверки роли.
Публичность курса, право на копирование преподавателем, назначение классу и
право ученика самостоятельно начать курс — независимые решения.

На старте не вводить оплату, рейтинги курсов и сертификаты без реальных правил.
Уведомления о заданиях и результатах относятся к личному обучению, не к публичной ленте.

## 7. Социальные функции и безопасность участников

### 7.1. Комментарии

Запускать отдельным этапом после готовности модерации и назначения ответственного:

- Только под опубликованными работами, ответы максимум в один дополнительный уровень.
- Жалоба на проект/комментарий/публичный профиль, очередь рассмотрения в админке,
  скрытие, восстановление, ограничение комментирования, журнал решений.
- До налаживания модерации — премодерация комментариев новых участников;
  при отсутствии ответственного комментарии остаются выключены.
- Лимиты частоты/длины, защита от повторных запросов, экранирование текста,
  никаких HTML, вложений и произвольных внешних ссылок в первом выпуске.
- Защита от публикации контактов, оскорблений и спама: автоматические фильтры
  помогают, но не заменяют человека и должны допускать исправление ошибок.
- Возможность отключить комментарии к работе; блокировка взаимодействия с
  конкретным участником; опубликованный после редактирования текст проверяется снова.
- Публичный ник и отдельная безопасная публичная карточка. Не выводить email,
  IP, дату рождения, полное имя из школьного журнала, школу и контакты автоматически.
- Подтверждение MAX само по себе не является проверкой возраста или безвредности.
- Личные сообщения, поиск людей по школе и контактам, публичный статус «онлайн»
  не входят в этот план первого запуска.

Перед расширением публичной аудитории проверить применимые требования к
детским данным и правилам распространения с ответственным за правовые вопросы;
этот документ не является правовым заключением.

### 7.2. Настоящие уведомления

Первый набор: новое задание, результат проверки, ответ на комментарий после
модерации, решение по собственной публикации, важное событие безопасности.
Обычные реакции при необходимости агрегировать, не создавать сигнал на каждый лайк.

Нужны постоянное хранение, адресат, непрочитанное/прочитанное, идемпотентный
event ID, переход к объекту с повторной проверкой доступа. Доставка после
успешной транзакции, например через outbox, не должна теряться при перезапуске.
Список и счётчик синхронизируются между устройствами. Не обещать «новых нет»,
если загрузка не удалась. Первый канал — внутри сайта; email/MAX/push отдельно,
с явным включением, без фоновой рассылки по этому плану.

## 8. Расширяемость: Scratch, CAD и будущий ИИ

Переиспользовать существующий module-sdk, не строить новое универсальное ядро.
Для каждой среды явно проверять create/edit/view/run/copy/import/export,
формат и версию документа, миниатюру, правила публикации и участие в заданиях.
Каталоги и кнопка создания получают доступные возможности из общего реестра.
Экспериментальный или отключённый модуль не появляется как работающий.

### Scratch / блочное программирование

Название для ASA Lab: «Блочное программирование». Интеграция редактора и VM
не означает подключение аккаунтов, проектов или сообщества scratch.mit.edu.
Пользователь остаётся в ASA Lab, со своим аккаунтом, сохранениями и курсами.

До кода проверить выбранные версии пакетов, их лицензии, товарные знаки и
условия медиабиблиотеки. Текущий официальный scratch-editor обозначен AGPL-3.0,
а название/персонажи имеют отдельные ограничения использования. Не считать
«open source» разрешением на любое ребрендирование или автоматическое копирование
всех работ Scratch. Не менять лицензию ASA Lab без отдельного решения.

Технический пробный пакет: импорт/экспорт `.sb3`, сохранение в Project Core,
запуск/стоп, собственное хранилище медиа, лимиты распаковки/размера/времени,
сетевая изоляция, проверка расширений, отсутствие доступа пользовательского
кода к сессии ASA Lab, мобильная работоспособность. Не выполнять недоверенный
код на production-сервере. Для viewer и runtime нужен отдельный security review;
плашка read-only сама по себе не является границей безопасности.

Для локальной школы проверить запуск без CDN, облачных аккаунтов и обязательного
внешнего соединения. Офлайн-публикация и слияние баз не входят в этот пакет.

### CAD и ИИ

Инженерное 3D — будущая отдельная среда с собственным форматом и возможностями,
а не переименование текущего редактора. Совместимость форматов не обещать заранее.
ИИ пока не самостоятельный пункт меню: сначала выбрать конкретную учебную задачу,
модель данных, контроль стоимости и приватность. Ученические работы и контакты
не отправлять стороннему провайдеру автоматически.

## 9. Публичные адреса, производительность и сохранность

- Предлагаемые адреса: `/explore`, `/explore/:publicationId`, `/courses`,
  `/courses/:courseId`. Проверить коллизии и выбрать один canonical URL для объекта.
- Старые `#/gallery` и ссылки на работы/редакторы не ломать; перенаправлять
  совместимо, сохраняя параметры. Миграция публичных URL не требует одновременно
  переписывать все внутренние hash-маршруты.
- Для разрешённых публичных страниц выдавать содержательный HTML, метаданные,
  canonical, Open Graph и sitemap. Приватные, удалённые, скрытые и link-only
  объекты не должны попадать в sitemap или выдачу через кэш. Одного noindex для
  защиты данных недостаточно: необходима серверная проверка.
- Ответ страницы для гостя не содержит персонализированного кэша другого
  пользователя. После скрытия/изменения доступа обновлять и API, и HTML, и медиа.
- Тяжёлый viewer загружается по открытию конкретной публикации; при закрытии
  освобождаются Worker/WebGL/таймеры. Карточки не запускают расчёт.
- Пагинация запросов, индексы под реальные фильтры, отсутствие N+1, измерение
  времени загрузки до/после на том же устройстве и сети. Числовые бюджеты выбрать
  после базового замера по протоколу §4.5, не объявлять ускорение без измерения.
- Публикации с зависимыми медиа и лицензиями должны переживать backup/restore.
  Изменения схемы — только согласованные совместимые добавления, не удаление
  существующих работ, пользователей, реакций или подборок.
- Выключение новой функции не удаляет данные. Обновление Docker выполняется
  отдельно через guarded updater с backup и проверкой фактических Web/API SHA.

## 10. Порядок внедрения и критерии приёмки

Каждый пакет завершается работающим сценарием; не выдавать макет или кнопку
за завершённую возможность. Предлагаемый порядок:

| Пакет | Видимый результат | Обязательная проверка перед приёмкой |
| --- | --- | --- |
| 1. Личная оболочка и создание | Понятная мобильная панель, подписанная кнопка, прямое создание, исправленные полки и имена | Все способы обычного входа ведут домой; повторы не создают дублей; возврат и reload сохраняют документ |
| 2. Просмотр публикаций | Модель можно вращать, схему запускать без копирования | Нет записи оригинала; опубликованный снимок отличается от черновика; просмотр недоступен после отзыва |
| 3. Открытое Исследовать | Разрешённые работы доступны гостю по верхней ссылке, поиск и фильтры работают | Публичная проекция не раскрывает закрытые работы/PII; ссылки, HTML, кэш и индексация согласованы; есть жалобы и управление публикациями |
| 4. Публичные курсы | Просмотреть программу, начать/продолжить, увидеть курс в Моём обучении | Повторная запись без дублей, прогресс только свой, версия курса стабильна, классные права сохранены |
| 5. Взаимодействия и уведомления | Надёжные лайки, сохранённое, просмотры, реальные уведомления | Идемпотентность, школа с общим IP, два устройства, рестарт сервера, корректные непрочитанные |
| 6. Обсуждения | Комментарии и ответы под проектом | До включения работают модерация, жалобы, ограничения, безопасный текст и назначен ответственный |
| 7. Блочная среда | Отдельно проверенная интеграция Scratch-компонентов | Лицензии и бренд согласованы, файлы/сеть/исполнение изолированы, save/load и локальная школа проверены |

В пакете 1 нельзя объявлять нынешнюю авторизованную галерею уже общедоступной.
Публичные ссылки для гостей становятся активными только с готовой серверной
выдачей. В preview можно проверить целевую шапку; на действующем сайте не
показывать фиктивные курсы, уведомления и «скоро» вместо работающих функций.

Сначала согласовать этот документ и визуальный образец ключевых состояний
телефон/компьютер, затем реализовывать принятый пакет. Макет, локальная проверка,
push, CI, deployment и owner acceptance — разные результаты.

| Реальный пользовательский путь | `pnpm e2e:creator-portal` — на изолированном стеке; предварительно исправить устаревшее ожидание шахматной полки и добавить mobile/error/retry сценарии |
| Сборка и размеры | `pnpm gate:code` — существующий единый gate, включая build, SEO и bundle budget; не исполнять `bundle:check` над старым dist как доказательство новой сборки |
| Настоящая БД и доступ | `pnpm gate:data` — изолированный PostgreSQL, миграции/данные/RLS; включить реальные новые регрессии транзакций, не подменять запуск наличием файла теста |
| Release candidate | `pnpm gate:repository` — после согласованного объёма изменений; focused PASS не отменяет красный общий gate |

При работе только над этим документом достаточно форматирования и проверки
control plane: это не продуктовая приёмка. При реализации читать вход агента,
§1.1 и §§3–4, затем только затронутые исходники. Не перечитывать весь будущий
социальный roadmap для изменения одной полки. Короткий отчёт о срезе содержит
его результат, пути, команды/артефакты и оставшиеся проверки; текущее состояние
не копируется из `current.yaml` в дополнительные конкурирующие списки задач.

Для каждого затронутого пакета проверить:

- Гость, обычный аккаунт, StudentSeat, преподаватель, администратор.
- Обычный вход, прямую ссылку, приглашение, истёкшую сессию, logout, reload и Back.
- Создание из шапки/полки/списка, два нажатия, таймаут после записи, два устройства.
- Просмотр оригинала не создаёт проект; копирование создаёт одну собственную
  работу; закладка не создаёт копию; авторство сохраняется.
- Анонимный и cross-tenant доступ к закрытому документу, медиа, черновику,
  комментариям на модерации и личному прогрессу запрещён сервером.
- Ошибка API не подменяется пустым списком/нулём уведомлений, retry понятен.
- Мобильный drawer, меню создания, touch viewer, fullscreen, клавиатуру и фокус.
- Отзыв публикации, смену прав, кэш, медиа и прямую ссылку с другого устройства.
- Регрессии классов, заданий, сохранений, 3D и электроники: общая навигация
  не должна переопределить права или запуск редактора.

Полный release gate и операции с БД проводятся по AGENTS.md и
`docs/delivery/AGENT_CHANGE_WORKFLOW.md`. Тесты БД — на согласованной изолированной
базе, не запись тестовых пользователей в production. Итоговый отчёт разделяет
фактически выполненные тесты, кэш, CI точного SHA, deployment и приёмку владельца.

## 12. Открытые решения до соответствующих этапов

Не блокируют обсуждение и первый локальный пакет, но должны быть решены до включения:

1. Использовать согласованные названия «Проекты»/«Знания»; Сохранённое остаётся личным разделом.
2. Определить, кто разрешает расширение аудитории существующих публикаций.
3. Согласовать публичные имена/профили и ограничения ученических публикаций.
4. Назначить ответственного за модерацию и порядок реагирования.
5. Определить самостоятельную запись для StudentSeat и политику курсов.
6. Выбрать версию, лицензионную схему и медиабиблиотеку блочной среды.

## 13. Внешние первичные источники

### Уточнение принятого первого выпуска

- В шапке — «Проекты» и «Знания», с прежним фирменным знаком и аватаркой.
  Для этого выпуска оба каталога доступны вошедшим пользователям; гостевые
  права не расширяются переименованием. Знания показывают только публичные
  опубликованные курсы через существующие серверные функции доступа.
- Личные полки содержат до 10 последних работ каждой среды. Компьютер показывает
  четыре карточки, телефон — несколько и часть следующей; мобильная полоса
  прокрутки скрыта, нативный свайп и клавиатурная прокрутка сохранены.
- Ниже — последние публикации сообщества и курсы. Нет вымышленных материалов;
  видео и статьи как отдельные типы контента относятся к дальнейшему этапу.
- Большая точка у аватара обозначает существующее предложение привязки MAX,
  у меню — реальные счётчики заданий/работ на проверку. Подпись внутри меню
  называет источник. Это не новая система непрочитанных оценок или игровых событий.
- Мягкая пульсация ограничена тремя циклами; затем точка остаётся видимой.
  При prefers-reduced-motion анимация отключена. Открытие меню не обнуляет
  серверный счётчик и не выдаётся за прочтение заданий.
- Видимая высота кнопки «Создать» уменьшена без уменьшения шрифта;
  сенсорная область остаётся не меньше 44 px. На телефоне кнопка рядом с Главной.
- Управление проектами остаётся в полном списке, доступном из каждой полки;
  домашние миниатюры открывают проекты без перекрывающих их выпадающих меню.
- Помощь доступна из меню аккаунта и бокового меню, с адресами сообщества
  `https://vk.ru/asalabru` и бота `https://max.ru/id231408577954_3_bot`.
