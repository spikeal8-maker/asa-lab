# ASA Lab — целевой UX входа, регистрации и доступа к классу

**Статус:** нормативная спецификация пользовательских маршрутов Identity / Onboarding.  
**Продуктовая основа:** [`ASA_USERS_ACCESS_AND_SETTINGS_SPEC.md`](ASA_USERS_ACCESS_AND_SETTINGS_SPEC.md) определяет категории пользователей, scoped обязанности, меню и кабинеты. Настоящий документ уточняет маршруты входа; он не вводит конкурирующие типы аккаунта.  
**Приоритет:** выше локальной реализации временных экранов; область каждого нормативного источника и порядок разрешения коллизий заданы в §0 основной спецификации. Инженерные правила, принятый security profile и архитектурные ограничения не отменяются.  
**Основание:** три owner-video reference-пакета Tinkercad, `ASA_TARGET_PLATFORM_BLUEPRINT.md`, Issue №48 и решения владельца.  
**Цель:** воспроизвести понятную продуктовую логику Tinkercad, но убрать лишние переходы Autodesk, неоднозначные термины и повторяющиеся выборы.

Описание TARGET не означает внедрение или разрешение менять рабочие credentials.
Числа возраста ниже — продуктовый маршрут исходной спецификации, не универсальная
правовая норма. Действующие возрастные/consent-условия проверяются серверной policy.
Подтверждение преподавателем принадлежности учебного профиля не подменяет требуемое
подтверждение законного представителя.

## 1. Главная проблема, которую устраняет документ

Следующие понятия относятся к разным уровням и не должны показываться пользователю как взаимоисключающие типы аккаунта:

```text
Account             постоянная глобальная учётная запись
Educator            дополнительная серверная capability Account
Registered student  Account под student/consent/Safe Mode policy
StudentSeat          локальный вход в конкретный класс без email
Personal Workspace  обязательное личное пространство Account
Organization        добровольное пространство команды; подтверждение учреждения отдельно
Class membership    участие Account или StudentSeat в конкретном классе
```

Следовательно:

- **личный аккаунт может позднее стать педагогическим**;
- педагог не создаёт второй аккаунт;
- зарегистрированный ученик входит тем же обычным входом, что и взрослый Account;
- «ученик с кодом класса» — не тип аккаунта, а отдельный способ доступа без email;
- код организации — не основной credential обычного Account;
- выбор карточки в браузере не выдаёт role/capability.

## 2. Три понятных действия на публичной странице

На `/` показываются только три пользовательских намерения:

```text
[ Войти ]
Для всех, у кого уже есть постоянный аккаунт ASA Lab.

[ Создать аккаунт ]
Для личных проектов. Педагогические возможности можно включить после регистрации.

[ Войти по коду класса ]
Для ученика, которому педагог выдал карточку или подтвердил конкретный вход.
```

### Обязательное название

Используется **«Войти по коду класса»**, а не неоднозначное «Присоединиться к классу».

Причина:

- StudentSeat может входить по выданным индивидуальным данным многократно;
- существующий Account может через тот же маршрут впервые присоединиться к классу;
- пользователь сначала понимает, какой credential ему нужен.

Термин «Присоединиться к классу» допустим только внутри подтверждения конкретного найденного класса.

## 3. Универсальный вход Account

Маршрут:

```text
/sign-in
```

Форма:

```text
Email или имя пользователя
Пароль
[ Войти ]

Забыли пароль?
Создать аккаунт
Войти по коду класса
```

Этот вход используется одинаково для:

- взрослого creator;
- педагога;
- guardian;
- зарегистрированного ученика;
- school admin;
- platform admin.

После проверки credentials сервер возвращает:

```text
Principal
Account
Profile
Capabilities
Workspaces
ActiveContext
```

Интерфейс не спрашивает роль до входа и не возвращает hard-coded `role: teacher`.
Список реально подключённых альтернативных способов входа приходит от сервера.
Упоминание guardian здесь не активирует родительский кабинет.

### Legacy organization login

Временный совместимый путь скрывается под вторичной ссылкой:

```text
Вход для ранее подключённой организации
```

Он открывает отдельную форму `workspace code + email + password` и не является частью основного входа.

После завершения migration cutover ссылка удаляется отдельным owner-approved этапом.

## 4. Создание Account без выбора «педагог или личный»

Маршрут:

```text
/sign-up
```

Пользователь создаёт один Account. Педагогические возможности не являются отдельным видом регистрации.

### Шаг 1 — возрастная и региональная политика

```text
Страна / регион
Дата рождения
[ Продолжить ]
```

Сервер вычисляет `AgePolicyResult`.

### Шаг 2 — профиль и credentials

Для взрослого Account:

```text
Псевдоним / username
Отображаемое имя — необязательно
Email
Пароль
Согласия
[ Создать аккаунт ]
```

Не требуются:

- фамилия;
- настоящее имя;
- школа;
- организация;
- педагогическая должность.

Username не вычисляется из email. Он проверяется на доступность до отправки всей формы.

### Шаг 3 — первый вход

После регистрации взрослый получает:

```text
creator capability
Personal Workspace
Account session
Creator Home
```

Педагогическая capability отсутствует до отдельного onboarding.

## 5. Маршрутизация несовершеннолетнего

Несовершеннолетний не получает тупиковую ошибку `422` без следующего действия.

После определения AgePolicy показывается понятный выбор. Пример для продуктовой
policy с границей взрослого маршрута 18+:

```text
Для самостоятельного взрослого аккаунта требуется возраст 18+.

[ Создать ученический аккаунт ]
Постоянный аккаунт с Safe Mode и подтверждениями, необходимыми действующей policy.

[ Войти по коду класса ]
Без личного Account и email, по данным или подтверждению преподавателя.

[ Назад ]
```

### Registered student Account

Постоянный Account:

```text
Account
Profile
registered_student capability
pending approval / Safe Mode policy
Personal Workspace
Classroom memberships optional
```

### StudentSeat

Локальный principal конкретного класса:

```text
class code
login handle
individual secret OR approved browser-bound teacher login
no email required
no public profile
Safe Mode by default
```

Registered student Account и StudentSeat не сливаются в один auth-subject.
Доказанная связь Account с существующим учебным профилем разрешена по §10
основной спецификации и Learner Identity ADR: учебная история сохраняется,
Principal/Project ownership не переписываются автоматически.

## 6. Вход по коду класса

Маршрут:

```text
/join-class
```

### Экран 1 — код

```text
Введите код класса
[ Продолжить ]
```

Код нормализуется без учёта пробелов, дефисов и регистра.

### Экран 2 — подтверждение класса

После безопасного разрешения кода:

```text
Класс: 7Б Робототехника
Педагог: отображаемое имя
Организация: если policy разрешает показывать

Как вы будете входить?

[ У меня есть аккаунт ASA Lab ]
Войти в аккаунт и запросить присоединение к этому классу.

[ У меня данные от преподавателя ]
Войти без email по своей карточке или запросить подтверждение входа.
```

До подтверждения membership не создаётся. Общий код не выдаёт список учеников,
чужие профили, приватные работы или staff permissions.

### Ветвь Account

```text
universal sign-in
→ показать current account + target class
→ [Присоединиться к классу]
→ teacher approval либо точное индивидуальное preapproved invitation
→ ClassroomMembership
```

### Ветвь StudentSeat

```text
login handle + individual secret
OR
short-lived browser-bound challenge → teacher approves this exact login
→ StudentSeat session
→ собственное обучение и разрешённые учебные работы
```

Режим подтверждения входа не показывается как «без пароля», пока защищённый flow
не реализован. Общий код с угадываемым именем или один пароль на весь класс не
являются целевым индивидуальным входом. Параметры credentials определяет принятый
security profile. Переход со старого способа выполняется совместимо, с выдачей
новых карточек/восстановлением, а не внезапной блокировкой детей.

Ошибки не раскрывают, существует ли конкретный login handle в roster. Успешная
аутентификация профиля не означает создание Attempt или активацию всех его
Enrollment/Participation. Режим оценивания задаётся назначением, не наличием
личного Account. При последующем linking отзыв старого credential не является
выводом ученика из класса.

## 7. Educator — capability существующего Account

После регистрации Account уже может создавать личные проекты.

Педагогические возможности включаются позднее:

```text
Account menu / onboarding card
→ Стать педагогом
→ возрастная проверка действующей policy
→ текст полномочий и ответственности
→ self-attestation
→ provisional educator CapabilityGrant
→ AuditEvent
→ раздел Классы становится доступен по выданным действиям
```

Педагог не теряет Personal Workspace и не создаёт второй Account.

```text
тот же Account
├── личные проекты
├── educator capability
├── собственные классы
└── optional Organization memberships
```

Capability серверная, аудируемая, приостанавливаемая и отзывная. Сохранение имени
или биографии не включает role mutation. Сворачивание рабочего меню — preference,
не отзыв educator. Авторство учебных материалов и scoped edit/publish приглашения
не требуют автоматически выдавать управление классами; см. §4 основной спецификации.

## 8. Связь педагога со школой

Школа не требуется при регистрации Account и не является credential обычного входа.

После educator onboarding доступны варианты:

```text
[ Работать самостоятельно ]
Первый класс в разрешённом самостоятельном teaching context.

[ Присоединиться к организации ]
По подтверждённому приглашению и правилам конкретной команды.

[ Создать свою команду ]
Явно создать новую организацию для совместной работы.

[ Указать учреждение ]
Необязательная профильная заявка InstitutionClaim(state=unverified).
```

Свободно введённое название школы:

- не выдаёт права;
- не создаёт school_admin существующей школы;
- не является security boundary;
- может быть проверено позднее.

Организационная связь моделируется как:

```text
Organization Workspace
+ WorkspaceMembership
+ scoped role
```

Организация может быть добровольной онлайн-командой без подтверждённого статуса
реального учреждения. Статус учреждения хранится и показывается отдельно.
Совпадение email-domain или знание organization code сами по себе не выдают
административное право. Один Account может работать в нескольких областях;
доступ школы А не действует в школе Б или личном self-study.

В workspace switcher пользователь видит, например:

```text
Личное пространство
Самостоятельное преподавание
Школа №1580 — подтверждено
```

Непринятое приглашение кружка показывается отдельно в «Приглашениях», а не как
уже действующий рабочий scope. При единственном контексте не нужен лишний chooser.
Физическая поддержка самостоятельного обучения/преподавания должна соответствовать
принятому ADR и инженерным ограничениям: этот UX не разрешает произвольное изменение
tenant/RLS или создание фиктивной публичной школы.

## 9. Термины, видимые пользователю

### Использовать

- Войти
- Создать аккаунт
- Войти по коду класса
- Личный аккаунт / Аккаунт ASA Lab
- Стать педагогом
- Ученический аккаунт
- Личная карточка / данные входа от преподавателя
- Личное пространство
- Организация / школа
- Присоединиться к найденному классу

### Не использовать на первом экране

- Principal
- Capability
- StudentSeat
- Workspace membership
- Registered student как отдельный способ обычного входа
- Personal Account и Educator как взаимоисключающие типы
- Присоединиться к классу без объяснения credentials

Технические термины остаются в модели и документации, но не перегружают ученика.

├── adult-account

Это карта назначения маршрутов, не утверждение об их текущей физической реализации.

Отдельный `ContextChooserPage` с карточками «Педагог / Зарегистрированный ученик /
Личный аккаунт» в основном публичном flow **не нужен**. Его продуктовая логика
распределена по понятным действиям и серверной политике.

## 11. Acceptance gate публичного UX

Публичный UX принимается только если новый пользователь без объяснений понимает:

1. у меня уже есть аккаунт → `Войти`;
2. мне педагог выдал доступ → `Войти по коду класса`;
3. аккаунта нет → `Создать аккаунт`;
4. педагог и обычный пользователь входят одной формой;
5. педагогические возможности включаются после создания Account;
6. школа не требуется для личной работы;
7. несовершеннолетний получает рабочий маршрут, а не тупик;
8. никакая клиентская карточка не выдаёт role/capability;
9. общий код не открывает чужой учебный профиль;
10. ученик может продолжать обучение без обязательной личной регистрации.

Обязательные browser-сценарии:

```text
A. adult visitor → sign-up route
B. existing creator → universal sign-in
C. existing educator → same universal sign-in → Classes visible from server grant
D. student with class code → class preview → individual credential/approved challenge login
E. registered student → same universal sign-in → confirmed learner join from code route
F. underage sign-up → student-account/class-code options
G. legacy organization account → separate compatibility link
```

Проверка только UI не заменяет negative API evidence общего кода, чужого профиля,
просроченного challenge и повторного linking.

## 12. Запрещённые UX shortcuts

- показывать роль как тип credentials;
- спрашивать «Педагог или личный аккаунт?» как взаимоисключающий выбор;
- показывать отдельную кнопку входа для зарегистрированного ученика;
- называть StudentSeat личным Account;
- требовать школу или organization code для личного Account;
- делать `Присоединиться к классу` главным термином до ввода кода;
- выдавать educator capability по выбранной карточке;
- создавать фиктивную школу для Personal Workspace;
- перенаправлять несовершеннолетнего в тупиковую ошибку;
- выводить username из email;
- дублировать вход через несколько последовательных chooser-экранов;
- использовать общий class code и публичное имя как достаточную индивидуальную аутентификацию;
- считать смену credential после linking выходом из учебного участия.

## 13. Историческое решение для PR №59

Следующий перечень сохраняет происхождение документа. Он **не определяет текущую
задачу, не возвращает исполнителя к C1.1 и не активирует старые milestones**.
Текущее состояние читается только из `docs/execution/current.yaml`.

Исходное решение для PR №59:

1. сохранить публичную страницу с тремя действиями;
2. переименовать `Присоединиться к классу` в `Войти по коду класса`;
3. удалить обязательный contextual chooser из основного маршрута;
4. `Войти` открывает универсальный Account login;
5. `Создать аккаунт` открывает age-aware registration;
6. возраст маршрутизирует adult/student flow;
7. `Войти по коду класса` открывает code-first flow;
8. educator onboarding остаётся отдельным процессом;
9. legacy organization login остаётся отдельной совместимой ссылкой;
10. внедрение и последующее развитие выполняются в актуальном явно разрешённом объёме.
