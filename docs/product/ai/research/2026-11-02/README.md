## 1. Вывод для продукта

Полноценный чат требует не только системного промпта. Нужны согласованные **каталог возможностей → модельный адаптер → проверка полномочий → исполнитель → результат → следующий шаг модели → видимый результат в чате**. Промпт объясняет поведение, но не создаёт функцию, не разрешает доступ и не подтверждает успех.

Для ASA предлагается единый реестр, из которого формируются определения инструментов для разных API, карточки админки, доступный контекст промпта, журнал операций и тестовые контракты. Модель выбирает действия внутри разрешённого набора; приложение проверяет каждое действие и его результат. Например, «сайт с котиками, картинки найди» должен приводить к поиску, выбору ресурсов, созданию HTML, проверке ссылок и показу файла, а не завершаться отдельной сгенерированной картинкой.

Это не основание написать второй оркестратор или заменить весь чат. В ASA уже есть общий `AiChatService`, определения native tools, сервис поиска и хранилище файлов. Следует сначала воспроизвести сбой и определить точку нарушения существующего цикла. Объединение описаний и управления не требует повторной реализации работающих исполнителей. Независимые проверки ожидаемых результатов задаются отдельно от генерируемых схем, иначе тесты лишь повторят ошибку реестра.

«Лучше» здесь означает проверяемые свойства: меньше ложных заявлений о результате, восстановление без перезагрузки, понятные ограничения преподавателю, сохранность работы и выполнение составного запроса. **Сравнительных продуктовых испытаний с конкурентами не проводилось; превосходство не установлено.**

## 2. Как проводилось исследование

Изучены официальные API-документы, руководства разработчиков и публичные продуктовые инструкции. Основные семейства: OpenAI/ChatGPT, Anthropic/Claude, DeepSeek, Qwen; дополнительно Ollama, Gemini и MCP. Все веб-источники ниже просмотрены 02.11.2026. Внешние страницы меняются; выводы относятся к указанной дате и документированному интерфейсу, а не ко всем историческим версиям.

Используются четыре уровня доказательств:

| Метка | Что установлено | Чего она не доказывает |
| --- | --- | --- |
| API | Публичный контракт API поставщика | Внутреннее устройство его потребительского чата |
| Framework | Открытые возможности библиотеки/примеров | Что именно эта библиотека используется в Qwen Chat или другом продукте |
| Product docs | Описанный пользователю интерфейс | Что функция доступна каждому аккаунту, региону и устройству |
| ASA source | Статическое чтение конкретного исходного кода | Успех живого сценария на текущем тестовом сервере |

В этом срезе не выполнялись платные модельные вызовы, вход в чужие продуктовые аккаунты, инструментирование закрытых чатов или обновление серверов. Не исследованы закрытые алгоритмы маршрутизации, внутренние системные промпты, устройство хранилищ и приватные правила повторов конкурентов. Снимок интерфейса сам по себе таких сведений не даёт.

Покрытие неравномерно: ChatGPT/Claude рассмотрены по продуктовым инструкциям; Qwen преимущественно по framework, DeepSeek преимущественно по API. Проверки одних и тех же задач в четырёх пользовательских интерфейсах нет. Сравнительную UX-часть нельзя считать завершённой; исходы отправки, восстановления, изменения артефакта и действий с изображениями требуют отдельного наблюдения с указанием версии/поверхности.

## 3. Сравнение подходов

### 3.1. API и агентные библиотеки

В таблице приведены краткие факты первоисточников; последний столбец — **наш проектный вывод**, а не обещанная функция поставщика.

| Система | Документированный подход | Существенное ограничение | Вывод для ASA |
| --- | --- | --- | --- |
| OpenAI, API | Модель возвращает вызов функции, приложение исполняет его и возвращает результат; есть схемы и управление параллельными вызовами. [S01](https://developers.openai.com/api/docs/guides/function-calling) | Поддержка зависит от модели/endpoint. Встроенные инструменты имеют отдельные правила; строгая схема не является разрешением доступа | Компилировать определения под конкретный маршрут; тестировать пакет вызовов, не считать «совместимый API» полной совместимостью |
| Anthropic, API | Разделены клиентские и серверные инструменты; серверный ход может приостанавливаться через `pause_turn` и требовать продолжения с сохранённым состоянием. [S09](https://platform.claude.com/docs/en/agents-and-tools/tool-use/server-tools) | Пауза не означает законченный пользовательский ответ или уже выполненный последний вызов | Сохранять состояние протокола, ограничивать продолжения, показывать реальную стадию |
| DeepSeek, API | Есть function calling; для thinking-запросов с `tools` документация требует передавать `reasoning_content` в последующих запросах, иначе возможен HTTP 400. [S15](https://api-docs.deepseek.com/guides/tool_calls/), [S16](https://api-docs.deepseek.com/guides/thinking_mode/) | Правила состояния зависят от режима; нельзя выкинуть служебные поля общим нормализатором | Хранить необходимое продолжение внутри адаптера, не показывая скрытые рассуждения пользователю |
| Qwen-Agent, framework | Документированы многошаговые, многотуровые и параллельные вызовы, парсинг и управление контекстом. [S17](https://qwenlm.github.io/Qwen-Agent/en/guide/get_started/features/) | Возможности framework не гарантируют аналогичного поведения любой Qwen-модели или Qwen Chat | Проверять конкретную модель, шаблон и сервер; не заменять весь ASA импортом framework |
| Ollama, runtime | Описан агентный цикл, включая сборку потоковых частей ответа и последующую передачу результатов инструментов. [S19](https://docs.ollama.com/capabilities/tool-calling) | Не каждая установленная модель поддерживает tools/Vision одинаково | Реальные capability-профили вместо разрешения по названию провайдера |
| Gemini, API | Function calling позволяет модели выбрать функцию и параметры для исполнения приложением. [S20](https://ai.google.dev/gemini-api/docs/function-calling) | Это отдельный протокол, а не доказательство взаимозаменяемости сообщений разных API | Нормализованный внутренний вызов и независимые адаптеры, без добавления нового платного подключения |

**Практическое следствие:** «инструменты доступны всем моделям» означает общий продуктовый набор при наличии проверенного способа планирования. Это не превращает текстовую модель в Vision-модель. Native tools предпочтительны; для остальных нужен проверяемый структурированный план или детерминированная обработка явного запроса по R01. Если модель не даёт надёжного плана, интерфейс сообщает ограничение, а не незаметно отправляет данные другой платной модели.

### 3.2. Поиск и чтение

OpenAI документирует web search с поисковыми действиями, открытием страниц и ссылками-цитатами. Это размещённый у поставщика инструмент, а не бесплатная зависимость для ASA. [S02](https://developers.openai.com/api/docs/guides/tools-web-search)

Anthropic разделяет web search и web fetch: поиск может выполнять несколько ограниченных обращений; чтение возвращает содержимое и время получения, а ошибка исполнения может находиться внутри успешного HTTP-ответа. [S10](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool), [S11](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)

DeepSeek также публикует отдельные Search и Fetch API: структурированную выдачу и извлечение страницы в Markdown. Это внешние авторизованные обращения с собственной оплатой; наличие текстового подключения DeepSeek в ASA не включает их автоматически. Они пропущены в первой редакции исследования. [S25](https://api-docs.deepseek.com/guides/search/) Для текущего бесплатного поиска ASA это сравнительный материал, не предлагаемый новый backend.

Предлагаемый вывод для ASA: сохранять отдельные действия поиска и чтения, давать модели сниппет и метаданные кандидатов, позволять ей выбирать страницы и уточнять запрос. Пустая выдача, ошибка сервиса, запрет домена и недостаток материала — разные результаты. Не надо читать все страницы автоматически или объявлять сниппет прочитанной статьёй. Переход на другой способ извлечения не должен обходить авторизацию, CAPTCHA или ограничения сайта.

### 3.3. Файлы, предпросмотр и изображения в продуктах

Публичные инструкции ChatGPT описывают просмотр создаваемых файлов, включая некоторые интерактивные HTML-результаты, и отдельные способы работы с изображениями. Доступность зависит от поверхности продукта. [S06](https://learn.chatgpt.com/docs/artifacts-viewer), [S07](https://learn.chatgpt.com/docs/image-generation)

Claude Artifacts описывает работу с результатом рядом с разговором, изменение существующей работы и экспорт. Описания новых и прежних типов артефактов различаются; единая неизменная панель всех версий не предполагается. [S14](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them)

Вывод для ASA: файл должен иметь устойчивую идентичность и версию, а сообщение — ссылку на фактический результат. Предпросмотр, скачивание, история изменений и продолжение разговора должны работать вместе. Это не доказательство, что конкуренты хранят файлы только в браузере; такой способ хранения является отдельным решением ASA с собственными ограничениями.

### 3.4. Качество описаний, контекст и наблюдаемость

Anthropic рекомендует чёткие границы инструментов, полезные компактные результаты и проверку на наборах задач; перегруженные пересекающиеся наборы затрудняют выбор. [S12](https://www.anthropic.com/research/writing-tools-for-agents) Другая публикация описывает поддержание компактного контекста и получение нужных материалов по мере работы. [S13](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

OpenAI документирует события потокового ответа и оценку агентных трасс. [S03](https://developers.openai.com/api/docs/guides/streaming-responses), [S04](https://developers.openai.com/api/docs/guides/agent-evals) Это основания для собственных проверок ASA, но не доказательство автоматического восстановления наших запросов.

В MCP версии 2025-06-18 отдельно описаны схемы входа/результата, ошибки протокола и исполнения; аннотации инструментов требуют оценки доверия. Отмена допускает гонки. [S21](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [S22](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation) Это выбранная датированная редакция стандарта, не заявление о его последней версии. Внедрение MCP не требуется, чтобы реализовать собственный реестр ASA.

## 5. Проект архитектуры

### 5.1. Один реестр, разные представления

Запись инструмента содержит стабильный ID, версию входа/выхода, назначение, условия выбора, пример, пределы, эффект, необходимые полномочия, зависимости, обработчик и правила восстановления. Из неё получаются:

1. Определение для API конкретной модели.
2. Краткое описание доступных действий в контексте модели.
3. Карточка и настройки администратора/преподавателя.
4. Классификация события для чата и журнала.
5. Контрактные тесты и документация.

Ключи, URL внутреннего ComfyUI, секреты подключений и чужие данные в описание модели не включаются. Бот видит публичное имя модели генерации и реальные возможности. Формулировка «ComfyUI не подключён» не должна появляться из устаревшего промпта, когда исполнитель готов.

### 5.2. Граница модели и приложения

Модель предлагает имя и аргументы. Приложение проверяет схему, scope, полномочия, версии объектов, лимиты, адреса и готовность зависимостей. Только после этого начинается внешний вызов. Ответ инструмента возвращается модели как результат с тем же ID, а не поддельное сообщение пользователя. Следующий шаг выбирается в пределах общего бюджета операции.

Внутренний формат унифицирован; сообщения провайдера сохраняются его адаптером без потери необходимых полей продолжения. Скрытые рассуждения не превращаются в публичный текст и не попадают в обычные аналитические логи. Строгая схема не заменяет серверную авторизацию.

Независимые чтения допускают ограниченную параллельность. Изменения одного файла выполняются последовательно с проверкой версии. Смешанный пакет нельзя просто объявить успехом: каждое действие получает собственный исход, а зависимое действие запускается только после результата предшественника.

### 5.3. Состояние, поток и восстановление

```text
принят запрос → планирование → предложен вызов → допущен → исполнение
                                                        ↓
             ответ модели ← результат / частичный результат / отказ
                    ↓
             следующий шаг либо завершение
```

Любой этап может перейти в отмену, конечный отказ или неизвестный исход. `cancel_requested` не равен `cancelled`; принятие генерации не равно готовому изображению. При потере соединения сначала сверяется operation ID, а не повторяется потенциально платное действие.

Для чата передаются раздельные события текста и стадий инструментов. Аргументы tool call собираются до валидации; это не повод удерживать весь пользовательский текст. Показать «Ищу изображения» допустимо после фактического допуска поиска, а «Сайт обновлён» — только после новой версии файла. Поле ввода остаётся доступно для следующего черновика.

### 5.4. Хранение и проверка результата

Текущее серверное хранение файлов/версий сохраняется как baseline. IndexedDB рассматривается только как вариант для локального черновика/кэша, а не выбранная замена хранилища. Браузерные квоты, вытеснение и отсутствие переноса между устройствами требуют понятного экспорта и предупреждений о несохранённом. [S23](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) До отдельного решения о семантике сохранения не переносить туда канонические файлы или историю. Предположение владельца о временных файлах не следует трактовать как поручение переписать всю persistence-модель.

Для сверки внешних операций всё равно нужен минимальный серверный журнал ID/стадий/ссылок/расхода, с ограниченным сроком хранения. Содержимое временного сайта в таком журнале не требуется. Нельзя автоматически удалить уже существующие серверные файлы или обещать продолжение работы с локальным файлом после закрытия его браузера.

HTML-изоляция и визуальная проверка — разные задачи. Sandbox iframe может разрешать скрипты без прав origin родителя; совместное разрешение скриптов и same-origin для недоверенного содержимого опасно. [S24](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) Проверка кода не доказывает видимого результата. Скриншот, состояние DOM и runtime-ошибки требуют отдельного проверенного механизма; доступность универсального захвата из изолированного iframe пока не установлена.

### 5.5. Рассмотренные альтернативы

| Подход | Польза | Почему не выбран как основа |
| --- | --- | --- |
| Дописать все правила в один большой промпт | Быстрый эксперимент | Не создаёт исполнителей, не обеспечивает права и восстановление; описание легко расходится с готовностью |
| Распознавать все запросы регулярными выражениями | Предсказуемые простые команды | Не покрывает контекстные композиции и неоднозначность; пригодно как узкий слой явных намерений, не весь planner |
| Скрыто передавать планирование другой сильной модели | Может улучшить сложный выбор | Меняет получателя данных и расход; противоречит запрету неявного платного переключения |
| Принять hosted tools одного поставщика для всех моделей | Меньше собственной инфраструктуры отдельных функций | Не решает общий доступ и может ввести новую платную зависимость; не соответствует текущему ограничению владельца |
| Сделать MCP обязательным внутренним транспортом сразу | Стандартное описание и расширяемость | Сам по себе не решает admission, хранение и UX; сначала достаточно собственного versioned registry, затем адаптер при необходимости |
| Дать один универсальный инструмент «сделать всё» | Короткий список для модели | Теряются проверяемые границы, policy и диагностика; композиция лучше выражается оркестратором понятных действий |
| Не хранить на сервере даже квитанции | Минимум серверных данных | Нельзя надёжно сверять принятые внешние задания после обрыва; нужен отдельно ограниченный журнал, без скрытого копирования файлов |

Выбор собственного общего слоя требует больше контрактных тестов и поддержки адаптеров. Это сознательная стоимость переносимости и единых правил ASA; он не обещает автоматически более сильное планирование, чем у специализированного продукта поставщика.

## 6. Решения и открытые вопросы

| Решение исследования | Причина | Связь с действующим ТЗ |
| --- | --- | --- |
| Предпочесть общий исполнитель собственных инструментов ASA | Не вводит новую платную зависимость; сохраняет права и существующие сервисы | R01–R02 |
| Сохранить native tools и добавить проверенный fallback только там, где нужен | Равные продуктовые функции не требуют одинакового протокола модели | R01, R13 |
| Разделить инструкции поведения, реестр функций и неизменяемые проверки безопасности | Редактирование промпта не должно выдавать права | R02, R22, R24 |
| Поиск изображений первым при создании обычного сайта | Соответствует явной просьбе владельца; генерация не заменяет поиск без основания | R07–R08, R16 |
| Локальные черновики проектировать отдельно от журналов и явного сохранения | Сохранность, повтор платного вызова и хранение байтов — разные проблемы | R02, R16 и глава 07 |
| Показывать доказанную стадию и итог, а не внутреннее рассуждение | Понятность, отсутствие ложных успехов и утечек | R03–R05, R20 |

До реализации уточнить в архитектурном решении: срок хранения серверных квитанций; перенос/экспорт локального workspace; механизм визуальной проверки; новые schema-версии и совместимость истории. Численные профили поиска из следующего документа — кандидаты для измерений, не автоматическая замена действующих лимитов. Доступ к репозиторию, презентации и 3D остаются отдельными будущими возможностями с собственными полномочиями и приёмкой.
