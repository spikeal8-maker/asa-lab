# 4. Единые инструменты и модельные адаптеры

## R01. Общая возможность, независимо от провайдера

Платформа предоставляет разрешённые web_search, image_search, weather, чтение/поиск по явно приложенным файлам, создание файлов и generate_image. Названия адаптируются к существующим контрактам без дублирования сервисов.

Исполнение делится на общий слой авторизации/лимитов/истории и адаптеры. Native tool calling используется при реальной поддержке. Для остальных моделей работает серверный управляющий слой: явные просьбы обрабатываются детерминированно, сложный план проверяется по закрытой схеме до исполнения. Набора регулярных выражений недостаточно. Невозможность корректного плана приводит к понятному уточнению, не к отказу доступной функции из-за бренда модели.

Нельзя незаметно передавать приватные данные или запрос другой платной модели для маршрутизации. Дополнительный планировщик — только явно настроенный маршрут с правами, журналом и бюджетом. Внешняя смена провайдера и резервный платный вызов не включаются автоматически.

Приёмка: один набор просьб через все четыре семейства при одинаковых правах. Текстовая модель без Vision находит и показывает картинки, не заявляя анализа пикселей. Неисполняемый инструмент не рекламируется как доступный.

## R02. Контракт инструмента и надёжность

У каждого инструмента: версия аргументов/результата, полномочия, допустимые источники, пределы размера, timeout, квота, отмена и классификация ошибок. Аргументы модели недоверенные; URL, ID и пути проверяет сервер.

Операция хранит owner/scope, requestId, выбранную модель, версию политики и дочерние вызовы. Результаты или ссылки на неизменяемые версии сохраняются. Replay/SSE recovery/reload не повторяют успешно выполненное внешнее действие. Неизвестный исход сначала сверяется, а не повторяется вслепую. Универсальное exactly-once без поддержки внешнего API не обещается.

Поддержать последовательность разрешённых инструментов, например поиск → чтение файла → таблица. Цикл ограничен числом шагов, временем и бюджетом, настроенными сервером. Предел «один инструмент и один ответ» не должен молча блокировать такую просьбу.

Приёмка: отказ прав/бюджета до внешнего вызова; повтор ID без дубля; Stop между этапами не запускает следующий; неизвестное остаётся UNKNOWN/PENDING, не SUCCESS.

# 5. Поток, стадии и остановка

## R03. Настоящий потоковый вывод

Устранить подавление onDelta при предложенных инструментах. Пользовательский текст передаётся по мере получения независимо от наличия и фактического вызова tools. Служебные аргументы, внутренние сообщения и скрытые рассуждения не отображаются. Не удерживать весь ответ ради возможного будущего tool call и не имитировать поток печатанием готового текста.

Итог после инструмента также идёт потоком. Порядок показанного текста сохраняется; повторы событий не дублируются. Для объективно непотокового провайдера показывается честное ограничение, streaming-приёмка этой модели не считается успешной.

Приёмка: управляемый провайдер отдаёт минимум три фрагмента; первый виден в браузере до разрешения провайдеру завершиться. Повторить без tools, с предложенными невызванными tools, с вызовом, с длинным кодом и recovery. Проверять порядок событий, не хрупкий таймер. Проектная накладная задержка ASA после получения содержательного фрагмента: p95 ≤ 300 мс на согласованном стенде; размышление модели измеряется отдельно.

## R04. Правдивые статусы

Добавить обратно совместимые структурированные progress-события: operationId, монотонный sequence, phase и безопасные метаданные инструмента. Секреты, цепочка рассуждений, полные документы и приватный поисковый запрос не отправляются в служебную телеметрию.

| Реальное состояние | Подпись |
| --- | --- |
| Ожидание исполнителя | В очереди… |
| Обработка без известной стадии модели | Обрабатываю запрос… |
| Провайдер подтвердил размышление | Обдумываю… |
| Запущен web search | Ищу в интернете… |
| Запущен image search | Ищу изображения… |
| Читается выбранный файл | Читаю файл… |
| Формируется файл | Создаю файл… |
| Работает генератор | Создаю изображение… |
| Приходит пользовательский текст | Пишу ответ… |
| Stop запрошен, не подтверждён | Останавливаю… |

«Готовлю ответ…» не является универсальным статусом. Допустим спокойный accent существующей темы, но смысл передаётся текстом. Не выдумывать проценты. Индикатор не ухудшает различимость Stop и не перемещает кнопку.

Heartbeat имеет интервал меньше минимального согласованного idle timeout API → прокси → браузер. Начальное проектное значение 10 секунд уточняется измерением. Heartbeat не сообщение и не расход квоты.

Приёмка: подписи соответствуют реальным событиям; выключенный поиск не показывает «Ищу»; terminal/error/cancel убирают индикатор. Проверить внешний установленный прокси, не только localhost.

## R05. Stop, обрыв и восстановление

Stop немедленно меняет UI и отправляет серверную отмену; цель локального UI-отклика ≤ 1 секунды. Следующие инструменты после отмены не запускаются. Повтор Stop безопасен и проверяет владельца.

Полученный текст сохраняется как незавершённый. Пока upstream не подтвердил остановку, нельзя объявлять отмену завершённой или расход нулевым. Расход и lease сверяются управляемо; зависший запрос не блокирует диалог бессрочно. Recovery использует тот же requestId. «Повторить» — новая генерация, а не замаскированное бесплатное восстановление.

Приёмка: Stop до первого текста, во время текста/поиска/генерации изображения; разрыв/reload; чужой owner не отменяет запрос; история и расход без дублей; после terminal поле ввода снова работает.
