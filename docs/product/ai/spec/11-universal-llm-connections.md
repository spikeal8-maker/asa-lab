# 11. Универсальные подключения Ollama, llama.cpp и совместимых API

**Редакция 1.0 — 26 ноября 2026 года.** Дополнение [единого ТЗ AI-блока](../../ASA_AI_ASSISTANT_SPEC.md), а не отдельный master. Задача реализации: [Issue #1333](https://github.com/spikeal8-maker/asa-lab/issues/1333). Предшествующее требование удалённой Ollama: [Issue #708](https://github.com/spikeal8-maker/asa-lab/issues/708).

**Назначение:** администратор вводит доступный серверу ASA Lab адрес, при необходимости включает авторизацию, получает модели, выбирает модель и подключает её. Одинаковый сценарий работает на своём компьютере, в локальной сети, через Tailscale и с предоставленным внешним HTTPS API. Интерфейс остаётся компактным; особенности протокола переводит адаптер.

**Статус документа — целевое требование.** Публикация не подтверждает реализацию, готовность D2R2 или доступ школьной установки. Состояние исполнения находится только в [current.yaml](../../../execution/current.yaml) и связанных evidence. UC-01–UC-14 ниже — ограниченные уточнения ASAI-03, ASAI-09 и ASAI-43; они не заменяют каталог ASAI-01–ASAI-44 и не разрешают запускать всю программу автоматически.

## 1. Как использовать ТЗ

1. Прочитать [AGENTS.md](../../../../AGENTS.md), [START_HERE_FOR_AI.md](../../../../START_HERE_FOR_AI.md), [вход AI-исполнителя](../README.md) и [контракт карточки](../TASK_CONTRACT.md). Восстановить Git/CI snapshot и выполнить preflight с точными planned paths.
2. Получить один выбранный UC-ID с соответствующим ASAI, зависимостями, границами и разрешениями. Первое рекомендуемое поручение — UC-01, если контролёр не подтвердил, что его результат уже принят.
3. Реализовать одну цельную пользовательскую вертикаль. Каждый затронутый экран должен работать в этом же срезе; «backend готов, UI потом» не закрывает карточку.
4. Проверить конкретные сценарии из раздела 14, актуальные domain contracts и обязательные gates. Отчёт и evidence привязать к точному SHA.
5. Предъявить результат и остановиться. Следующий срез назначает контролёр. Документ не разрешает deployment, изменение школьной БД, VPN или процесса модели.

Требования этой главы уточняют R21, R24, R28, R31–R33 и `AI-LOCAL-LLAMACPP-001`. Они устраняют ограничения прежней реализации и недопустимые для универсального подключения предположения «только частная сеть», «всегда 8080», «всегда 120000», «одна конкретная Qwen», «ключ обязателен» и «сохранение всегда вызывает модель» **по мере принятия соответствующего среза**. Не все эти предположения были фактическим контрактом: текущий llama.cpp уже допускает отсутствие ключа. Остальные требования единого ТЗ сохраняются.

До принятия UC-02 действует текущий private-only transport contract. UC-02 обязан одним согласованным изменением реализовать новую политику назначения, обновить [AI domain contract](../../../agent/contracts/ai-assistant.yaml) и [surface map](../../../agent/surfaces/ai-assistant.yaml), сохранив защиту адресов и секретов и проверив production transport. Простое удаление `public_llamacpp_endpoint` из запретов не является реализацией.

## 2. Границы совместимости

### 2.1. Три адаптера, общие настройки

| Адаптер | Основной протокол | Обнаружение | Что сохраняется отдельным |
| --- | --- | --- | --- |
| Ollama | Native `/api/chat`, NDJSON | `/api/tags`, затем `/api/show` выбранной модели; `/api/ps` и версия при доступности | Существующий раздел Ollama, его модельная семантика и параметры |
| llama.cpp | Chat Completions `/v1/chat/completions`, SSE | `/v1/models`, доступные метаданные llama-server | Существующий отдельный раздел llama.cpp рядом с Ollama |
| Совместимый API | Проверенный профиль Chat Completions, SSE | `/v1/models`, если разрешён; иначе ручной ID модели | Отдельный дополнительный тип подключения, без переименования облачных провайдеров |

Общими являются профили подключений, нормализация адреса, проверка назначения, авторизация, секреты, ревизии, жизненный цикл настроек, модельные возможности, ошибки и компоненты формы. Native Ollama не превращать в OpenAI-совместимый адаптер. llama.cpp не направлять в `/v1/responses`.

Совместимость определяется работающим контрактом, а не названием программы. LM Studio, vLLM и чужой шлюз могут использовать совместимый адаптер в поддерживаемой части API. Responses-only, Anthropic Messages, интерактивный OAuth, клиентские TLS-сертификаты и произвольные нестандартные протоколы не обещать без отдельного адаптера. Отсутствие необязательных метаданных не должно запрещать рабочий Chat Completions.

Ollama Cloud, DeepSeek, OpenAI, Polza и другие существующие подключения сохраняют независимые настройки, порядок навигации и поведение. Ollama Cloud не является другим названием DeepSeek. Доступный через локальную Ollama облачный маршрут показывать как облачный, если это подтверждено метаданными; не подписывать весь раздел «бесплатно» или «без ключа».

### 2.2. Поддерживаемые размещения

| Размещение модели | Что вводит администратор | Откуда должна проходить проверка |
| --- | --- | --- |
| Тот же компьютер, что backend ASA | Разрешённый loopback/адрес хоста и порт | Из runtime backend; при Docker loopback относится к контейнеру |
| Отдельный компьютер в LAN | IP или DNS и порт | Из backend ASA с реальной маршрутизацией этой установки |
| Tailscale / другая частная сеть | Доступный VPN IP или DNS | Из backend ASA; наличие VPN только на ноутбуке пользователя недостаточно |
| Чужой сервер в интернете | HTTPS URL, включая разрешённый префикс, и при необходимости ключ | Из backend ASA с проверкой TLS и назначения |
| Reverse proxy / подкаталог | Полный выданный URL и нужный режим авторизации | Из backend ASA; префикс сохраняется во всех маршрутах |

Если пользователь открывает ASA Lab в браузере, браузеру не требуется прямой доступ к модели. Нельзя проверять подключение из браузера и выдавать это за проверку backend, обходить CORS публикацией ключа клиенту или автоматически открывать порты роутера. Смена сети требует доступного маршрута и актуального DNS/VPN; интерфейс честно сообщает проблему, а не обещает доступ из любой сети без инфраструктуры.

### 2.3. Что не входит в реализацию

Не устанавливать модели, не менять файлы GGUF/mmproj, GPU offload, MTP, серверный chat template, power limit, глобальные свойства llama-server, параметры запуска и службы ОС. Не запускать загрузку всех моделей при discovery. Не менять ComfyUI и выделенный для него компьютер/GPU. Не создавать второй постоянный стек ASA, параллельную рабочую БД или второй AI-чат. Изолированные тестовые БД и копии данных для проверки миграции используются только по штатному тестовому контракту. Проверка доступа не является разрешением перезапускать сервер, менять Tailscale, firewall или публиковать API в интернете.

## 4. Профиль подключения и идентичность модели

### 4.1. Обязательные сущности

Это требования к доменной модели, не команда создать параллельную схему вместо существующей.

| Сущность | Обязательные свойства |
| --- | --- |
| Подключение | Неизменяемый `connectionId`, административный scope существующей установки, тип адаптера, пользовательское название, нормализованный endpoint/API root, политика назначения, режим авторизации, ссылка на секрет, включение, ревизия |
| Модель подключения | Пара `(connectionId, upstreamModelId)`; ID сервера хранится без самовольного изменения; имя для интерфейса отдельно; источник auto/manual; доступность и возможности |
| Настройки модели | Конкретное подключение + модель; лимиты ASA и поддерживаемые параметры, режимы наследования и явные значения |
| Доказательство | Вид проверки, модель, endpoint scope, ревизия credentials/config, время, версия сервера при наличии, результат/ограничения; без секрета и текста пользовательского запроса |
| Операция чата | Неизменяемый snapshot подключения, модели, параметров и policy на момент допуска, собственный ID учёта/отмены |

Одно имя модели на двух серверах означает две разные доступные модели. Изменение URL не меняет `connectionId`, но инвалидирует связанные проверки и повторное использование credentials. Переименование модели для UI не меняет upstream ID. Не выводить модель из имени файла, бренда GPU, названия профиля или ранее установленной Qwen.

Смена endpoint scope сохраняет прежние model-specific overrides только как непроверенный черновик, даже если новый сервер вернул тот же model ID. До активации валидировать их по контракту нового назначения; прежние metadata, runtime-контекст и capability evidence не переносить. При недоступных свойствах предложить «Как на сервере» либо явно подтверждённую администратором ручную настройку в рамках разрешённого parameter registry, не выдавая её за обнаруженную. Не сбрасывать пользовательские значения и не отправлять их новому назначению незаметно.

Администратор может добавить, переименовать, выключить и архивировать несколько подключений одного типа. Архивирование не удаляет историю, usage и оригинальные идентификаторы. Если модель исчезла, прежняя история остаётся читаемой, а новая генерация сообщает недоступность и предлагает явный разрешённый выбор. Не переносить пользовательские default-модели автоматически и не подменять недоступную модель другой.

### 4.2. Миграция

Каждое существующее singleton-подключение получает ровно один профиль, устойчивую связь со старым provider/model ID и прежний административный scope. Сохранить ключи, фактические параметры, включение, историю, персональные выборы, бюджеты и права. Повторный запуск миграции не создаёт дубликаты и не перешифровывает секрет новым случайным ключом. Опубликованные SQL-миграции не редактировать.

Если старое приложение неявно подставляло `120000`, `xhigh`, `false`, `keep_alive=-1` или `num_predict=-1`, сначала зафиксировать фактически действовавшую семантику существующей настройки как legacy override. При обновлении она не должна незаметно измениться. Для новых профилей эти аппаратно/модельно-зависимые подстановки не применяются. Администратор получает действие «Вернуть настройки сервера» с явным изменением overrides. Вредные/неподдерживаемые старые значения помечаются для исправления; нельзя молча заявить, что они работают.

Проверять обновление на копии базы с существующими профилями, диалогами, вложениями, ключами и model selections, а не только на пустой БД. Проверить обратную совместимость старых API-клиентов в поддерживаемом окне обновления и безопасный порядок API/Web migrations. План отката не должен требовать удаления новых диалогов или отката рабочей БД без штатного восстановления.

## 5. Адрес и сетевой транспорт

### 5.1. Нормализация

- Принимать IP, DNS, `host:port`, HTTP(S) URL, IPv6 literal в корректных скобках, корень API и разрешённый префикс reverse proxy. Не делать port scanning.
- Для голого IPv4/DNS без схемы/порта предложить видимый редактируемый preset: HTTP:11434 для native Ollama, HTTP:8080 для llama.cpp. Для совместимого API без явной схемы/порта предложить HTTPS:443; не угадывать нестандартный порт по названию программы. Показать итоговый адрес до применения.
- У полного `http://...` без порта сохранить стандартный HTTP:80; у `https://...` — HTTPS:443. Никогда не превращать полный HTTPS URL в `:8080` или `:11434`.
- Разделять origin, сохранённый proxy prefix и API suffix. Native Ollama использует `/api`, llama.cpp/совместимый профиль — `/v1`. Ввод корня или уже указанного API root не должен давать `/v1/v1`, `/api/api` или терять префикс.
- Неоднозначный нестандартный путь не «чинить» обрезанием. В «Дополнительно» разрешить указать API root явно, сохранить результат и использовать его во всех chat/discovery/probe/tokenizer маршрутах. Для llama-specific метаданных допускается отдельный подтверждённый server root того же разрешённого назначения; при неизвестном root метаданные необязательны.
- Убирать только безопасный завершающий slash, нормализовать схему/host/порт по URL parser, сохранять регистр значимой части path. Нельзя снимать `/v1` или `/api` в середине пользовательского префикса.
- Запретить userinfo/пароль в URL, query/fragment как средство передачи ключа, неподдерживаемые схемы, неоднозначные escaped/double-encoded пути, traversal и CR/LF. Модель и другие значения кодировать как данные, не как часть адреса.

Для одинакового ввода client preview и backend canonicalization должны совпадать; backend остаётся источником истины. Корректность URL не означает сетевую доступность.

### 5.2. Политика назначения

Настраивать endpoint может только существующая административная роль с правом управления AI. Подключение к частным сетям — штатный сценарий, не повод блокировать весь LAN/Tailscale. Внешние HTTPS назначения разрешаются утверждённой политикой установки и конкретным сохранённым профилем. Произвольный URL из сообщения, tool arguments или student request не может стать адресом LLM.

Все HTTP-операции, включая discovery, token counting и запросы метаданных, проходят один проверяемый transport. Сохранять:

1. Проверку IPv4/IPv6 и DNS-результатов, запрет metadata/link-local/multicast/unspecified и иных служебных назначений. Loopback допускается только как явно настроенное локальное LLM-подключение к точному адресу/порту, а не как разрешение доступа ко всем сервисам хоста.
2. Проверку всех кандидатов DNS, закрепление допустимого разрешения на время конкретного соединения, отсутствие повторного непроверенного DNS resolve. DNS rebinding, смешанный допустимый/запрещённый ответ и обход через IPv4-mapped IPv6 не должны открывать запрещённое назначение.
3. Запрет автоматического redirect для запросов с данными/секретами; предпочтительно единый запрет redirects для адаптеров. Ответ с перенаправлением показывает необходимость указать конечный адрес, не пересылает ключ автоматически.
4. Проверку TLS-сертификата и hostname; запрет `NODE_TLS_REJECT_UNAUTHORIZED=0` и аналогичного глобального обхода. Для частного CA использовать управляемое доверие установки, не переключатель «отключить TLS» в обычной форме.
5. Ограниченные timeout, размеры тела и каталога, streaming backpressure, отмену и максимальное число операций discovery. Настраиваемый длинный запуск модели не означает бесконечный запрос.

HTTP для разрешённого LAN/VPN/loopback допустим. Публичный нешифрованный HTTP с ключами/сообщениями не входит в базовый профиль; поддержка такого исключения требует отдельной явной политики установки и не включается адаптером автоматически. Не путать эту границу с необязательностью API-ключа внутри Tailscale.

## 6. Авторизация и секреты

### 6.1. Основная форма

Для **каждого** из трёх адаптеров обязательны режимы «Без ключа» и «API-ключ». Второй означает Bearer, если профиль протокола не определяет иное. При выборе «Без ключа» поле ключа скрыто, запрос не содержит `Authorization`, `x-api-key` или сохранённого ранее секрета. SDK-заглушка вроде `dummy`, `ollama` или `sk-local` не должна уходить на сервер ради удовлетворения клиентской валидации.

В режиме Bearer новый пустой ключ допустим только если у той же записи/endpoint scope есть действующий сохранённый ключ и показано «Ключ сохранён». Пустая строка сама по себе не означает удаление. «Заменить» и «Удалить» — разные явные действия. После перехода в «Без ключа» сохранённый секрет перестаёт использоваться; его удаление или сохранение для последующего осознанного возврата отражено в серверной модели, без скрытой отправки.

Не требовать ввод ключа при HTTP 403 на необязательные метаданные, если чат по тому же профилю разрешён. Не считать успех незащищённого `/health` доказательством правильного ключа. Проверка авторизации относится к конкретному API и операции.

### 6.2. Шлюзы и расширенные режимы

В «Дополнительно» предусмотреть явный Basic и именованный API-key header для шлюзов. Дополнительные заголовки — ограниченный проверяемый набор; секретные значения используют то же серверное хранилище. Нельзя одновременно сгенерировать два конфликтующих `Authorization` или переопределить `Host`, transport/routing headers, cookies приложения и hop-by-hop headers.

Если нужны credentials шлюза и upstream одновременно, это допустимо лишь при явно известной схеме разных заголовков; интерфейс не обещает решить два несовместимых Bearer в одном `Authorization`. Ошибка конфигурации видна до проверки. Login/OAuth/mTLS через неизвестный портал не имитируется API-ключом.

### 6.3. Обязательные гарантии

- Секреты шифруются существующим серверным механизмом. Backend после сохранения возвращает только наличие/тип/ревизию; значение не возвращается в HTML/DOM, JSON настроек, экспорт, telemetry, GitHub, exception stack или clipboard без отдельного предусмотренного механизма.
- Привязка включает scheme, host, port и path scope. Переход между `/tenant-a/` и `/tenant-b/` на одном host не разрешает автоматическую отправку прежнего ключа. Изменение адреса, режима или scope требует нового ввода либо явного подтверждения повторного использования для указанного назначения.
- Probe получает неизменяемую пару endpoint + credential revision. Поздний ответ от старого адреса/ключа не активирует новую форму. Нельзя отправлять «ещё не подтверждённый ключ нового поля» фоновым запросом на старый endpoint.
- Отсутствие ключа — нормальное состояние; оно не ослабляет права ASA, изоляцию владельцев и политику назначения. Не добавлять искусственный обязательный ключ ради интерфейса.
- В тестах только синтетические секреты и адреса. Реальные IP, tailnet names, ключи и эксплуатационные конфиги не коммитить и не публиковать в Issue/evidence.

## 7. Обнаружение, модели и доказанные возможности

### 7.1. Сценарий обнаружения

После ввода синтаксически корректного адреса автоматически запрашивать каталог с debounce около 450 мс. Изменение relevant credentials повторяет discovery. Разрешить явную кнопку «Обновить». Не выполнять запрос на каждый символ, не показывать красную сетевую ошибку для ещё не завершённого ввода.

Каждый запрос связан с ID профиля, canonical endpoint, ревизией auth, поколением формы и типом адаптера. Предыдущий запрос отменяется; ответ дополнительно отбрасывается, если snapshot устарел. Загрузка не сбрасывает введённые поля, фокус, scroll и выбранную модель.

Одна доступная chat-модель выбирается в **черновике** автоматически, несколько — предоставляют выбор. Автовыбор не включает провайдер, не меняет default пользователя и не запускает inference. Ноль моделей, недоступный каталог, restricted catalogue, loading и сетевая ошибка — разные состояния.

| Ситуация | Требуемое поведение |
| --- | --- |
| Native Ollama | `/api/tags` даёт каталог; `/api/show` выбранной модели — сведения и capabilities; `/api/ps` может уточнить загруженную модель/контекст. Отсутствие модели в `ps` не означает отсутствия в каталоге |
| llama.cpp, один сервер | `/v1/models` даёт ID; свойства выбранной модели запрашиваются только по доступному проверенному маршруту |
| llama.cpp router, холодная модель | При подтверждённой семантике использовать чтение свойств с `autoload=false`; не запускать все модели. Недоступные свойства = неизвестно. Глобальное `n_ctx=0` не означает нулевое окно всех моделей |
| Metadata закрыта 401/403 | Отметить ограничение конкретной операции. Если основной API разрешён, не блокировать подключение только из-за отсутствия метаданных |
| `/v1/models` отсутствует/закрыт | Дать «Указать ID вручную»; проверять выбранный ID коротким chat-запросом по явному действию администратора |
| Сервер вернул embedding-only/неизвестные типы | Не объявлять все ID пригодными для чата; неизвестное проверять выбранным ограниченным probe |
| Каталог сменился | Сохранять исчезнувший выбранный ID как недоступный; не подменять другой моделью автоматически |

Ручной model ID добавляет только администратор. Обычный пользователь выбирает разрешённую запись из серверного каталога ASA и не получает произвольный доступ к любой upstream-модели. Opaque ID отправляется серверу буквально, без удаления tag, namespace, quantization или alias.

Если для данной версии/шлюза не подтверждено чтение свойств без загрузки, не вызывать модельный `/props` при пассивном discovery: неизвестный параметр `autoload=false` может быть проигнорирован. Оставить свойства неизвестными и уточнить их после явной проверки выбранной модели. Запрет автозагрузки важнее полноты metadata на первом экране.

### 7.2. Возможности

Для vision, tools, reasoning, reasoning levels, streaming, structured output и иных используемых возможностей хранить минимум `supported / unsupported / unknown` с источником, временем и привязкой к snapshot. Отдельно различать «заявлено сервером/профилем», «проверено запросом» и «разрешено политикой ASA». Неизвестно не равно запрещено и не равно поддерживается.

Приоритет достоверности: проверенная семантика конкретной версии/адаптера и runtime evidence, затем корректные metadata. Вывод по имени Qwen/DeepSeek/Llama или успешный HTTP 200 с проигнорированным полем не является подтверждением. Смена модели/адреса/auth/релевантной версии сервера инвалидирует evidence; TTL и ручное обновление ограничены и отражены в диагностике.

Probe по действию администратора может загрузить **выбранную** холодную модель. Это показывается коротким состоянием «Модель запускается». Не запускать vision/tool/длинный контекст при обычном открытии страницы. Не хранить серверные рекламные claims как результат собственной проверки качества.

Официальные основания: [Ollama API](https://docs.ollama.com/api/tags), [model details](https://docs.ollama.com/api-reference/show-model-details), [running models](https://docs.ollama.com/api/ps), [llama-server API](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Реальный ответ установленной версии важнее предположения о текущем `master` документации.

## 8. Настройки модели: сервер, ASA и явное значение

### 8.1. Семантика значений

Каждый поддерживаемый параметр должен различать три состояния: наследовать профиль ASA, использовать настройки сервера и задать явное значение. В простой форме достаточно «Как на сервере» и доступных значений; наследование общей политики показывается короткой подписью с источником. Нельзя одинаковым `null` представить отсутствие значения, сброс и унаследованное значение.

Для каждого наследуемого параметра обязательно доступно действие «По настройкам подключения/ASA», отличное от «Как на сервере»; его допустимо поместить в «Дополнительно». Подпись источника не заменяет это действие. Наследование отслеживает последующие изменения родительской настройки, явное значение сохраняет своё значение, а выбор сервера продолжает исключать необязательный параметр из запроса.

Порядок разрешения: обязательные права/лимиты ASA → явные настройки конкретной модели подключения → настройки подключения → общие необязательные настройки ASA → сервер. «Как на сервере» является явным выбором **не отправлять** соответствующий необязательный параметр после всех merge, даже если выше есть старый default. Обязательный лимит ASA не обходится этим выбором; итоговая форма показывает «Ограничено ASA» и действующее значение, а не ложное обещание полного server default.

Backend валидирует итоговый request, а не только поля формы. Отсутствие поля и явные `false`, `0`, пустой массив или пустая строка не смешиваются. Недопустимое значение даёт полевую ошибку до inference; параметр нельзя молча отбросить, переименовать в случайное поле или отправить одинаково всем адаптерам.

Параметры temperature, top-p, top-k, min-p, seed, stop и output limit доступны только в подтверждённом контракте соответствующего адаптера/модели. Диапазоны и единицы определяет versioned registry с источником. Не применять один выдуманный диапазон ко всем серверам. В обычной форме — контекст, размышления и длина ответа; остальные параметры в «Дополнительно». Произвольный JSON, способный переопределить `model`, `messages`, `tools`, auth, endpoint или policy, не является универсальными настройками.

### 8.2. Контекст

| Значение | Что означает | Как показывать/использовать |
| --- | --- | --- |
| Максимум модели | Тренировочное/архитектурное окно из достоверных метаданных | Справочно, с источником; это не доступный объём запущенного сервера |
| Рабочий контекст сервера | Фактически доступное окно выбранной модели/слота | Read-only «Контекст сервера»; `null`/неизвестно вместо выдуманного числа |
| Лимит контекста ASA | Сколько полного запроса/истории разрешает использовать приложение | Административная политика; не обещает увеличить память сервера |
| Резерв / лимит ответа ASA | Допустимая генерация с учётом семантики модели, включая reasoning при необходимости | Отдельное поле, источник и единицы; не называть его размером входного контекста |
| Контекст Ollama | Поддерживаемый override `options.num_ctx` | Только в расширенных настройках native Ollama; «Авто» не отправляет поле |

У llama.cpp клиентский лимит истории не меняет выделенный сервером KV cache. Не отправлять ему Ollama `num_ctx`. Не делить общий серверный `n_ctx` на число слотов вслепую: использовать значение, документированное данной версией как доступное конкретному запросу/слоту. Глобальные нули router и metadata другой модели не являются лимитом выбранной модели.

В native Ollama изменение `num_ctx` может менять выделение памяти/перезагрузку модели; пояснение размещать в InfoHint. Не привязывать его скрыто к длине истории ASA. [Контекст Ollama](https://docs.ollama.com/context-length) и [API compatibility](https://docs.ollama.com/api/openai-compatibility) описывают разные возможности native и совместимого API; не смешивать их.

Для native Ollama отдельно хранить наблюдаемый контекст текущей загрузки, запрошенный `num_ctx` и достоверно известный жёсткий предел провайдера. `/api/ps.context_length` — наблюдение текущего runtime, не неизменный предел следующего запроса с другим `num_ctx`. Изменение override инвалидирует прежнее evidence; после явного probe обновляются доступные runtime-сведения. Старые наблюдаемые 4096 не запрещают сами по себе запрос 32768, но сохранённые 32768 ещё не означают подтверждённую аллокацию. До подтверждения отображать «Запрошено», при неоднозначном общем runtime — неизвестность. Дополнительные технические величины не превращать в пять одинаковых полей основной формы.

При известном применимом к данному запросу рабочем окне выполняется ограничение: **system + сообщения + schemas инструментов + tool results + изображения/служебный template + резерв ответа ≤ min(доступное окно сервера, применимый лимит ASA)**. Для нового Ollama override не использовать устаревшее наблюдаемое окно как hard cap; запрошенный размер остаётся непроверенным до evidence и ограничивается достоверными пределами/политикой ASA. Учитывать все части, а не только видимый текст пользователя. При несовместимых обязательных минимумах выдавать понятную ошибку, а не отрицательный/нулевой budget.

Если рабочее окно неизвестно, «Авто» сохраняет его неизвестным и не блокирует короткий обычный запрос. Действуют существующие ограничители ASA на размер запроса, объём принимаемого ответа, число шагов инструментов и время; content, reasoning и аргументы tools входят в лимиты. Источник этих ограничителей — политика ASA. Не показывать точный процент заполнения окна и не обещать вместимость длинной истории. Новые числовые presets должны быть отдельной версионированной политикой и пройти обычную и reasoning-модель; не вводить скрытый универсальный `120000` или короткий output cap, съедающий весь итоговый ответ размышлениями.

Если точный счётчик поддерживается, использовать его через тот же разрешённый transport и с реальным полным сообщением/template. Исправить allowlist и dispatch tokenization вместе; тест, заменяющий transport mock-ответом до маршрутизации, недостаточен. Для vision обычная токенизация строки base64 не равна цене изображения. При неполном счётчике использовать явно обозначенную оценку с запасом; estimated usage не выдавать за фактические данные провайдера.

Сжатие/усечение сохраняет системные ограничения, последний запрос, связанные вложения и целые пары tool-call/result; не оставляет orphan result. Пользователь видит факт сокращения истории. Если обязательное сообщение само не помещается — ошибка с действием уменьшить вход/изменить разрешённый лимит; не удалять его молча. Автоматический повтор генерации после ошибки контекста не входит в базовый сценарий: показать причину и предложить явное повторение после изменения, не создавать скрытый расход или повтор инструментов.

### 8.3. Размышления

Различать: возможность reasoning, включение вычисления, доступные уровни, бюджет reasoning и отображение reasoning пользователю. Скрытие текста размышлений в UI не означает отключение вычислений. MTP не является пользовательским уровнем reasoning.

| Состояние | Контрол |
| --- | --- |
| Серверный режим / неизвестная управляемость | «Как на сервере»; короткая отметка, что управление не подтверждено |
| Подтверждённый boolean | «Как на сервере / Включено / Выключено» только при подтверждённой семантике полного отключения; иначе название фактического режима |
| Подтверждённые уровни | Только реально поддерживаемые значения с короткими русскими подписями |
| Отдельно поддерживаемый budget | Число с единицами и допустимым диапазоном; отдельное от effort |
| Управление не поддерживается | Read-only «Управляется сервером»; не показывать действующий фиктивный выключатель |

Native Ollama использует поддерживаемую конкретной моделью семантику `think`; некоторые модели принимают boolean, другие — набор уровней. При наличии `thinking.values` и `thinking.default` в `/api/show` использовать их точные типы/значения; отсутствие этих полей у старой версии не превращать в отрицание reasoning. `false` не обещает полное отключение у всех моделей. llama.cpp может управлять через `reasoning_effort` или template-specific параметры: отправлять только подтверждённый вариант данной версии/template. Не дублировать взаимоисключающие параметры, не подставлять всем `xhigh`, не распознавать возможности по единственному имени `qwen3.8:27b`.

Если сервер принимает, но игнорирует поле, помечать управление непроверенным; валидный JSON и 200 не доказывают влияние на вычисление. Смена модели меняет набор допустимых настроек и сохраняет отдельный профиль прежней модели. Unsupported value не преобразуется незаметно в другой уровень. Основания: [Ollama thinking](https://docs.ollama.com/capabilities/thinking), [llama-server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

## 9. Vision, инструменты и поток ответа

### 9.1. Изображения

Vision — обязательная часть этого требования: после UC-10 подходящая модель должна получать и анализировать настоящие пиксели через ASA Lab. Флажок capabilities и успех текстового probe не закрывают её.

1. Убрать безусловный запрет изображений для llama.cpp только вместе с работающей цепочкой authorization → собственное вложение → проверенные байты/MIME → допустимое сообщение адаптера → upstream → ответ/история/replay.
2. Переиспользовать приватные вложения ASA, ограничения размера/количества и проверку владельца. Native Ollama получает поддерживаемый формат `images`; llama.cpp/совместимый Chat Completions — typed content с поддерживаемым представлением изображения, например data URL. Не отправлять путь на диске браузера, имя файла вместо пикселей или общедоступную ссылку на приватное вложение.
3. Проверить PNG и JPEG, несколько изображений при разрешённом лимите; WebP и преобразования — только по подтверждённому pipeline. Не объявлять весь набор браузерных MIME поддерживаемым автоматически.
4. Доступность определяется пересечением возможностей модели, runtime, адаптера и политики ASA. При unknown предложить явный ограниченный тест. При text-only — понятное сообщение до отправки, без скрытого удаления вложения или переключения в облако.
5. Проверить новый вопрос, продолжение, сохранение истории, повторный показ и новый вариант ответа с исходными вложениями по действующим owner contracts. Повторный показ не запускает inference заново.
6. Приёмка качества содержит изображения с непредсказуемыми из текста числами/метками и визуальным отношением объектов. Ответ не должен вытекать из filename/prompt. Раздельно фиксировать корректность передачи и качество конкретной модели.

Проблемы mmproj, vision encoder и размещения на CPU/GPU выводить в диагностике как сведения/предположения с основанием. ASA не должна «исправлять» их перезапуском чужого сервера или переносом нагрузки на ComfyUI GPU. Источники: [Ollama vision](https://docs.ollama.com/capabilities/vision), [llama.cpp multimodal](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md).

### 9.2. Инструменты

Проверять полный цикл: tool declaration → валидный tool call → существующий разрешённый executor ASA → tool result → финальный ответ. Безопасный probe не даёт права выполнять произвольную команду; для теста использовать ограниченный детерминированный инструмент без внешнего эффекта. Проверять схему, ID/имя, JSON-аргументы, принадлежность результата и поддерживаемость parallel calls.

Все существующие role/owner/category/rate/budget ограничения применяются к новому адаптеру. Не включать встроенные tools или MCP удалённого сервера автоматически и не выдавать ему системные credentials ASA. Синтаксическая генерация tool-call без успешного полного цикла помечается частичным evidence. Источники: [Ollama tool calling](https://docs.ollama.com/capabilities/tool-calling), [llama.cpp function calling](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md).

### 9.3. Streaming, отмена, usage

Native Ollama NDJSON и совместимый SSE разбираются разными protocol parsers с общим внутренним событием. Проверить разделение UTF-8/JSON/SSE события между сетевыми chunk, content/reasoning/tool deltas, finish, usage, терминальный `[DONE]`, disconnect и ошибку внутри HTTP 200. Не сохранять частичный ответ как успешный, не терять уже полученный текст при позднем сбое.

Стоп отменяет только собственный upstream/ожидание/инструмент в пределах действующего контракта. Не вызывать глобальные server cancel/restart/unload. После отмены и сетевого разрыва сохранять честное terminal/unknown состояние и usage. Неизвестный расход остаётся неизвестным, не становится нулевым; удаление чата не удаляет учёт.

Генерационные POST не повторяются автоматически после неизвестного результата, 5xx, disconnect или начавшегося ответа. Ограниченный retry разрешён только для безопасных read-операций с известной семантикой и deadline. Запрещены скрытая платная смена провайдера, подмена модели и повтор вызвавшего эффект инструмента.

## 10. Черновик, проверка и применение

### 10.1. Отдельные действия

| Действие | Что делает | Что не является его доказательством |
| --- | --- | --- |
| Автообнаружение | Читает каталог/доступные metadata | Не активирует профиль и не доказывает inference |
| «Сохранить» | Сохраняет валидный черновик, включая выключенный/временно недоступный адрес | Не обязано обращаться к модели и не даёт статус «Проверено» |
| «Проверить» | По явному действию выполняет короткий ограниченный запрос выбранной модели с snapshot формы | Успех другой модели, старого адреса или только `/health` недостаточен |
| «Применить» / включить | Проверяет актуальность evidence, при необходимости явно выполняет проверку и атомарно активирует точный snapshot | Ошибка или устаревшая проверка не перезаписывает рабочую конфигурацию |
| Выключить | Запрещает новые генерации профиля, сохраняет необходимые данные | Не требует доступности сервера; не удаляет историю |

Кнопок не должно быть слишком много: сохранить текущий паттерн действий ASA, вторичные операции оформить вторично/в меню; «Применить» может объединять проверку и активацию с явным состоянием. Семантика остаётся разделённой на backend. Начатая операция использует свой snapshot; смена настроек не меняет её credentials посреди потока. Выключение использует действующий контракт отмены уже начатых операций и явно отражает их статус.

### 10.2. Атомарность и гонки

Сохранённый черновик и активный snapshot не смешиваются. Неудачный apply оставляет предыдущую активную конфигурацию, но не теряет введённый черновик. При выключенном провайдере новый введённый URL действительно сохраняется и виден после перезагрузки; нельзя подменять его прежним URL/localhost.

Использовать существующие revision/CAS и долговечный idempotency key операции apply. Probe связан с exact endpoint, model, settings, credential revision и policy. Два окна администратора не перетирают настройки last-write-wins; конфликт предлагает обновить/сверить форму. Повтор кнопки/запроса после reload не запускает повторный probe/inference, если результат уже известен; при неизвестном исходе читается существующая операция, а не создаётся новая вслепую.

Состояния `configured`, `enabled`, `lastProbe`, `runtimeReady` независимы. Сохранённый URL не означает доступность, выключенное подключение не является ошибкой сети, зелёный probe вчера не гарантирует ответ сейчас. Диагностика должна показывать краткую причину и время, не сбрасывая администратору текущую позицию страницы.

## 11. Очередь и эксплуатационные пределы

Ограничение одновременной генерации задаётся на подключение/подтверждённую группу общего ресурса, а не одним singleton на все Ollama или llama.cpp. Несколько профилей, ведущих на один физический сервер/GPU, могут ссылаться на один `resourceGroup`; это явная настройка администратора. Не считать разные URL доказательством независимых ресурсов и не объединять посторонние серверы по одному имени модели.

Для нового непроверенного подключения консервативный старт — одна одновременная генерация; администратор может изменить предел после проверки. Это лимит ASA, не утверждение о числе физических slots. Сохранять fairness, предел ожидания/размера очереди, учёт владельца и отмену своей записи; несколько backend workers не должны независимо занять «единственный» слот. Недоступный сервер не держит общую очередь других подключений.

Разделять сетевой connect timeout, время загрузки холодной модели, первый токен и общий deadline генерации. Использовать существующие ограниченные значения политики ASA, явно документировать изменённые defaults и проверить длинный reasoning без бесконечных ожиданий. Порог истёк — честный timeout/unknown по фактическому этапу, а не успешное завершение. Не обещать конкретную конкурентность или длину контекста по количеству VRAM без реального теста.

## 12. Компактный интерфейс

### 12.1. Компоновка

Переиспользовать текущие `AiAdminWorkspace`, `AdminOllamaPage`, `AdminLlamaCppPage`, `InfoHint` и стили. Разделы Ollama и llama.cpp остаются раздельными и рядом; дополнительные подключения одного типа выбираются внутри своего раздела. Совместимый API добавляется отдельным типом без перестановки существующих облачных страниц. Не делать новый полноэкранный wizard, таблицу из десятков колонок или информационный баннер на полэкрана.

| Зона | Постоянно видимые элементы | Что скрывается до необходимости |
| --- | --- | --- |
| Заголовок | Короткое имя подключения/выбор профиля, включение, статус | Переименование/архивирование и редкие действия в существующем secondary menu |
| Подключение | Адрес, авторизация «Без ключа / API-ключ», поле ключа только при необходимости | Basic/custom header, API root и transport details в «Дополнительно» |
| Модель | Select, обновление, короткие признаки возможностей | Ручной ID при недоступном каталоге/явном выборе; детали metadata в popover |
| Основные настройки | Размышления, контекст сервера, лимит контекста ASA, длина ответа | Sampling, Ollama runtime override, очередь и timeouts в «Дополнительно» |
| Действия | Основная кнопка и короткий результат | Диагностические подробности в раскрытии, не JSON рядом с каждым полем |

Для одного профиля название допускается автоматически сформировать и убрать необязательное поле из основной части. С появлением нескольких профилей селектор и «Добавить» должны быть однозначны. Возможности отображаются одной компактной строкой с переносом, например «Изображения», «Инструменты», «Размышления» и состоянием; не делать большие карточки для каждого флага.

Краткие надписи должны объяснять действие. «Контекст сервера» read-only и «Лимит контекста ASA» editable не могут выглядеть как два одинаковых поля «Контекст». Единица «токены» рядом/в подсказке, число форматируется по locale; отсутствие данных отображается «Неизвестен», не 0.

### 12.2. Подсказки и сообщения

Длинные определения размещать в существующем InfoHint рядом с подписью. Нажатие, клавиатура и touch обязательны; hover не единственный способ. Использовать короткий текст, максимум 2–3 предложения в одном hint. Подробную эксплуатационную справку открывать отдельно, без растягивания обычной формы.

| Поле/состояние | Короткий текст интерфейса | Пояснение по значку |
| --- | --- | --- |
| Адрес | «Адрес сервера» | «К этому адресу подключается сервер ASA Lab. localhost означает компьютер или контейнер, где работает ASA Lab.» |
| Ключ | «Ключ сохранён» + действия замены/удаления | «Ключ хранится на сервере ASA Lab и используется только для этого подключения.» |
| Нет ключа | «Без ключа» | «Выберите этот режим, если сервер не требует авторизацию. Дополнительный ключ создавать не нужно.» |
| Reasoning auto | «Как на сервере» | «ASA не меняет режим размышлений. Доступные переключатели зависят от модели и сервера.» |
| Контекст ASA | «Лимит контекста ASA» | «Ограничивает историю, которую отправляет приложение. Не увеличивает память или контекст удалённого сервера.» |
| Неизвестный контекст | «Неизвестен» | «Сервер не сообщил рабочий размер контекста. Ограничения ASA продолжают действовать.» |
| Каталог закрыт | «Список моделей недоступен» + «Указать ID» | «Некоторые серверы разрешают чат, но не показывают каталог.» |
| Холодная модель | «Модель запускается» | Только при необходимости: «Первый ответ может занять больше времени.» |

Ошибку, мешающую действию, нельзя спрятать только в tooltip. Рядом с полем/действием видны короткая причина и следующий шаг: «Сервер отклонил ключ — замените его», «Не удалось подключиться — проверьте адрес и доступ с сервера ASA», «Проверка устарела — проверьте изменённые настройки». 403 metadata, 401 основного API, timeout, TLS, policy denial и model not found не объединять в «Неверный API-ключ».

Технические подробности открываются отдельно и очищаются от ключей, запросов и персональных данных. В основной форме не показывать имена параметров SDK, raw JSON, внутренние slot ID и stack trace. Обычный пользователь чата видит разрешённую модель и её возможности, но не внутренний endpoint или секреты администратора.

### 12.3. Доступность и устойчивость вёрстки

- InfoHint должен открываться по focus/нажатию/touch, закрываться по Escape и клику снаружи, оставаться в viewport, сохранять/возвращать фокус по паттерну компонента. `role=tooltip` содержит только неинтерактивное описание; ссылки, формы и действия требуют отдельного корректного popover/dialog.
- Использовать видимые label, `aria-describedby`, `aria-invalid`, доступное имя кнопки со значком и ненавязчивое объявление результата через live region. Не озвучивать ошибку на каждый символ ввода. Статус — текст/значок, а не только цвет.
- Сохранить принятую touch-область 44×44 для маленьких иконок без визуального раздувания формы. Tab order соответствует визуальному; открытие подсказки не запирает клавиатуру.
- Desktop: существующая сетка до двух колонок полей; узкая ширина — одна колонка. Сохранить действующие breakpoints там, где подходят (в том числе 660 px); проверять доступную ширину контейнера, не только весь viewport. Не вводить фиксированную высоту карточки, обрезающую ошибки.
- Длинные URL, IPv6, ID модели и сообщения не расширяют страницу. Использовать `min-width: 0`, перенос в статическом тексте, полное значение при просмотре/копировании; ellipsis не единственный доступ к ID. Прокрутка текста внутри input допустима, горизонтальная прокрутка всей страницы — нет.
- При загрузке сохранять место статуса, поля и введённые данные; не переставлять кнопки, не терять фокус/scroll. Раскрытая ошибка может занять нужную высоту и переноситься, а не перекрывать соседние поля.
- Обязательные ширины: 320, 390, 768, 1024, 1440, 1920 CSS px; светлая/тёмная тема, 200% увеличение текста/браузера и reflow узкого контейнера. На мобильном проверить экранную клавиатуру, select и открытый hint у края viewport.

Визуальная приёмка — реальный изменённый ASA Web с согласованной версией API: посмотреть снимки before/after, а не только сохранить их. Проверить empty/loading/ready/no-auth/auth-required/metadata-restricted/error/disabled/unsaved/conflict/long-value состояния. Для гонок, dropdown, hint, Save/Check/Apply — browser trace или запись. Детерминированный тестовый LLM допустим для состояний UI, но такой результат не объявляется живой приёмкой модели или школьной сети.

Основания для доступности: [WAI tooltip pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/), [content on hover/focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html). Следовать поведению паттерна, не копировать слово tooltip на интерактивную панель.

### UC-01 — профили и сохранность

**Проблема:** singleton-провайдер не различает одинаковые модели на разных компьютерах. **Результат:** администратор добавляет два профиля уже поддерживаемого типа, выбирает их в существующем разделе, сохраняет и повторно открывает; прежняя история и default-модель работают.

**Работа:** изучить текущие settings/catalog/model IDs и миграции; добавить аддитивную модель профилей и совместимый resolver старых идентификаторов. Подключить минимальную существующую форму выбора профиля, разрешённый каталог чата и архивирование без уничтожения истории. Сохранить прежние сетевые правила, секреты и ограничение общей нагрузки до UC-02/UC-12; не выдавать новые возможности заранее.

**Выход:** тесты ID-01, MIG-01 и действующих owner/usage contracts; пользовательская демонстрация двух профилей и старой истории; изменение одного не меняет другое. Миграция без доступного UI и проверки обратного чтения не закрывает UC-01.

### UC-02 — URL и сеть

**Проблема:** текущая локальная нормализация исключает законные HTTPS/proxy/IPv6 сценарии и может подставлять неверный порт. **Результат:** администратор вводит полный или короткий адрес, видит правильный canonical endpoint и получает проверку с backend ASA.

**Работа:** единый URL parser/policy/dispatcher для всех маршрутов; проверенные prefix/API-root правила, DNS pinning и TLS. Одновременно согласовать текущие compact contract/surface map с целевым внешним HTTPS при сохранении перечисленных запретов. Показать понятную policy/network ошибку в существующей форме. Не менять host network.

**Выход:** NET-01–NET-06 через production transport, включая отрицательные сценарии; отличие контейнерного localhost объяснено в InfoHint. Удаление private-only guard без замены и тестов — FAIL.

### UC-03 — авторизация

**Проблема:** optional key у llama.cpp и отсутствие общей auth у Ollama не дают одинакового сценария. **Результат:** оба раздела работают с «Без ключа» и Bearer; шлюзовые Basic/custom header доступны в «Дополнительно» без разрастания формы.

**Работа:** общий secret lifecycle и endpoint/path binding, отсутствие заголовка в none, корректная маска/наличие/замена/удаление, конфликты заголовков и права. При изменении адреса старый секрет не отправляется автоматически. Native Ollama не переводится в Cloud.

**Выход:** AUTH-01–AUTH-04, отсутствие секретов в client bundle/ответах/логах; видимый сценарий «401 → ввести ключ → каталог», «с ключом → без ключа», path-scope смена. Наличие dummy key на проводе — FAIL.

### UC-04 — discovery и capability evidence

**Проблема:** metadata и список моделей доступны не у всех серверов; опоздавший запрос может выбрать чужую модель. **Результат:** адрес автоматически даёт реальный каталог либо понятный ручной ввод; возможности отражают данные конкретной модели.

**Работа:** native discovery отдельно от Chat Completions; выбранные metadata без массовой загрузки моделей; tri-state/evidence, bounded catalogue, debounce/cancel/stale filtering. Не считать router `n_ctx=0` свойством всех моделей. Ручной ID остаётся административным действием.

**Выход:** DISC-01–DISC-04, ID-01, проверка двух быстро сменённых адресов/ключей и закрытых metadata; холодные модели не запускаются от открытия страницы. UI не придумывает capabilities по имени.

### UC-05 — совместимый API

**Проблема:** чужой Chat Completions endpoint не обязан иметь расширения llama.cpp. **Результат:** отдельный дополнительный тип подключения выполняет обычный потоковый чат с endpoint, где доступны только согласованные chat routes и model ID.

**Работа:** переиспользовать общий transport/settings/UI, реализовать профиль совместимости и явный набор supported fields. Сохранить существующие Cloud-разделы. Отсутствие `/props`, `/api/show` или `/v1/models` не блокирует ручной рабочий model ID. Не скрывать отсутствие Responses/Anthropic поддержки.

**Выход:** COMP-01, DISC-03, STREAM-01 базового текста, REG-01; видимый выбор разрешённой модели в обычном чате. Успех curl без чата ASA не закрывает UC-05.

### UC-06 — состояния и атомарность

**Проблема:** сохранение, выключение и проверка смешаны; возможна потеря нового URL. **Результат:** offline-черновик сохраняется и открывается, неудачное применение оставляет рабочий профиль, конфликт не теряет введённые значения.

**Работа:** чёткие draft/active snapshots, reuse bound probe, CAS, durable apply ID и восстановление unknown результата; точная семантика кнопок раздела 10. Переиспользовать хорошие свойства текущего llama settings вместо упрощения до last-write-wins.

**Выход:** STATE-01–STATE-04 через API и browser; два окна, двойной клик, reload во время apply, смена URL/model/secret, сохранение выключенного профиля. «После Save появился localhost» — FAIL.

### UC-07 — defaults и параметры

**Проблема:** параметры конкретной установки выглядят универсальными. **Результат:** серверные настройки действительно наследуются, явные overrides и лимиты ASA имеют источник; значения разных моделей не перемешиваются.

**Работа:** typed versioned parameter registry, merge/omit после всех уровней, ranges, пустое/false/zero, per-model settings и миграция эффективных legacy values. Добавить «Вернуть настройки сервера». Продумать фактические default limits ASA, не выдавая их за свойства модели; изменения числовой политики обосновать и проверить отдельно в этом срезе.

**Выход:** PARAM-01–PARAM-03 и MIG-01; capture фактического request доказывает отсутствие overrides в server mode. Прямая отправка Ollama-полей в llama.cpp или silent ignore неизвестного поля — FAIL.

### UC-08 — контекст и счётчики

**Проблема:** архитектурный максимум, рабочее окно и клиентский budget смешаны; tokenization не проходит через allowlist. **Результат:** администратор видит правильные разные значения/источники, чат корректно ограничивает полный запрос и сообщает неизвестность.

**Работа:** metadata selected model/slot, `null` вместо router zero/догадки, полный message budgeting, production-dispatch token counters и честный estimate fallback, безопасное сокращение истории. Ограничение ASA не перезапускает удалённую модель. Ollama runtime `num_ctx` вынести отдельно.

**Выход:** CTX-01–CTX-04 для действующих text/tool flows; вклад изображений в budget проверен ограниченными структурированными fixtures и уже поддерживаемым Ollama-путём без снятия текущего vision-запрета llama.cpp. Полная доставка IMAGE-01 принимается в UC-10, а не является зависимостью закрытия UC-08. Счётчики проходят production transport, fallback проверен при недоступном counter. Неверный «100% окна» при unknown или потеря последнего вопроса — FAIL.

### UC-09 — reasoning

**Проблема:** фиксированные `xhigh`/`false` и универсальный переключатель обещают неподдерживаемое управление. **Результат:** у выбранной модели видны только доступные режимы, server mode ничего лишнего не отправляет.

**Работа:** adapter/model capability mapping boolean/levels/budget, отдельное отображение reasoning, честное непроверенное управление. Версии/templates с разными contracts тестировать отдельными fixtures; не определять по имени модели.

**Выход:** THINK-01/THINK-02, переключение между моделями без потери их профилей; capture actual payload и проверка несовместимого значения. HTTP 200 на проигнорированный параметр не даёт PASS семантики.

### UC-10 — изображения

**Проблема:** текущая ветка llama.cpp блокирует картинки независимо от модели. **Результат:** пользователь прикрепляет PNG/JPEG в обычный чат ASA, модель читает их, история/повтор сохраняют исходные вложения и приватность.

**Работа:** весь разрешённый multimodal pipeline раздела 9.1, снятие unconditional 409 вместе с адаптером, форматами и owner checks. Не менять серверные GPU/mmproj и не переносить задачу на компьютер ComfyUI.

**Выход:** IMAGE-01–IMAGE-03 через обычный ASA chat и повтор CTX-03 на работающем multimodal path каждого затронутого адаптера; отрицательный text-only/чужое вложение, browser-вложение и вставка из буфера по существующему UI; отдельный живой quality result либо честный `BLOCKED_PROVIDER`. Иконка vision или текстовое описание файла не закрывают UC-10.

### UC-11 — tools и stream lifecycle

**Проблема:** отличия NDJSON/SSE и tool fragments могут ломать обычный чат, отмену и usage. **Результат:** модель выполняет разрешённый безопасный инструмент, продолжает ответ и останавливается по Stop без чужих отмен.

**Работа:** общий внутренний stream contract, отдельные parsers, валидация tools, terminal states/unknown/usage, собственная отмена. Сохранить существующие журнал и replay. Не делать автоматический POST retry/платный fallback.

**Выход:** TOOL-01/TOOL-02, STREAM-01–STREAM-03, действующие owner/usage tests; запись реального UI потока/Stop и trace исполнения. Mock parser test без чата не закрывает карточку.

### UC-12 — очередь и общий ресурс

**Проблема:** глобальный лимит блокирует независимые серверы, а разные профили одного GPU могут обходить реальную очередь. **Результат:** независимые подключения работают раздельно, связанные профили делят заданный ресурс и отменяют только свои задания.

**Работа:** per-connection/resource-group admission, durable owner accounting/fairness, bounded queue и deadlines, координация нескольких backend workers. При одном слоте показывать ожидание, а не зависшую генерацию.

**Выход:** QUEUE-01/QUEUE-02, две независимые цели + одна общая группа, отмена ожидания и неизвестный результат; изменение лимита не создаёт дополнительных незарегистрированных операций. Нагрузочный результат не экстраполировать на все GPU.

### UC-13 — компактность и доступность

**Проблема:** полный набор настроек может превратить форму в длинную инструкцию. **Результат:** простой сценарий остаётся коротким, сложные параметры доступны по необходимости, ни одно состояние не ломает layout.

**Работа:** общий UI review всех уже работающих вертикалей, устранение дублирующих пояснений, InfoHint/labels/keyboard/touch, responsive и длинные значения. Это завершающая общая проверка, а не разрешение отложить UI предыдущих UC.

**Выход:** UX-01–UX-03 на полном наборе ширин/состояний; просмотренные before/after обеих тем, trace динамики; короткий отчёт о реальных найденных/исправленных дефектах. Непросмотренные screenshots и красивые mockups не принимаются.

### UC-14 — обновление и передача

**Проблема:** успех на чистом стенде не доказывает сохранность старой установки и работу из нужного runtime. **Результат:** один согласованный release candidate с совместимым upgrade, точными ограничениями и подтверждёнными сценариями.

**Работа:** MIG-01/REG-01 и полная матрица; documented adapter/server versions, реальные запросы только с разрешённого тестового host/container после GitHub gates и штатного разрешения. Для текущего тестового Ubuntu следовать существующему MCP 1Panel-процессу; установка в школе и изменение D2R2 требуют своей применимой процедуры. Не обходить deployment blockers ради закрытия таблицы.

**Выход:** отчёт раздела 15, API/Web build SHA, tested versions, evidence text/vision/tools/context/cancel/auth/no-auth, сохраняющиеся ограничения и короткая инструкция администратору в продуктовой документации. При недоступной реальной проверке — `NOT_RUN`/`BLOCKED_PROVIDER`, не общий PASS. Не закрывать Issue только по наличию кода.

## 15. Definition of Done и формат передачи

Для каждого среза отдельно указать `CODE`, `CI`, `DEMO`, `IN_MAIN`, `DEPLOYED_TEST`, `OWNER_ACCEPTED` с доказательством или честным отсутствием. Один статус не заменяет другой. Общая функция считается реализованной после всех применимых критериев, а принятой владельцем — только после его фактической приёмки.

Обязательный отчёт исполнителя:

1. UC-ID, связанные ASAI/R, точный commit SHA и опубликованная ссылка; что изменилось для администратора и пользователя чата.
2. Где открыть, нужная роль и короткие действия проверки без реальных secrets/private endpoints в публичном отчёте.
3. Изменённые пути, миграция/совместимость и изменения compact contracts, если они были нужны.
4. Выполненные тесты по ID, команды и результаты; exact-SHA CI, independent review по применимому контракту. `NOT_RUN`, `BLOCKED_DEMO`, `BLOCKED_PROVIDER` не заменять на PASS.
5. Просмотренные screenshots before/after, размеры/темы и trace динамики. Синтетические данные пометить; credentials и персональные данные удалить из evidence.
6. Фактически проверенные endpoint contracts/версии, текст/vision/tools/reasoning/context и пределы доказательства. Успех API != качество модели != доступ школьного контейнера.
7. Оставшиеся проблемы с воспроизведением и зависимостью; безопасный rollback в рамках штатного процесса. После отчёта исполнитель останавливается.

Не считать ТЗ исполненным по количеству файлов/тестов или успешному mock. Не закрывать пользовательские замечания заменой терминов. В частности, «ключ необязателен» проверяется отсутствием auth на проводе, «модель определилась» — реальным каталогом/проверенным ручным ID, «server defaults» — финальным omit, «картинки работают» — доставкой пикселей и отдельным quality test, «компактная форма» — просмотренным реальным UI.
