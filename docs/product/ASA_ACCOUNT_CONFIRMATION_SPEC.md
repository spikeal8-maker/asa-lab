# ASA Lab — подтверждение аккаунта и доступность способов входа

Revision: 1.1

Этот документ фиксирует поручение владельца от 18 октября 2026 года. Активная
задача, выбранный срез, Git SHA, результаты CI и приёмка хранятся только в
`docs/execution/current.yaml`. Документ определяет требуемое поведение и критерии
проверки, а не объявляет реализацию готовой.

## 1. Пользовательский результат

Обычный пользователь может зарегистрироваться по email и паролю и пользоваться
ASA Lab в течение первых 24 часов без подтверждения внешнего канала. После этого
достаточно один раз подтвердить владение MAX, Telegram или, когда отправка писем
будет реализована, email. Это подтверждение аккаунта, не ежедневная повторная
аутентификация.

В админке есть отдельный сохраняемый переключатель «Обязательное подтверждение
аккаунта». Он независим от настроек ботов. Включённый MAX не включает обязательную
политику автоматически; выключенная политика не отключает добровольный вход или
привязку рабочего MAX/Telegram.

По прямому требованию владельца при отказе всех доступных каналов дополнительное
ограничение подтверждения снимается. Пользователь продолжает входить с правильным
паролем. Неверный пароль, приостановленный аккаунт, отозванная сессия, недостаточные
права и неверная подпись провайдера по-прежнему отклоняются.

## 2. Границы программы

В программу входят: серверная политика и её рубильник; исправления жизненного
цикла MAX; реальный Telegram provider; доступность каналов; страницы входа,
регистрации и способов входа; обязательный экран подтверждения; админские
настройки; регрессионные, PostgreSQL, HTTP и браузерные проверки.

Почта остаётся явно недоступной до отдельного подключения и проверки отправки.
Кнопка подтверждения email не имитирует работающий канал. Этот пакет не меняет
tenant/RLS-модель, школьные коды, роли учеников, содержимое проектов, тарифы или
политику удаления аккаунтов. Вход StudentSeat без Account сохраняется.

Подключение настоящего токена, обновление существующей Docker-установки,
миграция рабочей БД и приёмка владельцем являются отдельными действиями.
Код и проверки в GitHub не обозначают автоматическое обновление рабочего сайта.

## 3. Сохраняемая политика и правило времени

Настройка `enabled` по умолчанию равна `false`. `activatedAt` фиксируется при
первом включении и не сбрасывается повторными переключениями. Срок неподтверждённого
Account вычисляется от его первого входа, но не раньше первого включения политики:

`dueAt = max(firstAuthenticatedAt, activatedAt) + 24 hours`.

Это даёт существующим аккаунтам переходные сутки. Новый вход, refresh, новая
вкладка, смена workspace, выключение и повторное включение политики не продлевают
индивидуальный срок. Время берётся с сервера; клиентские часы не определяют доступ.

| Состояние | Обычный доступ |
|---|---|
| Рубильник выключен | Разрешён после штатной аутентификации |
| Аккаунт уже подтвердил разрешённый канал | Разрешён |
| Первые 24 часа не закончились | Разрешён |
| Срок закончился, есть рабочий канал | Требуется подтверждение |
| Срок закончился, все каналы недоступны | Разрешён с правильным паролем; причина видна в админке |
| StudentSeat без Account | Школьный путь сохраняется |

MAX/Telegram подтверждает владение профилем соответствующего провайдера. Такой
proof не изменяет `email_verified`, дату рождения, организационные права или
школьную принадлежность. Для выполнения политики достаточно одного действующего
доказанного канала.

## 4. Серверное ограничение и восстановление

Успешная парольная аутентификация может сохранять текущую сессионную cookie как
контекст личности для подтверждения. При `verification.required=true` сервер не
выдаёт продуктовые capabilities/actions и блокирует защищённые действия единым
контролем. Только скрытие интерфейса не считается ограничением.

Одна политика применяется к обычному и организационному входу, существующей
сессии, refresh и прямым HTTP-запросам. Bearer-доступ Scratch проверяется после
штатной проверки bearer по его доказанному principal; отсутствие cookie не
становится обходом. К школьному principal без Account эта политика не применяется.

Доступны необходимые операции входа, выхода, чтения состояния, подтверждения и
восстановления. У ограниченной сессии администратор может открыть только раздел
управления подтверждениями после обычной серверной проверки административных
полномочий. Исключение не освобождает весь admin API и не выдаёт новую роль.

Отказ внешнего провайдера обрабатывается серверным пересчётом состояния. Ошибка
браузерного запроса или переданный клиентом флаг не могут самостоятельно снять
требование подтверждения. Отказы базы данных и проверки личности не превращаются
в успешную аутентификацию.

## 5. Проверенная доступность каналов

Источник истины — серверная проверка текущей конфигурации и доставки. Сохранённый
токен, заданный URL и флаг включения по отдельности не доказывают готовность.

MAX проверяет токен и нужную webhook-подписку. Telegram проверяет `getMe` и
`getWebhookInfo`, ожидаемый URL и актуальные ошибки доставки. Внешние проверки
ограничены временем, объединяют одновременные вызовы и используют короткий cache.
Смена настроек сбрасывает cache. Выключенный или ненастроенный канал не вызывает
внешние API при каждом входе.

Публичное состояние не содержит токены, секреты webhook, необработанные ответы
провайдера или секретные части URL. Недоступные каналы не показываются как кнопки
входа, регистрации или подтверждения. При ошибке загрузки capabilities социальные
кнопки скрываются; обычная парольная форма остаётся доступной.

Админка отдельно показывает выбранное владельцем состояние, наличие токена,
результат его проверки и фактическую доступность канала. Сообщение об успешном
сохранении не заменяет подтверждение работоспособности webhook.

## 6. Вход, регистрация и привязка

Три намерения различаются явно: `login`, `register`, `link`.

Для существующего email/password Account подтверждение всегда выполняет `link`
к тому же Account. ID, личное рабочее пространство, проекты и учебная история
сохраняются. Совпадение имени или email не является основанием объединить аккаунты.

Новый MAX/Telegram-профиль получает состояние `registration_required`. Он завершает
регистрацию настоящими данными профиля и запасным паролем по штатной парольной
политике ASA. Пароль позволяет войти при недоступности мессенджера. Нельзя сохранять
сегодняшнюю дату как выдуманную дату рождения, молча подставлять страну или создавать
неизвестный пользователю случайный пароль. Повторный social login существующего
аккаунта не требует заполнения этой формы.

## 7. Одноразовый запрос и жизненный цикл identity

Для каждого запроса создаются два независимых случайных секрета: токен перехода
в бот и nonce исходного браузера. База хранит их хэши. Nonce помещается в HttpOnly
cookie и не возвращается в JSON или ссылке провайдера. Срок запроса — 10 минут;
завершение атомарно и однократно.

Открытие бота само по себе не завершает вход: пользователь явно подтверждает
действие. MAX callback определяет человека, нажавшего кнопку, а не отправителя
вложенного сообщения. Bot proof сначала сохраняется в запросе. Привязка происходит
при browser consume после проверки nonce, активной cookie и совпадения текущего
Account с Account, начавшим привязку. Выход и вход другого пользователя между
start/complete не создают привязку к ошибочному аккаунту.

При consume повторно проверяются срок, purpose, конфигурационная версия,
состояние Account и identity. Выключение канала, смена конфигурации и отзыв identity
погашают относящиеся к ним незавершённые запросы. Ранее одобренный запрос не может
восстановить отозванный доступ. Отзыв охватывает provider-сессии и refresh, включая
сессии, которым ещё не создан refresh family.

Самостоятельная отвязка последнего пригодного способа входа запрещена с понятным
объяснением. Повторная привязка после самостоятельной отвязки восстанавливается
только для разрешённой пары Account/subject. Административный запрет автоматически
не снимается.

## 8. HTTP-контракты

| Путь | Контракт |
|---|---|
| `GET /api/auth/providers` | `{providers: AuthProviderAvailability[]}` |
| `GET /api/auth/verification` | Текущее серверное состояние подтверждения |
| Ответы login/register/me | Дополнительное поле `verification` |
| Защищённое действие при required | HTTP403, `error.code=account_verification_required`, актуальное состояние |
| `GET/POST /api/admin/v1/auth/verification-policy` | `{enabled,activatedAt,graceHours:24}`; POST принимает `{enabled}` |
| `GET/PUT /api/admin/v1/integrations/max` | Настройки и диагностика MAX |
| `GET/PUT /api/admin/v1/integrations/telegram` | Настройки и диагностика Telegram |
| `POST /api/auth/{provider}/pairing/start` | Намерение; возвращает pairingToken, launchUrl, expiresAt |
| `POST /api/auth/{provider}/pairing/complete` | Pending, terminal error, registration_required, authenticated или linked |
| `POST /api/auth/{provider}/pairing/register` | Pairing token, реальные данные и запасной пароль |
| `GET /api/auth/{provider}/status` | Действительное состояние связи, доступность и canUnlink |
| `POST /api/auth/{provider}/unlink` | Штатная отвязка или объяснимый конфликт |

ProviderAvailability содержит `id`, `available`, `reason`, `checkedAt` и допустимый
публичный `launchUrl`. Причины: ready, disabled, not_configured, invalid_token,
delivery_unavailable, unavailable. `id` — max, telegram или email.

VerificationState содержит `policyEnabled`, `required`, `reason`, `dueAt`,
`verifiedProvider`, `providers`. Причины: disabled, verified, grace_period,
providers_unavailable, verification_required.

Совместимый login complete сохраняет `{status:'authenticated',session}`.
Успешный link возвращает `{status:'linked',linked:true}` без замены аккаунта или
создания второй сессии.

## 9. Интерфейс и наблюдаемый результат

Вход и регистрация используют один компонент MAX/Telegram: запуск, ожидание,
повторное открытие мессенджера, отмена, истечение срока и понятная ошибка.
Нет кнопок неработающих провайдеров и вечного ожидания после терминального отказа.

Экран обязательного подтверждения объясняет причину, показывает только доступные
способы, позволяет выйти и реагирует на изменение серверной политики. При возврате
во вкладку и наступлении срока состояние обновляется. Успешная привязка возвращает
пользователя в тот же аккаунт.

В админке рубильник расположен отдельно от карточек каналов. Изменения сохраняются
на сервере и переживают перезапуск. Результат сохранения и ошибка видны и доступны
скринридеру. Пароли и токены не сохраняются в диагностические события.

Применяется существующий стиль ASA; проверяются ширины 1440, 1024, 390 и 320,
длинный текст, loading/error/disabled/empty/ready states, видимость основного
действия, клавиатурный фокус и отсутствие горизонтального переполнения страницы.

## 10. Пакеты и роли

| Пакет | Исполнитель | Проверяемый результат |
|---|---|---|
| AUTH-C1 — провайдеры | Provider backend | Рабочие MAX/Telegram, health, nonce, регистрация и исправленный отзыв |
| AUTH-C2 — политика | Policy backend | Рубильник, срок, серверный gate, сохранённый парольный вход при отказе каналов |
| AUTH-C3 — интерфейс | Web UI | Кнопки, формы, подтверждение того же аккаунта и админские настройки |
| AUTH-C4 — интеграция и приёмка | Контроллер и независимый reviewer | Совместимый API, миграции, HTTP/PG/browser evidence и точный GitHub SHA |

Исполнители имеют непересекающиеся пути и не публикуют main самостоятельно.
Контроллер ведёт зависимости, ТЗ, точный Git/CI snapshot и интеграцию. Проверяющий
не изменяет проверяемый код; замечания возвращаются соответствующему исполнителю,
после исправлений проводится новый review. Остановка отдельного исполнителя
не завершает порученную владельцем программу.

Из IZO_ASA адаптируются независимый browser nonce, явное подтверждение, привязка
по внутреннему ID, обработка actor в MAX callback, диагностика и сценарии Telegram.
Python/SQLite-код переводится в архитектуру TypeScript/PostgreSQL ASA. Trial,
тарифные ограничения, лимит генераций и автоматическое удаление не переносятся.
Документация провайдеров проверяется для выбранного webhook/Mini App сценария.

## 11. Обязательные проверки

1. Рубильник default-off, сохранение, административные права и повторное чтение.
2. Граница 23:59:59/24:00:00, переходный срок и отсутствие сброса дедлайна.
3. Один подтверждённый канал достаточен; email не подтверждается через MAX/Telegram.
4. Отказы обоих провайдеров сохраняют правильный парольный вход; здоровый оставшийся
   провайдер сохраняет обязательность; клиент не может объявить outage.
5. Login, organization login, refresh, старая cookie, прямой API и Scratch bearer
   не обходят обязательную проверку; StudentSeat не затронут.
6. Неавторизованный пользователь не меняет политику/токены, restricted admin
   восстанавливает настройки без получения посторонних полномочий.
7. Expiry, replay, чужой nonce, чужой Account, одновременный consume и запоздалый
   callback отклоняются без новой привязки/сессии.
8. Approved challenge после revoke/disable не выдаёт доступ; последняя пригодная
   login-связь не отвязывается; self-unlink recovery отличается от admin revoke.
9. Реальная регистрация требует корректный профиль и запасной пароль, сохраняет
   тот же Account при последующих login/link и не объединяет аккаунты по email.
10. UI скрывает недоступные кнопки, сохраняет парольную форму, переживает outage
    во время подтверждения и не показывает ложную успешную готовность канала.
11. Новые миграции применяются к одноразовой PostgreSQL-базе; существующие миграции
    и рабочие данные не переписываются. Unit mock не заменяет SQL evidence.
12. Штатные focused/code/governance/data gates выполняются с отключённым Nx cache;
    новый независимый review проверяет финальную совокупность изменений.

## 12. Уровни готовности

В отчёте отдельно указываются изменённые файлы, выполненные проверки, commit,
доступность SHA в GitHub, CI того же SHA, развёртывание, действия с рабочей БД и
принятие владельцем. Реальный вход с настоящими ботами фиксируется отдельно от
проверок с тестовым провайдером. Отсутствующее доказательство обозначается NOT_RUN.

Прежний `ADMIN_AUTH_MAX_EXECUTION_PLAN.md` остаётся технической историей. Его
неблокирующее напоминание и отсрочка на семь дней не определяют поведение включённой
новой обязательной политики. Настоящее ТЗ и уточнение владельца о входе при отказе
каналов имеют приоритет для этой программы.

## 13. Подготовка к обновлению и отказам (уточнение от 19 октября 2026 года)

Срез AUTH-C5 закрывает подтверждённые при повторном аудите пробелы подготовки.
Ранее полученное CI evidence сохраняется как история проверенной версии; оно
не доказывает работоспособность настоящего бота на конкретной установке.

### 13.1. Доступность и проверенная доставка

Возможность начать вход через бот и пригодность канала для обязательного
подтверждения различаются. Правильный токен и сохранённая подписка позволяют
проверять настройку, но сами по себе не являются доказательством доставки.

Сервер проверяет публичный callback этой установки коротким диагностическим
запросом с nonce, версией конфигурации и криптографическим доказательством.
Проверка не создаёт Account, не подтверждает identity и не отправляет сообщений.
Обычный HTTP 200 с HTML, чужой экземпляр, redirect, неверный secret, 404/403/503,
ошибка TLS/DNS или превышение deadline не считаются исправным ingress.
Разрешены только явно настроенные доверенные public origins; произвольный Host
или адрес из запроса не расширяет список. Проверки ограничены общим временем,
объединяют одновременные обращения и используют короткий cache.

Для участия в обязательном подтверждении дополнительно требуется настоящее
успешное подтверждение текущей версии конфигурации: событие провайдера, явное
одобрение человеком и завершение в исходном браузере. Первый пробный вход
доступен до появления такого evidence, иначе настройка образует замкнутый круг.
Смена токена, адреса, версии или выключение канала прекращают применимость
старого evidence. Ошибка одного получателя и переданный клиентом флаг не
отключают канал для остальных.

Проверка собственного публичного адреса не является доказательством доступа
из сети MAX или Telegram. Избирательная блокировка только входящих запросов
провайдера после ранее успешной доставки остаётся отдельным эксплуатационным
риском; нельзя обещать её мгновенное обнаружение по одному списку подписок.
На целевой установке до включения обязательности отдельно проверяются реальные
start, approve и browser consume, а также известные сценарии отказа.

### 13.2. Сохранение входа существующих пользователей

Подписанный старый MAX Mini App вход не зависит от доставки webhook.
Его доступность проверяется отдельно, с сохранением проверки включённого бота,
токена, подписи, срока, replay, актуальной конфигурации, Account и отзыва.
Отсутствие новой webhook-отметки после миграции само по себе не отключает этот
старый доказанный credential.

Нельзя предполагать, что каждый старый MAX-only Account знает пароль. До
обновления такой установки требуется read-only оценка наличия этих аккаунтов
и проверенный резервный вход администратора. Запасной пароль задаётся самим
пользователем после действительной аутентификации; массовая генерация неизвестных
паролей или простая подмена password_configured запрещены. При отказе единственного
credential доступ к Account не выдаётся без аутентификации.

Новые настройки не должны автоматически захватывать webhook другого приложения
или тестовой установки. Неожиданная существующая подписка требует понятного
отказа настройки и выбора отдельного бота. Публичный GET и startup не
перенастраивают живой бот.

### 13.3. Адреса, ключи и понятная настройка

Для внешнего входа staging передаёт сохранённый ASA_PUBLIC_WEB_ORIGINS так же,
как production. HTTPS allowlist, CSRF и Secure cookies сохраняются. Сценарии
loopback, HTTPS IP и публичного HTTPS адреса проверяются отдельно; обычный
HTTP LAN/IP не объявляется поддержанным production-входом.

Карточка бота показывает назначение публичного HTTPS-адреса, вычисленный
callback, состояние токена, доступность ingress и наличие реального подтверждения.
Для открытой по HTTP админки HTTP не подставляется как готовый адрес бота.
Ошибка адреса отличается от несовпадения имени бота и токена. Порты проверяются
по требованиям соответствующего провайдера. Неизвестное после ошибки чтения
состояние не называется выключенным.

Bootstrap сохраняет существующий ключ шифрования. Некорректная или дублированная
запись останавливает подготовку с указанием восстановить исходный ключ; новый
ключ не дописывается поверх старого. Генерация допускается для действительно
новой конфигурации. Значения ключей и токенов не попадают в отчёты.

### 13.4. Конечное ожидание и проверка

Auth/provider/configuration requests имеют конечный deadline, включая refresh.
Ожидание подтверждения учитывает независимый срок pairing; доступные отмена,
возврат к паролю и выход не удерживаются зависшим запросом. Проверка состояния
не запускает параллельные незавершённые запросы. Поздний ответ отменённого
сценария не переводит интерфейс в другой Account и не выдаёт capabilities.

Timeout не подтверждает Account, не снимает серверное ограничение и не является
основанием автоматически повторять регистрацию или изменение настроек:
результат записи может быть неизвестен. Сообщение объясняет возможность повтора
и восстановления без ложного сообщения об успехе.

Приёмка среза требует тестов неправильного ingress и версии, первого успешного
подтверждения, миграции старого MAX-входа, чужого webhook, зависшего transport,
отмены и позднего ответа, staging origin и сохранности ключа. Изменения проходят
независимый review финального исходного кода и штатные focused/repository gates.
Настоящие боты, домен/TLS целевого сервера, deployment и owner acceptance
фиксируются отдельно и не подменяются синтетическими проверками.
