## Source-backed mechanism and bounded repair direction

`use-electronics-workbench.ts` advances the host horizon every 100 ms. `ElectronicsLiveSimulationWorkerController.beginGeneration()` seeds a canonical zero-horizon target, but `update()` can replace that target while preflight is in flight. The existing focused unit named `publishes only canonical ready observations and coalesces preflight horizons` explicitly expects the first advance to use the latest 200,000 µs target after preflight is delayed. Once preflight crossed the first host tick in the loaded run, the first requested target became 115,300 µs instead of zero.

The E2 fixture contains an Arduino Uno with `void loop() {}`. `arduino-program-runtime.ts` assigns one virtual microsecond to each compiled instruction or loop return; `arduino-circuit-scheduler.ts` defaults to a maximum of 256 clock events per advance. The loaded Worker therefore yielded after only 255 and then 511 committed microseconds. The controller correctly withholds `onResult` until a complete `ready` result at the requested horizon; `use-electronics-workbench.ts` calls `confirmSimulationStarted()` only in `onResult`. Thus a preflight delay past the host tick can turn a quick zero-time initial observation into a long catch-up before the UI reaches `running`.

The next **separately selected** bounded repair should preserve a complete canonical zero-horizon first observation before chasing newer host horizons, even when preflight finishes after a timer tick. It must keep pending input ordering, generation/cancellation behavior, fail-closed physics, and the prohibition on publishing a partial future-horizon result. Directed unit and built-browser E2 checks should show the initial `ready` result, `running` state and unchanged strict active-style assertions under delayed preflight; later horizon processing should continue. This diagnostic does not implement or accept that repair.
