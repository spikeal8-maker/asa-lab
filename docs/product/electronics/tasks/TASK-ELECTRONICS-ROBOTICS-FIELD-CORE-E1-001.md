# E1 — квалификация пространственного ядра поля

Программа ROBOTICS-FIELD-CORE-001, этап E1. Идентификатор и расположение карточки
следуют существующему контракту дочернего направления Electronics; это не отдельное электрическое ядро.

## Цель и источник состояния

Подтвердить применимость физического кандидата, не меняя пока рабочий редактор.
Выбранный этап, Issue, фактический checkpoint и разрешения читаются только из
[current.yaml](../../../execution/current.yaml). Эта карточка — контракт, не журнал готовности.
Основное [ТЗ 1.1](../../robotics/FIELD_CORE_SPEC.md), [аудит](../../robotics/FIELD_CORE_SPEC_REVIEW.md) и
[матрица требований](../../robotics/FIELD_CORE_TRACEABILITY.json) сохраняют весь объём будущей системы.

## До первой записи

1. Прочитать root AGENTS и выполнить scoped preflight с точным списком будущих файлов.
2. Получить актуальный main, убедиться, что он содержит эту каноническую задачу и ТЗ.
3. Проверить E0 receipt, remote checkpoint и неизменность исходного 4630. Никакого reset/clean/stash.
4. Работать в отдельной чистой копии исходников, не обслуживающей работающий порт.
5. До changes в shared package/lockfiles проверить свежий main и пересечения. Не регенерировать зависимости из старой ветки PR1044.

## Разрешённый объём

Квалификационный harness в основном репозитории, версии fixtures, результаты,
ADR D01 и отчёт D02. Предполагаемые каталоги: tests/robotics/field-core-qualification,
tools/robotics-field-core и docs/product/robotics/evidence. Точные файлы определяются
preflight до записи. Корневой package.json/lockfile — только если это необходимо
для выбранного способа подключения; UI, API, схема БД и production wiring не входят в E1.

### Шесть механических сцен

| Сцена | Что измерить | Что не подменять демонстрацией |
|---|---|---|
| Свободное падение | z(t), v(t), ошибку относительно аналитики, сходимость шага | Успешный import WASM не означает физический PASS |
| Цилиндр в покое и опрокидывание | дрейф, контакты, COM/инерцию, порог устойчивости | Нельзя поворачивать картинку вместо тела |
| Скатывание шара | поступательное/угловое движение, энергию и сцепление | Не задавать траекторию вручную |
| Колёсное шасси на плоскости | тягу, контакты и отклик ограниченного привода | TEST_ONLY момент не выдавать за Arduino-мотор |
| Подъём на рампу | положение/наклон, пробуксовку и невозможный подъём | Не привязывать высоту робота к формуле поверхности |
| Механизм минимум из трёх звеньев | пределы суставов и усилий, реакцию контактов | Не фиксировать всё шасси кинематически |

Численные fixtures и допуски берутся совместно из §16.2 и §19.7 ТЗ. Недостающие
параметры шасси, рампы и механизма, окна измерений и знаки энергетических величин
фиксируются в исходном fixture до первого прогона, а не подбираются по результату.
Предложения аудитора не становятся утверждёнными допусками автоматически.
Для каждой сцены: исходный JSON, шаг/подшаги, параметры solver, seed, исходные данные,
сырые метрики и отдельный verdict. Неуспех фиксируется, а не лечится ослаблением допуска.

### D01 — выбор движка

Rapier проверяется первым; MuJoCo рассматривается при конкретной существенной
непригодности. Зафиксировать точную npm-версию, package integrity, WASM SHA-256,
лицензию, браузер/Node/Worker и офлайн-загрузку. Сохранить также отрицательные случаи:
NaN/Infinity, ошибочная геометрия, недоступный WASM и лимит вычислений.
Проверка на D2-R2 не объявляется доказательством школьной производительности.

### D02 — граница электроники

Исследовать действующие public API и source-time contracts, по точным символам
показать возможности и пробелы: остановка перед внешним событием, Trig/Echo,
publication committed motor observations, принятие механической скорости/нагрузки.
Составить таблицу владельцев состояния и единиц. Минимальный воспроизводимый probe
может использовать существующие API; нельзя переписать scheduler/solver, добавить
фиктивный load-port или объявить TIME-01…03 успешными по одной типизации.
Отсутствующая возможность становится отдельной ограниченной зависимостью E7.

## Проверки и evidence

- Сначала точечные команды harness, затем регрессия pnpm test:robotics и применимые build/dependency gates.
- Реальные Web/API/PostgreSQL релизные проверки — штатный изолированный GitHub CI; пользовательская БД не используется.
- На exact SHA приложить команды, входные fixtures, необработанные результаты и hash manifest.
- Независимый reviewer проверяет финальный кандидат до закрытия D01. Авторский самоаудит не заменяет независимую проверку.
- D02 может завершиться честным отчётом GAP с отдельной задачей; это не даёт допуска зависимой продуктовой интеграции.

## Explicitly not doing

Не подключать новое ядро к пользовательскому полю; не менять UI/данные, owner SVG,
моторный solver, Arduino, публикации, RLS, серверы или зависимости другого модуля.
Не заявлять готовые походку/жидкость/деформацию, persistent resume или точность реального
набора оборудования. E3/E4 — отдельный выбранный срез, не «попутные правки» E1.

## Завершение

E1 закончен только с воспроизводимыми результатами шести сцен, ADR D01, D02 отчётом,
точными ограничениями и требуемым review. После результата исполнитель останавливается;
контроллер выбирает следующую ограниченную задачу канонически. Production не обновляется.
