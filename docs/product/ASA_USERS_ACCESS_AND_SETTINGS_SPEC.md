Для целевой модели пользователей и меню этот файл заменяет разрозненные одноимённые решения прежних черновиков. Он не отменяет проверки безопасности, неизменяемость истории, академическую семантику и инженерные запреты. При противоречии: указать два точных положения и затронутую операцию; применить безопасное действующее ограничение; подготовить ограниченную поправку соответствующего контракта. Пока она не разрешена, не обещать неподдерживаемую операцию. Не блокировать несвязанный готовый пользовательский путь.

### 0.2. Исторические факты и TARGET

Проверки V1/V1.1 установили: Auth-spec разделяет Account/Seat и не требует школу при регистрации; admin API различает platform/organization; ADR задаёт school-scoped LearnerIdentity; текущая навигация включает классы по умолчанию; AccountPage смешивает сохранение профиля с ролью и предлагает создать школу. Это адресные SOURCE-CODE наблюдения, не полный security-аудит и не browser/production evidence. Источники закреплены в §29.

Все U/R/P/UI/SET/PREF и permissions здесь являются продуктовым контрактом. Физические имена таблиц и endpoints не выводятся из названий экранов. Наличие permission в каталоге не означает, что endpoint уже существует.

### 0.3. Принятые уточнения модели

- D01: организация — добровольная команда; подтверждение реального учреждения отдельно.
- D02: «Классы» — staff-раздел; ученические классы находятся в «Моём обучении».
- D03: авторство, публикация, преподавание, проверка, помощь и управление независимы.
- D04: Seat — устойчивый учебный профиль по коду, не временный/полностью анонимный гость.
- D05: общий код и угадываемое имя не аутентифицируют ученика; нужен индивидуальный секрет либо защищённое подтверждение конкретного входа.
- D06: способ входа не задаёт resultMode; регистрация не превращает тренировку в оценку.
- D07: публичное чтение, самообучение и обучение с преподавателем различны.
- D08: личный learning context не маскируется школьным классом; физическое расширение требует отдельно разрешённого решения.
- D09: прежние декоративные схемы обязательной цепочки «платформа → школа → класс → любой человек» ненормативны.
- D10: StudentSeat.status, состояние credential/session и Enrollment/Participation.status — разные жизненные циклы. Вход не доказывает начало выполнения.
- D11: отзыв одного membership отключает только зависимые основания. Независимое право не теряется из-за чужого revoked membership.
- D12: выдача собственного org-role владельцем допустима только как явная audited операция. Поэтому отсутствие detail grant означает «нет текущего доступа», а не невозможность получить его уполномоченным назначением.
- D13: учёт scoped learners не равен глобальной идентификации физических людей между школами.
- D14: верхнее меню может показывать наличие разрешённых областей; данные, кнопки и запросы внутри области проверяются только по её ресурсам.
- D15: штатный успешный linking отзывает старый способ входа по выбранной policy, но не помечает learner/Seat removed и не отзывает учебное участие только из-за смены credentials.
- D16: потерянный ответ выдачи секрета не разрешает читать старый пароль или бесконечно повторять reset; восстановление описано в §9.

## 1. Словарь и общая структура

| Понятие | Смысл и граница |
|---|---|
| Account | Постоянный личный аккаунт; не педагогическая роль и не школа |
| Personal Workspace | Собственные проекты, сохранённое, материалы и личное обучение |
| Учебный профиль / StudentSeat | Подготовленный преподавателем вход в конкретный класс без создания Account |
| LearnerIdentity | Стабильный владелец учебной истории в доказанном контексте; не credential |
| Ученик | Человек относительно конкретного прохождения, не необратимый тип Account |
| Курс | Содержание программы; не группа людей |
| CourseVersion | Закреплённая опубликованная редакция, не текущий черновик |
| Проведение / CourseRun | Обучение по версии: участники, персонал, сроки и правила |
| Самостоятельное прохождение | Личный прогресс без назначенного класса и staff |
| Класс / учебная группа | Устойчивый состав для организованного обучения; одна группа может проходить несколько курсов |
| Подгруппа | Часть одного класса, не организация |
| Организация | Явно созданная команда и область управления; число курсов её не создаёт |
| Школа | Название организации или подразделения; не родитель каждого личного Account |
| Роль R | Набор scoped разрешений; не обязательная лестница наследования |
| Персонаж P | Сценарий работы человека для UI и тестов, не persisted user.role |
| Ответственный | Организационная ответственность; доступ API возникает отдельно из grants |

```text
ASA Lab
├─ Гость → разрешённые Инструменты / Сообщество / Знания
├─ Личный Account
│  ├─ собственные проекты и игры
│  ├─ личное обучение
│  ├─ авторство материалов по подключённым возможностям
│  ├─ самостоятельное преподавание
│  └─ выбранные организации по действующим назначениям
└─ Вход по коду без регистрации Account
   └─ свой учебный профиль → назначенное обучение
      └─ позднее: доказанный link с Account, та же история
```

Курс может иметь несколько проведений по одной версии и независимые адаптации. Два вхождения одной активности в разные блоки — два block identity. Чтение страницы не создаёт Enrollment. Самостоятельное преподавание не требует предварительного создания организации.

## 5. Вычисление доступа

### 5.1. Области и основания

Области: Personal, Content, CourseRun, Classroom, Organization с выбранными school units, Platform, Case/SupportSession. Grant содержит subject, permission/template, scope, subset, issuer, origin, state, сроки, parent при делегировании, policyVersion, reason/requestId и version. Это логическая модель; существующие таблицы переиспользуются.

Grant: `active|suspended|revoked|expired`. Pending относится к приглашению или заявке. Организационное членство не даёт все ресурсы организации. Один grant на run не поднимается автоматически до всего класса.

### 5.2. Решение каждой операции

Сервер разрешает actor из проверенной сессии; ресурс и lineage — из доверенного хранения; затем проверяет account/session safety, действующие основания на этот ресурс, caps, состояние ресурса, feature support и учебные preconditions. Возвращает только разрешённые поля. Client-supplied IDs — запрос, не доказательство права.

Порядок: глобальная применимая блокировка → реальный scope → действующее основание → resource/safety restrictions → academic conditions → действие. Для каждой grant-chain проверяются её собственные зависимости. Отозванное членство школы А не запрещает независимое личное действие или действие школы Б. Блокировка Account по безопасности, напротив, ограничивает все действия этого Account в своей заявленной области.

Allow объединяются по конкретному ресурсу, не по наличию слова permission где-либо в аккаунте. Edit курса А + publish курса Б не дают publish А. Classroom staff может иметь доступ ко всем явно включённым run этого класса; run-only staff — только к своему run. Parent CourseRun ограничения сужают child доступ, не переписывая историю.

### 5.3. Делегирование, отзыв, гонки

Нужны и permission на выдачу, и delegation ceiling. Нельзя раздать действие только потому, что умеешь выполнять его сам. Org assignment действует от организации и не исчезает с увольнением прежнего оператора. Personal delegation зависит от parent grant; при отзыве проверяются остальные независимые основания.

Новые запросы после committed revoke должны отказывать по отозванному основанию. Mutation и отзыв упорядочиваются транзакционно; outcome сохраняется. Старый JWT, кэш, меню или websocket не обходят отзыв. Уже полученные данные невозможно отозвать из памяти человека.

Защищённые файлы выдаются через проверяемый proxy/отзываемый механизм. Если разрешена короткая signed URL, явный остаточный срок доступа учитывается; он не называется мгновенным отзывом. Bulk и фоновые jobs проверяют право и при выполнении, и при выдаче результата.

Legacy ученическая ссылка класса переходит в соответствующий learner view после auth. Не создавать 19 меню/аккаунтов. Скрытие рабочих разделов — preference, а не отзыв права; lawful deep link может открыть рабочую область.

## 8. Регистрация и подключение возможностей

Регистрация запрашивает только необходимые поля действующего Auth/age/region flow. Школа, должность, ФИО и телефон не добавляются ради полноты. После регистрации — один Account, личное пространство и личная Главная. Unverified contact не доказывает принадлежность Seat.

Авторство: Профиль → Возможности → Создавать материалы. Серверная eligibility; private draft не равен праву публичной публикации. Scoped приглашённому редактору не требуется выдавать авторство всей библиотеки.

Преподавание: Профиль → Возможности → Подключить преподавание. Условия ответственности и действующая policy, отдельная server-command; pending/provisional/verified/suspended/revoked отображаются через фактический mapping. Self-attestation не является подтверждением диплома/работы в учреждении. После допуска можно преподавать самостоятельно, без обязательной организации.

Сохранение имени/биографии не вызывает role-command. «Свернуть рабочее меню» не прекращает преподавание. Реальное прекращение полномочий имеет отдельный preview класса/персонала/последствий и не удаляет материалы.

Создание команды: Профиль → Работа с командой → Создать организацию. Название, описание, разрешённый контакт ответственного; новая собственная область. Совпадение названия с реальной школой не выдаёт её данные. Подтверждение учреждения — отдельный статус, не prerequisite самостоятельной команды.

Приглашения сотрудника показываются в own inbox: кто, куда, обязанности, срок. До acceptance права не действуют. Вступление не переносит личные проекты/материалы. Один Account продолжает одновременно учиться и работать в нескольких областях.

## 9. Ученик по коду класса

### 9.1. Подготовка и данные

Классы → Учащиеся → Добавить/Добавить списком. Нужен `class.roster.manage`. Псевдоним допускается нейтральный; email, телефон, ФИО и дата рождения не требуются только ради карточки. Иные обязательные policy имеют отдельное объяснение.

`issued`/`active` StudentSeat описывают состояние учебного профиля по CURRENT identity contract. Credential имеет свою версию/состояние; session — своё. Enrollment/Participation `assigned → active` происходит только от meaningful учебного взаимодействия. Нельзя считать Seat-login доказательством Attempt или массово активировать все участия.

Минимальные данные: internal ID, класс, псевдоним/login, статус, credential reference, учебные работы и события. Название — «Ученик по коду класса», «Учебный профиль», «Без личной регистрации». Не обещать полную анонимность и не называть профиль временным, если он сохраняет историю.

### 9.2. Разные коды

Общий код класса находит join flow; логин называет профиль; индивидуальный секрет подтверждает профиль; Account invitation добавляет конкретное участие; linking token доказывает одну связь; staff invite предлагает перечисленные обязанности. Ни один не заменяет другой.

A — базовый личный доступ: код класса + логин + индивидуальный секрет, либо персональная карточка/QR с эквивалентной защитой. QR — credential, его нельзя показывать на общей доске. B — teacher-approved login: короткий browser-bound challenge, до approval никаких данных профиля; преподаватель сопоставляет конкретного ребёнка с конкретным запросом. Нереализованный B не предлагается как «без пароля».

Путь: публичная кнопка или Моё обучение → код → минимальный разрешённый preview без roster → данные преподавателя либо свой Account → проверка → собственная учебная сессия. Ошибка не раскрывает существование логина. Account join по общему коду требует approval; точное preapproved приглашение может сокращать этот шаг, но не выдаёт staff.

Уже открытый чужой/учительский Account требует явного безопасного переключения или изолированного browser profile. Нельзя складывать cookie principals. Linking — отдельная ограниченная процедура доказательства двух сторон, а не общий режим объединения сессий.

### 9.3. Обучение и ограничения

Видны свои назначения, работы, feedback и опубликованные результаты. Нет чужого roster, сдач, credentials, личных проектов преподавателя. Редакторы открываются по назначенным активностям. Свободная практика допускает выбранные поддержанные модули внутри учебного профиля; это не управление Personal Workspace связанного Account.

Тренировка сохраняет реальные работы/самопроверку/feedback без официальной отметки по умолчанию. Completion сохраняет решение о выполнении без выдуманного числа. Graded использует легитимные шкалу и result revision независимо от наличия почты. «Быстрый старт» — preset нового ungraded задания, не account-wide запрет оценок. Старые результаты не переинтерпретируются сменой типа входа.

### 9.4. Выдача, reset и общий компьютер

Учащиеся → профиль → Доступ. Команды раздельны: выдать карточку; сбросить личный доступ; завершить учебные входы; приостановить; история. Нужен соответствующий credential manager; причина и при bulk точный preview.

Старый секрет не читается. Свежая карточка показывается только в защищённом issuance flow, не в общей таблице, логах, чате или test screenshots. Потерян ответ: сначала запросить безопасный статус операции по requestId. Нельзя автоматически выполнять новый reset. Если первоначальный credential больше нельзя безопасно получить, нужен явный новый reset с новым requestId и объяснением; старый credential отзывается. Сохранение/повторная выдача первоначального response возможны только отдельным утверждённым защищённым issuance-контрактом, не plaintext archive.

Reset старого credential и отзыв сессий имеют явный server outcome. Ротация общего кода отдельно показывает эффект на новые входы и существующие сессии. Потерянная карточка восстанавливается через уполномоченного преподавателя, не поиск ФИО в публичном roster.

На общем устройстве нет длительного remember-me по умолчанию; псевдоним и выход видны. Logout очищает scoped caches и subscriptions. Unsaved не называется saved; предупреждение не удерживает ребёнка в чужой сессии бесконечно. Допустимый локальный draft изолирован от следующего пользователя и не хранит credentials.

## 10. Связывание учебного профиля с Account

Разделить: контроль Account/канала; принадлежность учебного профиля; применимую age/consent policy. Учительское подтверждение профиля не объявляется юридическим согласием родителя. Email, одинаковое имя, IP, устройство и похожий login не merge keys.

Путь ученика: Моё обучение → Учебный профиль → Связать с личным аккаунтом. Approver: Классы → Учащиеся → Запросы связывания.

1. Доказать доступ к Seat либо пройти его законное восстановление.
2. Создать request с source learner/context, nonce, expiry; в Account-flow передать одноразовое доказательство, не постоянный школьный пароль.
3. Войти/создать нужный Account и завершить применимые подтверждения. Показать обе конкретные стороны, не связывать случайно открытую учительскую сессию.
4. Для подготовленного teacher профиля требуется classroom approval принадлежности. Если нужны иные защитные/правовые подтверждения, они независимы.
5. На commit заново проверить обе стороны, expiry, approver, статус профиля, отсутствие конфликтующего link и lineage; атомарно записать связь.
6. Сохранить learner/Enrollment/Participation/Attempt/Submission/Result IDs и прошлых actors. Account/Seat Principals не сливаются; Project owner не переписывается массово.
7. Применить явно показанную credential policy: по умолчанию старый reusable Seat-secret отзывается после успешного перехода. Это не удаляет Seat, не withdraw учебное участие и не помечает learner suspended. Дополнительный школьный credential возможен только как отдельная управляемая policy.

Pending/expired/rejected запрос не закрывает законное текущее обучение. Повтор успешной команды возвращает существующую связь без второго audit. При linked-to-other-Account, двух learner identities в одном school/context или утраченном proof — conflict/recovery, не автоматическое слияние. School histories не объединяются; suspension не снимается linking.

Reconciliation — отдельная уполномоченная операция с evidence/preview, не обычное «Одобрить». Безопасное историческое linking removed профиля, если нужно, рассматривается отдельно от восстановления текущего доступа.

<a id="section-11"></a>

## 11. Знания, публикация и самообучение

Сообщество содержит проекты; Знания — статьи/видео/уроки/курсы; Моё обучение — свои прохождения; Курсы и задания — рабочее авторство/использование. Не создавать параллельные библиотеки одного материала по роли.

Четыре независимые политики материала:

| Политика | Значения / default нового материала |
|---|---|
| Просмотр | private / named / organization / public; default private |
| Самостоятельный старт | disabled / eligible_accounts / approval_required; default disabled |
| Использование преподавателями | owner_only / granted_educators / permitted_public_use; default owner_only |
| Адаптация | forbidden / explicit_grant / permitted_by_license; default forbidden |

Public URL не лицензия copy/deliver и не доступ к answers. Приватное назначение не требует public курса. Чтение не создаёт enrollment, организацию или подписку. Account явно выбирает «Начать самостоятельно», видит pinned version, режим проверки и наличие staff.

Личная история доступна самому пользователю; автор получает только разрешённые агрегаты. Обещание человеческой проверки требует назначенного проверяющего и явных условий передачи конкретных работ. Иначе текст: «Самостоятельное прохождение без проверки преподавателем».

Переход «Записаться с преподавателем» создаёт отдельное участие, не переносит личную историю в школу. Возможный зачёт — отдельное академическое признание source evidence.

Отзыв public visibility запрещает новые публичные обращения, но не удаляет историю разрешённых pinned проведений. Для каждого use/self-enrollment grant при выдаче фиксируется, сохраняет ли он доступ к уже начатой версии после unpublish/ухода автора; UI показывает это до запуска. Нельзя молча обещать вечный доступ или отозвать ранее обещанное. Срочное safety takedown — отдельное ограничение с причиной, без бесследного удаления результатов.

<a id="section-12"></a>

## 12. Материал, проведение, адаптация и авторство

Другой преподаватель/группа — новое проведение той же версии; допустимые сроки — Run/Participation overrides; обновление общей программы — новая версия; независимая методика — новый content root с source provenance; совместное редактирование — grants на общий draft. Старые pinned runs не ретаргетируются.

Раздельные списки: Курс → Соавторы и доступ; Проведение → Команда обучения; Проведение → Участники. Добавление в один список не добавляет в два других.

«Адаптировать» проверяет copy/license, показывает preview графа и владельца копии. Operation map переиспользует общие зависимости без duplicate nodes; learner/grades не копируются. Обновления оригинала не подменяют адаптацию автоматически. Ограничение чужой лицензии не снимается сменой владельца.

Draft edit использует expected version; stale overwrite даёт conflict. Publisher валидирует точную редакцию. Авторский thread не содержит ученических работ без отдельного разрешённого вложения.

Личный материал остаётся личным после вступления в организацию. Организации можно дать use grant без передачи ownership. Передача ownership — согласие обеих сторон, preview зависимостей, неизменность authors/history и audit. Org-owned материал остаётся в организации после ухода сотрудника. Архивирование не удаляет прошлые версии и сдачи.

<a id="section-13"></a>

## 13. Самостоятельное преподавание и класс

«Самостоятельное преподавание» не требует учреждения. CURRENT физическое соответствие school/workspace нужно доказать; не создавать публичную фиктивную школу и не обходить scope. Два курса/класса не создают организацию; одного коллегу можно пригласить на ресурс без команды.

Создать класс: название, явно выбранное допустимое владение, timezone, применимая safety policy, вход и defaults. Проверить `class.create` в этом контексте. Org-класс требует org authorization; глобальный educator этого не заменяет.

Назначение: content.deliver, published version, teacher scope, classroom, audience, resultMode и даты. Whole class dynamic; named snapshot меняется явно. Course audience материализует нужные child Participation при initial/late join ровно один раз независимо от порядка событий. Course child не получает конкурирующую независимую audience. Direct assignment не создаёт фиктивный CourseEnrollment.

Приглашённый помощник получает выбранные role/scope/time, не edit оригинала по факту преподавания. Закрытие последнего ответственного требует замены или разрешённого завершения/архива. Pending review не становится accepted из-за ухода сотрудника.

<a id="section-14"></a>

## 14. Организация и ответственность

Организация добровольна: школа, центр, кружок, онлайн-команда; возможен один человек на этапе подготовки. Organization и конкретное school unit не считаются равными без physical mapping. Subset доступа явный. Подтверждение учреждения не следует из названия/domain.

Создатель получает owner только новой команды. Owner не имеет текущего скрытого доступа ко всем сдачам; может назначить себе разрешённый дополнительный учебный профиль отдельной audited командой. Это контролируемая управленческая возможность, не обещание технической невозможности чтения владельцем при последующем законном self-grant. Запрет self-review и safety caps не снимаются.

Org admin приглашает только разрешённые ceiling роли. Другой org admin и ownership — отдельное право владельца; platform никогда не входит в ceiling. Уже принятые org assignments принадлежат организации и не исчезают с увольнением issuer. Pending invite после ухода issuer требует подтверждения другой действующей authority. Personal delegation зависит от parent, но независимые grants сохраняются.

Передать ownership: recent step-up, действующий подходящий recipient, preview, acceptance, атомарная смена и уведомления. Pending transfer не лишает прежнего владельца ответственности. Нельзя оставить организацию без последнего owner; потеря доступа — отдельный recovery с evidence, не название школы.

Уход staff закрывает его организационные права, не Account/другие области. Прошлые actors оценок остаются. Закрытие команды имеет export/retention процедуру, не hard delete всех детей.

Первый platform admin назначается контролируемым bootstrap для конкретного подтверждённого Account ID; не первому зарегистрированному. Операция недоступна web-role, защищена от повторного использования, аудируется. Действующую команду исполнитель проверяет, а не придумывает CLI. Дальнейшие grants — через platform.roles.manage и нужную assurance.

Авторский preview не официальное обучение. Сотрудник с answer-key доступом не получает метку независимой проверки знания автоматически. Учёба у других преподавателей тем же Account разрешена; собственная ручная оценка — нет.

## 15. Запросы, приглашения и одобрение

Own центр: Профиль → Мои доступы; Профиль → Приглашения и запросы. Management решения — в конкретном материале, проведении, классе или Организация → Запросы, а не чужие заявки в личном inbox.

| Запрос | Где | Кто решает / результат |
|---|---|---|
| Авторство/преподавание | Возможности | Server eligibility/onboarding; соответствующая capability |
| Вступление Account в класс | Моё обучение → Войти по коду | Roster approver или exact preapproved invite; только learner |
| Teacher-approved login | Public join | Credential manager точного challenge; session |
| Linking | Учебный профиль → Связать | Proof обеих сторон, classroom approval, safety; link |
| Self-study | Знания → Начать самостоятельно | Published self-enrollment policy; personal participation |
| Обучение с преподавателем | Разрешённая карточка проведения | Members manager; это проведение |
| Edit/publish/use/copy | Известный материал | Content manager/license policy, раздельные действия |
| Teacher/reviewer/mentor/coordinator | Команда обучения | Staff manager и ceiling |
| Org staff/admin | Команда и роли | Org manager; admin только в допустимом ceiling |
| Детализация | Сводка → Запросить расширение | Authorized manager; не grade mutation |
| Передача ownership | Ответственность | Owner + recipient |
| Поддержка | Помощь → Обращение | Support approval, scope/time |
| Platform role | Защищённый platform процесс | Platform roles manager |

Request: type, requester, known target, requested action/template, reason, timestamps, expiry, approver scope, policyVersion, idempotency и version. Invite привязан к Account ID либо проверенному challenge получателя. Неподтверждённая почта не связывает произвольного человека.

Request lifecycle `pending → approved|rejected|cancelled|expired`; Invite `pending → accepted|declined|revoked|expired`. Последующий отзыв — отдельное событие, не переписывание решения. Approved без успешно применённого grant/необходимой acceptance не показывается как действующий доступ.

Commit повторно проверяет issuer/recipient/scope/version. Изменение присланной роли требует новой версии и согласия. Same key+same payload — тот же результат; другой payload — conflict. Pending не даёт permission. Отсутствующий approver — `approval_unavailable`, не auto-approval.

Предложения из V1, НЕ введённые этим документом в рабочую конфигурацию: staff invite 72 часа; teacher approval linking 24 часа; browser challenge 5 минут; переходный одноразовый token 10 минут. Срок awaiting approval не продлевает истёкшие proofs: требуются новые. Действующий более строгий security profile не понижается.

У неизвестного private UUID нет карточки владельца и кнопки произвольного запроса. «Запросить доступ» только на уже допустимом landing. Bulk approval имеет точные counts/preview/reason/per-item outcome; не массовый merge детей по имени.

<a id="section-16"></a>

## 16. Общение и уведомления

Четыре области: public material discussion; discussion конкретного проведения; private thread работы ученика с назначенным staff; авторское обсуждение редакции. Один курс в двух группах не объединяет их приватные чаты. Автор не получает learner messages по author grant.

«Попросить помощь» маршрутизирует назначенным наставникам. Если их нет, не обещать ответ. Наставнический draft-read требует отдельного точного доступа. Произвольный глобальный мессенджер и обязательные внешние контакты ребёнка не входят в контракт.

Comment edit не меняет результат. «Отлично» не review. Переход к официальной проверке требует `review.publish`; решение связывается с точной Attempt/Submission, обсуждение сохраняет эту ссылку.

Subscriptions и каждое read/send авторизуются; отзыв закрывает обычное дальнейшее общение. Историческое чтение имеет отдельное основание. Moderation evidence — минимум конкретного case, не автоматический доступ ко всем перепискам.

Уведомления: приглашения/решения, назначения, ответы, сдачи, возвраты, результаты, linking/recovery/privileged changes. Учебные — в приложении; внешние только поддержанные подтверждённые каналы и нужное согласие. Наличие MAX-login не подписывает на MAX-рассылку. Security сообщения не отключаются как реклама. Перед доставкой проверить актуальную область; внешнее preview без оценок, secret и лишней PII. Count также scoped; link повторно авторизуется.

<a id="section-17"></a>

## 17. Дашборды, метрики и экспорт

Личный кабинет показывает свои проекты/обучения; ученический — следующий шаг/срок/feedback; teacher — свои работы и журнал; reviewer — порученную очередь; mentor — вопросы; руководитель — scoped aggregates; org admin — staff/структуру/audit; platform — health/jobs/security. Это представления одного источника, не новые grade engines.

Внутри одного доказанного learner context уникальные ученики считаются по stable LearnerIdentity. При двух школах один Account может иметь две identities: без отдельно разрешённого межконтекстного mapping показатель называется «учебные профили по областям», а не число уникальных физических людей. Нельзя merge по Account/имени ради красивой метрики. Два курса в одном контексте: один learner и два участия.

Programs — content roots; versions отдельно; deliveries — runs. Submitted требует реальной canonical semantics; legacy-only помечается для authorized staff. Waiting review — реально проверяемая сдача; completed — pinned policy. Last login не освоение темы. Фильтр, область, `asOf` и basis видны. Не усреднять несопоставимые шкалы и не выводить качество преподавателя из кликов.

Aggregate-only не даёт learner names/detail/submission/export. Public авторская аналитика: предложенный threshold 5 с подавлением малых категорий и защитой разностных запросов; это не гарантия анонимности и не текущая configuration. Законный teacher видит точные данные своего класса по праву. Объединённая staff-сводка нескольких организаций требует отдельного контракта; наличие двух memberships недостаточно.

Export — отдельное действие с requester/scope/filter/форматом/полями. Долгая job повторно проверяет grant при выполнении и download. Выход содержит дату, scope и применённые фильтры, не секреты; spreadsheet strings не исполняются как пользовательские формулы. Download отзываем/ограничен, audit обязателен. Нельзя экспортировать личную межшкольную историю всех участников по общему Account ID.

## 20. Приоритет настроек

Права: действующие основания + scope + применимые caps. Безопасность: platform minimum ограничивает org/class; lower scope может сузить, не ослабить. Academic: разрешённый Participation override > explicit/pinned Run > Course block template > LAV default, с проверкой согласованности. Grading: exact pinned basis, не новый school default. UI preference меняет только представление.

Live grants/visibility могут менять доступ, но не content/result history. Versioned content/keys/resultMode/completion требуют новой версии или отдельной нормативной correction. Timer extension активной Attempt — отдельная audited семантика, не обратный пересчёт часов.

Перед sensitive change показывать людей/ресурсы, текущий источник, новое значение, affected active attempts, будущие starts и неизменные данные. Нельзя общим «Сохранить настройки» переоценить историю. Practice scores не official selected result; linking этого не меняет.

<a id="section-21"></a>

## 21. Жизненные циклы и сохранность

Logout заканчивает одну сессию. Reset меняет credential и указанные сессии. Grant revoke ограничивает свою область. Membership revoke ограничивает зависимые organisational основания. Security suspension Account имеет свою глобальную заявленную область. Learner leave прекращает новые starts/current access, но сохраняет identity/evidence. Архив материала/закрытие проведения не стирают сдачи. Retention deletion — отдельная принятая процедура.

Обычный leave и security suspension не равны. Досдача ранее начатой Attempt возможна только если policy и scoped command это поддерживают; она не возвращает класс целиком. Если Seat потерял единственный credential, нужен новый безопасный attempt-bound доступ либо отказ, не работа без auth. Нереализованную continuation UI не обещает.

Rejoin переиспользует identity только при доказанной связи; он не реактивирует withdrawn Enrollment/Participation вопреки принятому lifecycle. В текущем целевом минимуме — новая явная выдача/Run либо отдельно принятая rejoin-policy.

Бывший teacher не читает историю бессрочно только из-за прошлого авторства оценки. Собственный исторический learner-read определяется явно identity/retention policy. Новый reviewer не меняет авторство старого решения. Отсутствие ответственного показывается оператору, способному назначить замену.

<a id="section-22"></a>

## 22. Минимизация данных и безопасность

Псевдоним не обещает полную анонимность. Юрисдикция, согласия, сроки хранения, возрастные условия и публикация детей определяются принятой рабочей policy, не языком интерфейса. Teacher approval принадлежности профиля не универсальное согласие законного представителя. Guardian dashboard не появляется из контакта подтверждения.

Автору — контент, не roster; наставнику — порученная помощь, не семья/контакты всех; координатору — нужные организационные сведения, не ответы; администратору — необходимые управления без plaintext secrets. Search, avatar/preview URLs, notifications, logs и export имеют те же scope restrictions.

Security profile перед рабочим включением affected функций содержит secure verifier/hashing, key management, rate limits с учётом общего школьного IP, idle/absolute session bounds, cookie/CSRF, step-up, token TTL, audit retention и recovery. V1 предложила Seat idle 60 минут/absolute 8 часов, generated секрет минимум 12 случайных непохожих символов, QR минимум 128 бит случайности. Это предложения к конфигурации, НЕ уже введённые параметры и НЕ разрешение ослабить существующие более строгие нормы. Короткий PIN не объявляется эквивалентом без отдельного доказанного профиля.

SupportSession: действительный actor, ticket/reason, scope/actions, approval, начало/expiry и видимый banner. Не используется cookie пользователя; self-approved support не открывает произвольные данные. Административная remediation не меняет grade прямым UPDATE. После завершения — безопасная сводка.

Если authority доступа недоступна, private action fail-closed, не cached role allow. Публичный кэш только для действительно public материала. Ошибка сохранения/сдачи сообщает неопределённый outcome и безопасное восстановление, не ложное «Сохранено».

## 23. Интеграция с CURRENT

Переиспользовать Account, Principal, WorkspaceMembership, StudentSeat, learner mappings, grants/audit/admin shell и Learning runtime. Не создавать новую Auth или таблицу на персонажа. Каждый logical permission сопоставить с существующим методом и негативным тестом.

School-scoped ADR остаётся действующим physical constraint. Personal self-study, independent teaching, organization-school teaching — разные требуемые контексты, НЕ приказ немедленно создать `LearningContext`. Перед соответствующим DDL нужны адресное решение, разрешение на изменение защищённой области, migration/rollback и доказательство: личная история недоступна школьному staff; две школы не сливаются; школа/класс не фабрикуются; ядро попыток общее. Принятие этого файла не отменяет запрет произвольного tenant/RLS change из AGENTS.

Минимальные read models: own context/actor/nav/actions/permission version; resource allowed actions и безопасная причина; requester/approver invites; own Seat/linking; scope-aware summary. Общий DTO не содержит class secrets или все школы. Resource action read не заменяет mutation recheck.

Команды: request capability; issue/reset/revoke credential; join/login/link approval; staff invite/accept/revoke; permission grant; organization create/transfer; self-start; publish/use/copy; scoped message; export; support. Для каждой зафиксировать actor, trusted lineage, permissions/states, idempotency/digest, expected version, transaction, audit и response. Нет generic `PATCH user.role`, `approved=true` или произвольного `setTenant`.

БД обеспечивает uniqueness links/memberships, lineage, immutable history, token single-use, duplicates/revoke races. Error result после ранних writes не доказывает rollback; тестируется весь outcome. Bulk atomic либо явно resumable с per-item results.

Новые HTTP contracts идут вместе с OpenAPI. UI aliases сохраняют безопасный путь. Weak legacy login выводится управляемым credential transition с рабочим восстановлением, не внезапной блокировкой детей и не скрытым bypass. Проверять fresh, mixed-data и upgrade. Старый read-only feature toggle не доказательство rollback новых identity writes.

## 32. Полный Account: формы и настройки

### UI-01 — Профиль

Аватар: выбрать/загрузить/вернуть стандартный только по media policy. Username, display name и plain-text bio — отдельная coherent profile form. Исторические UI limits 3–40 username, 2–255 displayName, bio 960 не принимаются за универсальный backend контракт: проверить CURRENT и обязательность, не вводить имя против разрешённого Auth пустого поля.

Error сохраняет несекретный ввод; username_taken фокусирует поле; stale version предлагает сравнение, не overwrite. Avatar сохраняется независимо и не затирает незаписанную bio. Role picker здесь отсутствует.

### UI-02 — Вход и безопасность

Способы входа с server state connected/pending/expired/unavailable, контакт verification, пароль, active sessions, фактически поддержанный step-up. MAX/login не доказательство школьной identity. Не рисовать несуществующие SMS/провайдеры.

Password форма: текущий когда требует сервер, новый/повтор, show/hide. Исторические UI 10–200 — observation, действующая security policy главнее. Success очищает secrets; сообщения об отзыве сессий только по server outcome. Незавершённое подключение нового метода не отключает старый.

Disconnect требует доказанную альтернативу login/recovery, re-auth и preview sessions. Нельзя потерять последний usable метод. Session list: устройство, времена, current marker, «Завершить»/«Завершить остальные»; revoke idempotent. Unknown provider не not-linked. Приватные DOB/country отображаются только при наличии и не считаются verified по факту заполнения; correction не safety bypass.

### UI-28 — Уведомления

Матрица событие×действительный канал, destination, возможность отключить. Security отдельно от обычных уведомлений; quiet hours только где разрешено. Нет внешних каналов — не заставлять Seat регистрироваться. Pending/failed channel отдельно, consent на рассылку не следует из провайдера входа.

### UI-03/04/05 — Возможности, доступы, приглашения

Возможности: польза, открываемые действия, что НЕ выдаётся, действующая policy, state, request/cancel/open/recovery. Преподавание подключается отдельно; после успеха независимые «Создать класс» и необязательное «Создать организацию».

Мои доступы: действие/обязанность, scope, источник, срок, состояние. «Открыть», «Почему», «Запросить изменение», допустимый отказ от grant с last-owner проверкой. Pending invite — не active allow. Технические коды только раскрываемой деталью.

Invites: Мне/Мои заявки/История; issuer, exact resource, роль, действия, срок/version. Показать каким Account принимается. Recipient mismatch не выдаёт private данные. Accept/decline/cancel/reissue по состоянию; изменение предложения требует нового согласия.

### UI-29/30 — Данные и учебные связи

Приватность: public preview, свои публикации, реально поддержанные data/deletion requests. Удаление — не быстрый hard delete; preview own/org/retained history и ответственности, pending/сроки только из действующей процедуры.

Связанные профили: только собственные scope, псевдоним, participation state, link. «Открыть обучение», «Посмотреть связь», «Запросить исправление». Не показывать старые карточки и не выполнять reconcile обычным «Отвязать».

## 33. Учебный профиль и классный вход: UI

Переиспользовать SeatAccountPage. Read-only псевдоним/группа/teacher/safety, разрешённый avatar picker, отдельные достижения без превращения badge в grade. «Попросить изменить имя», помощь входа, optional linking, ясный logout. Нет обязательной почты/биографии/org dropdown. U04 Account не урезается до Seat только по возрасту.

UI-06: объяснение «данные выдаёт преподаватель; Account необязателен»; код → минимальный preview → auth ветвь → своё обучение. CTA Продолжить/Назад/У меня Account/Войти/Отменить. Общая ошибка без existence leak; pending с deadline; expired новый challenge; rate-limit retry-after.

UI-07: намерение linking, доказанные source/target, preview неизменности работ, Continue/другой Account/отправить approval/отменить. Подтверждение credential outcome только после успеха, не на pending.

UI-08: профиль, scope, статус доступа, версия выдачи и допустимая link-detail; не старые secrets. Выдать/reset/завершить входы/suspend/history — разные команды. Одноразовая карточка и lost-response §9, не бесконечный повтор reset.

UI-09: отдельные вкладки Join/Login/Link. У login — challenge; у link — две доказанные стороны; у join — только learner role. Нет «Одобрить всё», смешивающего разные proofs. После revoke approver controls закрываются; reload отражает server state.

## 34. Точные паспорта P01–P19

P — сценарии и fixtures, не global userType. Каждый паспорт наследует форму/ошибки §§31–36, permissions §6 и policy §5. Ни одна персона не выдаётся клиентом. Общие обязанности совмещаются по resource, не через 19 независимых кабинетов.

<a id="persona-p01"></a>

### P01 — Гость (U01)

**Цель:** понять возможности, посмотреть проекты/знания. **Вход:** отсутствует личная session; public policy. **Данные:** только опубликованное разрешённое. **Кнопки:** Смотреть/Читать/Войти/Создать Account/Войти по коду. **Настройки:** допустимые local presentation, не cloud profile. **Запрет:** private roster/history, auto-enrollment, обязательная школа. **Связь:** public authors, а не их staff. **Пусто/ошибка:** нет материала/недоступен без раскрытия owner. **Доказательство PERSONA-AC-01:** public read и отказ private UUID; кодовый вход не требует регистрации.

<a id="persona-p02"></a>

### P02 — Личный создатель проектов (U02/U03/U04)

**Цель:** модели, схемы, игры для себя. **Основание:** Account и действительная policy/entitlement. **Данные:** Personal Workspace, own/share. **Кабинет:** Главная/Мои проекты/Игры/Сохранённое. **CTA:** Создать/Открыть/Сохранить/допустимый Export/Publish. **Настройки:** собственный профиль/security/PREF. **Запрет:** class/org/admin от регистрации; author учебного курса не следует из авторства модели. **Ошибка:** pending verification ограничивает конкретную функцию, save failure не success. **PERSONA-AC-02:** реальное сохранение без школы; чужой проект закрыт.

<a id="persona-p03"></a>

### P03 — Самостоятельный ученик (Account)

**Цель:** пройти открытый курс. **Основание:** explicit self-start и version policy. **Данные:** своё personal прохождение. **Кабинет:** Моё обучение → Самостоятельно. **CTA:** Начать/Продолжить/самопроверка/результат. **Настройки:** своё отображение и уведомления, не правила автора. **Запрет:** fake classroom, передача автору всех ответов, обещание отсутствующего reviewer. **Ошибка:** unsupported personal scope не изображается работающим; сохранённое не переносится в школу. **PERSONA-AC-03:** курс без org и без раскрытия ответов автору.

<a id="persona-p04"></a>

### P04 — Account-ученик у преподавателя (U03/U04/U06)

**Цель:** назначенное обучение и обратная связь. **Основание:** approved участие, не просто известный код. **Данные:** свои Run/Participation, работы и допустимая история. **Кабинет:** Моё обучение → С преподавателем. **CTA:** Открыть/Начать/Сдать/Доработать/Результат/Помощь. **Настройки:** own preferences, льготу просит у staff. **Запрет:** чужой журнал/роль управления; teacher в другом контексте не self-review. **Ошибка:** withdrawn/срок/awaiting feedback различны. **PERSONA-AC-04:** своя сдача доступна, соседняя закрыта; Account может преподавать отдельно.

### P05 — Ученик по коду (U05)

**Цель:** быстро войти по карточке без почты. **Основание:** точный Seat credential либо approved challenge. **Данные:** свой подготовленный профиль. **Кабинет:** Обучение/Учебные работы/Помощь/упрощённый профиль. **CTA:** работать/сдать/попросить помощь/аватар/optional link/выйти. **Настройки:** безопасные preferences; login/name через teacher. **Запрет:** guest-to-Account prerequisite, global public profile, чужие Seat, grading от наличия email. **Ошибка:** восстановление у manager, pending link не блокирует обучение. **PERSONA-AC-05:** карточка→работа→result, сосед закрыт, link сохраняет историю.

**Цель:** помочь по обращению. **Основание:** approved временная session, actor/ticket/scope/actions/expiry. **Данные:** только согласованные объекты. **Кабинет:** case/session с постоянным banner. **CTA:** разрешённая помощь/завершить/безопасная сводка. **Настройки:** не продлевает/расширяет себе доступ. **Запрет:** чужой cookie, скрытый impersonation, читать другие работы, UPDATE grade. **Ошибка:** expiry/revoke закрывает новые действия, история помощи остаётся. **PERSONA-AC-19:** scoped помощь и отказ после окончания.

### Совмещение и состояния

Общий Account может быть P02/P03/P06/P09 одновременно. Editor А + publisher Б не publish А; learner А + teacher Б не self-review А; reviewer+mentor имеют одну работу с раздельными outcomes; summary+org admin не detail без grant. Две организации дают две разрешённые области, не неограниченный union. Pending/expired/under-policy/empty queue — состояния, не новые люди.

P05 linking становится Account-путём с прежней историей, не новой Attempt. P16 может явно получить дополнительную учебную роль, но dashboard не выдаёт её сам. Billing остаётся существующим отдельным scope; R15 guardian FUTURE. Не создавать 19 сайтов, классов auth или новых глобальных role enum.

PERSONA-AC-20…28: mixed learner/teacher/personal; editor А/publisher Б; reviewer+mentor outcomes; summary+admin без detail; revoke и delayed response двух scopes; linking history/resultMode; pending/unsupported/empty/denied различны; collapse UI не revoke; org invite не присваивает personal content.

Для реализации достаточно матрицы P → current component/route → logical action → server command/scope → test → readiness. Она часть рабочей заметки большого результата, не отдельный bureaucracy milestone.

<a id="section-36"></a>

## 36. Поведение всех экранов

Loading отображается до разрешения нужных данных; initial failure — retry/error, не вечный spinner. Независимые блоки profile/avatar/sessions/provider не обрушивают друг друга. Partial failure показывается там, где произошло. Unknown не empty, pending не success, zero не missing.

Dirty несекретный ввод защищён при переходе: сохранить/отменить/остаться; password/QR/token не сохраняются в persistent draft. Submit Enter принадлежит своей форме. Независимые операции не выполняются одним «Сохранить»: profile не role, avatar не bio, preferences не grants, message не review.

Mobile/desktop: 1440/1024/390/320 и увеличенный текст. Разрешённые actions не пропадают; панели не перекрывают exit/feedback. Keyboard focus/labels, focus trap modal, Escape для допустимой отмены и возврат в opener; critical pending outcome не теряется закрытием окна. Таблицы имеют readable mobile alternative, а не скрытые права в недоступной горизонтали.

Caches keyed actor/context/resource/permission version. Отзыв очищает private view и subscriptions; поздний ответ прежней области не перерисовывает новую. Уведомления/files повторно авторизуются. Preferred home после revoke заменяется безопасным собственным fallback, не неизвестной школой.

## 39. Как этот файл становится основой

Постоянные инструкции входа и Learning entry ссылаются на этот канонический путь. Отдельные Auth/Admin документы описывают свои протоколы и операции, а не второй конкурирующий набор персонажей. Ссылки на V1/V1.1/V1.2 из переписки — история, не параллельная исполняемая спецификация.

Для задачи о пользователе читать: §0 → нужный P §34 → action §6/правило §5 → screen §§18,31–36 → связанные tests. Для другого модуля нет обязанности загружать весь этот документ. Изменение норм сопровождается причиной, затронутыми IDs, согласованием доменных контрактов и тестом; не вводить новую роль только ради кнопки.

Принятие продукта, кода, миграций и deployment остаётся отдельно. Этот документ не говорит, что personal self-study уже внедрено, все 19 кабинетов работают или текущая база соответствует TARGET. Он не активирует следующую задачу Learning/Admin и не меняет current.yaml.

**Итог:** один человек — несколько занятий; один ресурс — конкретные разрешения; один курс — версии и разные проведения; добровольная организация — делегированная команда; учебный профиль по коду — прямой безопасный вход без обязательной личной регистрации. Интерфейс объясняет это действиями, а сервер доказывает границы каждого действия.
