## 1. Область и источник требований

Матрица проверяет [основное ТЗ](MASTER_SPEC.md), [контракт интерфейса](UI_CONTRACT.md), [контракт данных и рейтинга](DATA_AND_RATING_CONTRACT.md) и [контракт доступа](ACCESS_CONTRACT.md). Порядок ограниченных этапов задаёт [план внедрения](IMPLEMENTATION_PLAN.md). [Визуальный эталон](visuals/compact-progress-reference.html) определяет согласованную компоновку; сам по себе он не доказывает работу приложения, данных или разрешений.

Это перечень обязательных сценариев, а не отчёт об их выполнении. Здесь не ведутся текущие статусы, выбранная задача, рабочий SHA или таблица готовности этапов: их единственный источник — [current.yaml](../../execution/current.yaml). Фактические результаты хранятся в неизменяемых доказательствах конкретного прогона, на которые ссылается каноническое состояние. Наличие строки в этой матрице не означает `PASS`.

При расхождении матрицы и соседнего нормативного контракта исполнитель фиксирует конкретное противоречие до изменения поведения. Запрещено самостоятельно подбирать веса, создавать новые виды рейтинга, менять смысл доступа или заменять утверждённую компоновку. Изменение принятого решения проходит через журнал изменений основного ТЗ и обновление затронутых сценариев.

## 2. Общие условия проверки

- Проверки выполняются на точном кандидате приложения. Для браузерного прогона подтверждаются SHA работающих Web и API; скриншот автономного макета не заменяет приложение.
- Используются синтетические участники и изолированные проверочные данные. В доказательства не попадают Student Code, токены, имена реальных детей или закрытые данные Account.
- Набор личностей включает самостоятельный Account без группы; Account с одной и несколькими доказанными связями с StudentSeat; StudentSeat без Account; связанную Seat-сессию; преподавателей с точным разрешённым контекстом; постороннего участника.
- Набор данных включает пустую группу, отсутствие заданий, нулевые результаты, равенство баллов, несколько групп с противоположными правилами, доступную и закрытую возможность, ошибку и задержку ответа.
- Для видимых чисел используются, в частности, `0`, `58,42`, `68,25`, `82,46`, `99 999,99` и трёхзначное место. Большое значение относится к допустимому общему показателю; оно не подменяет шкалу рейтинга группы.
- Основные пользовательские состояния проверяются в настоящем приложении при ширине viewport **1440, 1024, 390 и 320 CSS px**. Высота, масштаб браузера и плотность пикселей фиксируются в доказательстве. Длинные названия групп и широкие числовые метки включаются в каждый проход адаптивности.
- SQL, серверные разрешения и атомарность проверяются исполнимыми assertions. Визуальные размеры, читаемость и наложения дополнительно проверяются по изображениям. Один вид доказательств не заменяет другой.
- В каждом ограниченном этапе запускаются относящиеся к нему проверки и обязательные gates репозитория. Не запускаются повторно тяжёлые общие проверки без нового изменения, требуемого gate или конкретной гипотезы о риске. `cancelled`, пропуск проверки и результат старого SHA не считаются `PASS`.

## 3. Формат доказательств

Для каждого выполненного сценария обязательна строка со следующими колонками. Один запуск может покрыть несколько ID, если для каждого ID приведены его assertions и наблюдения.

| Колонка доказательства | Обязательное содержимое                                                                                                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `case_id`              | Точный ID из этой матрицы.                                                                                                                                                                               |
| `source_sha`           | Полный SHA проверенного исходного кандидата; для браузера также подтверждённые идентификаторы запущенных Web/API. Несовпадение указывается явно.                                                         |
| `command_or_steps`     | Фактически выполненная полная команда, идентификатор CI job или воспроизводимая последовательность действий в приложении. Для UI — маршрут, тип сессии и viewport. Общая фраза «все тесты» недостаточна. |
| `assertions`           | Какие именно условия строки проверены; значения входных данных и границы, если они влияют на результат.                                                                                                  |
| `observed_result`      | Полученные значения, разрешение/отказ, состояние интерфейса либо конкретная ошибка. Планируемый результат не переносится в эту колонку как наблюдение.                                                   |
| `artifacts`            | Ссылки на точный лог, результат API/SQL и скриншоты соответствующего прогона. Чувствительные данные исключаются.                                                                                         |
| `limitations`          | Неисполненные части сценария, недоступная среда, использование кэша и иные ограничения доказательства.                                                                                                   |

Невыполненная проверка отмечается в отчёте прогона как `NOT_RUN`; невозможная в данной среде — с конкретной причиной блокировки. Их нельзя заменять предположением по коду. Owner acceptance и развёртывание не следуют автоматически из зелёного CI или из заполненной матрицы.

## 8. Условия принятия ограниченного этапа

1. Исполнитель указывает, какие ID входят в его этап по плану внедрения, и прикладывает фактические доказательства на финальном SHA. Самостоятельно сокращать принятую матрицу нельзя.
2. Для каждого затронутого инварианта есть проверка поведения, а не только проверка наличия поля или совпадения текста реализации. Для изменения UI обязательны относящиеся к нему реальные браузерные состояния и размеры.
3. Неисполненные сценарии и ограничения среды названы явно. Они не становятся автоматически выполненными после merge соседнего этапа, зелёного общего CI или просмотра макета.
4. Изменение схемы, формулы, режима доступа, состава ролей или компоновки требует обновления нормативного контракта и связанных ID через принятый порядок изменений. Исполнитель не начинает соседний этап и не чинит постороннюю область для формального зелёного результата.
5. После технического внедрения оцениваются завершённые и принятые задания, исправления по обратной связи и продолжение курса. Посещения, клики и время на странице сами по себе не доказывают улучшение обучения. Без наблюдений не заявляется достигнутый психологический эффект.

Приёмка документации подтверждает только полноту и согласованность контрактов. Приёмка функций, разрешение на развёртывание и оценка пользовательского результата требуют собственных доказательств и не выводятся из факта существования этого файла.
