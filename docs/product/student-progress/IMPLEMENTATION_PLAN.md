## 2. Общий контракт задачи исполнителю

Перед работой контроллер выбирает одну карточку и фиксирует полный точный план файлов. Preflight, перекрытия с параллельной работой и применимые blockers проверяются по `AGENTS.md`. Перечень точек кода в карточке — ориентир; новые файлы и тесты фиксируются в точном плане до записи.

Каждая карточка содержит: результат, зависимости, scope, запреты, реализацию, проверки и выход. Если нужны два независимых доменных изменения, контроллер разбивает карточку на ограниченные подэтапы с теми же критериями; автор не расширяет её самостоятельно.

Фактические source/CI/review receipts сохраняются в execution state. Requirements и матрица приёмки не получают дублирующих зелёных флажков. Один документ с запланированным тестом не означает, что тест существует или выполнен.

## 3. Проверки и скорость исполнения

- Для документации: governance, ссылки/уникальные IDs, формат, точный diff и независимая проверка согласованности.
- Для L1: адресные существующие unit/component checks, typecheck/build затронутого проекта и настоящий browser layout затронутых consumers.
- Для данных/permissions: реальный изолированный PostgreSQL с ограниченной application role, отрицательная авторизация, конкуренция/retry, migration compatibility; independent challenge review.
- Общий `ASA / required` и требуемые workflow читаются на точном финальном SHA. Старый зелёный запуск не переносится на новый код.
- Если нет подходящей адресной команды, она добавляется одним проверяемым шагом в рамках выбранного среза. Локальный и CI runner используют одинаковую команду. Ослабление существующего gate не входит в программу.
- Браузерные и data acceptance выполняются на существующем изолированном CI-маршруте. Новый постоянный сервер или Compose-проект не создаётся.
- При unrelated красном CI фиксируется классификация и отдельная зависимость; чужой модуль не исправляется в этой программе ради зелёного статуса.

Существующие точки проверки: `pnpm gate:governance`, `pnpm test:learning-e1`, `pnpm gate:projects-publication`, `pnpm gate:projects-publication:browser`, `pnpm gate:repository`. Это разные уровни доказательств; публикационные gates требуют реального PostgreSQL. Адресная UI-проверка не называется полным publication gate.

## 4. Управление отклонениями

Техническая проблема сначала сопоставляется с принятым SP-D решением. Исправление, сохраняющее пользовательский смысл, выполняется внутри среза. Изменение формулы, области права или композиции требует записи решения и обновления связанных сценариев до реализации.

Для product deviation записываются пять полей: изменяемая норма, причина, конкретный вариант, влияние на пользователя/данные, основание принятия. Блокирующий вопрос передаётся владельцу с уже подготовленными вариантами; обычные implementation details не превращаются в вопросы согласования.

## 5. Выход каждого этапа

Отчёт содержит фактические `TASK`, `ISSUE`, `COMMIT_SHA`, `CI`, `DEPLOYMENT`, `DATABASE_ACTIONS`, `VISIBLE_RESULT`, `USER_FLOW`, `PORTS`, `DEMO_URLS`, `SCREENSHOTS`, `TESTS_RUN`, `MAP_NODES_CHANGED`, `WORKING_TREE`, `NEXT_ALLOWED_TASK` по `AGENTS.md`.

Для UI указываются layout impact, проверенные viewport и реально просмотренные изображения. Для data/permissions — отрицательные сценарии и совместимость. Незапущенная проверка остаётся `not_run`. Контроллер завершает этап только в его границах и затем выбирает следующую готовую зависимость.
