# SP-02 — реальная персональная сводка

**Зависимость:** SP-00; существующие identity/publication contracts. **Класс:** L3 данные и доступ.\
**Нормы:** MASTER SP-D12, SP-D13, SP-D21, SP-D22, SP-D24; DATA_AND_RATING_CONTRACT.

## Результат

Сервер одним авторизованным запросом возвращает собственные показатели публикаций и ограниченную сводку разрешённых учебных групп. Ответ пригоден для личного блока и не требует клиенту обходить весь каталог или каждый проект.

## Scope и источник истины

Новый progress read-model и controller используют существующих principals/links, стабильные publication IDs и канонические learner projections. Account и Seat проходят действующие guard/authorization boundaries. В модели нет начисления новых баллов и нет клиента, выбирающего владельца сводки.

Основные показатели: `everPublishedWorks`, `currentLikes`, `createdCopies`; `activePublicWorks` доступен в деталях. Данные содержат `asOf`, область, coverage и состояние доступности. Собственные группы используют прежние score/rank/period; общий балл не вычисляется.

## Реализация

1. Сначала разрешить actor scope, затем выбрать уникальные исходные публикации.
2. Суммировать в owner-authorized проекции, не выдавать сумму public-only функций за всю историю.
3. Развести успешный ноль, отсутствие источника и ошибку.
4. Порцию групп ограничить сервером; избежать отдельных тяжёлых расчётов для каждой карточки и каждого peer.
5. Любое добавление схемы — новая недеструктивная миграция после актуального frontier; существующие migration bytes не редактируются.

## Приёмка

Один источник через несколько links считается один раз; новая ревизия не увеличивает число работ; снятие лайка влияет на текущие реакции; удалённая конечная копия не стирает существующий исторический receipt. Seat не получает Account-private документы или чужие группы. Другой actor, отозванная связь, cross-tenant и произвольный class ID не раскрывают сводку.

Использовать настоящий isolated PostgreSQL и application role, regression existing publication/identity cases, concurrent/retry tests и независимый challenge review. Новые API contracts фиксируются в принятом формате репозитория.

## Выход

Есть воспроизводимый запрос с проверенными числами и отрицательными тестами. На этом этапе API readiness не называется улучшенной главной: подключение настоящего личного блока выполняет SP-03.
