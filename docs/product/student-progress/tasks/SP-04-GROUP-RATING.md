# SP-04 — безопасная аватарная лента группы

**Зависимость:** SP-03. **Класс:** L3 learner read permissions + UI.\
**Нормы:** MASTER SP-D04, SP-D06…SP-D09, SP-D21…SP-D24; UI/DATA contracts.

## Результат

Ученик видит собственный закреплённый аватар и разрешённые аватары участников своей группы с местами и баллами. Полный список открывается ограниченными порциями. Принятый референс реализован на настоящих данных.

## Серверная граница

Отдельная learner-safe проекция: opaque peer key, безопасный avatar reference, score, rank, isSelf, период/версия расчёта, cursor/hasMore. Она не возвращает teacher roster, имена, credentials, last-active, оценки, private work IDs и чужие access reasons. Защищается и выдача пикселей аватара, а не только JSON.

Own profile и peers используют один согласованный результат расчёта. Сохраняются формула и `rank()`; точность до двух десятичных знаков. Stable paging привязан к actor/class и версии результата. Новая версия не должна создавать дубли и пропуски незаметно: клиент начинает согласованную порцию заново.

## UI

Own слева крупнее, тонкий разделитель; peers по server rank без own-дубля. Desktop — до пяти peers, narrow — столько, сколько помещается с трёхзначным местом и дробным score без сокращения значения. «Все» доступно с клавиатуры и touch. Никаких знаменателей и имён, включая скрытые подписи.

## Приёмка

Не участник/removed/revoked/cross-tenant не читает ленту, связь участника с аватаром и приватные изображения. Общие стандартные ассеты `/assets/avatars/default/*.webp` остаются публичными. Account видит только группы с действующим разрешением. Проверены ties `1,2,2,4`, все нули, null, own вне верхней порции, повторяющиеся аватары, смена версии при paging, длинные названия, недоступное изображение и logout.

Серверные отрицательные тесты выполняются в реальном PostgreSQL; browser evidence — в built ASA Lab на 1440/1024/390/320. Независимый challenge review обязателен.

## Выход

Лента подключена к главной и обучению; реальный ученический API даёт только разрешённые поля. Выдача всего staff DTO с последующим скрытием имён CSS не принимается.


## SP-04 — реализуемые API-контракты и границы проверки

Сервер использует новые отдельные learner-safe маршруты, а не преподавательский roster:

- `GET /api/progress/groups/:groupId/rating?view=preview&limit=1..5` — Account.
- `GET /api/class-join/progress/groups/:groupId/rating?view=preview&limit=1..5` — StudentSeat.
- Оба GET с `view=all` и `cursor` — постраничная выдача до 20 peers.
- `POST /api/progress/groups/:groupId/avatars` и `POST /api/class-join/progress/groups/:groupId/avatars`, тело `{"tickets":[...]}` — авторизованная пакетная выдача изображений, не более 20 элементов.
- Все ответы `Cache-Control: private, no-store`. Ни одна сессия не передаётся через URL.

Публичная DTO `GroupRatingPageV1` содержит только `groupId`, `periodDays`, `asOf`, `version`,
`own`, до 20 `peers` (opaque `peerKey`, `avatarSrc`, encrypted `avatarTicket`,
`score`, `rank`, `isSelf:false`), `hasMore`, `nextCursor`. Внешний DTO не содержит
`seatId`, `avatarId`, имён, Student Code, ведомости, персональных оценок,
teacher roster, чужих проектов и идентификаторов tenant/Account.

Приватный SQL `personal_progress_group_rating` переиспользует
`classroom_participant_metrics` из 0209, серверную нормализацию score
и ранжирование SQL `rank()`. SQL возвращает ограниченный внутренний срез
с seat UUID только серверу; публичная DTO явно конструируется API.
`personal_progress_group_member` проверяет действующую сессию и актуальное
связанное членство для каждого запроса. Защищённое изображение возвращается
только через POST с аутентифицированным зашифрованным билетом;
фактические пиксели повторно проверяются с SQL application role.

Курсор является AEAD-билетом сессии и содержит группу, версию расчёта,
позицию и вторичный seat UUID исключительно в зашифрованном виде. При
несовместимой версии API возвращает `409 progress_rating_stale`, клиент
сбрасывает старые страницы и повторно начинает выдачу. Лента Home/Learning
использует `ProgressLifetime`, abort и ограничение двух параллельных
групповых чтений, не загружая весь roster. На узких экранах серверный
`limit` уменьшает сам объём данных, а не скрывает их CSS.

Эта запись определяет реализуемый контракт, а не факт окончательной
приёмки. Итоговые SQL/RLS, реальные браузерные скриншоты, независимое
заключение и exact-SHA CI должны пройти прежде, чем SP-04 получит `done`.


## SP-04: ключи безопасности и жизненный цикл запросов

`avatarTicket` и `nextCursor` шифруются AES-256-GCM. Ключ каждого билета
формируется HMAC-SHA256 от **независимого серверного** 32-байтного master key
и хеша текущего cookie-сессионного токена; ключ невозможно вычислить, зная
только собственную cookie. В URL не попадают cookie, JWT, Student Code,
Account/Seat UUID и нешифрованные идентификаторы других учеников.
Проверки access/session/tenant/identity/avatar permission выполняются SQL
при **каждом** чтении, поэтому даже ранее выданный билет не обходит отзыв
доступа, удаление членства или выключенный преподавателем рейтинг.

Для одно- или многопроцессного окружения допускается серверная переменная
`ASA_SP04_TICKET_SECRET`: ровно 64 шестнадцатеричных символа (256 бит),
созданных криптографически безопасным генератором, единый секрет между
всеми API-процессами одного deployment. Не размещать секрет в Git,
публичных `.env`, фронтенд-сборке, логах или URL. Если переменная отсутствует,
каждый API-процесс генерирует **свой** случайный master key при запуске:
конфиденциальность сохраняется, но курсоры и билеты перестают работать
после рестарта, а между разными API-репликами не переносимы. Такой режим
пригоден для одиночного тестового процесса, но **не является**
устойчивой настройкой для нескольких API-реплик. Некорректная непустая
переменная отвергается на старте.

В браузере SP-04 разделяет **только ещё выполняющийся** preview-запрос
одной `ProgressLifetime` (actor, generation, continuity), группы и лимита
1–5. Результат не кешируется после завершения запроса. Для ожидающего
запроса есть верхняя граница 12 с; прекращение старого consumer по
AbortSignal освобождает локальный слот сразу, а результат никогда не
показывается после смены пользователя/сессии. Максимум одновременно
обрабатываемых потребителей групп — два. Полная лента `view=all`
обрабатывается отдельными страницами не больше 20, со stale-409
restart; запреты ролей, scope и SQL остаются серверными.

Эти параметры и модели доступа должны проверяться непосредственно
в `personal-progress.controller.spec.ts`, реальном PostgreSQL/HTTP,
переходах Home ↔ Learning/смене Account/Seat и браузерных сценариях.
Отдельного разрешения на публикацию или production deployment
данный раздел не предоставляет.
