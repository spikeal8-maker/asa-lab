# ASA LAB — SP-PLATFORM-RATING-ACCESS-V2: платформенные права обычного Account

**Статус:** отдельный будущий **L3 security/product stage**, НЕ изменение действующей v1 policy.  
**Зависимости:** принятая версия SP-05; реальный серверный ledger/total SP-06; доказанная Account identity; controller selection и отдельное owner acceptance.  
**Основание:** [owner correction](../OWNER_PLATFORM_PROFILE_UX_2026-11-16.md).  
**Цель:** обычный пользователь ASA Lab без участия в учебном классе может получать отдельные платформенные возможности по накопленному общему рейтингу; администратор управляет условиями, не обходя существующую модель доступа.

## 1. Области и режимы

Платформенный scope — authenticated Account, не группа и не StudentSeat. Начальный список отдельно настраиваемых действий: `ai.use` и `games.play`; точные resource/action keys сверить с существующими admission, не выдумывать второй API.

Для каждой возможности предусмотреть версионированную policy:

- `inherit_existing` (default): в точности существующая семантика, без новых запретов;
- `allow`: explicit account/platform grant **только если** остальные обязательные ограничения разрешают действие;
- `deny`: явный запрет с причиной;
- `min_global_rating`: динамический серверный порог общего рейтинга выбранного Account; при пересчёте применим действительный подтверждённый total.

Рейтинг сам по себе не является ролю, административным правом, лицензией или способом обойти tenant/owner restrictions. `unknown`/not_enabled/identity_unproven не подменяются 0 или любым пороговым положительным решением; для `min_global_rating` — безопасный deny с reason, при `inherit_existing` — старый evaluator без изменений.

Эта версия **не выдаёт постоянный earned grant**: состояние `min_global_rating` динамическое. Если владелец впоследствии выберет бессрочный доступ после достижения, это отдельная версионированная миграция/решение, не скрытая реализация.

## 2. Приоритеты и безопасность

Server effective decision = auth/tenant + platform/entitlement + scope/resource constraints + explicit denies + versioned policy. Административный `allow` не обходит более высокий обязательный запрет. Старые условия classroom games/AI и их исключения продолжают работать для StudentSeat/учебных ресурсов; platform Account policy не расширяется на школьный контекст.

- StudentSeat не получает `Account.ai.use` через имя, совпадающую аватарку, email или неавторизованную связь.
- Доказанные Account→Seat links не дают читать скрытые проекты/историю без отдельного safe-scalar контракта.
- Server admission проверяется **на самой операции**, а не только на кнопке.
- Применение policy и отмена имеют строгие revision/race правила; старый клиент не может затереть новый mode.
- Actor, rule version, scope, threshold, reason, effective decision и запись изменения policy доступны аудиту без раскрытия лишних персональных данных.

## 3. Админка

Компактная панель «Платформенные возможности» на существующей странице Admin, не второй центр управления. Для каждой возможности: режим, число порога (только `min_global_rating`), текстовое объяснение эффекта, scope Account, предварительное отображение «пользователь увидит», сохранение с revision check и отмена. Индивидуальные overrides только в рамках существующей модели авторизации/при отдельном точном продукт-решении; не изобретать новую роль.

Пользователь видит действие и короткую причину `доступно / нужен подтверждённый рейтинг / административный запрет / право не поддерживается`. Остаток до порога показывать **только** по корректному серверному total. Не обещать доступ за клик, логин, копию или ненадёжный zero.

## 4. Приёмка и выход

- Account без класса, с 0/ниже/ровно-на-пороге/выше рейтинга.
- Account с учебной группой: platform policy не выдаёт scoped classroom permissions.
- StudentSeat, другой tenant, revoked identity, absent total, service error.
- Deny выше allow/threshold; old-client stale write; concurrent admin changes.
- Прямой API вызов при скрытой/заблокированной кнопке; negative auth и SQL/RLS.
- Обновление баллов меняет динамический доступ без stale-cache bypass; нет бесконечного polling.
- Регрессия существующих игр и ИИ на прежней policy `inherit_existing`.
- 1440/1024/390/320 admin/UI и доступные reason statuses.

Новый additive SQL/repository/API/admin UI планировать **после** отдельного approval по этому ТЗ; обратимая миграция, exact-SHA CI, независимый security review. По умолчанию функция OFF/inherit; публичная активация и deploy — отдельное решение.

**Запрет:** вводить platform-rating grants в P0/P1, менять завершённые C3/SP-05, рассчитывать права по фронтенду или изменять живую БД без разрешения.
