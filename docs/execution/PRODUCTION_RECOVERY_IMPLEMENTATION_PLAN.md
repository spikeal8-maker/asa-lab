# План стабилизации и восстановления ASA Lab

Этот документ задаёт воспроизводимый порядок восстановления **кода и проекта ASA Lab**.
Текущее состояние задачи, checkpoint и owner acceptance находятся только в
[`current.yaml`](current.yaml).

## Границы

- В области работ: Git-история, сборка web/API, PostgreSQL ASA Lab, тестовый
  preview, пакеты кандидата и отката, запуск ASA Lab и проверка публичного URL.
- Вне области: FRP-маршруты, DNS, Cloudflare, Selectel, VPN, IZO и настройки
  Windows, не относящиеся к процессу ASA Lab.
- Секреты не входят в release-пакеты и отчёты. Скомпрометированный секрет MAX
  не используется повторно.
- Рабочая база, owner assets, локальные ZIP и резервные копии не удаляются.

## P0. Зафиксировать исходное состояние

1. Определить фактический production checkout, процесс, revision, schema и
   readiness (`/health/ready`, а не только `/health/live`).
2. Снять Git bundles, статусы и patches всех обнаруженных рабочих копий.
3. Снять PostgreSQL custom dump, TOC и globals; вычислить SHA-256.
4. Проверить восстановление dump в отдельную базу с суффиксом `_test`.

Критерий: код и данные можно восстановить без действующей рабочей копии.

## P1. Получить чистую кодовую основу

1. Создать отдельную чистую рабочую копию от проверенного baseline.
2. Не переносить туда случайные `node_modules`, `dist`, `.env` или локальные
   незавершённые изменения.
3. Проверить `blocking` и `pnpm control-plane:check` до записи.

Критерий: изменения проекта изолированы и не перезаписывают чужую работу.

## P2. Сделать неизменяемый release-пакет

1. Собрать web и API без Nx cache.
2. Развернуть только production-зависимости API.
3. Включить web dist, API dist, миграции, lockfile и минимальные runtime tools.
4. Удалить точную служебную self-ссылку `pnpm deploy`; любую другую ссылку за
   пределы пакета считать ошибкой.
5. Сформировать рекурсивный manifest всех файлов и ссылок с SHA-256.
6. Запретить `.env`, дампы и cookies в пакете.
7. Запретить сборку внутри неизменяемого пакета.

Критерий: пакет запускается без исходного checkout и fail-closed реагирует на
любое изменение файла.

## P3. Подготовить независимый откат

1. Упаковать последнюю подтверждённую рабочую revision отдельно от кандидата.
2. Проверить тот же schema contract и рекурсивный manifest.
3. Хранить кандидат и откат в разных каталогах; не перезаписывать их.

Критерий: откат — готовый runnable artifact, а не команда `git reset`.

## P4. Проверить на восстановленной базе

Последовательно запустить кандидат и откат на `127.0.0.1:4612` против одной
изолированной восстановленной базы `_test` и проверить:

- `/health/ready`, `/api/version`, revision и schema synchronization;
- HTML и все рекурсивно перечисленные assets;
- реальный вход владельца и серверную роль platform admin;
- вкладки админки: пользователи, организации, безопасность, система, история;
- создание и чтение проекта после reload;
- открытие и reload электроники, 3D, шахмат и шашек;
- переходы назад/вперёд, отсутствие page errors и CSP errors.

Критерий: браузер работает с реальным API и PostgreSQL, без mocks.

## P5. Проверить репозиторий

На точном финальном SHA выполнить с `NX_SKIP_NX_CACHE=true`:

1. `pnpm gate:governance`;
2. `pnpm gate:code`;
3. `pnpm gate:data` с явными `TEST_DATABASE_URL` и `APP_TEST_DATABASE_URL`;
4. итоговый `pnpm gate:repository`;
5. релевантный браузерный gate на поднятом тестовом стеке.

Пропущенный из-за отсутствия Docker `compose:check` обозначается `SKIPPED`, а
не `PASS`. Кэшированный результат не считается новым доказательством.

## P6. Сохранить независимую копию

1. Добавить manifests кандидата и отката к исходным recovery-материалам.
2. Создать AES-зашифрованный архив на независимом синхронизируемом носителе.
3. Хранить ключ отдельно с ограниченным ACL.
4. Выполнить полную проверку архива и записать SHA-256.

Критерий: повреждение checkout или локального recovery-каталога не уничтожает
единственную копию.

## P7. Контролируемое переключение ASA Lab

1. Публиковать только SHA с зелёным CI.
2. Перед переключением повторно снять database dump и сохранить текущий
   launcher.
3. Остановить только процесс ASA Lab, не трогая FRP и другие сервисы.
4. Запустить неизменяемый кандидат; проверить локальный readiness, revision,
   schema и публичные пользовательские маршруты.
5. При любом нарушении критерия немедленно вернуть сохранённый launcher и
   отдельный rollback artifact.
6. Провести ускоренный soak: серия readiness, static asset и browser checks;
   после него продолжить наблюдение штатным supervisor.

Критерий: production работает с точного проверенного artifact, а откат не
зависит от сборки или изменения Git-истории.

## Незакрываемые извне решения

- MAX остаётся выключен до нового секрета: значение, попавшее в переписку,
  должно быть отозвано и не может считаться production secret.
- Owner acceptance может поставить только владелец после просмотра результата.
