# Единый план упрощения разработки и стабилизации продукта ASA Lab

## 1. Назначение

Этот документ объединяет два связанных направления:

1. устранение ложных ограничений между coding-агентами и сокращение служебной
   работы, не создающей пользовательской ценности;
2. первичную продуктовую стабилизацию запуска, маршрутов, загрузки и сохранения
   проектов.

План является дорожной картой и не хранит активную задачу, checkpoint, Issue,
ветку, PR, SHA или результаты gates. Единственный источник текущего состояния —
[`current.yaml`](current.yaml). Этот документ не выдаёт и не отнимает право
менять код и не создаёт новую очередь, lease, lane или блокировку.

Подробный технический контракт продуктовой части остаётся в
[`PROJECT_BOOT_AND_INTEGRITY_OPTIMIZATION_PLAN.md`](PROJECT_BOOT_AND_INTEGRITY_OPTIMIZATION_PLAN.md).
Настоящий документ задаёт порядок, зависимости и критерии всей программы.

## 2. Целевой результат

После выполнения программы:

- новый агент за один короткий вход понимает актуальную задачу и допустимые
  действия без чтения исторических веток и конфликтующих runbook;
- несколько исполнителей не создают постоянные взаимные запреты и не копируют
  проект без необходимости;
- настоящие защиты данных и production остаются обязательными;
- публичные и авторизованные страницы запускаются в одном визуальном каркасе
  без вспышки старой SEO-страницы, белого кадра и лишней перезагрузки;
- проект открывается один раз, а desktop и mobile используют один контракт
  загрузки и сохранения;
- локальное закрытие, временная сеть и одновременная работа двух устройств не
  приводят к молчаливой потере данных;
- каждый вывод о качестве подтверждается конкретным gate и браузерным journey,
  а не предположением по исходному коду.

## 3. Что сохраняется без ослабления

Упрощение разработки не отменяет:

- защиту PostgreSQL volume, рабочей базы и backup dumps;
- явное подтверждение production-миграций;
- запрет force-push, `reset --hard`, rebase опубликованной истории и
  неразрешённых тегов;
- неприкосновенность owner SVG, ZIP, screenshots и backups;
- остановку перед перезаписью пересекающихся незавершённых изменений;
- запрет убивать неизвестный процесс на занятом порту;
- immutable release guard, tenant/RLS и security gates;
- отдельное подтверждение публикации, deployment и owner acceptance.

Это защитные инварианты. Они не считаются «ограждениями между ботами».

### 3.1. Критическая проверка исходных предположений

План нельзя реализовывать как список функций, которых якобы ещё нет. Проверка
текущего кода показывает смешанное состояние:

| Направление | Фактическое состояние | Следствие для реализации |
|---|---|---|
| G0: инвентаризация ограничений | Частично выполнена: противоречащие документы и валидаторы найдены | Превратить выводы в regression-тест, а не повторять аудит каждым агентом |
| G1: удаление bot-fence | Не выполнено: старые task/branch/lease/lane остаются в активных документах и validators | Первый обязательный implementation package |
| G2: короткий вход | Частично: `START_HERE_FOR_AI.md` существует, но единой preflight-команды нет; текущий полный набор обязательного чтения достигает 161 447 символов и 18 292 слов | Добавить машинный вывод, scoped context package и fresh-agent test |
| P0: измеримый baseline | Не подтверждён browser artifacts | Сначала измерить, не менять UI вслепую |
| P1: первый кадр | Частично: статический boot shell уже находится в `apps/web/index.html` | Не создавать второй shell; проверить filmstrip и исправить точную причину оставшейся вспышки |
| P2: единый запуск | Частично: `ModuleEditorHost` открывает проект, но предметные hooks также содержат `openProject` | Подтвердить число запросов, затем убрать доказанный дубль через `initialProject` |
| P3: сохранение | Существенная основа реализована: четыре редактора имеют local journal/flush, API принимает `baseRevision` и `mutationId` | Не переписывать сохранение; свести дубли к общему контракту после characterization-тестов |
| P4: конфликт и превью | Серверный CAS, `409 project_revision_conflict` и `sourceRevision` уже реализованы | Проверить реальный two-context UX, recovery и RLS; дополнять только найденные разрывы |
| Q1: выпуск | Частичные unit/contract/PG проверки существуют | Нельзя считать готовностью без fresh browser, uncached repository gate и owner acceptance |

Эта таблица — проверяемая архитектурная отправная точка, а не источник текущего
статуса исполнения. Перед каждым продуктовым пакетом она обновляется по коду и
фактически запущенным тестам. Если возможность уже реализована, агент обязан
сначала написать characterization/regression-тест и не создавать её вторую
параллельную реализацию.

## 4. Единая модель управления

### 4.1. Источники истины

| Вопрос | Единственный источник |
|---|---|
| Постоянная политика и безопасность | `AGENTS.md` |
| Активная задача, checkpoint и blocking | `docs/execution/current.yaml` |
| Порядок входа агента | `START_HERE_FOR_AI.md` |
| Архитектура и тесты конкретного пакета | профильный plan/spec и код |
| Фактический результат проверки | вывод команды и CI на том же SHA |

Manifest, project map, README, старые планы и отчёты могут описывать структуру
или историю, но не могут запрещать обычную работу в `direct_main`.

### 4.2. Значения остановки

Чтобы слово `blocked` не смешивало разные ситуации, используются четыре
различимых результата:

- `BLOCKED_SAFETY` — действие угрожает данным, production или защищённым файлам;
- `WAITING_HANDOFF` — другой исполнитель прямо сейчас меняет пересекающиеся
  пути; блокируется только пересечение, а не весь проект;
- `OUT_OF_SCOPE` — работа не входит в текущий пакет, но не запрещена навсегда;
- `FAIL` — проверка была выполнена и обнаружила дефект.

Исторический lease, lane, branch, PR или `owned_paths` не создаёт ни один из
этих результатов в режиме `direct_main`.

### 4.3. Модель совместной разработки

- По умолчанию используется один канонический checkout `main`.
- Перед записью исполнитель проверяет `git status`, текущий SHA и изменяемые
  пути.
- Параллельная работа допустима для непересекающихся файлов и модулей.
- При реальном пересечении исполнители передают короткий handoff: SHA, список
  файлов, незавершённая работа и фактически пройденные тесты.
- Worktree или feature branch создаётся только когда он упрощает конкретную
  работу, а не как обязательный ритуал.
- Нельзя создавать постоянные ownership-записи, которые переживают работу и
  воспринимаются следующими агентами как запрет.
- Временный coordination-файл, если он когда-либо нужен, должен иметь автора,
  точные пути и срок окончания; после handoff он удаляется тем же пакетом.

## 5. Поток работ и зависимости

```text
G0 Зафиксировать baseline
        │
        ▼
G1 Удалить ложные bot-fence правила
        │
        ▼
G2 Сделать короткий и проверяемый вход агента
        │
        ▼
P0 Измерить пользовательские сбои
        │
        ▼
P1 Единый первый кадр и маршруты
        │
        ▼
P2 Один запуск проекта и единый editor shell
        │
        ▼
P3 Единое локальное и серверное сохранение
        │
        ▼
P4 Конфликты устройств и revision-bound preview
        │
        ▼
Q1 Производительность, безопасность и приёмка
```

G1–G2 выполняются раньше масштабной продуктовой доработки: иначе каждый новый
агент продолжит расходовать время на старые правила. Product-фазы не начинают
изменять Electronics, пока выполняющий её исполнитель не передал работу; при
этом непересекающаяся governance-работа не блокируется целиком.

### 5.1. Исполнимые пакеты

План выполняется небольшими пакетами. Каждый пакет имеет одну цель, ограниченный
набор файлов и собственный критерий отката.

| Пакет | Конкретный результат | Основные файлы | Минимальная проверка |
|---|---|---|---|
| GOV-1 | Тест на противоречащие agent-инструкции | `tools/test_validate_control_plane.py`, новый hygiene-validator | новый validator + `pnpm gate:governance` |
| GOV-2 | Универсальные runbook и docs без старого состояния | `BOT_RUNBOOK.md`, `TASK_SYSTEM.md`, agent-facing README, `TEST_STRATEGY.md` | hygiene-validator + `control-plane:check` |
| GOV-3 | Удаление активной зависимости от lease/lane/фиксированной очереди | `current.yaml`, `validate_control_plane.py`, `validate_delivery_program.py`, их тесты | control-plane tests + governance gate |
| GOV-4 | Одна preflight-команда и fresh-agent journey | новый `tools/agent-preflight.mjs`, `package.json`, тесты | preflight fixtures + governance gate |
| DOC-1 | Малый контекстный пакет конкретного модуля | `tools/agent_context.py`, индекс профильных контрактов, generated artifacts | context snapshot tests + size budget |
| UX-0 | Browser baseline без изменения продукта | новый `e2e/project-boot-integrity.spec.ts`, artifacts | focused Playwright journey |
| UX-1 | Ноль кадров старой страницы и безопасный chunk recovery | `index.html`, `AppBootShell`, error boundaries, `lazy-editor.ts` | filmstrip + SEO + accessibility |
| UX-2 | Один запрос открытия и единый editor shell | `ModuleEditorHost.tsx`, module hooks, API client | network assertion + module regressions |
| DATA-1 | Characterization и унификация существующих save paths | project modules и их tests | unit/contract tests четырёх редакторов |
| DATA-2 | Доказанный конфликт двух устройств и recovery UX | Project Core, API, новый two-context E2E | PostgreSQL CAS/RLS + Playwright |
| QLT-1 | Бюджеты, полный gate и evidence package | gate scripts, CI artifacts, release evidence | uncached repository gate |
| REL-1 | Штатный read-only release status и контролируемый local release | новые `release:status` и `release:local`, release tests | dry-run, rollback fixture, exact revision check |

Названия пакетов — адреса частей плана, а не активные task ID. Они не добавляются
в `current.yaml` все сразу и не образуют новую обязательную очередь. В каждый
момент активируется только требуемый владельцем результат.

### 5.2. Обязательный протокол пакета

Для каждого пакета исполнитель делает одинаковые семь шагов:

1. Проверяет актуальный `current.yaml`, Git и фактическое пересечение файлов.
2. Пишет failing или characterization-тест на наблюдаемое поведение.
3. Делает минимальное изменение без параллельной реализации уже существующего
   механизма.
4. Запускает focused gate и фиксирует, использовался ли кэш.
5. Проверяет diff на чужие и защищённые файлы.
6. Делает один смысловой коммит с понятным откатом.
7. Передаёт receipt: SHA, файлы, тесты, оставшиеся риски и уровень evidence.

Если между шагами 1 и 5 другой исполнитель изменил пересекающийся файл, пакет
не объявляется завершённым: выполняется повторная сверка и явный handoff.

## 6. Этап G0 — baseline без изменения поведения

### Работа

- составить машинно проверяемый список agent-facing документов;
- зафиксировать все упоминания старых task ID, branch, lease, lane,
  `owned_paths`, «только этот бот» и «остановиться до разрешения»;
- разделить найденное на действующую защиту, историческую запись и ложный
  запрет;
- сохранить текущий вывод `control-plane:check`, governance gate и состояние
  рабочего дерева;
- определить документы, которые будут перенесены в history, переписаны или
  удалены как дубликаты.

### Приёмка

- у каждого найденного ограничения есть классификация и конечное действие;
- продуктовый код, Electronics, база и production не изменены;
- существует тест, который до исправления видит противоречащую инструкцию.

## 7. Этап G1 — удаление ложных ограждений

### Работа

- переписать `BOT_RUNBOOK.md` как универсальный runbook без конкретной задачи,
  ветки, PR и очереди;
- убрать императивное состояние из `TASK_SYSTEM.md`, agent-facing README,
  `TEST_STRATEGY.md` и старой development programme;
- перенести действительно полезные исторические материалы в явно обозначенный
  архив, который агенты не обязаны читать при входе;
- заменить раздел «один писатель» старого stabilization plan моделью проверки
  фактического пересечения файлов;
- удалить активные lease/lane/worktree/owner-lane структуры из схемы состояния
  после обновления их потребителей;
- в `direct_main` полностью отключить сбор и валидацию legacy lanes;
- убрать из обязательного governance жёсткие списки `EXPECTED_TASKS` и
  `EXPECTED_ROADMAP`;
- запретить hard-coded task/branch/SHA во всех agent-facing документах, а не
  только в `AGENTS.md` и `START_HERE_FOR_AI.md`.

### Приёмка

- поиск не находит старых обязательных задач и веток в активных инструкциях;
- нормальное изменение приложения в `main` не требует lease, lane или PR;
- изменение shared-файла не отклоняется только из-за исторического owner lane;
- защищённый owner-файл и неподтверждённая migration по-прежнему отклоняются;
- `pnpm control-plane:check` и `pnpm gate:governance` проходят.

### Откат

Governance меняется отдельными небольшими коммитами: сначала тесты, затем
документы, затем схема состояния и валидаторы. Каждый шаг можно откатить без
отката продуктового кода.

## 8. Этап G2 — короткий вход агента и снижение служебных затрат

### Работа

- оставить обязательным чтение только политики, текущего состояния и
  профильного контракта задачи;
- создать одну preflight-команду, которая печатает: ветку, SHA, dirty paths,
  blocking, доступные gates и реальные пересечения с незавершённой работой;
- создать `pnpm agent:context --scope <module>`, который собирает короткий
  контекст только из канонической политики, состояния и профильного контракта;
- выдавать context package одновременно в читаемом и JSON-формате, чтобы агенту
  не приходилось повторно читать исходные карты ради одного поля;
- разделить крупные предметные документы на постоянный `CONTRACT` и отдельную
  evidence/history часть без дублирования активного checkpoint;
- выводить рекомендации отдельно от ошибок и не возвращать ненулевой код для
  исторических или справочных расхождений;
- генерировать производные карты и отчёты из канонических данных вместо ручного
  дублирования;
- определить короткий формат handoff и итогового отчёта;
- добавить тест «fresh-agent»: новый исполнитель по чистому clone получает
  правильную последовательность действий без знания старой истории.

### Измеримые показатели

- не более трёх обязательных документов до начала предметной работы;
- одна preflight-команда вместо серии ручных сверок;
- scoped context package не превышает 30 000 символов и 4 000 слов; фактический
  token count сообщается только если доступен tokenizer выбранной модели;
- ноль дублированных активных task/branch/checkpoint/SHA;
- смена активной задачи не требует править hard-coded список валидатора;
- ноль ложных остановок в синтетических сценариях direct-main;
- каждый реальный stop содержит точную причину и безопасное следующее действие.

Токены нельзя одинаково измерить для всех моделей одним репозиторным gate,
поэтому контролируются воспроизводимые причины расхода: символы и слова
контекстного пакета, число обязательных документов и команд, дубликаты состояния
и ложные остановки. Создание новой Codex-задачи не является обязательной
оптимизацией: без качественного handoff оно может увеличить расход и породить
повторную реализацию.

## 9. Этап P0 — измеримый продуктовый baseline

Исполняется по Фазе 0
[`PROJECT_BOOT_AND_INTEGRITY_OPTIMIZATION_PLAN.md`](PROJECT_BOOT_AND_INTEGRITY_OPTIMIZATION_PLAN.md#6-фазы-реализации).

Обязательно зафиксировать до исправления:

- filmstrip cold reload и прямого editor URL;
- появление старой SEO-страницы или белого кадра;
- число `openProject` и document reload;
- размеры initial bundle и editor chunks;
- desktop/mobile различия загрузки и сохранения;
- abrupt close, временную сеть и два browser context;
- текущую матрицу fallback, autosave и recovery по модулям.

Baseline хранится как artifact проверки, а не как вручную обновляемое состояние.

## 10. Этап P1 — единый первый кадр и маршруты

- нейтральная фирменная `AppBootShell` закрывает SEO fallback до React render;
- `noscript` сохраняет содержательную публичную страницу без JavaScript;
- Портал, sign-in, Admin и прямые editor URL используют один визуальный каркас;
- ошибка маршрута или chunk не вызывает мгновенную циклическую перезагрузку;
- логотип и явные действия «назад/домой» ведут в канонические маршруты;
- desktop, tablet и mobile проходят один набор browser journeys.

**Готово, когда:** на app/editor route старая страница видна `0` кадров, белый
кадр отсутствует, обычная навигация выполняет `0` document reload, SEO и
доступность не ухудшены.

## 11. Этап P2 — один запуск проекта

- вводится единый `ProjectLaunchCoordinator`;
- API открывает проект не более одного раза на переход;
- editor получает уже загруженный `initialProject`;
- один `EditorBootShell` заменяет каскад полноэкранных fallback;
- intent-prefetch выполняется по реальному намерению пользователя;
- тяжёлые editor chunks не попадают в начальный bundle без необходимости;
- устаревший ответ другого project ID не применяется к текущему редактору.

**Готово, когда:** карточка и direct URL дают одинаковый результат, на обычный
запуск приходится один запрос проекта, а lazy-loading остаётся подтверждённым.

## 12. Этап P3 — единое сохранение

Это этап конвергенции существующих реализаций, а не разработка сохранения с
нуля. До рефакторинга фиксируется поведение каждого из четырёх действующих
редакторов; общий контроллер вводится только если тесты доказывают одинаковый
контракт и безопасную миграцию.

- общий `ProjectDraftController` задаёт состояния `clean`, `dirty`, `saving`,
  `offline`, `conflict` и `error`;
- каждое изменение сначала синхронно попадает в локальный journal;
- ordered queue, retry/backoff и visibility flush одинаковы для модулей;
- сервер принимает `baseRevision` и идемпотентный `mutationId`;
- клиент не показывает «Сохранено» до подтверждения текущей редакции;
- внедрение идёт по одному модулю с отдельным откатом и без изменения
  предметной физики или формата документа.

**Готово, когда:** быстрое закрытие и временная сеть не уничтожают локальную
работу, а desktop/mobile показывают одинаковый смысл состояния сохранения.

## 13. Этап P4 — защита между устройствами и правильное превью

Серверные примитивы этого этапа уже присутствуют. Работа начинается с проверки
их сквозного использования клиентами и реального браузерного UX. Запрещено
добавлять вторую таблицу revision, второй idempotency-механизм или альтернативный
snapshot API без доказанного дефекта существующего Project Core.

- атомарное сравнение `baseRevision` предотвращает silent last-write-wins;
- конфликт возвращает `409 project_revision_conflict`;
- обе версии остаются восстанавливаемыми, локальную можно сохранить как копию;
- повтор одного `mutationId` возвращает тот же результат;
- preview привязывается к точной `sourceRevision` сохранённого документа;
- устаревшая картинка допустима, но картинка от другой revision не выдаётся за
  актуальную;
- additive migration проверяется на изолированной PostgreSQL и не затрагивает
  рабочую базу без отдельного разрешения.

**Готово, когда:** два устройства не могут молча перезаписать друг друга,
потерянных версий в browser/PostgreSQL тестах `0`, RLS остаётся зелёным.

## 14. Этап Q1 — производительность, безопасность и выпуск

- зафиксировать бюджеты initial bundle, editor chunks, запросов и CLS;
- проверить отсутствие секретов, небезопасных зависимостей и обходов auth/RLS;
- проверить login, class code, Admin и project journeys на desktop/mobile;
- прогнать focused gates изменённых пакетов;
- прогнать полный repository gate без Nx cache на реальной тестовой PostgreSQL;
- сохранить rollback для schema/API/web изменений;
- отдельно подтвердить CI, deployment revision, readiness и owner acceptance.

Для сокращения повторного анализа выпуска вводятся две разные команды:

- `pnpm release:status` — полностью read-only: показывает HEAD/origin,
  незавершённые изменения, последний release manifest, процессы, readiness и
  фактическую build revision;
- `pnpm release:local` — контролируемый выпуск с preflight, сборкой во временную
  директорию, атомарным переключением, проверкой readiness и автоматическим
  откатом при ошибке.

`release:local` не запускается автоматически из product gate, не публикует
секреты и требует отдельного явного поручения владельца на deployment/restart.
Git push и production restart остаются разными действиями. Deployment receipt
хранит только revision, schema, время, результат readiness и путь rollback — без
секретов и полного журнала промежуточных команд.

Merge, зелёный CI, deployment и визуальная приёмка — разные доказательства и не
подменяют друг друга.

## 16. Порядок исполнения

1. G0 — дописать regression-тесты вокруг уже найденных противоречий.
2. G1 — очистить agent-facing документы и только затем legacy-валидаторы.
3. G2 — добавить единый preflight и fresh-agent journey.
4. DOC-1 — ввести scoped context package и бюджет документации.
5. P0 — снять пользовательский baseline после handoff пересекающихся работ.
6. P1 — исправить первый кадр и маршруты как самый заметный безопасный пакет.
7. P2 — убрать двойную загрузку и каскад fallback.
8. P3 — охарактеризовать действующие save paths и свести только доказанные
   различия к общему lifecycle-контракту.
9. P4 — подтвердить действующие revision conflict и revision-bound preview в
   PostgreSQL и двух browser contexts, затем закрыть найденные UX-разрывы.
10. Q1 — бюджеты, полный gate и evidence package.
11. REL-1 — автоматизировать status/release без объединения push и restart.

Нельзя объявлять всю программу завершённой после очистки governance или после
одной визуальной правки. Организационный результат готов только после G2,
первичная пользовательская стабилизация — после P2, защита данных — после P4,
а release-ready состояние — только после Q1.

## 17. Условия остановки программы

Работа останавливается только если:

- `current.yaml` содержит реальный пункт `blocking`;
- обнаружено фактическое пересечение незавершённых изменений;
- требуется необратимо изменить защищённые данные;
- миграции нужна отсутствующая owner-авторизация;
- gate обнаружил воспроизводимый дефект, который нельзя безопасно исправить в
  границах текущего пакета.

Старая ветка, lease, lane, PR, owner lane, roadmap-очередь или исторический
статус не являются условиями остановки в `direct_main`.

## 18. Критические риски и защита от них

| Риск | Почему он реален | Обязательная защита |
|---|---|---|
| Новый план становится новым забором | Исторические планы уже воспринимаются агентами как разрешения | В плане нет active state; validator запрещает task/branch/SHA в agent-facing docs |
| Удаление legacy ломает зелёный governance | Validators всё ещё структурно читают lanes и фиксированный roadmap | Сначала tests и consumers, затем schema; отдельные откатываемые коммиты |
| Другой бот меняет `current.yaml` или Electronics одновременно | Эти файлы являются частыми точками пересечения | Не писать в пересечение до handoff; governance и product-пакеты разделять |
| Повторная реализация готового механизма | Boot shell, CAS, local drafts и snapshot revision уже существуют | Characterization-first и обязательный поиск существующего owner-механизма |
| Визуальная правка ломает SEO | SEO fallback находится в том же `index.html`, что и первый кадр | Filmstrip, JS/no-JS, SEO и accessibility проверяются пакетом UX-1 |
| Общий save controller меняет предметную семантику | У модулей разные документы и анализ | Controller управляет только lifecycle; предметная валидация остаётся в модуле |
| Unit PASS принимается за пользовательскую готовность | Основные жалобы видны при реальной навигации и загрузке | Обязательный browser journey desktop/mobile |
| Кэш выдаётся за новую проверку | Nx может вернуть старый зелёный результат | Owner evidence только с `NX_SKIP_NX_CACHE=true` и отчётом cache hits |
| Merge принимается за deployment | Опубликованный сайт может исполнять другой SHA | Build identity, readiness и owner acceptance проверяются отдельно |

## 19. Definition of Done всей программы

Программа завершена только когда одновременно выполняется следующее:

- active agent-инструкции не содержат старых задач, веток, lease/lane запретов;
- новый агент начинает scoped-работу после не более трёх документов и одной
  preflight-команды;
- `agent:context` укладывается в установленный символьный/словесный бюджет и не
  включает историю других модулей;
- synthetic direct-main тесты различают safety block, overlap и обычную работу;
- ни одна уже существующая подсистема не продублирована альтернативной;
- filmstrip показывает `0` кадров старой страницы на app/editor routes;
- на открытие проекта выполняется не более одного API-запроса;
- abrupt close и временная сеть не теряют локальное изменение;
- two-context test доказывает отсутствие silent overwrite;
- snapshot соответствует точной сохранённой revision;
- focused, browser и полный repository gates выполнены на принятом SHA с
  требуемой базой и без Nx cache;
- deployment исполняет тот же SHA, readiness зелёный, rollback сохранён;
- `release:status` не изменяет систему, а `release:local` не может продолжить
  выпуск после проваленного preflight или readiness;
- владелец отдельно подтвердил видимый результат на desktop и mobile.

«Код выглядит правильно», «unit-тесты зелёные», «ветка merged» и «сайт
открывается» по отдельности не являются выполнением этого Definition of Done.
