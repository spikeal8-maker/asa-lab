# Стабилизация админки, сессий и MAX

Этот документ задаёт неизменный порядок реализации. Он не хранит номер Issue,
ветку, SHA, статус или checkpoint: текущее состояние читается только из
[`current.yaml`](current.yaml).

## Целевой результат

- админка остаётся защищённой частью общего Web-приложения ASA Lab;
- право владельца выдаётся сервером и не исчезает после завершения cookie;
- пользовательская сессия безопасно возобновляется после первых 12 часов;
- MAX реально привязывается к существующему аккаунту и используется для входа;
- через 24 часа после первого успешного входа появляется ненавязчивое
  предложение подтвердить аккаунт через MAX;
- email остаётся контактным идентификатором без пользовательского подтверждения;
- production сообщает точный build SHA и версию схемы;
- API и ASA Lab FRP восстанавливаются после сбоя и перезагрузки;
- результат подтверждён реальной PostgreSQL, API, браузером и owner acceptance.

## Правила исполнения

1. Пакеты выполняются строго по порядку.
2. Код в Git, развёрнутый production и проверенный внешний результат — разные
   состояния. Следующий пакет не получает статус готового по наличию исходников.
3. До миграций необходим проверяемый backup. До переключения production —
   готовый rollback.
4. Секрет MAX не попадает в Git, frontend, тестовый отчёт или журнал.
5. Старый токен, опубликованный в переписке, не используется.
6. Никакого второго постоянного сервиса, домена, порта или базы для админки.
7. Пользовательские и параллельные незавершённые изменения не перезаписываются.
8. Email-провайдер, CRM, биллинг, соревнования и модерация не входят в этот
   критический контур.

## Пакет 0. Безопасная исходная точка

Результат:

- актуальный `main`;
- отдельный чистый worktree без смешивания с незавершёнными изменениями;
- Issue и активное состояние исполнения;
- точные production SHA, schema version, процессы и порты;
- проверяемый PostgreSQL backup;
- сохранённый предыдущий build и команды rollback.

Стоп-условие: без проверенного backup миграции не начинаются.

## Пакет 1. Интегрированная архитектура и build identity

Изменения:

- карта проекта описывает Admin как поверхность `APP-WEB`, а не отдельное
  приложение;
- health/system API возвращает безопасные `buildRevision`, `builtAt` и
  `schemaVersion`;
- раздел «Система» показывает эти значения;
- readiness не выдаёт ложную синхронизацию приложения и схемы.

Приёмка: внешний сайт однозначно сообщает, какой коммит и схема работают.

## Пакет 2. Возобновляемые сессии устройств

Следующая свободная миграция добавляет семейства сессий и rotating refresh
tokens. Рабочая cookie остаётся короткой, refresh-cookie хранится как
`HttpOnly Secure`, а в базе сохраняется только hash.

Обязательные свойства:

- транзакционная ротация;
- отзыв одного устройства и всех устройств;
- обнаружение повторного использования старого refresh token;
- отзыв при блокировке аккаунта и смене пароля;
- единая модель для password и MAX;
- `401` запускает ровно одну попытку refresh;
- `403` означает отсутствие права и никогда не маскируется под окончание входа;
- возврат на исходный маршрут, включая `#/admin`;
- синхронизация logout между вкладками.

Приёмка: вход сохраняется после 13 часов, закрытия браузера, restart API и
deployment, пока не произошло явное security-событие.

## Пакет 3. Устойчивое право владельца

Добавляются идемпотентные административные команды grant/verify. Право хранится
в `capability_grants`, каждое изменение аудируется, а deployment preflight
останавливается, если владелец не имеет `platform_admin`.

Запрещено определять администратора по email во frontend или позволять снять
последнего platform admin без безопасной процедуры.

## Пакет 4. Жизненный цикл MAX

Расширяется существующая `account_external_identities`, а не создаётся
параллельная identity-система.

Добавляются:

- `verified_at`, `revoked_at`, actor и reason;
- история отозванных связей и уникальность только активной связи;
- `first_authenticated_at`;
- server-owned cooldown предложения MAX;
- API статуса, dismiss и unlink;
- источник сессии `password|max|organization`;
- отзыв MAX-сессий без уничтожения парольного входа.

## Пакет 5. MAX в production

Порядок:

1. владелец перевыпускает и отзывает раскрытый токен;
2. новый секрет размещается вне Git;
3. в MAX настраивается `https://asa-lab.ru/max-login`;
4. включается отдельный feature flag;
5. на реальном клиенте проверяется существующий поток launch → password login →
   link → MAX login;
6. cross-device QR/pairing добавляется только если этот реальный поток не даёт
   приемлемого UX.

Аварийный флаг обязан выключать MAX без поломки password login и без удаления
существующих связей.

## Пакет 6. Предложение MAX через 24 часа

Условие показа:

```text
first_authenticated_at + 24 часа <= now
AND активной MAX-связи нет
AND MAX включён и готов
AND cooldown завершён
```

Desktop: маленькая метка у аватара, пункт меню и карточка профиля.

Mobile: индикатор на аватаре и пункт внутри меню без широкой надписи в header.

Напоминание не блокирует продукт, показывается не более одного раза за сессию,
после закрытия получает cooldown и исчезает после успешной привязки.

Из пользовательского интерфейса удаляются обещания будущего подтверждения
email. Email показывается только как контактный адрес.

## Пакет 7. Профиль и админка

Профиль получает раздел «Безопасность и вход»: MAX, устройства, активные входы,
unlink и revoke.

Админка получает MAX-статус, даты, фильтры, аудит и отзыв MAX-связи/сессий с
обязательной причиной. Она никогда не показывает bot token, raw initData и не
позволяет вручную подменить MAX subject.

## Пакет 8. Реальный gate

Focused gate включает:

- unit-тест подписи MAX;
- PostgreSQL миграции, RLS и уникальность;
- API password/MAX/refresh/revoke;
- time travel более 12 и 24 часов;
- реальный Playwright без mock API;
- desktop/mobile UX;
- secret scan.

Перед production выполняется полный repository gate с
`NX_SKIP_NX_CACHE=true`; кэшированный PASS не считается новым доказательством.

## Пакет 9. Controlled production cutover

1. Собрать точный `origin/main`.
2. Проверить миграции на копии production БД.
3. Запустить preview и smoke.
4. Создать свежий backup.
5. Применить миграции и переключить только ASA Lab.
6. Проверить health, SHA, schema, password login, Admin, MAX и внешний домен.
7. При провале выключить MAX либо вернуть предыдущий build по подготовленному
   rollback, не выполняя непроверенный destructive downgrade БД.

## Пакет 10. Эксплуатационная устойчивость и приёмка

- API и ASA Lab FRP запускаются управляемо и восстанавливаются после сбоя;
- проверены restart и reboot;
- внешний маршрут проверен из российского подключения без VPN;
- владелец под своим аккаунтом проверил Admin, долговечную сессию, привязку,
  MAX login, отзыв MAX-сессии и сохранение password login.

## Definition of Done

Работа закончена только когда все пункты целевого результата доказаны на одном
и том же production SHA, обязательные gates прошли без Nx-кэша, rollback
сохранён, а owner acceptance записан в `current.yaml` отдельным переходом.
