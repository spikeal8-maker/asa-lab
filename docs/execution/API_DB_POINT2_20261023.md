# Пункт 2: конкуренция при проверке ученической сессии

## Задача и границы

Устранить воспроизводимое ожидание строк при обычной проверке StudentSeat,
не меняя полномочия, идентификаторы, пароли, срок действия сессии или настройки
рабочего сервера. Изоляция аналитики и распределение пулов относятся к пункту 3.

## Наблюдаемая проблема

23 октября, 14:49–14:51 МСК, журналы содержат 41 HTTP 500, три HTTP 503,
25 уникальных таймаутов запросов и 18 таймаутов получения соединения.
Максимальное ожидание соединений API — 12 при размере пула 10.
В PostgreSQL есть восемь ожиданий transaction ShareLock до 7,497 секунды
и ожидание tuple ExclusiveLock в relation 17468. Read-only сопоставление relation
на работающем сервере указывает на `classroom_student_sessions`.

Прежняя публичная функция проверяет credential version и idle timeout,
затем вызывает приватную функцию из миграции 0143. Та при каждом обращении
обновляет строку сессии, а затем иногда строку StudentSeat. Конкурирующие запросы
одного ученика могут ждать эти записи, занимая соединения пула.
Миграция 0216 устранила аналогичный эффект только для Account.

Это подтверждённый механизм лишней сериализации, совпадающий с наблюдаемым
отношением блокировки. Он **не доказывает единственную причину всего эпизода**:
тексты SQL в историческом журнале скрыты, ресурсные замеры имеют пробелы.

## Исправление

Новая forward-only миграция 0237 заменяет только публичный Seat resolver:

- один актуальный SELECT одновременно проверяет credential version, отзыв,
  абсолютное истечение, простой менее 60 минут, активность Seat и класса;
- необязательные отметки активности сессии и Seat обновляются независимо,
  не чаще раза в минуту, через `FOR UPDATE ... SKIP LOCKED`;
- занятую строку пропускают, а не ставят запрос авторизации в ожидание;
- сохраняются безопасное имя преподавателя, avatar, safe mode, SECURITY DEFINER,
  фиксированный search_path, закрытый legacy helper и прежние ACL/RLS;
- нет кэша авторизации, продления absolute expiry или перезаписи credentials.

При обычной работе `last_seen_at` теперь может отставать от последнего запроса
менее чем на минуту. Строгий прежний порог `> now() - interval '60 minutes'`
сохранён: отказ из-за простоя может произойти до минуты раньше, но не позже.
Во время длительной блокировки отметка также пропускается; запрос после
истечения прежнего idle-порога не оживляет сессию.

## Проверка

`pnpm test:session-database:pg` включает реальный PostgreSQL before/after:

1. Исторические wrapper 0106 и helper 0143 копируются в изолированные функции.
2. Отдельная транзакция удерживает строку сессии, затем отдельно строку Seat.
3. Четыре старых запроса показывают Lock, очередь пула и SQLSTATE 57014.
4. Двенадцать новых запросов завершаются при всё ещё удерживаемой блокировке,
   возвращая прежние значения без изменения заблокированной отметки.
5. После освобождения due heartbeat обновляется; 30 запросов не меняют xmin
   обеих строк и absolute expiry.
6. Проверяются отзыв, expiry/idle на точной границе, неверная/отсутствующая
   версия credentials, отсутствующий credential, inactive Seat/class,
   неизвестный token, committed revocation/rotation, публичные поля и ACL/RLS.

Реальные PostgreSQL проверки выполняются только в изолированном GitHub workflow
`Session Context Database`, с отключённым Nx cache. Наличие тестов в исходниках
не является PASS; точный SHA, conclusion и измеренные длительности фиксируются
контроллером после CI. Рабочая база этим изменением не проверяется и не меняется.

## Приёмка и ограничения

Приёмка требует зелёного точного SHA PostgreSQL before/after и независимого
HIGH review авторизации/миграции. Исторические миграции не редактируются;
каталог forward-upgrade расширен 0237 с сохранением проверок истории/RLS.
Deployment не входит в этот пункт. Исправление не доказывает ёмкость 5000
пользователей и не закрывает остальные причины инцидента без новых измерений.
