# План оптимизации запуска и целостности проектов ASA Lab

## 1. Назначение

Этот документ определяет следующий продуктовый пакет оптимизации ASA Lab:

- убрать показ старой SEO-страницы во время запуска приложения;
- сделать переход из Портала в редактор визуально непрерывным;
- загружать каждый модуль и проект ровно один раз;
- унифицировать сохранение Электроники, 3D, Шахмат и Шашек;
- не допускать молчаливого перезаписывания проекта между телефоном и компьютером;
- связать превью карточки с конкретной сохранённой редакцией проекта;
- ввести измеримые ограничения на загрузку, восстановление и потерю данных.

Документ является спецификацией будущей работы, а не источником текущего
состояния. Активная задача и checkpoint по-прежнему читаются только из
[`current.yaml`](current.yaml). До отдельного перехода владельца этот план не
изменяет активную задачу и не разрешает публикацию.

## 2. Границы

### Входит в работу

- Web-приложение, Project Core и API сохранения черновика;
- общий хост редакторов и lazy-loading модулей;
- Электроника, 3D, Шахматы и Шашки как первые потребители общего контракта;
- загрузочная оболочка, сохранение, локальное восстановление, конфликты версий;
- карточки проектов и их превью;
- desktop, tablet и mobile browser journeys;
- измерение первого кадра, перехода в редактор и размера загружаемых chunks.

### Не входит в работу

- изменение компьютера, Windows, FRP, Cloudflare, DNS и сетевых маршрутов;
- редизайн самих редакторов и изменение предметной логики;
- изменение tenant/RLS-модели;
- destructive-миграции или удаление рабочих данных;
- service worker и offline-first режим;
- автоматическое смысловое слияние двух конфликтующих схем или 3D-сцен;
- замена существующего Module SDK новым фреймворком.

### Связь с уже зарегистрированными работами

План не создаёт параллельную архитектурную программу. Он собирает в один
пользовательский результат существующие planned-направления карты проекта:

- `TASK-PERF-BASELINE-001` — измерения и бюджеты;
- `TASK-WEB-BOOTSTRAP-001` — неблокирующий первый render;
- `TASK-ASSET-DELIVERY-001` — chunks и cache policy;
- `TASK-E2E-GATE-001` — браузерные регрессии;
- `TASK-SCALE-PREP-001` — подготовка загрузки к росту.

Отдельно этот документ закрывает не зарегистрированный в них разрыв Project
Core: общий local journal, optimistic concurrency, multi-device conflict и
revision-bound preview. При активации пакет должен получить одну исполнимую
задачу в `current.yaml`, а не пять независимых реализаций одного перехода.

## 3. Подтверждённые исходные проблемы

| ID | Проблема | Текущее следствие |
|---|---|---|
| B1 | В `#root` до React находится полноценная SEO-страница | При document reload видна старая главная |
| B2 | Сессия, Project Host и lazy editor имеют разные полноэкранные fallback | Пользователь видит несколько сменяющихся экранов загрузки |
| B3 | Host открывает проект, затем предметный editor открывает его повторно | Лишний API-запрос и последовательная задержка |
| B4 | Ошибка старого chunk вызывает `window.location.reload()` | Снова появляется B1; при несохранённой работе возможен риск потери |
| P1 | У четырёх редакторов разные debounce, очередь и recovery | Поведение сохранения зависит от модуля |
| P2 | Только 3D немедленно пишет локальную страховочную копию | Быстрое закрытие Электроники, Шахмат или Шашек менее защищено |
| P3 | Клиент не передаёт базовую `revision` при сохранении | Последнее устройство может молча перезаписать другое |
| P4 | Превью сохраняется своим таймером и при `pagehide` | Карточка может не соответствовать последней подтверждённой редакции |
| P5 | Состояние меню хранится локально, а данные проекта — на сервере | Пользователь может принять разницу интерфейса за разницу проекта |

## 4. Целевые инварианты

После выполнения плана должны всегда выполняться следующие правила.

### Запуск

1. До первого React render видна только нейтральная фирменная оболочка ASA Lab.
2. Старая SEO-страница не появляется ни на одном кадре app/editor route.
3. На один переход в проект приходится не более одного `openProject`.
4. После определения модуля данные проекта и editor chunk повторно не загружаются.
5. Ошибка chunk не оставляет белый экран и не перезагружает страницу до фиксации
   локального черновика.
6. Lazy-loading не отменяется: неоткрытые предметные редакторы не входят в
   начальный bundle.

### Сохранение

1. Любое изменение сначала синхронно попадает в локальный журнал этого браузера.
2. Серверное сохранение выполняется упорядоченно и подтверждает точную редакцию.
3. Запрос содержит `baseRevision` и уникальный `mutationId`.
4. Сервер обновляет документ только при совпадении текущей и базовой редакций.
5. Несовпадение возвращает `409 project_revision_conflict`, а не `200`.
6. Ни один редактор не показывает «Сохранено», пока сервер не подтвердил именно
   текущий документ.
7. При конфликте ни локальный, ни серверный вариант не удаляются.
8. При уходе страницы в background запускается немедленная отправка, но
   надёжность не зависит от завершения этой отправки: локальный журнал остаётся.

### Превью

1. Превью содержит редакцию документа, из которой оно получено.
2. Сервер не связывает картинку с более новой редакцией, чем изображённая.
3. Карточка отдельно сообщает о состоянии проекта и актуальности превью.
4. Mobile `visibilitychange` не меняет смысл сохранения проекта.

## 5. Целевая архитектура

```text
Project card / direct URL
          │
          ▼
ProjectLaunchCoordinator
  ├─ получает или переиспользует ProjectOpenResult
  ├─ проверяет moduleKey
  ├─ загружает lazy editor по реестру
  └─ передаёт initialProject в editor
          │
          ▼
Subject editor
          │
          ▼
ProjectDraftController<TDocument>
  ├─ local journal: immediate
  ├─ ordered save queue
  ├─ baseRevision + mutationId
  ├─ retry/backoff
  ├─ visibility flush
  └─ conflict recovery / safe copy
          │
          ▼
Project Core API
  ├─ validate module document
  ├─ compare-and-swap revision
  ├─ idempotent mutation result
  └─ revision-bound preview
```

Предметный модуль по-прежнему отвечает за документ, валидацию, анализ и
визуализацию. Project Core отвечает только за жизненный цикл, порядок записи и
защиту от потери данных.

## 6. Фазы реализации

### Фаза 0 — измеримый baseline и защищающие тесты

**Работа**

- записать текущие размеры initial bundle и chunks четырёх редакторов;
- измерить cold reload, тёплый переход и переход после новой публикации;
- добавить браузерный filmstrip-тест с искусственной задержкой JS;
- добавить счётчик `openProject` на один переход;
- зафиксировать текущую матрицу autosave/recovery по модулям;
- добавить два независимых browser context для сценария телефон + компьютер.

**Приёмка**

- тест воспроизводит старую SEO-вспышку до исправления;
- тест доказывает два открытия проекта до исправления;
- тест воспроизводит молчаливое last-write-wins до исправления;
- baseline сохраняется как CI artifact, а не как вручную обновляемая цифра в
  `current.yaml`.

### Фаза 1 — единый первый кадр

**Работа**

- добавить в `index.html` компактную `AppBootShell`, визуально закрывающую
  SEO-fallback до монтирования React;
- для браузера без JavaScript скрывать boot shell через `noscript`, оставляя
  содержательный fallback доступным;
- использовать те же логотип, фон и размеры, что у загружаемого Портала;
- заменить глобальное «Загрузка…» на ту же оболочку;
- не применять стили `login-card` к состояниям загрузки и ошибкам редактора.

**Приёмка**

- на кадрах от navigation commit до готового Портала отсутствует старый hero;
- нет белого кадра и скачка основного фона;
- SEO validator, `noscript` и публичные метаданные остаются зелёными;
- refresh `/#/home`, `/#/admin`, sign-in и прямого editor URL имеет один стиль.

**Откат**

- изолированный revert boot shell без изменения Project Core.

### Фаза 2 — единый запуск модулей

**Работа**

- ввести `ProjectLaunchCoordinator` и тип `ProjectOpenResult`;
- передавать известный `moduleKey` из карточки как подсказку, но проверять его по
  ответу сервера;
- передавать загруженный проект в editor через `initialProject`;
- удалить повторные `openProject` из предметных hooks;
- заменить два Suspense fallback одним стабильным `EditorBootShell`;
- добавить intent-prefetch по `pointerenter`, `focus` и первому `touchstart`;
- не prefetch-ить тяжёлые 3D/Arduino chunks в фоне на мобильной сети без
  пользовательского намерения;
- сохранить generic unavailable state для неизвестного module key.

**Приёмка**

- один `GET /api/projects/:id` на обычное открытие;
- direct URL и открытие из карточки дают одинаковый результат;
- смена проекта во время запроса не применяет устаревший ответ;
- lazy-loading и границы предметных модулей остаются подтверждены тестами.

### Фаза 3 — общий контроллер сохранения

**Работа**

- создать module-neutral `ProjectDraftController<TDocument>`;
- определить единые состояния: `loading`, `clean`, `dirty`, `saving`, `offline`,
  `conflict`, `error`;
- немедленно писать локальный журнал с `projectId`, `moduleKey`, версией схемы,
  `baseRevision`, документом, digest и временем;
- сохранить ordered queue и coalescing промежуточных изменений;
- добавить ограниченный retry с jitter для временных ошибок;
- запускать flush при `visibilitychange=hidden` и `pagehide`;
- внедрять по одному модулю: 3D как референс локального recovery, затем
  Электроника, Шахматы, Шашки;
- сделать единый индикатор и одинаковый пользовательский текст на всех размерах
  экрана.

**Приёмка**

- закрытие вкладки сразу после изменения не теряет локальный документ;
- повторное открытие восстанавливает его до первого нового редактирования;
- неуспешная отправка не блокирует следующую;
- ответ старого projectId не меняет текущий editor;
- одинаковый сценарий имеет одинаковые состояния на desktop и mobile.

### Фаза 4 — optimistic concurrency и безопасный конфликт

**Работа**

- расширить API сохранения полями `baseRevision` и `mutationId`;
- выполнять атомарный `UPDATE ... WHERE revision = baseRevision`;
- различать `not_found`, `forbidden` и `revision_conflict`;
- вернуть при конфликте текущую серверную revision и metadata без раскрытия
  чужого документа;
- сделать mutation idempotency, чтобы повтор после сетевого обрыва не создавал
  лишнюю редакцию;
- при конфликте предлагать безопасные действия:
  - открыть серверную версию;
  - сохранить локальную работу как копию;
  - для поддерживаемых документов позже выполнить предметное сравнение;
- по умолчанию для детского интерфейса сохранять конфликтующую локальную работу
  как копию, а не требовать технического выбора под угрозой потери.

**Приёмка**

- два устройства, открывшие revision N, не могут оба молча записать N+1;
- первое сохранение проходит, второе получает `409`;
- обе версии остаются восстанавливаемыми;
- повтор одного `mutationId` возвращает тот же результат;
- RLS и tenant isolation проходят с новым контрактом.

**Миграция**

- только additive schema change для журнала idempotency, если он необходим;
- существующие `project_drafts` и их revision не переписываются;
- старый клиент на период совместимости получает явно ограниченный контракт,
  после cutover legacy-режим удаляется.

### Фаза 5 — согласованное превью проекта

**Работа**

- захватывать snapshot после подтверждённого сохранения либо передавать точную
  `sourceRevision` и digest документа;
- серверу отклонять картинку для несовпадающей редакции;
- не считать `pagehide`-snapshot доказательством сохранения проекта;
- обновлять URL карточки только после подтверждённого snapshot;
- различать в интерфейсе «проект сохранён» и «превью обновляется»;
- сохранить best-effort capture при сворачивании только как дополнительный путь.

**Приёмка**

- карточка никогда не подписывает старую картинку новой revision;
- мобильное сворачивание не меняет документ и его save status;
- устаревшее превью допустимо, неверно привязанное — нет.

### Фаза 6 — chunks, восстановление после публикации и бюджеты

**Работа**

- разделить тяжёлые каталоги и редакторы по фактической необходимости;
- проверить immutable cache headers только у hashed assets;
- при preload/chunk error сначала фиксировать локальный journal;
- вместо немедленной невидимой перезагрузки показывать внутри стабильной
  оболочки краткое состояние «Обновляем среду…»;
- разрешать не более одной автоматической перезагрузки на build + URL;
- после повторной ошибки оставлять рабочую страницу восстановления, а не цикл;
- добавить CI budget на initial bundle, editor chunk и число запросов запуска.

**Начальные бюджеты для утверждения после Фазы 0**

- старая SEO-страница: `0` видимых кадров на app/editor route;
- `openProject`: не более `1` запроса на переход;
- document reload при обычной навигации: `0`;
- потерянные изменения в тестах abrupt-close/conflict: `0`;
- layout shift загрузочной оболочки: визуально отсутствует, численный CLS budget
  фиксируется по baseline;
- размер chunk не увеличивается без явного budget approval.

## 7. Тестовая матрица

| Сценарий | Desktop | Tablet | Mobile |
|---|---:|---:|---:|
| Cold reload Портала без старой страницы | да | да | да |
| Прямой URL Электроники | да | да | да |
| Прямой URL 3D | да | да | да |
| Шахматы и Шашки через карточку | да | да | да |
| Медленная загрузка API и chunk | да | да | да |
| Устаревший chunk после публикации | да | — | да |
| Сворачивание сразу после изменения | да | — | да |
| Телефон и компьютер редактируют revision N | два browser context | — | два browser context |
| Ошибка сети и повтор | да | — | да |
| Превью соответствует sourceRevision | да | — | да |

Обязательные уровни проверки:

1. Unit: reducer/controller, queue, digest, conflict state, lazy recovery.
2. Contract: API body/response/OpenAPI и module registry parity.
3. PostgreSQL: compare-and-swap, idempotency, RLS, tenant isolation.
4. Browser: filmstrip первого кадра, число запросов, abrupt close, два context.
5. Build: chunk inventory и budgets.

## 8. Команды приёмки

Во время разработки запускаются целевые проверки изменяемого слоя. Конечный
пакет не принимается без одинаковых локальных и CI-команд:

```bash
pnpm test:creator-portal
pnpm test:project-slice
pnpm exec vitest run \
  apps/web/src/electronics/testing/workbench-autosave.spec.ts \
  apps/web/src/chess/testing/chess-save-queue.spec.ts \
  apps/web/src/checkers/testing/checkers-save-queue.spec.ts
pnpm e2e:creator-portal
pnpm gate:code
NX_SKIP_NX_CACHE=true pnpm gate:repository
```

К этому пакету должны быть добавлены отдельные E2E для boot filmstrip,
single-open, abrupt-close и multi-device conflict. Существующие зелёные тесты
очередей не считаются доказательством отсутствия межустройственного конфликта.

## 9. Порядок выпуска

1. Фазы 0–2 можно выпускать отдельно: они не меняют формат данных.
2. Фазы 3–4 разрабатываются совместно, но контроллер включается по одному
   модулю, чтобы сохранить управляемый откат.
3. Сервер с новым backward-compatible контрактом публикуется раньше клиента.
4. После подтверждения новой версии legacy save path отключается.
5. Фаза 5 включается после общей revision-модели.
6. Фаза 6 завершает пакет и фиксирует бюджеты на будущие модули.

Каждый cutover требует проверки фактической revision web/API и readiness; merge
или зелёный CI сами по себе не являются production verification.

## 10. Критерий готовности

Пакет готов только когда одновременно доказано:

- ни один app/editor route не показывает старую главную во время запуска;
- переход сохраняет один визуальный каркас и не выполняет document reload;
- каждый проект открывается один раз;
- все четыре редактора используют общий persistence contract;
- телефон и компьютер не могут молча перезаписать друг друга;
- abrupt close не уничтожает последнюю локальную работу;
- превью связано с точной серверной revision;
- все целевые, PostgreSQL, browser и repository gates прошли без Nx cache;
- результат проверен в реальном браузере на desktop и mobile;
- владелец отдельно принял визуальное поведение первого кадра и конфликтов.

## 11. Рекомендуемая очередность ближайшей реализации

Самый безопасный и заметный первый пакет:

1. Фаза 0: тест, который фиксирует вспышку и двойной `openProject`.
2. Фаза 1: единый первый кадр — немедленно убирает пугающее мерцание.
3. Фаза 2: один загрузочный экран и один запрос проекта.
4. Фаза 3: общий local journal и save state, начиная с Электроники.
5. Фаза 4: серверная защита revision до объявления cross-device надёжности.
6. Фазы 5–6: превью, chunks и постоянные бюджеты.

Нельзя объявлять проблему сохранения решённой после одной только Фазы 3:
локальная страховка защищает от закрытия браузера, но только Фаза 4 защищает от
молчаливого перезаписывания другим устройством.
