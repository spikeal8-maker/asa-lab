### Остановка на внешнем HTTP и завершение операции

Первый запуск штатно вернул RETRY_NEW_MANAGER после смены исходников менеджера, до изменения контейнеров/БД. Повтор той же команды новым менеджером создал копию, применил миграции и поднял новые сервисы.

После переключения строгая проверка внешнего `/health/ready` трижды получила HTTP 404. Менеджер сохранил failed_switch/verify_entry; это не было принято за успешное обновление. При отдельной диагностике локальный и внешний health, metadata и главная уже возвращали HTTP 200 с новым SHA. Временный отказ внешнего входа подтверждён; его конкретная сетевая причина этим наблюдением не доказана.

Перед завершением отдельно проверены фактические digest всех четырёх сервисов, одинаковый SHA API/Web/Scratch, схема212, успешный точный CI и **настоящая строгая проверка public embedded entry** менеджера, включая runtime-config, `/internal/blocks/` и его healthz. Затем штатный acknowledge архивировал исходные маркеры, а функции менеджера сохранили установленный manifest и успешную квитанцию с recovered=true. Повторного переключения сервисов и восстановления БД не потребовалось. Исходная неуспешная квитанция и доказательство ручного завершения сохранены отдельно.

Финальные внешний `/`, `/health/ready`, `/build-metadata.json`, `/internal/blocks/` — HTTP 200. В настоящем браузере после reload открылись главная, форма регистрации и форма входа. Авторизованный сценарий владельца «редактор → сохранить → повторно открыть» — **NOT_RUN**, действующей сессии владельца в проверяемом браузере не было. Готовность сервера и CI не выданы за такую приёмку. Новые рабочие аккаунты и проекты для проверки не создавались.
