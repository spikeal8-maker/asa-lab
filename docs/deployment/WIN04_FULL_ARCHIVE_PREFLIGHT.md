# WIN-04A — проверка полного архива перед переносом ASA Lab

WIN-04A — **только чтение**. Он необходим перед переносом данных ASA Lab на
новую Windows/Proxmox-инсталляцию, но не выполняет восстановление PostgreSQL,
MinIO, настроек или ключей.

## Запуск

В проверенном официальном checkout ASA Lab, при наличии исходного каталога
полного архива оператора:

```powershell
python tools/asa_manager.py import-preflight --backup "D:\ASA-Archive\complete-backup"
```

Указанный путь — пример; используйте действительный защищённый каталог
полного архива, не копируйте секреты в GitHub или отчёт.

Скрипт читает `manifest.json` формата `asa-backup-v1`, сверяет
SHA-256 **каждого** файла архива и запрещает `.incomplete`, повреждённые
файлы, сторонние пути, символические ссылки. Он отдельно проверяет:

- наличие `database.dump`, `globals.sql`, `private.env`;
- `configuration/runtime-configuration.json`, `installed-release.json`,
  точный исходный SHA, версию схемы и закреплённые Docker-образы;
- все Compose-конфигурации исходного профиля: обязательные `compose.yaml` и
  `compose.production.yaml` / `compose.staging.yaml` / `compose.dev.yaml`
  (для `base` только `compose.yaml`), а также при наличии
  `.asa/docker-networks.yaml` и `compose.frp.yaml`. Каждая конфигурация
  должна физически присутствовать в проверяемом файловом инвентаре, а её
  байты — совпадать с UTF-8 текстом recovery JSON в одном из двух строгих
  форматов: LF или исторический Windows CRLF. В обоих случаях оригинальные
  физические байты проходят отдельный SHA-256 из манифеста. Смешанные
  окончания строк и посторонние пути запрещены;
- полноту MinIO-экспорта `objects/`, наличие пользовательского bucket
  `asa-blocks` и точные SHA-256 объектов по манифесту;
- наличие **исходных**, а не вновь сгенерированных ключей PostgreSQL,
  MinIO/S3, `ASA_SETTINGS_ENCRYPTION_KEY`, `CLASSROOM_CODE_SECRET`;
- ключи Student Code для production/staging: режим `compat` или `enforced`,
  корректный JSON keyring, выбранные ID, длину 32 байта для encryption,
  не менее 32 байт для lookup и отличие между ключами.

Секретные значения, содержимое БД и объектов не выводятся. Только счётчики,
SHA релиза, версия схемы и логические индикаторы, необходимые оператору.

## Результат

`ARCHIVE_VERIFIED_NO_IMPORT` и exit 0 означают, что архив полностью прошёл
проверку исходных компонентов. **Не означают**, что данные уже перенесены,
что новые тома доступны, что учётные записи позволяют войти или что
проекты Scratch/3D открываются. В ответе явно:
`writesPerformed=false`, `targetProvisioned=false`, `userFlow=not_run`,
`publisherSignatureVerified=false`. Важно: архивный SHA-256 манифест
проверяет **внутреннюю целостность**, но без подписанного независимого
доверенного манифеста не удостоверяет издателя. Из непроверенного источника
такой архив нельзя автоматически импортировать даже при совпавших хешах.

Любой недостающий ключ, расхождение SHA, профиля, релиза, схемы или объекта
блокирует перенос; новые ключи не генерируются.

## Следующие этапы WIN-04

WIN-04B — отдельный новый Docker Compose project и проверенное восстановление
в новые PostgreSQL/MinIO volumes, исходные `private.env` и ACL/RLS.
Сначала VERIFY → STAGE; не удалять и не переименовывать существующие volume
или БД, не включать автоматическое переключение старого порта.

WIN-04C — сопоставление счётчиков и хешей PostgreSQL/MinIO, проверка ключей,
полный браузерный вход преподавателя/ученика, сохранение/повторное открытие
Scratch/3D, затем явное принятие оператором. После сбоя кандидат сохраняется
для диагностики, исходная установка остаётся рабочей.

Действующие D2R2 4610/4620/18570/28620, production H-04 и школьные серверы
не являются объектами автоматического переноса этим скриптом.

## Испытания

Набор `test_import_preflight.py` создаёт только синтетический маленький архив:
отсутствующий ключ, чужой профиль/проект, неполные keyrings, неверную длину
ключа, одинаковые encryption/lookup ключи, испорченный MinIO-файл, чужую
ревизию и частичный архив. Положительный реальный тест допускается только
как read-only, без публикации `private.env`.
