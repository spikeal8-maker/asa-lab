# Установка, обновление и перенос ASA Lab

Один рабочий каталог, один Compose project, один набор данных. Для эксплуатации
используется `tools/asa_manager.py`; PowerShell и shell оборачивают ту же программу.
Нужны Git, Python 3.11+ и работающий Docker с Compose и Linux containers (amd64).
Node.js и pnpm нужны разработчику, но не серверу с готовыми образами.

## Сначала выбрать диск и существующую установку

Исходники, каталог `backups` и данные Docker должны находиться на SSD/NVMe.
Быстрый каталог проекта сам по себе не переносит Docker volumes на быстрый диск.
В Windows проверьте расположение Docker Desktop disk image; в Linux — Docker
Root Dir и точку монтирования. Менеджер не переносит действующие volumes.
Предусмотрите место для новых и предыдущих образов, полной копии данных и
проверочной БД. `doctor` показывает свободное место рядом с checkout; это не
измерение скорости диска и не проверка достаточности места внутри Docker.

Если ASA уже работает, найдите каталог по метке PostgreSQL
`com.docker.compose.project.working_dir`, как описано в
[SCRATCH_INSTALLATION.md](SCRATCH_INSTALLATION.md). Сохраните `.env`, profile,
transport overlay и project name. Команды ниже выполняются только в этом каталоге.
Не используйте разработческий worktree как второй постоянный сервер.

## Готовые выпуски

GitHub Actions собирает API, Web, Scratch и MinIO один раз. Публикация разрешена
только после зелёного общего CI точного SHA и проверки сборки, запуска,
backup/restore в одноразовом CI. Манифест `deployment:stable` содержит SHA,
версию схемы и неизменяемые digest образов. Клиент дополнительно сверяет
успешную публикацию и общий CI на GitHub. При недоступности проверки остаётся
прежняя установка. Если main изменился во время сборки, старый workflow не
продвигает канал: выпускается следующая прошедшая проверки версия.

Однократная настройка владельцем GitHub: Actions должны иметь право записывать
Packages, а пакеты `api`, `web`, `scratch`, `minio`, `deployment` — быть доступны
серверу. Для публичной установки сделайте их Public в GitHub Packages; иначе
заранее выполните `docker login ghcr.io` с доступом на чтение. Токены не храните
в репозитории. До первого успешного выпуска команда установки из образов
останавливается; исходная сборка остаётся в [QUICK_START.md](QUICK_START.md).

Первая установка на чистом компьютере после публикации:

```powershell
git clone https://github.com/spikeal8-maker/asa-lab.git
cd asa-lab
python tools/asa_manager.py install --profile production
```

В Linux та же команда с `python3`. Production не создаёт демонстрационного
пользователя. Выдача владельцу доступа выполняется по инструкции
[«Главный администратор»](OWNER_ADMIN.md) после регистрации нужного аккаунта.
Новая `.env` создаётся один раз со случайными паролями и ключами. Существующая
`.env` не заменяется. Установка рассчитана на amd64; ARM пока не поддерживается.

## Обновление существующего сервера

Переход со старой схемы отдельного editor origin требует однократной проверки
конфигурации. Новый редактор загружается внутри портала по `/internal/blocks/`;
оба `ASA_BLOCKS_*_ORIGIN` должны совпадать с утверждённым origin портала.
Сохраните этот же точный адрес в приватной `.env` как
`ASA_UPDATE_ENTRY_ORIGIN` (без пути и завершающего `/`). Новая установка
создаёт локальное значение автоматически; для существующей установки адрес
подтверждает владелец. Менеджер не угадывает его по контейнеру или свободному
порту и останавливает `check`/`update`, если его нет или он отличается от
обоих Blocks origins. В профиле `dev` допустим утверждённый HTTP-адрес в
локальной сети; внешний адрес production/staging требует HTTPS, а локальный
`127.0.0.1` остаётся допустимым для установки без публичного домена. После переключения менеджер
проверяет встроенный Scratch через этот адрес, но записывает пользовательский
сценарий save/reopen как `not_run` до отдельной браузерной приёмки.
Для public HTTPS этот origin также входит в `ASA_PUBLIC_WEB_ORIGINS` production.
Менеджер блокирует несовместимую сохранённую `.env` до замены контейнеров с
кодом `EDITOR_ENTRY`. Сначала сохраните полный backup старой конфигурации;
затем выполните контролируемый переход в том же project/root с сохранением
томов и ключей. Обычный `update --profile production` не является командой
смены существующего dev-профиля. Отдельный домен Scratch не создаётся.
Локальные recovery-черновики IndexedDB прежнего browser origin не переносятся
автоматически и не удаляются; подтверждённые серверные проекты остаются в ASA.

```powershell
python tools/asa_manager.py doctor --profile dev
python tools/asa_manager.py check --profile dev
python tools/asa_manager.py update --profile dev
```

Используйте фактический профиль сервера; для production замените `dev` на
`production`. `check` скачивает небольшой манифест и проверяет CI, но не меняет
checkout, контейнеры или БД. `update` заранее скачивает образы, проверяет историю
миграций, создаёт полную копию, заменяет сервисы и проверяет Web/API/Scratch и
схему. Повтор того же установленного выпуска не делает backup и перезапуск.
Дополнительно сверяются фактические имена томов PostgreSQL/MinIO и совпадение
базы приложения, миграций и backup. Переназначение хранилища блокирует обновление.
Изменение PostgreSQL image или `PGDATA` требует отдельного обновления движка БД:
обычное обновление приложения не инициализирует новую пустую БД на месте старой.
В копию включается конфигурация прежней работающей версии, даже если checkout
уже переключён на следующий выпуск.

Операционный checkout закрепляется на точном SHA (`detached HEAD`); это нормально.
Разработку ведите в другом checkout. Локальные изменения блокируют обновление,
они не удаляются. `RETRY_NEW_MANAGER` означает, что на диске обновился сам
менеджер: повторите ту же команду. При расписании повтор произойдёт следующим
разрешённым запуском. До повтора контейнеры остаются на прежней версии.

После перехода на готовые образы старые `asa-lab up` и `docker-update` блокируют
пересборку этой установки. Не запускайте прямой `docker compose up`: он не
читает закреплённый манифест из `.asa/installed-release.json`.

## Воскресенье 03:00–05:00 МСК

В Windows, из канонического каталога, один раз:

```powershell
powershell -ExecutionPolicy Bypass -File tools/install-maintenance.ps1 -Profile dev
```

В Linux (пользователь должен иметь доступ к Docker):

```bash
sudo ASA_COMPOSE_PROFILE=production sh tools/install-maintenance.sh
```

Windows Task Scheduler и Linux systemd вызывают общий менеджер. Он сам
проверяет московское время, поэтому смена часового пояса компьютера не меняет
окно. Проверка выполняется каждые 15 минут в разрешённом окне. Пропущенное
окно не догоняется при включении компьютера. Перед началом простоя оставляется
резерв времени; уже начавшаяся миграция не убивается в 05:00. Долгая операция
может закончиться позже окна — жёсткое прерывание повредило бы восстановление.

**Windows:** задача работает в сеансе пользователя, запускающего Docker Desktop.
Автозапуск службы Docker Desktop сам по себе не гарантирует Linux containers
до входа пользователя. Для автономной работы до входа используйте Linux с
Docker Engine. Планировщик не меняет настройки входа Windows.

Логи: `.asa/logs/`; итог: `.asa/last-operation.json`. При сбое переключения
новые автоматические попытки блокируются до разбора. Автоматического отката БД
нет. Уведомления в мессенджеры и облачная выгрузка в этой версии не настроены.
Отключение: `python tools/asa_manager.py configure --profile dev` (без
`--enable-auto-update`); установленная задача после этого ничего не обновляет.

## Экспорт со старого компьютера

Если Windows и Docker запускаются, не извлекайте файлы БД из работающего VHDX.
В каноническом каталоге старой установки выполните:

```powershell
python tools/asa_manager.py backup --profile dev --output F:\ASA-Transfer
python tools/asa_manager.py verify-backup --backup F:\ASA-Transfer\ИМЯ-КОПИИ
```

Если в старой версии ещё нет менеджера, скопируйте **весь** новый каталог `tools`
в отдельное место и запустите новый `asa_manager.py backup --root ПУТЬ-К-СТАРОЙ-УСТАНОВКЕ
--profile dev --output ПУТЬ-К-КОПИЯМ`. Это не требует обновлять старые контейнеры.
Сначала `doctor --root ... --profile ...` должен подтвердить единый SHA и профиль.
Если старый состав отличается или хранилище внешнее, нужен отдельный адаптер:
менеджер откажется вместо создания неполной копии.
Дополнительные постоянные mounts, включая отдельные файлы конфигурации FRP,
также требуют явного добавления в экспорт. Наличие overlay не означает, что
менеджер может молча пропустить подключённый им том или файл.

На время снимка Web/API/Scratch/MinIO останавливаются; PostgreSQL продолжает
работать. Копируются:

- `database.dump` с ACL и отдельный `globals.sql` без паролей ролей;
- `objects/` — физические данные локального MinIO;
- `private.env` — пароли, ключи шифрования и подписи, параметры доступа;
- `configuration/` и `manifest.json` — состав, версии образов, права, хеши файлов.

После копирования прежние сервисы запускаются. Каталог `.incomplete` не является
готовой копией. Исходная БД и volumes не удаляются. Обновления не удаляют старые
backup автоматически: срок хранения и размер надо выбрать после оценки данных.
Скопируйте готовый каталог на другой физический носитель и снова выполните
`verify-backup`. Копия на том же диске не защищает от поломки этого диска.

`private.env` содержит секреты. Храните экспорт в закрытом каталоге; Windows
наследует ACL родительского каталога. До Яндекс Диска нужно отдельно настроить
шифрование, ключ восстановления и политику хранения. Не загружайте сырой экспорт.

## Проверочное и аварийное восстановление

Команда ниже восстанавливает только в новую БД с суффиксом `_test`. Она
проверяет хеши полного комплекта, pg_restore, таблицы, права приложения и RLS.
Существующая целевая БД блокирует команду; рабочая БД не заменяется:

```powershell
python tools/asa_manager.py restore-check --profile dev --backup F:\ASA-Transfer\ИМЯ-КОПИИ --database asalab_transfer_test
```

Это ещё не ввод восстановленной установки в эксплуатацию: подключение MinIO и
пользовательские действия отдельно проверяются в одноразовом CI. Для реального
переноса на новый компьютер оператор сначала согласует исходный комплект и
пустые целевые volumes, затем использует совместимые версии PostgreSQL/MinIO
из манифеста, сохраняет прежние ключи, восстанавливает нужные роли и БД с ACL,
возвращает `objects/` в остановленный MinIO с uid/gid 1000, проверяет вход,
список проектов, открытие и сохранение проекта и только затем переключает FRP.
Не импортируйте `globals.sql` вслепую: в нём могут быть привилегированные роли.
Пароли ролей восстанавливаются из приватной конфигурации.

Менеджер намеренно не содержит команды перезаписи живой БД. Реальный перенос
старых пользовательских данных — отдельная операция с конкретным источником и
целевым хранилищем; один только зелёный `restore-check` не подтверждает её.

## Короткий маршрут для агента и разработчика

Изменение → focused checks → общий GitHub CI → готовые образы → публикация
манифеста → проверка/обновление канонического сервера. Нельзя обходить красный CI,
удалять volumes, менять порты для обхода ошибки или пересобирать на каждом
компьютере при наличии готового выпуска.

| Код                                      | Следующее безопасное действие                                  |
| ---------------------------------------- | -------------------------------------------------------------- |
| `DIRTY`                                  | Сохранить и разобрать локальные изменения; не reset/clean      |
| `IDENTITY_*`                             | Проверить каталог PostgreSQL, профиль и overlays               |
| `CI_BLOCKED`, `CI_UNAVAILABLE`           | Проверить точный workflow; сохранить прежнюю версию            |
| `RETRY_NEW_MANAGER`                      | Повторить ту же команду новым менеджером                       |
| `LOCKED`                                 | Дождаться уже выполняющегося обслуживания                      |
| `WINDOW_CLOSED`                          | Дождаться следующего разрешённого окна                         |
| `BACKUP_*`, `RESTORE_*`                  | Проверить комплект/хранилище; не заменять живую БД             |
| `MAINTENANCE`, `FAILED_SWITCH`, `HEALTH` | Проверить `.asa` и логи сервисов; автоматического rollback нет |

После успешного ручного ремонта переключения `acknowledge` архивирует маркеры
сбоя только при работоспособной прежней либо выбранной версии. Прерванный backup
требует отдельного возобновления перечисленных в `maintenance.json` сервисов и
проверки состояния; команда не удаляет этот маркер автоматически.

Focused checks (те же команды в CI):

```text
python -m unittest discover -s tools/deployment -p "test_*.py" -v
node --test tools/blocks/deployment.test.mjs
```

Полная сборка и проверка данных: workflow `ASA Portable Delivery Checks`.
Workflow `ASA Portable Release` повторно проверяет публикуемые digest. Тяжёлый
одноразовый стенд создаётся в GitHub Actions, не рядом с рабочей БД.
