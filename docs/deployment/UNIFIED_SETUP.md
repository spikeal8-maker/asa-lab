# Единый установщик и обновлятор ASA Lab

Координация: [#792](https://github.com/spikeal8-maker/asa-lab/issues/792).

`asa-setup.sh` — общий вход для первоначальной установки, обновления,
проверок, резервирования и продолжения известной операции. Рабочее приложение
поступает из опубликованных образов. Node.js и pnpm на эксплуатационном хосте
не требуются.

## Состояние распространения и границы приёмки

Ветка с этим документом содержит кандидат реализации. До отдельного успешного
запуска публикации **публичного выпуска установщика нет**. Артефакт PR с названием
`asa-setup-candidate-<SHA>` предназначен для проверки исходников; он не является
разрешением выполнять его от root на рабочем сервере.

Первый целевой профиль — **Ubuntu 24.04 LTS amd64, действующий 1Panel и системный
systemd**. Проверки функций Python, контейнерный CI и запуск на чистом сервере
с 1Panel — разные свидетельства. Поддержка профиля считается эксплуатационно
подтверждённой только после двух отдельных испытаний: новой установки на чистом
хосте и обновления существующей установки с контрольными данными.

Историческое состояние тестового сервера — выпуск
`813e1f00fce00055882cd678d19a6ed52ddaf992`, схема 275 — служит исходной точкой,
а не закреплённой целью нового установщика. Автоматический restore рабочего
архива из облака в обычный install/update не входит. Реальное восстановление
остаётся `UNVERIFIED` до отдельного разрешённого испытания.

## Получение проверенного пакета

Публикация реализована в
[setup-release.yml](../../.github/workflows/setup-release.yml). После merge и
успешной проверки точного `main` владелец отдельно запускает workflow с
`publish=true`. Он требует опубликованного приложения того же SHA, зелёных
канонических проверок и синтетического испытания. Затем создаёт **новый** GitHub
Release `setup-<полный SHA>` с файлом `asa-setup-<полный SHA>.tar.gz` и GitHub
artifact attestation. Существующий выпуск не перезаписывается.

Ниже инструкция для уже опубликованного выпуска. **До публикации команда
`gh release download` закономерно не найдёт пакет; подменять его архивом `main`
нельзя.** Полный SHA берётся из одобренного выпуска. Для получения нужен заранее
установленный из доверенного источника GitHub CLI, поддерживающий указанные
флаги `gh attestation verify`, и Python 3.11+. Это проверка происхождения до
выполнения загруженного кода, а не установка приложения.

Выполните из обычной административной сессии с `sudo`:

```bash
set -euo pipefail
read -r -p 'Полный SHA одобренного опубликованного ASA Setup: ' asa_setup_revision
[[ "$asa_setup_revision" =~ ^[a-f0-9]{40}$ ]]
asa_setup_download="$(mktemp -d)"
gh release download "setup-$asa_setup_revision" \
  --repo spikeal8-maker/asa-lab \
  --pattern "asa-setup-$asa_setup_revision.tar.gz" \
  --dir "$asa_setup_download"

# Проверяется уже root-owned копия: оператор не сможет заменить её между
# проверкой provenance и последующим привилегированным запуском.
sudo /usr/bin/python3 -I - <<'PY'
import os, stat
for path in ('/', '/opt', '/opt/asa-setup'):
    try:
        metadata = os.lstat(path)
    except FileNotFoundError:
        if path != '/opt/asa-setup':
            raise SystemExit('Не найден защищённый родитель пакета')
        os.mkdir(path, 0o755)
        metadata = os.lstat(path)
    if (not stat.S_ISDIR(metadata.st_mode) or metadata.st_uid != 0
            or metadata.st_mode & 0o022):
        raise SystemExit('Родитель пакета не защищён; его права не изменены')
PY
asa_setup_incoming="$(sudo mktemp -d /opt/asa-setup/acquire.XXXXXXXX)"
sudo chmod 0755 "$asa_setup_incoming"
asa_setup_archive="$asa_setup_incoming/asa-setup-$asa_setup_revision.tar.gz"
sudo install -o root -g root -m 0644 \
  "$asa_setup_download/asa-setup-$asa_setup_revision.tar.gz" "$asa_setup_archive"
gh attestation verify "$asa_setup_archive" \
  --repo spikeal8-maker/asa-lab \
  --signer-workflow spikeal8-maker/asa-lab/.github/workflows/setup-release.yml \
  --source-ref refs/heads/main \
  --source-digest "$asa_setup_revision" \
  --deny-self-hosted-runners

# Только после успешной attestation извлекается проверенный упаковщик.
# tar пишет один файл в stdout; произвольные пути из архива не извлекаются.
sudo /usr/bin/tar -xOf "$asa_setup_archive" tools/deployment/setup_bundle.py \
  | sudo /usr/bin/tee "$asa_setup_incoming/setup-bundle.py" >/dev/null
asa_setup_digest="$(sha256sum "$asa_setup_archive" | cut -d ' ' -f 1)"
sudo /usr/bin/python3 -I "$asa_setup_incoming/setup-bundle.py" stage \
  --archive "$asa_setup_archive" \
  --revision "$asa_setup_revision" --sha256 "$asa_setup_digest" \
  --destination "/opt/asa-setup/$asa_setup_revision"
cd "/opt/asa-setup/$asa_setup_revision"
sudo bash ./asa-setup.sh
```

При любой ошибке цепочка останавливается. Отдельная SHA-256 сумма проверяет
целостность; происхождение подтверждает именно attestation с указанным
репозиторием, workflow, source ref и SHA. Упаковщик проверяет полный список
файлов, каждый hash, типы архивных записей и отсутствие перенаправляющих ссылок.
Незавершённый каталог пакета не считается готовым и не перезаписывается вслепую.
Новые версии размещаются в отдельных неизменяемых каталогах.

Описание проверки подписи:
[GitHub CLI: gh attestation verify](https://cli.github.com/manual/gh_attestation_verify).

## Обычный запуск и дополнительные команды

В root-терминале 1Panel `sudo` можно опустить. Привилегированный загрузчик
сначала проверяет собственный пакет, затем определяет владельца по файлам
установки и запускает Git, Compose и менеджер от этого пользователя.

```bash
sudo bash ./asa-setup.sh
sudo bash ./asa-setup.sh --root /srv/asa-lab
sudo bash ./asa-setup.sh --help
```

Первый запуск спрашивает недостающие параметры. Повторный использует приватный
`.asa/setup.json`. При нескольких согласованных целях выберите каталог через
`--root`; выбор связывается с installation ID и Compose project. Новому
каталогу нужен существующий Linux-оператор. `--operator` задаёт его явно,
но не разрешает менять владельца прежней установки.

| Команда | Назначение |
|---|---|
| `auto` или без команды | Выбрать install/update/NO_CHANGE по фактической инвентаризации |
| `check`, `--check` | Проверить состояние без переключения приложения |
| `status` | Показать сохранённый результат и незавершённую операцию |
| `resume --operation-id ID` | Продолжить известную операцию с закреплённой целью |
| `configure` | Явно изменить сохранённую конфигурацию |
| `cloud-configure` | Явно настроить или заменить облачную авторизацию |
| `backup` | Создать отдельную полную копию без обновления приложения |
| `retry-cloud --snapshot-id ID` | Повторить доставку сохранённого ciphertext |
| `cloud-retry --snapshot-id ID` | Псевдоним `retry-cloud` |
| `schedule` | Установить/согласовать системное расписание по сохранённым настройкам |
| `acceptance --operation-id ID` | Повторить приёмку известного запуска без повторной миграции |
| `doctor`, `diagnose` | Диагностика состояния и зависимостей |
| `repair-collector` | Отдельное явное исправление службы диагностики |
| `restore-plan` | Проверка ограничений восстановления; архив не применяется |

Для автоматизации используются `--non-interactive` и приватный JSON через
`--config-file /абсолютный/путь/setup.json` (`--config` — псевдоним).
Недостающий обязательный параметр возвращает блокировку, а не ожидание ввода.
`--json` выдаёт машинный результат; обычный вывод предназначен для человека.

## Конфигурация и первоначальный доступ

Файл настроек принадлежит подтверждённому оператору, имеет права `0600`,
каталог состояния — `0700`. Symlink, hardlink, неизвестные поля и расхождение
идентичности блокируют выполнение. Конфигурация не является источником
произвольных привилегированных команд.

| Поле | Содержание |
|---|---|
| `format` | `asa-setup-config-v1` |
| `installationId` | Уникальный UUID в виде 32 строчных hex-символов |
| `root`, `operatorUid` | Канонический абсолютный каталог и UID его оператора |
| `profile` | Согласованный Compose-профиль; для новой обычной установки `production` |
| `entryOrigin` | Реальный публичный адрес; для production требуется HTTPS |
| `project` | Согласованное имя Compose project, включая нестандартное существующее |
| `backupDirectory` | Абсолютный приватный каталог полных локальных копий |
| `ports` | Три отдельных порта `web`, `api`, `blocks`; defaults 4610/4611/4613 |
| `backup.policy` | Явный выбор `required` или `best-effort` |
| `backup.ageRecipient` | Настоящий публичный AGE recipient; закрытый ключ на сервер не требуется |
| `backup.cloud.enabled` | Требуется ли облачная доставка |
| `backup.cloud.transportPath`, `transportSha256` | Путь закреплённого компонента из пакета и его известный SHA-256 |
| `backup.cloud.rcloneConfigFile` | При необходимости ссылка на отдельный приватный файл авторизации Yandex |
| `backup.maxWriteFreezeSeconds` | Ограничение окна запрета записи, 30–7200 секунд |
| `backup.schedule` | `enabled`, время `HH:MM`, IANA timezone, допустимый `maxAgeHours` |
| `backup.retention` | Отдельные `localKeep` и `remoteKeep`; `null` отключает удаление |
| `browser` | Закреплённый компонент, runtime Python, приватный fixture и timeout |
| `onboardingFile` | Приватные данные нового владельца; только для первоначальной настройки |
| `dataIdentity` | Сохранённая доказанная идентичность PostgreSQL/MinIO; не заполняется догадкой |

Интерактивный режим создаёт согласованные пути компонентов и installation ID.
При подготовке конфигурации вручную берите пути из **того же проверенного
пакета**. Не заменяйте отсутствующие ключи, OAuth или browser fixture фиктивными
значениями ради прохождения проверки.

Данные первого владельца хранятся отдельно в `asa-owner-onboarding-v1`:
installation ID, статус `NEW`, email, username, displayName, birthDate,
country и пароль длиной не менее 10 символов. Пароль вводится скрыто или
читается из приватного файла. Он не передаётся в аргументах процесса. Создание
аккаунта использует обычный путь регистрации и последующее проверяемое
назначение владельца через существующий административный компонент.
Повторная операция не должна создавать второго владельца или менять прежние
пароли. Неоднозначный результат регистрации сначала проверяется.

Доступ владельца ASA, OAuth Yandex и публичный AGE recipient — три независимые
настройки. Приватные данные и дампы не прикладываются к issue, PR или evidence.

## Что проверяется до изменения приложения

Загрузчик сопоставляет repository, `.env`, `.asa`, общий lock, backup root и
фактического владельца. Он не использует `safe.directory=*`, рекурсивный
`chown` или замену существующего Docker. Legacy-установка с рабочими файлами,
принадлежащими root, требует отдельного разбора владельца; выполнять изменяемый
код репозитория от root автоматически запрещено.

Инвентаризация получает работающие и остановленные контейнеры, образы, все
volumes, оставшиеся без контейнеров тома, bind mounts и Compose labels.
Отсутствие каталога, `.env` или работающего web не доказывает пустую цель.
Ошибка Docker означает неизвестное состояние. Отсутствующий или подменённый
том прежней установки блокирует создание новой базы.

Старая согласованная установка принимается под управление только после
сопоставления конфигурации, владельца, проекта и фактических данных.
Неизвестная частичная установка блокируется. Известная прерванная операция
обрабатывается через её журнал и `resume`.

Подготавливаются только недостающие зависимости поддержанного профиля.
Установленный совместимый Docker используется без upgrade, смены data-root
или перезапуска чужих приложений. При действительно отсутствующем Engine
используется официальный Docker apt-источник. Системный upgrade, настройки
SSH/VPN/firewall и удаление чужих пакетов не входят в эту операцию.

До простоя проверяются место и inodes, доступ к registry/DNS, системное время,
порты и адрес сайта. Образы загружаются заранее. Обнаруженная занятость порта
или недоступность публичного адреса не исправляется переездом чужих сервисов.

DNS, домен, сертификат и reverse proxy 1Panel должны соответствовать
`entryOrigin` и настройкам редакторов. Если внешний вход ещё не настроен,
публичная приёмка остаётся незавершённой. Localhost healthcheck не доказывает
готовность HTTPS-сайта. Не изменяйте внутреннюю БД 1Panel или его vhost-файлы
в обход предусмотренного управления.

## Выпуск, блокировка и прерывания

Приложение выбирается по существующему контракту опубликованного выпуска:
точный commit, успешные CI/publication, release manifest и digest образов.
Цель сохраняется в журнале до переключения. Изменение `stable` после этого
не меняет выбранную версию.

Установка, update, backup и restore используют общий `.asa/operation.lock`.
Журналы `setup-operations/<operationId>.json` содержат намерение и результат
каждой стадии. Передача управления совместимому новому менеджеру сохраняет
тот же installation ID, operation ID, release и унаследованный lock.
Общий exit code `2` не означает «повторить установку».

После прерывания до переключения проверяется исходное состояние и возможность
безопасного продолжения. После записанного намерения переключения обычный
`resume` сначала проверяет фактический runtime. Он не повторяет вслепую
миграцию, не восстанавливает рабочую БД из архива и не откатывает образы на
непроверенную совместимость схемы.

`NO_CHANGE` не создаёт backup, не запускает миграции, не переключает образы и
не ремонтирует collector. Для оставшейся приёмки или облачной доставки
используются отдельные команды и прежние ID.

## Полный backup и облако

Управляемая копия включает PostgreSQL, необходимые роли и права, хеши паролей
ролей, MinIO, приватную конфигурацию, сведения о runtime/schema и manifest с
installation ID, operation ID, snapshot ID, временем снимка и хешами файлов.
Эти данные остаются приватными; в облако отправляется только AGE ciphertext.

Проверка писателей включает сервисы приложения, другие обнаруженные
контейнеры с теми же хранилищами и клиентские соединения БД. Неизвестный
писатель блокирует снимок. При update запрет записи сохраняется от снимка
до подтверждённой доставки и переключения, с общим ограниченным сроком.

| Политика | Условие переключения |
|---|---|
| `required` | Полная проверенная локальная копия, AGE и подтверждённое чтением обратно облачное содержимое текущего снимка |
| `best-effort` | Проверенная полная локальная копия; отсутствие шифрования/облака или ошибка доставки остаётся предупреждением |

Политика сохраняется заранее и не ослабляется после ошибки. При отказе до
переключения возвращаются только те прежние контейнеры, которые остановила
эта операция; восстановление доступности проверяется отдельно.

Для standalone backup писатели возобновляются после согласованного снимка.
Позднейшие записи в него не входят: в квитанции явно указаны время снимка и
`writesAfterSnapshotIncluded=false`.

Ciphertext имеет неизменяемый snapshot ID. Удалённая копия сначала загружается
во временное имя, читается обратно, проверяется по SHA-256 и только затем
получает окончательное имя. Совпадение имени или размера не считается
доставкой. Конфликтующее содержимое не перезаписывается.

`retry-cloud` использует те же сохранённые байты. Он не запускает deployment
и не создаёт новую БД или новый snapshot. Последняя попытка и последняя
успешная копия хранятся раздельно. При повреждении ранее проверенного
локального комплекта старый статус успеха не используется.

Если первый export новой установки оборвался до появления полного снимка,
`resume` сначала восстанавливает только остановленные этой операцией сервисы.
После проверки места команда `backup --operation-id ID_УСТАНОВКИ` создаёт
отдельную связанную копию уже подтверждённого runtime. Прежний incomplete
снимок и его ID сохраняются. Затем `resume --operation-id ID_УСТАНОВКИ`
проверяет квитанцию новой копии и завершает приёмку, без новой миграции.

Связанная доставка имеет собственный ID и закреплённый snapshot; прерванную
доставку можно продолжить `resume --operation-id ID_ДОСТАВКИ` без повторного
ввода snapshot. Явно переданный другой snapshot отклоняется. Журнал родителя
и одна проверенная дочерняя операция не считаются двумя конкурирующими
установками; чужая связь или несколько активных дочерних действий блокируются.

Используется закреплённый компонент `Server-setings`:
`88f3f76144d8b499fe70a3c9beccba16c80e0856`. Облачное назначение отдельное для
installation ID: `yandex:Server-Backups/asa-<installationId>`.
Старое назначение `yandex:ASA-Backups` и его архивы не смешиваются с новыми
копиями и не удаляются новой политикой.

Локальная целостность, шифрование, доставка и испытанное восстановление —
четыре отдельных результата. `pg_restore --list`, успешный hash и upload
не меняют restore status на `VERIFIED`.

## Расписание и хранение

Расписание backup независимо от `automaticUpdates`; существующее отключение
автообновления сохраняется. Время, timezone, допустимый возраст и retention
выбираются явно. Предлагаемое время — 03:00 Europe/Moscow. Удаление по
умолчанию отключено (`localKeep=null`, `remoteKeep=null`).

Для installation ID создаётся один системный service/timer
`asa-backup-<hash ID>`. Он запускается от оператора, не требует пользовательской
сессии и использует `Persistent=true`. Перед общей блокировкой расходуется
durable лимит: не более трёх запусков в одном суточном слоте, включая
занятость lock. После исчерпания `ExecCondition` останавливает автоматические
повторы до следующего слота; длительный сетевой отказ не обходит этот лимит.
Повтор одного суточного запуска использует тот же ID операции. Явный `resume`
доступен оператору после проверки причины сбоя.

Сохранённая настройка не равна работающему timer. Итог проверяет фактические
LoadState/ActiveState/UnitFileState, следующее выполнение, последний запуск,
последние успешные локальную/облачную копии и их возраст.

Retention применяется отдельно локально и в облаке, только к доказанным
копиям этой установки. Последняя подтверждённая копия, незавершённая доставка,
активная операция и материалы незавершённого restore защищены. Неизвестные
файлы и чужие ресурсы не удаляются ради освобождения места.

## Приёмка, отчёт и коды возврата

Техническая приёмка проверяет фактические commit/digests, schema, health,
хранилища, адрес и HTTPS. Браузерный компонент закреплён тем же ops SHA,
использует Playwright 1.56.0 и проверяет шесть сценариев: teacher login,
student login, course, project, Scratch save/reopen и electronics save/reopen.
Fixture принадлежит этой установке; реальные пользовательские проекты не
используются. Отсутствующие реквизиты, пропущенный сценарий или недоступный
browser runtime означают незавершённую приёмку.

Collector оценивается отдельно по режиму system/user, systemd, процессу и
свежести цикла. Необязательная ошибка диагностики не отменяет доказанный
результат приложения. Исправление выполняется явной `repair-collector`.

Человеческий итог содержит шесть пронумерованных разделов:

1. Сервер и зависимости.
2. Версия ASA Lab.
3. База и файлы.
4. Резервные копии.
5. Сайт и пользовательские действия.
6. Диагностика.

В отчёте отдельно указываются URL, фактическая версия, источник данных
(новая пустая установка или сохранённые данные), snapshot/time, operation ID,
приватный путь журнала и одно следующее действие. Цвет зависит от TTY и
`NO_COLOR`; текстовые статусы остаются понятными без цвета и Unicode.
Машинный JSON выдаётся только по `--json`, без секретов.

| Exit code | Значение |
|---|---|
| `0` | Принятый результат соответствующей команды, включая явно необязательные предупреждения |
| `2` | Блокировка или незавершённая обязательная приёмка |
| `1` | Ошибка выполнения |
| `130` | Прерывание оператором |

`executionCompleted`, `applicationAccepted` и `dataProtectionConfirmed`
обозначают разные вещи. «Можно работать» допустимо только при выполненных
обязательных условиях данной операции. Старый успех не подменяет результат
последней попытки.

## Проверки исходников и эксплуатационные evidence

Базовый воспроизводимый gate:

```bash
python3 -m unittest discover -s tools/deployment -p 'test_*.py' -v
bash -n asa-setup.sh
git diff --check
```

Полный suite запускается от обычного пользователя, как в GitHub-hosted runner.
Некоторые существующие collector tests намеренно требуют Linux-оператора;
запуск всего suite от root не эквивалентен этому окружению.

`ASA Unified Setup / docker-synthetic` выполняет реальный сценарий на
одноразовом GitHub runner: опубликованные образы, браузерная приёмка, полный
согласованный backup, AGE encrypt/decrypt, отдельные network-none PostgreSQL и
MinIO с новыми volumes, проверка ролей/паролей/ACL/RLS/контрольных строк,
объектов через S3, вход через ограниченную роль API и повторные браузерные
сценарии. Публикуется обезличенный
`test-results/setup-synthetic/evidence.json` с точными source/release SHA и
результатом каждого реально выполненного этапа. Очистка касается только
ресурсов этого disposable испытания.

| Испытание | Что оно доказывает | Чего не доказывает |
|---|---|---|
| Unit/fault tests | Контракты, блокировки, повторы, ошибки, отсутствие неподтверждённого PASS | Работу реального Docker/AGE/Yandex/1Panel |
| Docker synthetic CI | Реальное полное синтетическое восстановление и связанные проверки | Чистую установку Ubuntu+1Panel или восстановимость рабочего архива |
| Чистый отдельный 1Panel host | Полный путь установки, dependencies, ingress, owner, schedule, backup | Сохранение данных существующего сервера |
| Обновление существующего тестового сервера | Сохранение его PostgreSQL/MinIO/ролей/доступа и новый runtime | Восстановление производственного архива |
| Разрешённый тест отдельного Yandex namespace | Доставку и независимый remote readback настоящего ciphertext | Восстановление данных |
| Отдельное real restore rehearsal | Восстановление конкретного архива в согласованную изоляцию | Разрешение применять архив к рабочей установке |

Для каждого внешнего испытания требуются конкретная цель, безопасный доступ,
точный одобренный выпуск и отдельная запись результата. Отсутствие чистого
хоста, облачной авторизации или разрешённого restore-назначения фиксируется
как незавершённый этап. Подмена этого evidence моками запрещена.

Ограничения P1-R3A сохраняются: отсутствие владельческого signing key pin,
утверждённого image set или доступа к нужному ключу не обходится вымышленными
значениями. `restore-plan` не содержит скрытого `restore_apply`.
