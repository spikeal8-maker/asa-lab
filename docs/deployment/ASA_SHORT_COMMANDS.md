# Короткие команды ASA Lab для Linux и 1Panel

Один и тот же механизм использует версионированный менеджер
[`tools/asa_manager.py`](../../tools/asa_manager.py). Новая команда не
содержит обхода CI, схемы, фиксации OCI digest или проверки backup.

## Подключение

На production администратор один раз подключает команду из отдельного checkout
официального `origin/main`. Этот checkout с зафиксированным коммитом и родительские
каталоги должны принадлежать root и быть недоступны на запись другим пользователям.
Сам коммит менеджера выбирают по [руководству по обновлению](PORTABLE_OPERATIONS.md#один-immutable-deployment-на-нескольких-узлах).

```sh
cd /opt/asa-approved-tools
sudo git fetch origin main
sudo env ASA_INSTALL_ROOT=/srv/asa-lab sh tools/install-asa-command.sh --production
sudo asa check
```

Команда `/usr/local/bin/asa` запоминает пути к установке и проверенным
инструментам. Смена исходников приложения их не меняет. Инсталлятор может заменить
старую штатную ссылку `asa` той же установки; стороннюю команду он не перезапишет.
В 1Panel для проверки и установки достаточно сохранить `sudo -n /usr/local/bin/asa check`
и `sudo -n /usr/local/bin/asa update`, если терминал настроен на их запуск через sudo.
В тестовой установке без production достаточно `sh tools/install-asa-command.sh`
из каталога приложения: он создаст обычную ссылку на команду checkout.

Школьный профиль один раз подключает локальную квитанцию полной облачной копии
после установки GFS из связанного выпуска Server-setings и первого подтверждённого архивирования:

```sh
sudo asa configure-offsite --offsite-receipt /var/backups/asa-school-gfs/receipts/latest-full.json
```

Политика сохраняется в настройках установки. При новом выпуске менеджер
проверяет квитанцию формата `asa-school-gfs-receipt-v1` с подтверждённым чтением
зашифрованного архива. Версия и схема в квитанции берутся из проверенного
манифеста архива (`runtimeSource: verified-manifest`) и сверяются с текущим приложением.
Копия должна быть не старше 36 часов. Перед переключением менеджер отдельно
создаёт и проверяет новую локальную копию. [Школьное подключение](https://github.com/spikeal8-maker/Server-setings/pull/105).

## Сервисные операции

```sh
asa doctor
asa check
asa update
asa backup
asa logs api --tail 100
asa rollback-plan
```

На production `asa check` показывает установленную и опубликованную версии и
результат проверки штатного возврата. `asa update` повторяет проверки, создаёт
проверенную резервную копию и устанавливает выпуск. Запускайте установку
в согласованное время обслуживания. В каждой команде менеджер один раз
закрепляет выпуск по OCI digest. При смене исходников менеджера установка
продолжается с тем же сохранённым выпуском в рамках вызова.

Короткая команда использует существующий допуск возврата из CI. Если такой
допуск отсутствует или пара выпусков не поддерживается, установка остановится.
Для выбора конкретного выпуска по-прежнему доступен `--deployment-digest`. Пути
установленной production команды меняются повторным запуском установщика.
При вызове `tools/asa` напрямую путь к установке можно задать через
`ASA_INSTALL_ROOT=/absolute/path`. Для новой установки без
`.asa/installation.json` профиль нужно указать явно, например
`ASA_PROFILE=production`.

`asa report` показывает фактическое состояние шести контейнеров, закреплённый
релиз, текущую версию локальной копии и 1/5/15-минутную **среднюю нагрузку
системы** (load average). Это не процент CPU. Если подтверждённой истории CPU
за 1 или 24 часа нет, выводится «нет данных», а не выдуманное значение.

Наличие backup manifest и локальной записи об отправке не является
подтверждением удалённой копии. Проверять фактическую доступность Яндекс Диска
нужно независимо и **после шифрования**. Старые резервные копии схемы 300
не доказывают готовность возврата схемы 307. Специализированный
`rollback` не является универсальным downgrade базы данных и для
неподдерживаемой пары релизов должен завершаться блокировкой.

## Защищённая внешняя копия (не включается автоматически)

При наличии отдельно сохранённого ключа восстановления age оператор указывает
**только публичный** recipient file, текущую каноническую копию и проверенный rclone remote.
Пример для школьного VM100:

```sh
asa offsite-backup \
  --backup /srv/asa-lab/backups/20261108T214015Z-404d8510 \
  --recipient-file /etc/asa-lab/backup-recipients.txt \
  --remote-base yandex:ASA-Backups/asa-school-01 \
  --rclone-container asa-cloud-storage-rclone-1
```

Это явная команда, не таймер и не фоновые загрузки. Она отказывается
от устаревшей схемы, неполного backup, отсутствующего recipient,
небезопасного remote или перезаписи имеющегося архива. Загружается только
зашифрованный `tar.age` (полный PostgreSQL/MinIO/private config backup).
После загрузки все байты удалённого ciphertext читаются повторно,
проверяется SHA-256 и только затем записывается защищённый локальный
`.asa/offsite-last.json`. Для реального disaster recovery нужно
отдельное **внесерверное** хранение соответствующего приватного age ключа.
Скрипт никогда не генерирует новый приватный ключ и не копирует его в облако.
