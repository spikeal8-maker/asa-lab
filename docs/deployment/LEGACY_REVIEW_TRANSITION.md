# Переход существующей review-установки к официальному выпуску

Этот ограниченный адаптер относится к [#809](https://github.com/spikeal8-maker/asa-lab/issues/809).
Он не меняет обычные проверки `doctor`, `update`, `backup` и `restore-check`.
Неизвестная старая конфигурация по-прежнему останавливает операцию.

## Поддерживаемая исходная конфигурация

Поддержан профиль `dev` с восемью существующими сервисами ASA и файлами в порядке:

```text
compose.yaml
compose.dev.yaml
.asa/local-review/compose.review.yaml
```

Первые два файла должны совпадать с отслеживаемой Git-версией. Overlay проверяется
по фактическому результату Compose: API watcher и Vite работают из одного
workspace image, используют только пять известных подключений исходников в
`/workspace` с режимом `ro`. Остальные сервисы, сети, тома и настройки защиты
должны соответствовать базовому составу. Проверяются также реальные контейнеры,
image IDs, environment, команды, capabilities, tmpfs, mounts и опубликованные
порты. Одного имени `compose.review.yaml` недостаточно.

API/Web старого review работают с записываемой файловой системой контейнера и
пользователем `0:0`; это явно ограниченная исходная форма, а не разрешение таких
настроек для нового выпуска. План сохраняет точные image IDs, входные файлы и
конфигурацию. Новые сервисы используют штатные ограничения официального Compose.

Рабочий каталог, Compose project, входной адрес, host ports, PostgreSQL engine
и существующие volumes остаются прежними. Переключение пересоздаёт контейнер
PostgreSQL с теми же проверенными байтами образа и томом: это нужно для честных
меток стандартного Compose, без ручной подмены labels. Образ PostgreSQL не
скачивается и не обновляется этой операцией.

## Версия инструмента и версия продукта

Менеджер запускается из отдельного чистого Git checkout, который не подключён к
живым контейнерам. Это копия инструмента, не второй Compose stack. Нужны:

- опубликованный точный manager SHA;
- успешные General и ASA Portable Delivery Checks этого SHA;
- независимый review именно этого SHA, закреплённый в GitHub PR;
- отдельно выбранный полный product SHA из истории `main`;
- официальный OCI manifest, успешная публикация, General и immutable image digests
  выбранного продукта.

Обычный `update` продолжает читать stable. `legacy-plan` принимает только точный
product SHA. Он читает манифест и image manifests через реестр без Docker pull,
создания контейнеров или записи в живой checkout. Перемещение stable/main не
меняет выбранный продукт. План содержит отдельно `manager.revision` и
`release.revision`.

Отчёт независимого агента может быть закреплён review типа `COMMENTED`, если
он явно атрибутирован. Для машинной привязки review содержит строки:

```text
INDEPENDENT_REVIEW
VERDICT: APPROVE
REVIEWED_SHA: <полный manager SHA>
```

Менеджер проверяет URL, точный `commit_id`, текущую голову PR и заключения CI.
Такая привязка не назначает owner acceptance и не разрешает merge PR. Разрешение
на применение проверенного внешнего менеджера не означает разрешение на его merge.

## Подготовка плана

Сначала прочитайте `AGENTS.md`, `PORTABLE_OPERATIONS.md` и актуальное состояние
задачи. Найдите канонический каталог по PostgreSQL metadata. Не выполняйте
stash/checkout и не изменяйте подключённые исходники для подготовки плана.

Существующая приватная WIP-копия проверяется по её manifest и исходным файлам.
Её не пересоздают и не перезаписывают. Изменение источника после этой копии
требует отдельного сохранения новой работы. WIP-копия не заменяет backup БД/MinIO.

Пример с заполненными владельцем путями и версиями:

```text
python <tool-checkout>/tools/asa_manager.py legacy-plan
  --root <existing-canonical-root> --profile dev
  --release <approved-full-product-sha>
  --preserved-wip <existing-private-wip-copy>
  --entry-origin <actual-owner-origin>
  --review <exact-manager-review-url>
  --output <new-private-directory>/plan.json
```

Это одна команда; переносы выше служат только для чтения. Каталог для плана
должен быть приватным и находиться вне installation root. Существующий файл
плана не заменяется. План фиксирует root/project/files/order, actual containers,
образа, подключения, порты, Git/index/WIP, хеши реальных runtime inputs и
приватной конфигурации, историю миграций, соседние контейнеры и целевой выпуск.
План приватный: он содержит пути, хотя сами значения секретов в нём не печатаются.

Если старый Web возвращает HTML вместо `build-metadata.json`, его revision
записывается как `null`, статус — `unverified`. Он не выводится из API SHA,
имени image или HEAD каталога. До успешного переключения не создаётся
`installed-release.json`.

## Применение и проверочное восстановление

Применение требует отдельного разрешения владельца на существующую установку.
Оно не запрашивается повторно, если уже дано для этого действия. На D2R2 такое
разрешение является частью задания #809; приёмка владельца остаётся отдельной.

```text
python <tool-checkout>/tools/asa_manager.py legacy-apply
  --root <existing-canonical-root> --profile dev
  --plan <new-private-directory>/plan.json
  --output <private-full-backup-directory>
  --database <new-unique-name>_test
  --allow-isolated-restore
```

Перед остановкой повторяются release/manager evidence, snapshot и проверка
отсутствия активного автора. Загружаются только выбранные immutable images;
штатный migration runner выполняет read-only `--plan` над фактической историей.
Разошедшаяся review-ветка не выдаётся за обычного ancestor релиза: её происхождение
сохраняется отдельно, а совместимость подтверждается реальной историей миграций
и обновлением восстановленной `_test` БД. Схема продукта должна быть новее старой.

Полный backup останавливает только известные writers этой установки по точным
container IDs. PostgreSQL продолжает работать. В комплект входят:

- custom-format database dump, globals без паролей и ACL/RLS;
- физические данные локального MinIO;
- реальные байты `.env`, Compose и вложенного overlay;
- все необходимые подключённые runtime inputs;
- private container configuration и старые image archives;
- writable filesystems старых API/Web;
- manifest с хешами, отдельно обозначающий неизвестную Web-версию.

При недостатке места или ошибке копирования остаётся `.incomplete`, которая не
принимается как готовая копия. Старые сервисы возобновляются только при
неизменённых исходниках и прежней схеме, по прежним container IDs.

До изменения живых исходников выполняется восстановление в новую одноразовую
БД с суффиксом `_test`: существующая БД, даже с таким суффиксом, запрещена.
Сравниваются ACL/RLS и контрольные количества. MinIO восстанавливается в новый
временный том и контейнер без опубликованных портов; проверяются реальные байты
и запуск. Cleanup допускается только по совпадающим operation labels.

Затем официальный migration runner проверяет upgrade восстановленной копии до
целевой схемы и повторный запуск без новых миграций. Проверочная БД сохраняется
для диагностики, живая БД не заменяется. Restore receipt привязан к хешу полного
backup и записывается отдельно от его неизменяемого manifest.

Только после этого writers остаются остановленными, создаётся дополнительный
именованный Git stash для существующего WIP и выполняется обычный detached
checkout выбранного продукта. Первичная приватная копия и исходная ветка
сохраняются; `reset`, `clean`, force checkout и автоматический stash pop не
используются. WIP не переносится в продуктовый код. Отсутствующий ранее
`ASA_UPDATE_ENTRY_ORIGIN` можно дописать после backup; существующие ключи не
регенерируются. Миграция выполняется с отключённым dev seed, без создания
пользователей для обходного входа.

Завершение требует штатной exact-SHA readiness API/Web/Scratch/Search, схемы,
image digest/ID, прежнего origin, томов, ключей и контрольных данных. Проверяется
неизменность соседних контейнеров. Только после этого записывается официальный
`installed-release.json`. HTTP readiness не считается показом интерфейса.

## Прерывание и повтор

`.asa/legacy-transition.json` различает `prepared`, `backing_up`, `backed_up`,
`restore_verified`, `switching_sources`, `switching`, `verifying`, `accepted`
и `failed` с сохранённой предыдущей стадией. Backup ведёт собственный
`maintenance.json` с точными IDs и путями recovery set.

```text
python <tool-checkout>/tools/asa_manager.py legacy-status
  --root <existing-canonical-root> --profile dev
```

После потери ответа сначала читается фактическое состояние. Незавершённый
transition не повторяется автоматически. Повтор `accepted` проверяет текущий
официальный runtime и возвращает `NO_CHANGE`. Изменённая установка не откатывается
к старому плану. После начала смены исходников/миграции старые приложения
автоматически не запускаются; live DB restore поверх новых записей отсутствует.

## Проверки и границы доказательства

Профильные команды совпадают с portable workflow:

```text
python -m unittest discover -s tools/deployment -p "test_*.py" -v
node --test tools/blocks/deployment.test.mjs
```

Негативные проверки покрывают unknown overlay/mount/volume, чужой root/project,
path links, drift, active author, ошибки backup, неверную restore target,
прерывание и повтор, неизвестную Web metadata и сохранение обычных guards.
Отдельный disposable CI scenario использует настоящие PostgreSQL/MinIO,
контролируемую review-конфигурацию и официальный целевой выпуск. CI может
симулировать лишь внешнее approval собственного проверяемого manager, чтобы
избежать циклической зависимости; продуктовый OCI/CI/readiness путь остаётся
реальным. Это не D2R2 demo.

Показ установленной D2R2 выполняется отдельно через обычный вход администратора:
ИИ → Обзор → реальные показатели/график → обновление → reload → раскрытия →
мобильный вид. Нужны фактические API/Web версии и открытые/оценённые снимки
1440×900 и 390×844 в обеих темах, дополнительно ширина320. Контрольные числа CI
не переносятся в рабочий журнал. Issue799 и owner acceptance не закрываются
автоматически после технического обновления.
