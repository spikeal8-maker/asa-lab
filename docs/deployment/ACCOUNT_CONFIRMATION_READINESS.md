# Проверка подтверждения аккаунта перед включением

Этот документ — порядок подготовки и приёмки MAX/Telegram на конкретной
установке AsaLab. Требуемое поведение определено в
[ТЗ подтверждения аккаунта](../product/ASA_ACCOUNT_CONFIRMATION_SPEC.md).
Активный срез, версия кандидата, CI и состояние реализации читаются из
`docs/execution/current.yaml`.

## 1. Что должно быть готово до обязательного подтверждения

Успешная сборка проверяет код. Для включения на выбранном сервере дополнительно
нужны четыре проверенных условия:

1. Пользователь действительно входит по выбранному адресу AsaLab; браузер
   сохраняет сессию, а последующие запросы проходят серверную проверку origin.
2. Администратор имеет известный ему пароль и может войти им в чистой сессии.
   Запись «пароль настроен» в базе не доказывает, что человек его помнит.
3. Для этой установки выбраны собственные боты MAX и Telegram. Рабочий токен
   IZO_ASA или production не переносится на test автоматически.
4. Каждый включаемый канал проходит настоящий путь: сайт → бот → явное
   подтверждение → возврат в исходную вкладку → завершение в том же Account.

Общий рубильник по умолчанию выключен. Настройка бота не включает его сама.
Почта пока не является доступным каналом отправки подтверждения.

## 2. Адрес входа и внешний адрес ботов

| Среда | Что необходимо |
|---|---|
| Локальная разработка через loopback | Штатный локальный режим, canonical ports и cookies. Такой тест не подтверждает работу через сеть. |
| HTTPS по IP | Сертификат, которому доверяют клиенты, и точный разрешённый origin. Для ботов отдельно требуется доступный им внешний callback. |
| Публичный HTTPS-адрес | Правильный TLS, разрешённый origin, proxy до API этой установки и настоящая доставка от провайдера. |
| Обычный HTTP по LAN/IP в staging/production | Текущий поддержанный путь отсутствует: дополнительные origins требуют HTTPS, а production cookies — Secure. Обещать полноценный вход в таком режиме нельзя. |
| Нет доступа к внешним мессенджерам | При недоступных каналах дополнительная обязательность снимается; штатная проверка пароля и прав остаётся. Сам AsaLab и его точка входа должны быть доступны. |

Собственный домен не является идентификатором Account. При смене адреса данные
остаются в той же базе, но cookies одного host не переносятся на другой:
потребуется новый вход. Начатую попытку подтверждения завершают в исходной
вкладке; потерянную попытку начинают заново.

В приватной конфигурации установки сохраняется `ASA_PUBLIC_WEB_ORIGINS`.
Список содержит точные HTTPS origins; произвольный Host/X-Forwarded-* не
добавляет доверия. Staging и production должны передавать этот список API.
Не заменяйте его значением из чужой инструкции или другой установки.

Для native ботов callback вычисляется из публичного адреса этой установки:

- MAX: `/api/auth/max/webhook`;
- Telegram: `/api/auth/telegram/webhook`.

MAX требует внешний HTTPS на 443 и доверенный сертификат. Telegram поддерживает
HTTPS webhook на 443, 80, 88 и 8443; текущая AsaLab не загружает собственный
self-signed сертификат в Telegram. Перед настройкой сверяйте актуальные
[требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) и
[требования Telegram](https://core.telegram.org/bots/webhooks).

Внутренние сервисы и host ports при этом не меняются. Новый постоянный Compose
project, случайный свободный порт, отключение CSRF/Secure или изменение DNS/VPN
не являются частью настройки подтверждений.

## 3. Ключ шифрования и прежние пользователи

`ASA_SETTINGS_ENCRYPTION_KEY` хранится в приватной конфигурации, переживает
обновление и восстанавливается вместе с защищённой конфигурацией установки.
Если в существующей конфигурации ключ отсутствует, повреждён или указан
несколько раз, установщик останавливается до изменения файла. Нужно восстановить
исходное значение из защищённой резервной копии; удалять конфигурацию и
генерировать замену нельзя, иначе сохранённые токены станут недоступными.
Значения ключа и токенов не включаются в отчёты.

Для совершенно новой установки штатный bootstrap создаёт ключ один раз.
При ручной подготовке нового `.env.local`, если в базе ещё нет зашифрованных
учётных данных интеграций, используется явная команда:

```text
node tools/provision-settings-key.mjs --env-file <абсолютный путь к .env.local> --new-store
```

Флаг `--new-store` не предназначен для восстановления существующей установки.
Проверка уже корректного ключа сохраняет файл без изменений; повреждённое или
дублирующееся значение эта команда не заменяет даже с указанным флагом.

Для старой базы отдельно проверяется наличие активных MAX Accounts с
`password_configured=false`. Историческая регистрация могла создать неизвестный
человеку пароль. Такие пользователи готовят свой пароль из действующей
аутентифицированной сессии до потери единственного способа входа.

Совместимый подписанный MAX Mini App вход проверяется независимо от готовности
нового native webhook. Он сохраняет Account ID и все проверки подписи, срока,
повтора, статуса и отзыва. Это не обход проверки личности при недоступном MAX,
потерянном ключе или единственном неработающем credential.

## 4. Порядок проверки в интерфейсе

Откройте раздел админки `/#/admin/confirmations`.

1. Оставьте «Обязательное подтверждение входа» выключенным на время подключения.
2. Для каждого выбранного бота укажите его имя, собственный токен и публичный
   HTTPS-адрес этой установки. Проверьте показанный callback.
3. Сохраните настройки. Пустое поле токена при последующем сохранении означает
   сохранение уже настроенного значения, а не его удаление.
4. Проверьте отдельные состояния: токен, подписка, ответ внешнего адреса и
   фактическое завершение подтверждения. «Сохранено» не заменяет последний пункт.
5. Выполните настоящее подтверждение через бот из текущего Account. Нажмите
   явное подтверждение в MAX/Telegram и вернитесь в ту же вкладку.
6. Повторно прочитайте состояние без нового сохранения настроек. Смена версии
   конфигурации требует новой проверки доставки.
7. В чистой сессии проверьте обычный вход паролем и вход через каждый выбранный
   бот. Account, проекты и личное пространство должны остаться прежними.
8. Только после этого включите общий рубильник и проверьте сценарии из таблицы
   ниже на тестовых пользователях.

При обнаружении чужого webhook настройка не должна молча перехватывать бота.
Для независимого test/production нужны отдельные bot identities. Общий бот
потребовал бы согласованной маршрутизации событий между приложениями.

## 5. Проверочная матрица

| Проверка | Ожидаемый результат |
|---|---|
| Рубильник выключен | Штатный вход работает независимо от отсутствующего подтверждения. |
| Первое включение для существующего неподтверждённого Account | Переходные 24 часа; начало срока хранится на сервере. |
| Срок истёк, есть проверенный работающий канал | Запрашивается одно подтверждение; защищённые действия ограничены до него. |
| Один канал успешно подтверждён | Достаточно для Account; ежедневная повторная проверка не требуется. |
| Бот настроен, но реальный путь ещё не проверен | Пробный вход доступен; этот канал ещё не создаёт обязательную блокировку. |
| Все каналы недоступны по серверной проверке | Правильный пароль открывает обычный доступ. Неверный пароль не принимается. |
| Один канал отказал, другой исправен | Остаётся исправный канал; пользовательская ошибка не отключает требование всем. |
| Токен, callback или версия меняются во время попытки | Старый результат не создаёт привязку и не возвращает готовность прежней версии. |
| Запрос завис, пользователь отменил попытку | Ожидание ограничено; действия восстанавливаются; поздний ответ не переключает Account. |
| Неверный nonce, replay, отозванная identity | Подтверждение отклоняется. |
| Смена адреса или другой браузер | Старая browser-bound попытка не переносится; новая начинается на выбранном адресе. |
| Повторный запуск установщика | Сохранённый ключ и токены не заменяются. |

Повторное включение рубильника не сбрасывает дату его первой активации.
Если он был выключен долго, старый неподтверждённый Account может сразу
потребовать подтверждение при наличии проверенного рабочего канала.

## 6. Предел проверки доставки

Диагностический запрос к публичному callback проверяет правильный адрес,
нужную установку, заголовки, протокол, TLS и ответ в пределах deadline.
Он не подтверждает Account и не отправляет сообщение пользователю.

Успешный запрос сервера к собственному адресу не доказывает доступ именно
из сети MAX/Telegram. После ранее успешного подтверждения избирательная
потеря только provider-origin доставки может не обнаружиться self-probe.
Одной записи в списке подписок MAX недостаточно для обещания мгновенного
автоматического fallback во всех сетевых отказах.

Если публичный адрес обслуживают несколько независимых процессов API, проверка
может попасть в другой процесс и дать отрицательный результат. Для такой
топологии отдельно проверяется маршрутизация диагностического запроса обратно
к экземпляру, который его начал; одинаковые база и ключ этого не заменяют.

Первый настоящий roundtrip и резервный парольный администратор обязательны
для эксплуатационной приёмки. Если такой избирательный отказ нужно
автоматически обнаруживать, требуется отдельный доверенный внешний canary;
клиентский тайм-аут не может самостоятельно отключать проверку для всех.

## 7. Как фиксировать приёмку

Укажите конкретную установку, точный SHA Web/API, проверенный адрес браузера,
провайдера и время фактического прохождения сценария. Не включайте токены,
пароли, cookies, полные provider payloads или персональные сведения.

Отдельно фиксируются:

- CI исходников и синтетические HTTP/PostgreSQL/browser тесты;
- фактическое развёртывание и сохранность данных;
- настоящий MAX roundtrip;
- настоящий Telegram roundtrip;
- правильный парольный вход при отказе каналов;
- проверка каждой заявленной точки входа по домену/IP;
- принятие владельцем.

Отсутствующая проверка записывается как NOT_RUN. Docker healthy, открывшаяся
страница и HTTP 200 сами по себе не закрывают пользовательский сценарий.
