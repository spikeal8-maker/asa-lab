# ASA Lab Setup Assistant — человек и ИИ-исполнитель

Поддержка: Ubuntu 24.04 amd64, Docker, Compose v2, 1Panel OSS, ASA Lab. Данный мастер — интерфейс к штатному install-ubuntu-1panel.py; отдельный движок миграций или управления БД не создаётся.

## Человек: мастер с окнами

В проверенном checkout Ubuntu:

~~~bash
python3 tools/bootstrap/asa-setup.py inspect
python3 tools/bootstrap/asa-setup.py wizard
~~~

При наличии графического окружения и tkinter мастер открывает диалоговые окна. По SSH используется whiptail, если он установлен, иначе последовательные текстовые вопросы. Пароль sudo или pkexec вводится в штатном системном запросе повышения прав, а не в конфигурации ASA Lab.

Мастер спрашивает только необходимые решения: действие, каталог, системного оператора, одобренную сеть администратора SSH/1Panel, источник данных, при необходимости путь к резервной копии и файл закрытого ключа age, школьный интерфейс и однократное разрешение следовать изменению адреса DHCP на том же интерфейсе. Для намеренно новой пустой production-БД требуется ввести точную фразу ПУСТАЯ ШКОЛА.

Резервный источник можно выбрать как проверенный распакованный backup либо как зашифрованный архив ASA формата tar.age. В последнем случае на Ubuntu должен быть установлен age, а архив и identity-файл доступны локально. Ключ выбирается через файловый диалог, его содержимое не попадает в JSON, GitHub и логи. Подготовка выполняется штатным prepare-age-backup.py: проверка полного manifest/хешей и распаковка в новую приватную папку, затем штатный восстановитель. Папка распакованных секретов требует отдельной защищённой политики очистки.

## Бот: машинный интерфейс

~~~bash
python3 tools/bootstrap/asa-setup.py inspect
python3 tools/bootstrap/asa-setup.py plan --answers /srv/asa-setup-answers.json
~~~

План возвращает JSON: ready, required_input, stages, command, installed_release_detected, will_modify_live_data, needs_windows_ca_trust и ограничения приёмки. Если ready=false, агент должен запросить недостающие решения, а не угадывать параметры. Unknown fields отвергаются. Формальная схема: tools/bootstrap/asa-setup-answers.schema.json.

Пример готового JSON для уже существующей production-установки (это НЕ импорт данных):

~~~json
{
  "schema_version": 1,
  "action": "school-lan",
  "root": "/srv/asa-lab",
  "operator": "admins",
  "profile": "production",
  "school_lan_interface": "auto",
  "school_lan_follow_interface": false
}
~~~

Только после проверки плана и согласования с владельцем:

~~~bash
python3 tools/bootstrap/asa-setup.py execute --answers /srv/asa-setup-answers.json --approve
~~~

Для восстановления зашифрованной копии одобренный файл закрытого identity указывается через переменную ASA_AGE_IDENTITY_FILE; сам секрет в ответах агента не хранится. Отсутствие источника, ключа или age — blocking issue. Прямой источник Яндекс Диска через OAuth/rclone пока не готов: см. issue #586. Отправка резервных копий в облако должна оставаться независимой от работы учеников без Интернета.

## Ограничения и обязательная приёмка

- inspect и plan не меняют сервер; execute требует отдельного --approve.
- Установка на уже действующем хосте не заменяет рабочую БД из нового архива. Для замены нужна отдельная контролируемая операция с проверенным backup и откатом.
- Открыть HTTP-страницу недостаточно. Production использует локальный HTTPS, Secure cookie, exact origin, CSRF. Доверие публичному школьному CA на клиентских Windows настраивается с согласия владельца или централизованной политикой.
- Хост, IP, MAC и сетевое имя не встраиваются в исходный код ASA Lab. При неоднозначном интерфейсе мастер блокирует произвольный выбор. Порты PostgreSQL/MinIO не открываются в школьную сеть.
- После установки обязательна фактическая приёмка входа учителя/ученика, классов, файлов, Scratch, электроники, 3D и сохранения/повторного открытия проекта без Интернета; затем restart, изменение IP, восстановление backup.
- Нагрузочное испытание 300 одновременных пользователей выполняется отдельно. Unit-тесты помощника не являются доказательством такой пропускной способности.
- Установка Windows Docker Desktop пока обслуживается install-windows.ps1, а не Ubuntu-мастером. OAuth-подключение к Яндекс Диску и полноценное новое-host E2E по-прежнему остаются открытыми работами.

Источники правил: START_HERE_FOR_AI.md, AGENTS.md, docs/execution/current.yaml, PORTABLE_SELF_HOSTED_DEPLOYMENT_STANDARD.md и docs/agent/contracts/deployment.yaml.

## Контракт распаковки зашифрованного снимка

Архив `.tar.age` содержит один верхний каталог. Проверенный распаковщик снимает **ровно этот архивный контейнер**: `snapshot/manifest.json` превращается в `ВЫБРАННЫЙ_КАТАЛОГ/manifest.json`, а `snapshot/objects/asa-blocks/...` — в `ВЫБРАННЫЙ_КАТАЛОГ/objects/asa-blocks/...`. Вложенный `snapshot/` в каталоге восстановления не допускается. Установщик повторно проверяет наличие `manifest.json` в корне до начала установки.

Архив с несколькими верхними каталогами, повторяющимися файлами, ссылками, переходами `..` или некорректным манифестом отклоняется. Проверка `--extract` проводится в новой закрытой папке; существующий путь не перезаписывается. Это не заменяет штатный `verify-backup` и пробное восстановление БД. Последняя проверка архива на Windows выполнялась **без распаковки на диск** и не меняла активную PostgreSQL.

### Длинные пути архивов на Windows

При восстановлении на Windows файлы MinIO могут иметь вложенные пути длиннее стандартного ограничения Windows. Распаковщик поддерживает такие пути без изменения логической структуры архива. Windows CI проверяет создание файлов и очистку временных каталогов с длинными путями. Успешная распаковка не заменяет отдельную проверку восстановления PostgreSQL и MinIO на новом сервере.

### Занятые порты и размещение рядом с другими установками

Перед первой установкой bootstrap проверяет свободность локальных портов **4610** (Web) и **4613** (Scratch). Если на машине уже работает ASA Lab, Docker Desktop или другое приложение, использующее эти порты, процесс останавливается **до установки Docker/1Panel и до создания БД**. Автоматически останавливать или перенастраивать чужие сервисы запрещено. Оператор должен освободить порты либо выбрать отдельный сервер; бот получает явную причину BLOCKED.

Проверка второго стенда WSL2 на одном Windows-компьютере с уже работающим Docker Desktop выявила именно такой конфликт. Для отдельной диагностики WSL использовались свободные внутренние loopback-порты, с сохранением точных Web/Scratch origins; это исключение тестового окружения, а не изменение стандартного школьного порта HTTPS 4610. Успешный запуск пяти контейнеров сам по себе не означает завершение восстановления школьной базы.

### Проверка источника до изменения сервера

Для `--restore-backup` установщик теперь проверяет полный манифест `asa-backup-v1`, утверждённый ID снимка, необходимые файлы PostgreSQL/конфигурации, инвентаризацию, размер и SHA-256 **каждого** файла до установки Docker/1Panel и создания production-базы. Повреждённая, переименованная или неполная копия отклоняется без начала развёртывания. При последующем restore штатный менеджер проводит независимую повторную проверку. Windows-установщик, как и Ubuntu, клонирует полную историю коммитов с частичной загрузкой содержимого, чтобы опубликованный стабильный релиз оставался достижимым.
