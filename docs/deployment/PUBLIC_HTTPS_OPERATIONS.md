# Публичный HTTPS для ASA Lab — единый способ установки и обслуживания

## Назначение

ASA Lab — **одно** приложение и один Docker Compose-проект с сервисами Web/Caddy, API, Scratch, PostgreSQL и MinIO.
Основной адрес для пользователей: **https://asa-lab.ru**. **www.asa-lab.ru** — только перенаправление на основной адрес; новый постоянный поддомен не нужен.
Веб-сервер Caddy уже встроен в существующий контейнер Web. Второй Caddy, отдельный контейнер Scratch, ещё одна база и второй Compose-проект для публикации запрещены.

## Что хранится в GitHub, а что — на компьютере

| GitHub (переносимый исходный набор) | Приватное состояние конкретной установки |
| --- | --- |
| `compose.yaml`, `compose.production.yaml`, `compose.public.yaml` | `.env`: созданные пароли БД, ключи приложения, точный адрес сайта и профиль |
| `docker/web/Caddyfile`, `docker/web/start.sh`, `Dockerfile.web` | `.asa/`: идентичность установленного выпуска, сведения об обновлении и восстановлении |
| `tools/asa_manager.py` и `tools/deployment/*`: установка, проверки, выпуск, резервирование | Именованные тома PostgreSQL и MinIO с реальными данными |
| Контракты, тесты, инструкция и настройки сборки GitHub Actions | Секреты транспорта, сертификаты HTTPS и подтверждённые резервные копии |

**Не добавлять в GitHub** `.env`, дампы, закрытые ключи, токены, реальные пользовательские данные и пароли.
Данные нельзя восстановить из GitHub: на другом компьютере потребуется полноценная резервная копия с базой, файлами и требуемыми секретами.

## 1. Новая локальная установка

Для отдельного локального компьютера оставить штатную установку без публичного домена:

~~~powershell
git clone https://github.com/spikeal8-maker/asa-lab.git
cd asa-lab
python tools/asa_manager.py install --profile dev
~~~

Сайт открывается по `http://127.0.0.1:4610`; HTTPS не нужен для изолированного loopback-доступа.
Имя Compose-проекта и пароли задаются только один раз; повторный вызов `install` не должен заменять существующее состояние.

## 2. Новая производственная установка с основным доменом

Требования: Docker Engine/Compose либо Docker Desktop с Linux containers, Git, Python 3.11+, x86-64;
доступность неизменяемых выпусков GitHub Container Registry; свободные порты TCP 80 и 443;
DNS A-записи `asa-lab.ru` и `www.asa-lab.ru` на публичный адрес выбранного сервера; при наличии AAAA корректный IPv6-маршрут.
Для домашнего сервера роутер направляет только TCP 80/443 на LAN-адрес этого компьютера.

~~~powershell
git clone https://github.com/spikeal8-maker/asa-lab.git
cd asa-lab
python tools/asa_manager.py install --profile production --public-domain asa-lab.ru
~~~

Менеджер создаёт закрытую конфигурацию один раз: общий HTTPS-адрес Web/API/Scratch, отключённые демонстрационные аккаунты, приватные случайные ключи, тот же Compose-проект.
Публичный профиль добавляет порты **80 и 443 только Web**. База PostgreSQL, MinIO, API и внутренний Scratch не публикуются.
Встроенный Caddy сам получает сертификаты HTTPS и хранит их в постоянном томе `caddy-data` своего Web-контейнера.
Локальный `http://127.0.0.1:4610` остаётся техническим интерфейсом, **не** публичным пользовательским адресом.

**Важно:** установка с внешним доменом проверяет фактический HTTPS-вход и нужную версию.
Если `asa-lab.ru` пока ведёт на другой работающий сервер, новая установка НЕ может считаться публично принятой.
Перед изменением DNS согласовать окно переноса и проверить полную копию данных; не переключать рабочий сайт ради простой проверки Docker.

## 3. Существующий сервер с реальной базой — только обновление

Сначала найти рабочий PostgreSQL-контейнер и прочитать метки `com.docker.compose.project`, `.working_dir` и `.config_files`.
Сверить их с реальным каталогом установки, приватным `.env`, именами томов, ревизиями Web/API/Scratch и состоянием БД.
На текущем домашнем экземпляре профиль/Compose могут называться `asa-lab-dev`, хотя там уже восстановлены реальные данные.
**Нельзя менять `COMPOSE_PROJECT_NAME`, выполнять вторую команду `install`, удалять тома или запускать Compose из другой копии репозитория.**

Переход существующей установки с локального/FRP-входа на встроенный публичный HTTPS
должен быть реализован отдельным защищённым действием **на том же Compose-проекте**,
с сохранением всех томов/секретов и проверкой старого и нового входа. Нынешняя команда
`install --public-domain` поддерживает **только действительно новую** установку и специально отказывается перезаписать существующую `.env`.
Простое редактирование `.env` или ручной запуск `docker compose up` не являются поддерживаемой миграцией.

До добавления безопасного перехода используйте существующий рабочий вход и штатные операции проверки:

~~~powershell
python tools/asa_manager.py doctor --profile dev
python tools/asa_manager.py check --profile dev
python tools/asa_manager.py backup --profile dev
~~~

Замените `dev` на фактический профиль **только после его проверки**. Резервную копию необходимо
проверить и отдельно испытать восстановление в `_test` базе; в рабочую БД ничего не восстанавливать без отдельного разрешения.
Обычное обновление уже установленного выпуска выполняется только через штатный менеджер, с проверкой точного SHA и версий данных.

## 4. Домен, маршрутизатор и проверка

Публичный IPv4 принадлежит роутеру/провайдеру, внутренний LAN IPv4 принадлежит выбранному компьютеру.
Код ASA Lab не должен хранить эти адреса как постоянную идентичность приложения.
Проброс: внешний TCP 80 → TCP 80 выбранного LAN-компьютера; внешний TCP 443 → TCP 443 того же компьютера.
**Не публиковать** TCP 4610, 4611, 4613, 5432 и MinIO/S3. Не использовать DMZ, полный UPnP или `network_mode: host`.
На Windows проверить разрешение входящих соединений в брандмауэре и фактический запуск Docker после перезагрузки/входа пользователя.
DNS и NAT на роутере не изменяются самим GitHub: это отдельные настройки оборудования и DNS-провайдера.

Проверить в указанном порядке:

1. Сервер остаётся на правильных томах и версии, PostgreSQL и MinIO доступны только внутри Docker.
2. `http://127.0.0.1:4610/health/ready` отвечает установленной версией, Scratch `/internal/blocks/healthz` отвечает через Web.
3. Снаружи открывается `https://asa-lab.ru` с действительным сертификатом; `https://www.asa-lab.ru` перенаправляет на основной адрес.
4. Внешний вход проходит реальным пользователем, а не только HTTP 200: авторизация, открытие проекта, редактирование, сохранение и повторное открытие.
5. Scratch использует тот же HTTPS-адрес; не происходит ошибки проверки адреса редактора, работают сохранение и повторный вход.
6. После повторного запуска контейнеров данные и сертификаты сохраняются. Проверить повторную установку/перезапуск без создания дублей.
7. При переносе на другой поддерживаемый компьютер восстановить проверенную копию, заново получить локальный LAN-адрес и поменять только конечный адрес на роутере; если меняется внешний IP — также DNS.

При отсутствии сертификата проверить DNS A/AAAA, порты 80/443, доступ Caddy к данным, время сервера, журналы Web и правила роутера.
При ошибке Scratch сравнить точные адреса портала, `ASA_BLOCKS_PARENT_ORIGIN`, `ASA_BLOCKS_RUNTIME_ORIGIN`, `ASA_UPDATE_ENTRY_ORIGIN` и `ASA_PUBLIC_WEB_ORIGINS`;
не отключать проверку происхождения запросов и не заменять её звёздочкой.

## 5. Ответственность бота и границы готовности

Для сетевых изменений сначала читать `AGENTS.md`, `START_HERE_FOR_AI.md`,
`docs/architecture/PORTABLE_SELF_HOSTED_DEPLOYMENT_STANDARD.md` и
`docs/architecture/ADR-PORTABLE-DEPLOYMENT-TRANSITION-001.md`.
Решение о публикации в GitHub не означает разрешение менять работающий Docker, DNS, базу или маршрутизатор.
CI-контракты и сборка Caddy доказывают корректность кода и конфигурации, но **не** подтверждают фактический доступ снаружи.
Отчёт всегда различает: код в GitHub → проверки точного SHA → слияние → запуск конкретного Docker → внешний HTTPS → проверку пользователя.
Оставшиеся требования переносимости по Issue #396 (в том числе существующая установка, автоматическое определение сети и испытание с другого компьютера) нельзя объявлять закрытыми без фактических проверок.
