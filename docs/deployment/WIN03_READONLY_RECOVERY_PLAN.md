# WIN-03A — безопасная диагностика прерванного обновления

Это первый ограниченный этап Resume/Repair. Команда **только читает**
`.asa/maintenance.json` и `.asa/failed-switch.json`, при необходимости
запрашивает текущее состояние контейнеров, возвращает диагностический код и
не открывает новый цикл обновления.

## Команда

На компьютере с ASA Lab, используя менеджер из проверенного исходника:

```powershell
python C:\ASA-Lab\tools\asa_manager.py repair-plan --root C:\ASA-Lab --profile production
```

Указанный путь — пример отдельного каталога приложения. Используйте реальный
каталог установленной ASA Lab и не подменяйте исполняемый скрипт сетевым
содержимым. Для работы с внешним постоянным Bootstrap WIN-01 отдельный
режим Repair будет добавлен в следующем этапе.

Вывод `REPAIR_PLAN` — JSON без секретов. Код `0` означает лишь
`NO_PENDING` — **отсутствуют записи незавершённого процесса**, а не
прохождение браузерной приёмки. При наличии незавершённых операций
возвращается код `2`, даже если запущен правильный релиз.

## Состояния

- `MANUAL_BACKUP_RECOVERY`: существует незавершённая резервная копия.
  Автоматически возобновлять экспорт, удалять `.incomplete` или запускать
  остановленные службы запрещено.
- `SELECTED_RUNNING_VERIFY_REQUIRED`: проверка readiness показала SHA
  выбранного релиза. Это **не завершение**. Необходимо удостоверить схему,
  реальный набор образов, HTTP-версию, проверенный полный backup и данные.
- `PREVIOUS_RUNNING_MANUAL_REVIEW`: запущен старый релиз, при этом транзакция
  не завершена; откат базы/схемы самостоятельно не выполняется.
- `UNEXPECTED_RUNTIME_MANUAL_REVIEW`: текущий SHA не совпадает ни с
  выбранным, ни с предыдущим; никакого автоисправления.
- `RUNTIME_UNAVAILABLE`: readiness не проходит; проверяются контейнеры,
  журналы и резервная копия без удаления информации.
- `BLOCKED REPAIR_* `: испорчены, чрезмерно велики, противоречат друг другу
  или являются symlink/reparse-point внутренние файлы состояния. Не удаляйте
  их ради обхода диагностики.

Ни один из перечисленных статусов не разрешает автоматический Resume/Repair.
Для фактического перехода требуются отдельные подтверждения и доказательства
целостности перед атомарным закрытием транзакции. Прямой `acknowledge` при
неизвестном состоянии использовать нельзя.

## Гарантии

Без `docker up/stop/down`, изменения `installed-release.json`, резервных
копий, `maintenance.json`, `failed-switch.json`, смены ключей, очистки
PostgreSQL/MinIO, миграций, сетевых настроек Windows. Размер каждого JSON
маркера ограничен 64 КиБ; нелегитимные пути не открываются.

Проверки: `tools/deployment/test_repair_plan.py` моделируют все фазы,
недоступность runtime, несогласованные и повреждённые маркеры, нераскрытие
секретов и отсутствие вызовов Docker-мутирующих операций. Реальную операцию
Resume/Repair следует разрабатывать отдельным небольшим PR WIN-03B.
