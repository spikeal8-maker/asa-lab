# ASA Lab — Windows restore, безопасный откат и границы гарантий

## Цель

После сбоя установки, обновления или восстановления данные пользователей должны оставаться восстановимыми. Программа не должна скрывать неполный результат, подменять проект/том или автоматически переписывать рабочую базу «на всякий случай».

**Порт не определяет роль среды.** На D2R2 `4610` соответствует source-mounted dev-стенду с незавершёнными изменениями; `4620` — отдельной Docker-установке с профилем `production`, предназначенной для приёмки. Называть `4610` production из-за номера порта нельзя. Перенос содержимого 4620 на 4610 не входит в обычное обновление.

## Реально проверенные исправления

1. `restore-check` читает полный TOC PostgreSQL, переставляет только запись `TABLE DATA public ai_ollama_cloud_models` перед зависимыми `ai_assistant_config` и `ai_generation_policy` и передаёт полный список `pg_restore --use-list`. Ограничения CHECK, права SQL и RLS остаются включёнными. Старые архивы без этого каталога не меняются.
2. Если восстановление в **новую** базу с суффиксом `_test` закончилось ошибкой уже после создания базы, утилита пробует удалить только ею созданную тестовую базу **без** `--force`. Если база занята или Docker недоступен, она сохраняется для ручного осмотра, а исходная ошибка не считается успешным восстановлением.
3. Проверка полного облачного архива `20261028T231505Z-d08c3ab7` на Windows/D2R2 успешно восстановила 94 аккаунта, 31 класс, 433 ученических места и 1730 проектов (схема 279), сохранив ACL/RLS. Это доказательство технического восстановления, не браузерной приёмки входа.
4. После запуска MinIO может изменять `.minio.sys`. Во время приёмки сравниваются SHA-256 **пользовательского бакета** и видимость объектов по S3. Прямое равенство всего тома после запуска MinIO — некорректный критерий: оно ранее вызвало ложный отказ и проверенный возврат старых данных.

## Контракт аварийного переключения

Порядок: `VERIFY → PLAN → BACKUP → STAGE → FREEZE WRITES → PRESERVE OLD DB + OBJECTS + ENV → SWITCH → VERIFY → ACCEPT`.

При любом отказе до `ACCEPT` оператор должен иметь проверенную точку восстановления. Во время отката сначала сохраняются неудачные новые БД, объектное хранилище и конфигурация в отдельные карантинные ресурсы (если они могли измениться), затем восстанавливаются прежние имена БД, объекты и приватная конфигурация. После перезапуска обязателен повторный `health/ready`, контроль схемы, счётчиков и S3. Ошибки отката фиксируются отдельно и **не** выдаются за `PASS`.

Длительная операция хранит журнал фаз вне каталога приложения. После обрыва процесса или питания неизвестная фаза трактуется как `RECOVERY_REQUIRED`; никаких повторов `apply` и автоматического удаления ресурсов до проверки фактических PostgreSQL/Docker identities. Проверяемая чистая повторная попытка не должна перезаписывать предыдущий журнал, архив или старые тома.

**Нельзя автоматически откатывать уже принятый релиз `SUCCEEDED`.** После открытия доступа могли появиться новые работы и сообщения. Если возврат необходим, он проводится отдельной операцией с сохранением и сверкой нового состояния, без потери пользовательских записей.

## Граница реализации

- Исправление `restore-check` находится в общем Python-менеджере и покрыто реальным Windows-восстановлением плюс unit-тестами.
- `cutover_safety.recovery_plan` — fail-closed контракт выбора действий при сбое; он не выполняет самостоятельный Docker rollback. Решение оператора должно быть реализовано исполнительным адаптером, проверяющим точные имена PostgreSQL и томов.
- Разовый Windows cutover на D2R2 уже продемонстрировал автоматический откат при ложном отказе MinIO и затем успешное переключение. Его частный журнал/исполнитель не следует без отдельной приёмки использовать как универсальный установщик.
- **Обычный `asa_manager.py update` пока НЕ гарантирует автоматический откат изменённой PostgreSQL-схемы.** Он выполняет полный backup, сохраняет `failed-switch.json` и останавливает повторные попытки. Чтобы гарантировать автоматический возврат старой версии при несовместимых миграциях, требуется отдельный shadow DB/volume switch с заморозкой записи и испытанием аварийных состояний. В отсутствие этого механизма заявление `100% automatic rollback` запрещено.
- Полная свежая установка Windows в пустой Docker Engine и браузерная приёмка преподавателя/ученика остаются отдельными тестами. Проверка `doctor` или HTTP 200 не заменяет их.

## Инварианты безопасности

Сохранять `project`, `root`, профили, точные составы Compose, PostgreSQL/MinIO volume identity, исторические ключи кодов, ACL и RLS. Не выполнять `docker system prune`, `compose down -v`, force-reset Git, изменение Windows VPN/DNS/firewall/маршрутов или переключение 4610 ради «успешной» проверки. Оригинальные архивы Яндекс Диска и USB age identity остаются вне GitHub; расшифрованные `private.env` и дампы никогда не включаются в коммиты/CI artifacts.

В отчёте использовать явные статусы `OK`, `NO_CHANGE`, `WARNING`, `BLOCKED`, `ROLLED_BACK`, `RECOVERY_REQUIRED`, `SUCCESS` только при наличии фактических доказательств.
