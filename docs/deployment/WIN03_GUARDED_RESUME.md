# WIN-03B — защищённое завершение прерванного обновления

## Ограничение действия

`resume` **не восстанавливает неисправную установку**, не запускает Docker,
не выполняет миграции и не откатывает PostgreSQL. Оно завершает запись
установочного релиза **только если выбранный опубликованный релиз уже реально
работает** и проверены все необходимые доказательства.

Сначала выполняется `repair-plan` из WIN-03A. Только при фазе `switch`
или `verify_entry` и при явно разрешённом оператором завершении:

```powershell
python C:\ASA-Lab\tools\asa_manager.py repair-plan --root C:\ASA-Lab --profile production
python C:\ASA-Lab\tools\asa_manager.py resume --root C:\ASA-Lab --profile production --confirm-resume
```

Пример каталога `C:\ASA-Lab` необходимо заменить на свой реальный каталог
установки, а код менеджера брать только из официального проверенного исходника.
Доступ к функции через постоянный внешний Bootstrap — отдельный этап; команда
прямого запуска менеджера остаётся необходимой до его реализации.

## Проверки перед записью

- Операция выполняется под эксклюзивной блокировкой `.asa/operation.lock`.
- Для `.asa/maintenance.json` и `.asa/failed-switch.json` проверяются
  известные фазы, совпадающие selected/previous/backup, предел размера 64 КиБ,
  отсутствие symlink/junction; копии при противоречиях не удаляются.
- `selected` должен быть полноценным опубликованным ASA-манифестом с точными
  SHA-256 всех образов; текущая схема и SHA из реального readiness должны
  совпасть.
- Действующий Docker Compose project/volumes проверяется через собственную
  модель identity; у каждого сервиса точный закреплённый image и состояние
  running, без подмены проектом с другого корня.
- Полный backup предыдущего релиза обязателен. Он должен лежать в настроенном
  каталоге резервных копий и успешно пройти `verify_backup` с совпадающим
  предыдущим SHA и схемой. Для чистой первичной установки, где `previous`
  отсутствует, backup не обязателен, но нельзя маскировать чужие данные.
- Проверяются разрешённый Compose-манифест, конфигурация PostgreSQL, безопасный
  entry origin и реальные ответы `health/ready`, `build-metadata.json`,
  `runtime-config.js`, встроенный Scratch.
- Сохранённый `installed-release.json` должен быть выбранным либо
  предыдущим подтверждённым релизом; чужая ревизия блокирует завершение.

**Только после полного PASS** атомарно записывается selected receipt, создаётся
отчёт `resumed_verified`, а два исходных маркера переименовываются в архивные
`reviewed-...` и `acknowledged-...` без стирания. Повторный вызов после
частичного архивирования допустим только после новой полной проверки.

Без `docker up/stop/down`, `pg_restore`, `pg_dump`, `db:migrate`,
удаления томов, ротации ключей, восстановления базы, настройки Windows/WSL/VPN,
перезагрузки компьютера или обхода HTTP/образов. При любой ошибке маркеры
сохраняются для ручной диагностики.

**Код возврата 0** подтверждает завершённую проверку и архивирование записей,
**но не пользовательскую приёмку**: `userFlow=not_run`. При остановленном
релизе, неподходящей схеме или неполном backup Resume завершается кодом 2;
исправление настоящего отказа сервиса остаётся отдельным ручным безопасным
сценарием (будущий WIN-03C).

## Испытания

`test_repair_resume.py`: сценарии положительного завершения, отсутствия
подтверждения, фазы backup, старой версии в runtime, недостающего/чужого backup,
ошибки HTTP, изменённого образа, расхождения маркеров, чужого installed-release,
отсутствия операции и повтора после частичного архивирования.

Тесты используют временные каталоги и замещённые функции Docker/HTTP/backup;
реальный production, test server или школьные машины не затрагиваются.
