# Локальный llama.cpp

Этот документ описывает независимый провайдер `llamacpp-local` в ASA Lab.
Он подключает уже работающий llama-server через OpenAI-совместимый HTTP API.
Запуск llama-server, выбор GPU, загрузка весов, серверный размер контекста и MTP
остаются задачами владельца этого сервера.

## Порядок проверки

1. Опубликовать продуктовый кандидат в GitHub и получить зелёные exact-SHA
   проверки AI, PostgreSQL, браузера и обязательный `ASA / required`.
2. Выполнить независимый критический review того же кандидата.
3. Провести реальную приёмку только на тестовом сервере ASA, с отдельной
   одноразовой базой с суффиксом `_test` и штатным E2E launcher на
   `127.0.0.1:4612`. Не использовать рабочую базу и не менять постоянный Compose.
4. Развёртывание постоянной установки возможно только после подтверждённой
   приёмки и отдельного разрешения на защищённый updater.

Школьные серверы исключены из этой работы по прямому указанию владельца.
Не запускать на них диагностику, тесты, установку, обновление или изменение
настроек в рамках AI-LOCAL-LLAMACPP-001.

## Настройка через админку

Откройте **Админ → ИИ → Подключения → llama.cpp**. Включите провайдера,
введите адрес существующего llama-server и при необходимости его API-ключ.
Поддерживаются IP, IP с портом, DNS-имя и HTTP(S) URL, включая суффикс `/v1`.
Без явно указанного порта ASA использует **8080**. Имя компьютера должно
разрешаться системным DNS с backend ASA.

После паузы во вводе ASA самостоятельно запрашивает список моделей. Одну
найденную модель выбирает автоматически; при нескольких выберите нужную.
Модель с файловым upstream ID сохраняет этот ID в приватной конфигурации,
но путь не становится открытой операционной меткой для пользователей.

Нажмите **«Сохранить и проверить»**. При неудачной проверке прежняя конфигурация
сохраняется. Во время проверки не меняйте адрес или ключ. При неизвестном исходе
не создавайте новую попытку автоматически: сохранённый request ID нужен для
восстановления результата. Отключить провайдера можно и при недоступном сервере.

В существующей политике разрешённых моделей включите `llamacpp-local`, если
используется собственный список. Выбор модели по умолчанию и школьные права
остаются отдельными административными действиями. После этого разрешённый
пользователь выбирает llama.cpp в обычном чате ASA.

## Ключи и сеть

Ключ хранится только на backend, штатно шифруется с помощью
`ASA_SETTINGS_ENCRYPTION_KEY` и привязывается к нормализованному адресу.
Чтение настроек возвращает лишь `apiKeyConfigured`. Ввод нового адреса
немедленно очищает черновик ключа; сохранённый ключ к другому адресу не отправляется.
Не помещайте ключ в URL, GitHub, командную строку, screenshots или журналы.

Соединение выполняет backend ASA. Loopback означает сам backend/container,
а не компьютер администратора. Для другого компьютера используйте доступный
backend адрес LAN или Tailscale. Список DNS-ответов проверяется полностью,
разрешённый адрес закрепляется для соединения, перенаправления не выполняются.
Публичные, link-local и metadata-адреса не разрешаются.
`ASA_LLAMACPP_ALLOWED_HOSTS` при наличии дополнительно ограничивает список
точных разрешённых имён; он не расширяет правила частной сети.

## Контекст, генерация и очередь

`GET /v1/models` подтверждает обнаруженный ID. Runtime-контекст из `/props`
показывается отдельно от training metadata и ручного лимита. Недоступное поле
остаётся неизвестным. В router режиме metadata не загружают все модели:
запрос использует `autoload=false`. Обычный запрос выбранной модели может
потребовать её загрузки самим сервером.

ASA передаёт поддерживаемые параметры температуры, top-p и максимального ответа
в `/v1/chat/completions`. Серверный `n_ctx` и MTP через ASA не перенастраиваются.
ASA рассматривает до 32 последних пользовательских ходов и их ответов. Перед
генерацией проверяется полный запрос со служебными инструкциями, схемами и
результатами инструментов. При нехватке места ASA оставляет последние целые
ходы и может уменьшить предел ответа. Текущий вопрос, системные инструкции
и результаты вызовов остаются целыми. Для подсчёта ASA использует
`/v1/chat/completions/input_tokens` или `/apply-template` и `/tokenize` на
старых версиях. Если подсчёт недоступен, применяется консервативный лимит в
байтах. [Документация llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-v1chatcompletionsinput_tokens-token-counting).
Остальные провайдеры сохраняют выборку 8 ходов. При повторной генерации история
заканчивается исходным вопросом.

Если обязательные части не помещаются ещё до первого запроса на генерацию,
попытка записывается с фактическим расходом 0 токенов и освобождает резерв.
Идентификатор попытки сохраняется для безопасного повтора.
Поток SSE дочитывает usage после финального текстового фрагмента и до `[DONE]`.
Все раунды tools входят в один существующий журнал использования и бюджет.
Неизвестный usage не превращается в ноль или оценку.

В пределах одной ASA-установки session advisory lock удерживает одну активную
операцию на весь цикл модели и инструментов. Он освобождается после закрытия
своего upstream; обрыв процесса снимает PostgreSQL session lock. Сохранённый
request ID с неизвестным результатом не выполняется заново. Эта блокировка
не является общей очередью для разных установок ASA или сторонних клиентов.

## Автоматические проверки

Все команды используют зафиксированный в репозитории pnpm 9.15.9:

```bash
corepack pnpm test:ai-llamacpp
corepack pnpm test:ai-chat
corepack pnpm test:ai-llamacpp:pg
corepack pnpm e2e:ai-llamacpp
```

PostgreSQL-команда требует явно заданных `TEST_DATABASE_URL` и
`APP_TEST_DATABASE_URL`, указывающих на одну изолированную `_test` базу.
Обычный AI workflow запускает новый PostgreSQL spec своим существующим glob,
а браузерный набор — `e2e/ai-llamacpp.spec.ts` с синтетическими API-ответами.
Эти проверки не являются доказательством подключения к физическому llama-server.

## Реальная приёмка после зелёного CI

Подготовленный opt-in runner использует построенные Web/API и реальный чат,
не подменяет успешные ответы backend и не устанавливает новые службы.
Он отказывается запускаться без точного SHA и явной изолированной базы.

Перед запуском приватно задаются:

| Переменная | Назначение |
|---|---|
| `ASA_LLAMACPP_LIVE_SHA` | Точный проверенный Git SHA кандидата |
| `ASA_LLAMACPP_LIVE_ENDPOINT` | Доступный backend адрес реального llama-server |
| `ASA_LLAMACPP_LIVE_API_KEY_FILE` | Необязательный приватный файл с ключом; значение ключа не передаётся через аргументы |
| `TEST_DATABASE_URL` | Административное соединение только с `_test` базой |
| `APP_TEST_DATABASE_URL` | Ограниченная роль `asalab_app` в той же `_test` базе |

Сначала штатно применяются миграции к этой одноразовой базе. Runner сам выполняет
свежую сборку identity/API/Web с отключённым Nx cache и переменными
`ASA_BUILD_REVISION` и `VITE_ASA_BUILD_REVISION`, равными проверенному SHA.
Чистота исходников и HEAD проверяются до и после сборки. Отдельный build receipt
содержит SHA исходников, Git tree, команду и SHA-256 каталогов API/Web; версия
из `/api/version` используется только как дополнительная runtime-проверка.
Сохранённая конфигурация теста не переносится в рабочую базу автоматически.

```bash
corepack pnpm e2e:ai-llamacpp:live
```

Runner использует `e2e/server.mjs`, не переиспользует неизвестный процесс на
порту 4612, выключает traces/video и сохраняет только маскированные screenshots
и агрегированный receipt. Реальный длинный запрос может занимать заметное время;
результат должен указывать фактический reported usage, а не только advertised
context. Подтверждённый `/props` предел сам по себе не доказывает испытание
на полном максимальном контексте.

Итоговые состояния каждого критерия и ссылки на exact-SHA CI находятся в
[evidence](../product/ai/evidence/AI_LOCAL_LLAMACPP_001.md).
