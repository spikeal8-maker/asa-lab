# Админ → Логи: критический разбор и контракт

## Разбор до реализации

1. Docker stdout принадлежит контейнеру, а не установке. При замене контейнера
   исчезает история. Сохранение должно выполняться независимо от Web/API и до
   следующего обновления. Повторный сбор не может восстановить уже удалённые записи.
2. История администраторов и аналитика в PostgreSQL не содержат всех технических
   ошибок. Ошибки вкладки/iframe/worker необходимо сообщать отдельно. Отсутствие
   сообщения о сбое не доказывает отсутствие сбоя: браузер может аварийно закрыться
   или потерять сеть до отправки.
3. Доступ API к Docker socket, произвольным путям и shell создал бы возможность
   управления сервером через страницу журналов. API читает только подготовленные
   сегменты; источники собирает отдельный host runner с существующим доступом
   оператора к Docker. Публичных портов и второго Compose project нет.
4. Чтение недельных файлов и упаковка на основном потоке API мешали бы ученикам.
   Поиск и экспорт выполняются в worker с ограничением времени, объёма и числа
   одновременных операций. Экспорт — фоновая задача с повторной проверкой доступа.
5. Технический журнал может раскрыть секреты, документы и сведения о других
   школах. Общие журналы доступны только существующему platform permission
   `administration.operations.read`; учебные payload и cookies не принимаются
   клиентской диагностикой, известные секреты очищаются перед сохранением.
6. «Все журналы» не означает гарантированную полноту. Для каждого источника
   показываются время последнего успешного сбора, границы сохранившихся записей,
   ошибки/ограничения доступа. Windows Security без прав остаётся недоступным.
7. Бесконечное хранение заполнит диск. Срок хранения — 30 дней по умолчанию;
   размер и рабочие архивы ограничены. При очистке удаляются только записи
   диагностического хранилища. Пользовательские данные и backup dumps не затрагиваются.

## Выбранная архитектура

Host collector (Python standard library) → собственный SQLite индекс →
атомарно опубликованные сегменты JSONL (gzip) и catalog → read-only mount API →
worker поиска/ZIP → защищённая страница «Логи».

SQLite используется только host collector; общий Windows/Linux WAL не передаётся
в контейнер. API читает завершённые сегменты. Идентификатор записи обеспечивает
повторяемый сбор без дубликатов. Настройки источников хранятся вне исходников.
В SQLite остаются бинарный идентификатор и номер опубликованной записи;
содержимое хранится только в неизменяемом сегменте. До публикации содержимое
сжато в приватной очереди SQLite. Ротация файлов отслеживается по файловому ID:
переименование не запускает повторное чтение; одинаковые самостоятельные
строки остаются отдельными событиями. Старые дубликаты автоматически не удаляются.

Файловые источники используют время события из текста или JSON `time`,
`timestamp`, `ts` (ISO, Unix seconds/milliseconds). Если его невозможно
распознать, запись помечается `timeBasis=file_mtime`; страница объясняет,
что показано время изменения файла. Явный уровень JSON/Pino и HTTP status
имеют приоритет над словами в сообщении. Windows сохраняет EventId и RecordId,
а новые HTTP access logs — revision для сопоставления с выпуском.

Источники: все контейнеры канонической установки; системные события Windows;
Docker Desktop; зарегистрированные файлы туннеля, обновлений и backup; таблицы
событий PostgreSQL. Недоступный источник имеет отдельный статус, а не пустой PASS.

Клиент сообщает ограниченные коды ошибки, модуль, версию и случайный временный
номер открытого редактора (`instanceId`, без привязки к учётной записи).
Запросы к своему API получают тот же номер и модуль; клиентский `request_failed`
содержит `relatedRequestId` именно неудачного запроса, HTTP status и длительность.
Поля строго проверяются; клиентские сведения помечены как недоверенные и не
определяют права доступа. Текст исключения,
содержимое проектов, URL query, произвольное содержимое browser storage и авторизационные данные не
отправляются. Повторения ограничены на клиенте и на сервере; недоступная
диагностика не меняет вход и сохранение проекта.

### Подсистемы и устойчивость доставки (11 октября 2026)

- Фильтр «Подсистема» отделяет проекты, классы, обучение, курсы, доступ,
  аналитику, администрирование, хранилище, БД, Scratch, электронику, игры,
  обновления, backup и сеть. Группа определяется маршрутом сервера или известным
  источником; клиентский контекст редактора остаётся отдельным недоверенным полем.
  Старые сегменты читаются с вычислением группы, без изменения ID и истории.
- «Скачать журналы приложения» выгружает все события приложения за выбранные
  даты, независимо от фильтров просмотра. «Скачать все журналы» сохраняет также
  Windows, Docker Desktop и нагрузку. Ошибка отдельного источника делает общий
  статус ошибочным и выводит заметное предупреждение; недоступный защищённый
  канал Windows по-прежнему указан отдельно.
- API пишет начало и завершение запросов с одним requestId и версией. Начало
  без завершения помогает расследовать обрыв; само по себе не доказывает его причину.
  Веб-сервер пишет HTTP status, путь без query, метод, длительность, версию и
  requestId API. Объекты request и response headers удалены из access log полностью.
  Токен приглашения преподавателя в пути также скрывается до записи stdout
  в API и [фильтром regexp Caddy](https://caddyserver.com/docs/caddyfile/directives/log#regexp).
  Отдельный runtime logger Caddy также исключает request и response headers:
  upstream 502 не должен сохранять query или заголовки запроса.
  Для закреплённого Caddy 2.10.2 используются `orig_uri.path` и `orig_method`:
  путь сохраняется до внутренних rewrite, без неподдерживаемого префикса `<`
  в имени поля. Скрытие токена применяется к обоим logger, включая upstream 502.
- Браузерная очередь ограничена 50 событиями и 15 минутами. В sessionStorage
  сохраняется только проверенный конверт диагностики со случайными eventId,
  instanceId и временем события; содержимое проекта и сообщения исключений
  не принимаются. При запрете storage используется память вкладки. После
  перезагрузки допустимые записи отправляются снова. HTTP 408/429/5xx и сетевые
  сбои повторяются с задержкой 1–30 секунд; попытка ограничена пятью секундами.
  Остальные HTTP ошибки прекращают повтор. При переполнении сначала вытесняется
  сообщение готовности/отклика, затем самое старое событие. Это ограниченная
  доставка, а не гарантия сохранения всех аварий при закрытии браузера.
- Сервер подавляет повторные eventId в пределах IP на 15 минут, до 8192 ID.
  При перезапуске API или вытеснении ID дубликат возможен. Серверное время приёма
  остаётся основным; occurredAt клиента недоверенно и может отличаться из-за часов.
  Старые клиенты без новых полей принимаются. При выпуске API обновляется раньше Web;
  старый API отвергает новый конверт, поэтому обратный порядок не поддерживается.
- Электроника сообщает безопасную категорию и код сбоя worker/расчёта, ошибки
  сохранения и обновления сессии — этап и HTTP status. Ошибки страницы могут
  содержать только путь `/assets/*.js` своей сборки и номер строки/столбца.
  Некорректная схема не смешивается с технической аварией: ожидаемые категории
  моделирования отмечаются предупреждением.
- Метрики PostgreSQL читаются через CSV, включая многострочный JSON. Отказ Docker
  stats не отменяет чтение метрик БД. Неполная выборка получает уровень error.
  Windows также сообщает доступный commit limit; малый остаток памяти или диска
  помечается предупреждением. Минутная выборка может пропустить короткий пик.
- Проверка публичного входа после обновления повторяет только временные HTTP
  404/502/503/504 и сетевые ошибки, не более трёх попыток. Постоянный отказ
  содержит точный проверявшийся путь, а незавершённая операция — фазу verify_entry.
  Проверка версии и origin обязательна; failed_switch не снимается автоматически.

Проверки: `pnpm test:admin-logs`, deployment unit tests, API/Web typecheck;
в GitHub — полный gate, браузерная вёрстка 1440/1024/390/320 и проверка настоящего
web image в portable smoke. Smoke посылает секрет-маркер в query, Cookie,
Authorization и body и проверяет отсутствие маркера в web log при наличии HTTP 404,
скрытом токене приглашения и намеренно вызванном HTTP 502 в одноразовом CI stack.

### Проверка качества сбора (исправления 9 октября 2026)

- Свежие события БД и повторная сверка истории используют независимые курсоры.
  История сверяется каждые шесть часов за весь срок хранения. Запросы read-only,
  ограничены 15 секундами и размером вывода; при превышении окно делится пополам,
  неуспешный курсор не продвигается. Статусы `database-history:<table>` показывают
  окончание сверки, `retainedFrom/To` вычисляются по исходной таблице.
- Поиск выполняется порциями до 200 000 строк или восьми секунд с продолжением
  по тому же снимку. Незавершённая порция не выдаётся за пустой результат.
  На API не более двух поисковых сеансов; срок сеанса пять минут, курсор привязан
  к администратору и неизменным фильтрам. Страница автоматически продолжает поиск
  до четырёх минут. При перезапуске API поиск нужно начать снова.
- Серверные исключения HTTP записываются одним JSON событием `server_error`:
  requestId, revision, безопасная категория причины, кадры стека, память процесса
  и состояние пула PostgreSQL. Сообщения исключений и SQL не копируются. HTTP
  ответ сохраняет прежнюю форму. Ошибки Fastify вне Nest также учитываются.
- Scratch после готовности посылает отклик каждые 15 секунд. Родитель фиксирует
  отсутствие отклика дольше минуты и восстановление. Скрытые вкладки и задержка
  самого родителя не считаются зависанием iframe. `editor_unresponsive` — признак
  отсутствия отклика, а не доказанная причина аварии. Отклик в журнал записывается
  не чаще раза в минуту. Ошибки запросов iframe связаны тем же instanceId.
- После каждого цикла атомарно обновляется `collector-health.json`. Ошибка
  публикации или запуска видна даже при свежем catalog. Время последнего успешного
  цикла сохраняется. Отказы отдельных источников видны в их собственных статусах.
- `metrics` сохраняет свободный диск, память/CPU Windows, Docker stats и только
  агрегированные подключения/ожидания PostgreSQL. Период не чаще минуты и не
  чаще цикла; это выборка, которая может пропустить короткий пик. При ошибке
  сохраняется доступная часть с `incomplete=true`, источник сообщает отказ.
- Изменения состояния контейнеров фиксируются отдельно: exit code, OOMKilled,
  health, restartCount и времена запуска/завершения; без environment и health log.
  Эти наблюдения доступны в источнике соответствующего контейнера.
- При 256 и более сегментах сборщик объединяет до 32 небольших файлов за цикл,
  до 3 MiB исходного текста. Проверяет SHA/count/ID, сохраняет durable intent и
  завершает операцию после сбоя. ID событий неизменны; старый снимок доступен ещё
  600 секунд после исключения из catalog. Данные приложения и хоста не смешиваются.
- Копии при ротации дедуплицируются только по доказанному совпадению уже собранного
  префикса активного файла (до 8 MiB, четыре последних отпечатка). Остальной текст
  и самостоятельные одинаковые события сохраняются. Ранее созданные копии не удаляются.
- PowerShell transcript использует границы сеанса из заголовка, помеченные
  `timeBasis=transcript`. Это приблизительное время строки, что указано в интерфейсе.

Исторические браузерные аварии без отправленного сообщения и показатели нагрузки
до подключения `metrics` восстановить невозможно. Новые данные помогают связать
сбой с запросами и нагрузкой, но сами по себе не доказывают причину перезагрузки
компьютера, исчерпания памяти браузера или потери сети.

## Приёмка

- Anonymous, StudentSeat и organization admin получают отказ на просмотр,
  экспорт, статус задачи и скачивание; отозванный доступ проверяется повторно.
- Потерянный ответ, повторный сбор и замена контейнера сохраняют историю.
- Проверяются очистка секретов, недоступный/устаревший collector, неправильные
  даты/cursor/source, выход за каталог, повреждённый сегмент, большие архивы.
- Поиск по источнику, модулю, уровню и периоду; время отображается по Москве.
- Архив содержит выбранные записи и сведения о полноте; ZIP проверяется.
- Страница проверяется на 1440/1024/390/320, включая загрузку, пустые записи,
  длинные сообщения, ошибку и готовность скачивания.
- Не выполняется очистка production logs, БД, volumes или существующих архивов.

## Эксплуатация

### Установка сборщика

Поддерживаемые команды запуска `tools/asa-lab.ps1 up` / `sh tools/asa-lab.sh up`,
защищённый source updater и `tools/asa_manager.py install/update` автоматически
подготавливают и сверяют сборщик своей канонической установки. Ручной второй шаг
для обычного запуска больше не нужен. `doctor`, `check` и `log_collector.py status`
только читают состояние: не создают `.env`, каталоги, задачи или службы.
Прямой `docker compose up` сам по себе не устанавливает host runner.
Для явного повторного согласования уже существующей установки доступна обёртка:

```powershell
.\tools\install-log-collector.ps1
```

Windows: задача `ASA-Lab-Logs-<project>` запускается от текущего пользователя
Docker Desktop; при закрытой пользовательской сессии сбор недоступен. Права
не повышаются автоматически. Недоступные каналы, включая Security, видны отдельно.

Linux: обычный оператор получает user systemd службу; при уже имеющихся правах
root и явно определённом непривилегированном Docker операторе (`SUDO_USER`)
создаётся system service. Существующий режим и владелец сохраняются. Автоматического
`sudo`, изменения членства в группах или включения lingering нет. Для автономного
запуска до пользовательского входа нужны уже настроенный lingering либо system mode.
API получает дополнительную числовую группу `ASA_LOG_READER_GID`, равную основной
ненулевой группе оператора; значение один раз сохраняется в приватной `.env`.
Доступ проверяется реальным `id -G` и чтением файла из контейнера API. Каталоги
публикаций имеют режим `2750`, файлы `0640`, приватный SQLite каталог — `0700`.
Старая история получает новую группу только после применения группы к API;
ошибка скачивания/backup до переключения не отнимает прежний доступ. При необходимом
пересоздании API обычный updater выполняет свой полный проверяемый backup/switch,
даже если SHA приложения тот же. Сам reconcile контейнеры приложения не перезапускает.
Rootless Docker / user namespace remapping пока не подтверждены для автоматического
host-store доступа и не входят в этот режим поддержки. Недостаток прав остаётся
видимым `degraded`/`unavailable`, без открытия журналов всем пользователям.

Перед изменением задачи/службы сверяются точные action, root, owner и interpreter;
для systemd также effective unit path, drop-ins, дополнительные команды,
User, NoNewPrivileges и WorkingDirectory загруженной службы, включая путь без перезапуска.
Полный executable и массив argv загруженной службы сверяются через `busctl --json=short`;
текстовый `systemctl show` склеивает аргументы и для этой проверки недостаточен.
Требуется штатная утилита systemd `busctl` с JSON-поддержкой; если запрос недоступен
или ответ неоднозначен, reconcile возвращает `degraded` до изменения службы.
`WorkingDirectory` записывается абсолютным путём без кавычек: его
[парсер systemd](https://github.com/systemd/systemd/blob/v255/src/core/load-fragment.c#L2400-L2452)
не снимает кавычки, в отличие от `ExecStart`. Пробелы внутри пути поддерживаются;
управляющие символы, кавычки, обратная косая черта, `%`, `$` и пробелы по краям
отклоняются до регистрации. Старый unit с `WorkingDirectory="..."` автоматически
не принимается: администратору нужно проверить принадлежность файла, команду,
пользователя и effective state, исправить только свой unit и повторить reconcile.
История и конфигурация при отказе сохраняются. В Linux CI отдельный временный unit
проверяется через `systemd-analyze verify`: старый quoted-вариант обязан завершиться
ошибкой, новый raw-вариант с пробелами — пройти, без регистрации тестовых служб.
Ошибка runner сообщает этап `systemctl`, exit code и безопасную категорию ошибки;
сырой stderr, environment и аргументы чужих служб не публикуются.
Перенаправления каталогов Windows (включая junction на Python 3.11) отклоняются.
Health/process, конфигурация/квитанции коллектора, каталог и сегменты публикуются
через новые эксклюзивно созданные временные файлы в том же каталоге: старые
hardlink/reparse temporary entries не открываются для записи и не усекут чужой файл.
Чужая задача/служба не заменяется. При изменении исходников сборщик своей установки
перезапускается; новый старт подтверждается новым nonce, PID, digest и временем.
`collector-process.json` обновляется отдельным heartbeat каждые 20 секунд, включая
долгий сбор Windows. Он подтверждает только жизнь процесса. `collector-health.json`
содержит успешность цикла и отдельную сводку применимых источников; ОС, к которой
adapter неприменим, исключается из completeness aggregate. Ошибка сборщика после
готовности сайта записывается отдельно в `.asa/collector-operation.json` и не
превращается в ложный `failed_switch` приложения.

### Поддержка host collection

| Хост | Условия автоматического старта | Ограничения |
| --- | --- | --- |
| Windows 11 x64 | Python 3.11+, Git, Docker Desktop с Linux amd64 containers, Task Scheduler, пользователь Docker вошёл в систему | Без входа пользователя сбор не обещается; Windows Security требует имеющихся прав |
| Linux amd64 с systemd и rootful Docker Engine | Python 3.11+, Git, systemctl и busctl с JSON-поддержкой, Docker Compose plugin, оператор уже имеет доступ к Docker; работает user manager либо заранее разрешён system mode | User mode до входа требует existing linger; system journal без прав честно unavailable |

Общие требования приложения, диска/RAM и браузеров описаны в
[Portable Operations](PORTABLE_OPERATIONS.md). ARM, macOS, non-systemd Linux и
Docker userns/rootless не объявлены поддержанными host-runner платформами.

### Нагрузка и события Linux/Docker

Linux дополнительно собирает `/proc/meminfo`, delta CPU из `/proc/stat`, load average,
swap и advisory commit values/policy. Первый CPU sample не выдумывает процент.
Windows сохраняет RAM, commit limit/available и delta CPU. Предупреждение о памяти:
доступно менее max(512 MiB, 5% RAM); о commit pressure: доступно не более 10% лимита.
Linux policy `overcommit_memory=1` не трактуется как enforceable commit limit.
Это выборка не чаще минуты, а не доказательство причины аварии: короткий пик может
произойти между измерениями, а снимок после завершения процесса уже изменён.

Linux journal читается хронологически только на уровнях warning/error, максимум
500 записей/2 MiB и 15 секунд за batch. Продолжение идёт с последнего принятого
cursor; backlog обозначается `pending`. Потеря/vacuum cursor фиксирует разрыв
покрытия, отказ прав — `unavailable`, runtime failure — `error`. Kernel OOM и
сообщения о сбоях system service отмечаются отдельными видами; настоящую OOM для
проверки не вызываем. Не сохраняются целиком journald metadata, environment или labels.

Docker lifecycle дополнительно сохраняет только события своей установки:
OOM/die/restart/stop/start/destroy/health. Идентификаторы дедуплицируются. Docker
удерживает только последние 256 событий daemon, поэтому полнота всей истории не
гарантируется. При destroy сравниваются последние stdout cursors и время удаления:
в событии указывается возможное несобранное окно (либо неизвестное начало), без
выдуманного числа потерянных строк. Die оставляет возможность дочитать существующий
контейнер. Linux journal и lifecycle относятся к host-источникам для приоритета
хранения; данные приложения сохраняют более высокий приоритет.

Настройки: `.asa/log-collector.json`. `project` берётся из
`.asa/installation.json`; `retentionDays=30`, `maxBytes=1073741824`,
`intervalSeconds=20`. Дополнительные каталоги задаются оператором через
`fileSources: [{"source":"backup","path":"абсолютный каталог"}]`.
Версия config — `1`; отсутствующие значения используют указанные defaults,
существующий файл имеет приоритет и сохраняется байт-в-байт. Неизвестные ключи
сохраняются для совместимости и пока не интерпретируются; неизвестная версия,
неправильные типы/границы и несовпадающий project блокируют согласование.
Windows installer находит журналы резервных копий рядом с установкой и
`logs/service-logs` рядом с ASAFrpc. Каталог журнала может содержать `.log`
или ротации `.log.*`/`.out.*`; конфигурационные и credential файлы не собираются.

SQLite, сегменты и каталог находятся в `.asa/diagnostics`. При достижении лимита
сначала сокращается старая объёмная история Docker Desktop и Windows, затем
история приложения. Это повышает сохранность журналов сайта, входа, Scratch
и электроники; гарантировать семь дней для произвольного объёма нельзя.
Границы истории и сокращение показываются отдельно для каждого источника.
Лимит учитывает активные сегменты и приватный индекс. Заменённые файлы остаются
не менее чем на 600 секунд после подтверждённого исключения из опубликованного
каталога для читателей с прежним снимком (экспорт ограничен 120 секундами);
их временный объём публикуется отдельно как `retiredBytes`. Временные пики во время чтения,
SQLite VACUUM и публикации требуют свободного места сверх лимита хранения.
Первое заполнение выполняется частями; `обработано по` показывает ход обработки.
Docker/Windows стартуют с последних семи дней; таблицы событий сверяются за
весь срок хранения, свежие события дополнительно перечитываются с перекрытием.
Старые удалённые контейнеры, журналы и сообщения, не отправленные браузером,
не восстанавливаются автоматически. Существующие ZIP и backups сохраняются.

Резервная копия приложения включает БД, объекты и конфигурацию. Независимый
каталог журналов сохраняется на хосте и не входит в этот снимок; это явно
отмечается в manifest как `externalDiagnostics`. Его отдельная копия создаётся
через **Скачать все журналы**. Backup допускает только точный каталог
`.asa/diagnostics/store`, подключённый API для чтения; произвольные новые
каталоги и тома по-прежнему блокируют неполную резервную копию.

### Пользование

Открыть **Админ → Логи**. По умолчанию показаны ошибки приложения за семь календарных
дней. В поле **Показывать** доступны также Windows/Docker/нагрузка и все журналы.
Выбрать даты, источник, модуль, уровень или текст; нажать **Показать**.
**Скачать все журналы** включает все сохранившиеся источники за выбранные даты;
**Скачать ошибки** — ошибки за те же даты. Остальные экранные фильтры на эти
две кнопки не влияют. Дождаться готовности и нажать **Скачать ZIP**.

Архив содержит JSONL записи, manifest со статусами источников и README.
Размер исходных записей ограничен 64 GiB, ZIP — 3.5 GiB; время сборки — 120 секунд,
память worker — 128 MiB. Каждый сегмент проверяется по размеру, gzip CRC и SHA-256.
Для целиком выбранного нового сегмента ZIP использует уже готовый deflate;
внутри архива остаются обычные `.jsonl`, дополнительных вложенных gzip нет.
Выбор по тексту и частичному периоду читает записи по одной ограниченной порции.
Идентификаторы уникальны в индексe сборщика; непересекающиеся диапазоны сегментов
проверяются при экспорте. Неограниченного списка всех экспортированных ID в RAM нет.
При превышении лимита страница предлагает сократить период; при повреждении
журнала или смене снимка сообщает соответствующую причину.
Одновременно создаётся один архив, сохраняется не больше
трёх архивов на API; они удаляются через час при следующем обращении к странице.
После перезапуска API нужно собрать архив снова. Скачанные файлы остаются у
пользователя. Эти лимиты не затрагивают собственные проекты и резервные копии.
Три готовых архива могут занимать до 10.5 GiB в `/tmp` контейнера API. Оператор
должен учитывать свободное место Docker; переполнение завершает задачу ошибкой.

### Совместимость формата и восстановление истории

Перед первым переходом сохраните отдельный снимок `.asa/diagnostics`:
SQLite копируется через его backup API, опубликованные файлы и catalog —
в отдельный защищённый каталог. Обычный backup приложения этот каталог не включает.
Обновление проходит только через штатный менеджер выпуска. Новый API читает
как прежние `.jsonl`, так и новые `.jsonl.gz`. Сборщик проверяет
`LOG_STORE_FORMAT` реально запущенного API и публикует gzip только после
подтверждения версии 2; при прежнем API продолжает публиковать plain JSONL.
Перед освобождением прежних SQLite payload проверяются реальные ID файлов.
Ошибка проверки сохраняет приватные payload и останавливает переход.

Старый сборщик и API не умеют читать новый приватный индекс/gzip. Слепое
понижение версии после перехода недопустимо: применяется исправленный новый
reader или восстановление целого защищённого диагностического снимка с остановленным
сборщиком. Откат отдельно только SQLite, catalog или сегментов не является восстановлением.

Если ранее был скачан нормализованный архив ASA с `manifest.normalized=true`,
его записи можно вернуть в диагностическую историю без изменения рабочей БД:

```powershell
# Остановить только задачу сборщика; сохранить исходный ZIP и снимок диагностики.
python tools/collect_logs.py --root "абсолютный путь установки" --once --import-history "абсолютный путь архива.zip"
# Возобновить существующую задачу сборщика после успешного завершения.
```

Импорт проверяет формат, CRC ZIP и число записей, выполняется атомарно и
сохраняет ID. Повтор того же файла или уже существующие ID не создают дубликатов.
Срок хранения и лимит объёма продолжают действовать. Это не восстановление
проектов/учеников PostgreSQL и не импорт произвольных raw архивов.

Проверки: `corepack pnpm test:admin-logs`; после сборки Web —
`corepack pnpm e2e:admin-logs`. CI запускает Python regression и browser gate;
общий Vitest suite также включает серверные тесты. Windows adapter отдельно
проверяется на Windows с синтетическими каналами и на живой установке.

Добавление страницы в исходники и запуск службы не равны публикации Web/API:
для канонической установки применяется обычный проверенный выпуск и менеджер.

## Адрес посетителя и границы доверия

Адрес в аналитике относится к посетителю только когда его происхождение
подтверждено цепочкой прокси. Если известны лишь доверенные промежуточные узлы,
API возвращает `unknown` / `proxy`, а аналитика сохраняет `NULL` вместо адреса
Docker-шлюза. Это не ошибка записи события: исходный адрес пока неизвестен.
Исторические строки не переписываются и не считаются исправленными задним числом.

Приватная конфигурация установки содержит две независимые политики:

| Настройка | Граница | Формат и значение по умолчанию |
| --- | --- | --- |
| `ASA_INGRESS_TRUSTED_PROXY_CIDRS` | Кто может передавать Caddy заголовок `X-Forwarded-For` | CIDR через пробел; `127.0.0.1/32 ::1/128` |
| `ASA_TRUSTED_PROXY_CIDRS` | Кто может передавать API проверенную цепочку | CIDR через запятую; `172.16.0.0/12` для существующей внутренней Docker-сети |

Caddy читает доверенную цепочку справа налево и передаёт API только вычисленный
`client_ip`. API также идёт справа налево, останавливаясь на первом недоверенном
адресе, включая адрес локальной сети. `CF-Connecting-IP` не даёт самостоятельного
доверия. Строгий отказ от неверной, повторной или слишком длинной цепочки относится
к заголовку, который получил API. Это не доказательство такого же отказа на
внешнем входе: Caddy 2.10.2 объединяет повторные заголовки и пропускает неверные
элементы при вычислении `client_ip`, после чего передаёт API один адрес.
[Исходный код Caddy 2.10.2](https://github.com/caddyserver/caddy/blob/v2.10.2/modules/caddyhttp/server.go#L936).
Поэтому API unit-тесты malformed/duplicate/oversize не заменяют проверку реальной
цепочки внешнего прокси. Для FRP, добавляющего фактический адрес справа, обход
доверия этими элементами не доказан; это ограничение доказательств, а не вывод
об эксплуатации или подтверждение исправности production.

Для внешнего HTTP-прокси или туннеля требуется установить точные CIDR реальных
входящих узлов после проверки подключения. Установка не угадывает доверие по
частному адресу, названию ОС или обнаруженному сетевому адаптеру. Docker Desktop
может показывать Caddy адрес шлюза вместо Windows-хоста: тогда без проверенной
ingress-политики внешний посетитель останется `unknown`. Заголовок, утраченный
предыдущим прокси, восстановить невозможно. При совпадении адреса посетителя с
доверенным диапазоном API происхождение также остаётся неоднозначным; доверенные
диапазоны следует ограничивать реальными промежуточными узлами.

Проверка выполняется через существующий адрес входа: контролируемый посетитель,
сопоставление адреса в защищённой аналитике, подложный `X-Forwarded-For` от
недоверенного источника и последовательность нескольких прокси. Только после
этого допустимо утверждать, что внешний IP данной установки определяется верно.
Нельзя переносить адреса шлюзов другого компьютера, задавать `0.0.0.0/0`, `::/0`
или доверять всем частным сетям внешнего входа. Менеджер проверяет CIDR до Docker
операций; Web дополнительно отвергает подстановку директив через переменную.
Новые необязательные настройки совместимы с текущей конфигурацией установки:
отсутствующее значение использует указанный безопасный default; сохранённое
значение приватной `.env` имеет приоритет над окружением оболочки.

Общие серверные журналы не получают сырые IP, строки заголовков или cookies.
Адреса остаются в защищённой аналитике с существующими правами администратора.

### Ограничения запросов при совместной работе класса

Общий лимит изменения данных сохраняет 900 запросов за 5 минут для
неподтверждённого источника и 600 для одной cookie-сессии. После исчерпания
первого лимита дополнительный объём разрешается только если существующий
серверный механизм Account или StudentSeat подтвердил сессию. Общий потолок —
9000 запросов за 5 минут: 15 ученических сессий по их прежним 600 запросов.
Это защитный предел, а не доказательство производительности для 15 компьютеров.
Точные ограничения входа, регистрации и неверных ученических кодов сохранены.

Подтверждение класса бюджета кэшируется на 30 секунд, отрицательное — на 5;
это не авторизация и не продление сессии. Проверки доступа каждого маршрута
по-прежнему обращаются к своему источнику состояния. Кэш и одновременные проверки
ограничены 1024 записями, новые проверки — 60 в минуту на источник, одинаковые
одновременные обращения объединяются. Ошибка БД не расширяет лимит. Cookies
хэшируются ключом процесса и не попадают в журналы.

Диагностика браузера сохраняет отдельный предел 600 сообщений в минуту, но
использует проверенный адрес посетителя, а не общий TCP-адрес Web-контейнера.
Если адрес не определён, применяется общий ограниченный бюджет `unknown`.
