# Полнота диагностики: Docker, PostgreSQL, запросы и IP

Сборщик остаётся одним процессом с одним хранилищем. Отдельный поток только
измеряет ресурсы каждые60 секунд, не ожидая завершения исторической выгрузки.
SQLite, сегменты и каталог записывает основной поток. В `runtime_metrics`:

- `sampling.streamId/sequence`: последовательность одного запуска;
- `scheduleLagMs/durationMs/missedIntervals`: задержка старта/замера и пропуски;
- `droppedSamplesTotal`: переполнение очереди из8 снимков;
- `publicationLagMs`: сколько замер ждал записи в журнал. Эта запись может
  появиться позже самого измерения при длинной обработке истории.

После сна/паузы пропуски показываются явно; серии выдуманных замеров задним числом
нет. Ошибка части источников сохраняет доступные данные с `incomplete`.
Помимо очереди, один снимок резервируется до подтверждённой записи SQLite.
Ошибка записи оставляет его для повторной попытки; переполнение очереди не
удаляет резерв. Подтверждение происходит после commit, поэтому последующий
откат другого этапа не удаляет уже принятый снимок.
Docker CPU измеряется в процентах одного ядра и может превышать100%; CPU host —
доля всех логических CPU. Это не доказательство отсутствия коротких пиков.

PostgreSQL отдаёт только агрегаты: число соединений/заблокированных процессов,
группы state/wait_event_type/wait_event, максимальный возраст активного запроса и
транзакции, накопительные deadlocks/tempBytes и момент сброса статистики. Текст
SQL, параметры, PID, адреса и application_name в метриках отсутствуют.

## Журнал блокировок PostgreSQL

Compose включает `log_lock_waits`. Событие появляется после штатного
deadlock_timeout, не при каждом микроскопическом ожидании. `terse` убирает
DETAIL/HINT/QUERY/CONTEXT; statement/bind/duration-text logging отключены.
`log_min_error_statement=panic` — штатный способ практически отключить запись
аварийного SQL. Обычный текст ошибки PostgreSQL всё ещё может содержать значение
в собственной формулировке; эти настройки не являются универсальным фильтром
произвольного RAISE EXCEPTION. Существующая очистка сборщика сохраняется.
Настройки начинают действовать после отдельно разрешённого штатного обновления
PostgreSQL; работающая конфигурация этой задачей не меняется.

Источник: [PostgreSQL17, logging](https://www.postgresql.org/docs/17/runtime-config-logging.html).
Slow SQL с текстом запросов намеренно не включён. Фазы Account context уже
измеряются пунктом6; новые агрегаты и lock events дополняют их.

## Завершение запросов

Обычный ответ остаётся `http_response`. Событие отмены запроса или закрытия соединения
записывается как `http_request_ended`, outcome=`request_aborted` либо
`connection_closed`, delivery=`disconnected`, mutationOutcome=`unknown`.
У одного обрыва первым может прийти любое из двух событий потоков; записывается
первое из них. Само `request_aborted` не доказывает обрезанное тело запроса.
Это не HTTP499, не доказанный сбой API и не доказательство отката сохранения:
обработчик мог завершить запись после ухода браузера. По одному requestId
записывается только один терминальный исход. В счётчиках runtime отмены —
отдельная группа `aborted`, не HTTP4xx/5xx. При аварийном завершении всего
процесса последняя запись всё ещё может отсутствовать; отсутствие terminal не
объявляется успехом или доказанным крахом.

## IP и данные посетителя

В JSON существующих журналов «Админ → Логи» есть `addressResolution` без самого
IP и заголовков. `state=resolved/unresolved`, source=`socket/forwarded/unresolved`.

| reason | Значение |
| --- | --- |
| direct_peer | Взята прямая точка подключения |
| untrusted_forwarded_ignored | Заголовок от недоверенного узла проигнорирован |
| trusted_boundary | Цепочка проверенных прокси привела к адресу посетителя |
| missing_socket | Нет достоверного адреса соединения |
| missing_forwarded | Доверенный прокси не передал цепочку |
| invalid_forwarded | Цепочка некорректна/слишком велика |
| trusted_hops_only | Видны только доверенные узлы инфраструктуры |

Правила доверия не расширены. API доверяет только прежним явно заданным CIDR;
Caddy принимает внешнюю цепочку только от `ASA_INGRESS_TRUSTED_PROXY_CIDRS` и
передаёт проверенный client_ip. Не добавляйте все private сети или0.0.0.0/0 ради
заполнения поля. NAT/TCP-туннель может скрыть исходный IP; его нельзя восстановить
из браузерного заголовка. Для такого входа настройте единственный контролируемый
ingress, который действительно передаёт адрес клиента, и доверяйте только его
границе. Проверяйте через настоящий адрес входа, включая подложный X-Forwarded-For.
Изменение живого ingress/FRP — отдельная операция владельца.

В будущих записях БД с NULL IP provenance=`server_unresolved`; с известным
адресом — `server_resolved`. Триггер не меняет авторизацию/ingest API/квитанции
и не делает исторический backfill. При новой проекции исходной DB-строки
пустой IP также корректно обозначается без выгрузки адреса в технические логи.
Browser/OS/device остаются `request_reported`, а не доказательством конкретного
физического компьютера. Закрытый словарь содержит visit.observed, blocks и
действующие literal/dynamic audit actions; неизвестные строки по-прежнему не
публикуются. Старые неизменяемые сегменты и их ID не переписываются: пропущенные
в них ранее поля задним числом не выдумываются.

Чистая остановка сохраняет ожидающие замеры. При аварийном завершении процесса
очередь до8 замеров, один резерв и текущий замер могут не сохраниться;
это отдельный ограниченный хвост,
не гарантия lossless telemetry. Нагрузка5000 учеников здесь не проверяется.
