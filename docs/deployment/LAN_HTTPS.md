# ASA Lab: локальный HTTPS-вход без Tailscale и изменения маршрутизатора

## Что исправляется

После восстановления production-БД одна открытая HTTP-страница ещё не означает
работающую авторизацию. Production-cookie имеют флаг Secure, а API допускает
изменения только с заранее разрешённого origin. Поэтому HTTP-вход по LAN-IP
отвечал `403 origin_forbidden`, а форма маскировала этот отказ общим сообщением
«Ошибка сервера. Попробуйте ещё раз».

`tools/bootstrap/lan-https-entry.py` переключает **существующий** LAN-прокси с
HTTP на HTTPS на том же IP и TCP-порту 4610. Он использует Caddy из уже проверенного
Web-образа, локальный CA, непривилегированный systemd-сервис и существующее
ограниченное правило UFW. Прежний HTTP-адрес автоматически возвращает 308 на HTTPS.
Домены, Интернет, Tailscale Serve и изменение роутера для этого не требуются.

Скрипт сохраняет внутренний Web `127.0.0.1:4610`, Docker volumes, PostgreSQL,
MinIO, аккаунты и пароли. В приватной конфигурации он задаёт один выбранный HTTPS
origin для `ASA_PUBLIC_WEB_ORIGINS`, `ASA_BLOCKS_PARENT_ORIGIN`,
`ASA_BLOCKS_RUNTIME_ORIGIN` и `ASA_UPDATE_ENTRY_ORIGIN`. Пересоздаются только
API, Scratch и Web с прежними pinned образами; данные не переносятся повторно.
CSRF, антибот-проверка, Secure-cookie и проверки origin не отключаются.

## Однократное доверие локальному сертификату Windows

Публичный корневой сертификат нужно передать через уже доверенный SSH-хост.
Нельзя скачивать произвольный CA из Интернета или доверять сертификату по
непроверенному HTTP. SHA256 должен быть заранее получен по аутентифицированному
каналу и совпасть с DER-кодировкой сертификата.

`tools/bootstrap/trust-local-https.ps1`:

1. Требует явный флаг `-TrustLocalServer` и SHA256 публичного CA.
2. Через SSH с `StrictHostKeyChecking=yes` экспортирует **только публичный** CA.
3. Через SCP копирует сертификат; приватные ключи остаются на Ubuntu.
4. Проверяет SHA256, срок действия и тип CA.
5. Добавляет CA в `Cert:\CurrentUser\Root`, не в LocalMachine, и открывает вход.

Доверие CA действует для текущего Windows-пользователя. Доверяйте только CA
собственного администрируемого сервера; закрытый ключ CA не должен утечь.
Скрипт выводит thumbprint и точную команду удаления доверия.

На текущем D2-R2 проверенный скрипт уже размещён в
`%TEMP%\asa-trust-local-https.ps1` без его исполнения. Его SHA256 сертификата:
`34643e709fe2ac15865689529177db35a0231551aa6984692ef7c40c0c409a0f`.
Владелец запускает из CMD:

```cmd
powershell -NoProfile -ExecutionPolicy RemoteSigned -File "%TEMP%\asa-trust-local-https.ps1" -Server 192.168.1.115 -ExpectedCaSha256 34643e709fe2ac15865689529177db35a0231551aa6984692ef7c40c0c409a0f -TrustLocalServer
```

На другом компьютере нужно получить скрипт той же проверенной GitHub-ревизии,
проверить SSH fingerprint сервера и SHA256 **его собственного** CA.
Не переносите приведённый отпечаток на другую установку без сверки.

## Ограничения приёмки

Работа сервера по HTTPS и правильная политика origin ещё не заменяют проверки
входа существующего пользователя. До пользовательского входа не утверждать,
что пароль верен, что создана сессия или что все сценарии редактора приняты.
Автоматическое доверие CA в клиентских системах не является неявной частью
серверного установщика. Публичный домен с доверенным ACME-сертификатом может
быть альтернативным ingress, но это отдельная выбранная оператором конфигурация.
