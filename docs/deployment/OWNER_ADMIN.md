# Главный администратор ASA Lab

Максимальный уровень управления приложением — `platform_admin`. Это право
существующего аккаунта, а не отдельный пользователь или пароль. Назначать его
может только оператор с доступом к приватной конфигурации сервера и Docker.

Используйте `tools/owner-admin.py` из актуальной проверенной копии репозитория.
Нужны Python 3.11+ и работающая каноническая Docker-установка. Node.js, pnpm,
открытый порт PostgreSQL и пересборка образов на компьютере оператора не нужны.
Скрипт работает в Windows и Linux, использует существующий API-контейнер и
проверяет происхождение контейнеров, томов, базы и блокировку обслуживания.

## Назначение существующему пользователю

Сначала владелец подтверждает точный email. Аккаунт должен уже существовать,
быть активным и иметь одно активное личное пространство. Скрипт не регистрирует
пользователя, не меняет его имя, пароль, email, проекты или чужие права.

Из канонического каталога установки выполните просмотр без изменения базы:

```powershell
python tools/owner-admin.py --email owner@example.test
```

Результат `PLAN` содержит имя базы, точный email, `accountId` и текущий признак
`platformAdmin`. Сверьте их с нужным сервером и подтверждённым аккаунтом.
Затем явно передайте UUID из просмотра и основание назначения:

```powershell
python tools/owner-admin.py --email owner@example.test --grant --account-id UUID_ИЗ_PLAN --reason "Назначение по подтвержденному запросу владельца"
python tools/owner-admin.py --email owner@example.test --verify --account-id UUID_ИЗ_PLAN
```

В Linux замените `python` на `python3`. Если инструмент запускается из отдельной
проверенной копии исходников, задайте `--root` с абсолютным путём **существующей
канонической установки**. Это не создаёт второй Compose project и не обновляет
запущенные образы. Не копируйте её `.env` в разработческий checkout.

`GRANTED` означает зафиксированную выдачу права. `VERIFIED` означает, что право
уже есть и доступ подтверждён. Проверяются штатные функции авторизации
`runtime_owner_admin_ready` и `admin_authorized_role` **до фиксации транзакции**.
При отказе проверки выдача права и запись аудита откатываются вместе.
Повторное назначение не меняет дату права и не дублирует аудит. Конкурентные
назначения сериализуются; восстановление ранее отозванного права записывается
как новое осознанное назначение с основанием и предыдущим состоянием.

Ошибочный UUID, другая база, неактивный аккаунт или отсутствующий/неоднозначный
личный контекст блокируют назначение. При обрыве связи результат может быть
неизвестен: сначала повторите просмотр или `--verify`, затем при необходимости
ту же команду назначения. Секрет подключения передаётся через stdin, не через
аргументы процесса или публичные логи. Email/UUID результата тоже не публикуйте
в GitHub, если они относятся к реальному пользователю.

После будущего восстановления или объединения баз снова выполните просмотр
финального аккаунта. Не используйте старый UUID вслепую и не назначайте права
автоматически при импорте, регистрации или каждом запуске приложения.
Объединение баз и перенос проектов — отдельные операции.

## Прямой CLI для сопровождающих

Существующие `pnpm admin:verify-owner` и `pnpm admin:grant-owner` сохранены.
Они используют `DATABASE_URL` и `ASA_OWNER_ADMIN_EMAIL`; для выдачи теперь
обязательны также `ASA_OWNER_ADMIN_ACCOUNT_ID`, `ASA_OWNER_ADMIN_DATABASE` и
`ASA_OWNER_ADMIN_REASON`. Просмотр: `node tools/platform-admin.mjs --plan`.
Это локальный операторский доступ к БД, не HTTP endpoint. Docker-обёртка выше
сама берёт приватное миграционное подключение из канонической установки.

Проверки ввода: `pnpm vitest run tests/admin/platform-admin-options.spec.ts`.
Полный набор проверок назначения: `pnpm test:owner-admin`
в изолированной CI-базе `_test` с миграциями, `TEST_DATABASE_URL` и
`APP_TEST_DATABASE_URL`. Полный `pnpm gate:data` включает обе проверки.
Не запускайте тесты на пользовательской базе.
